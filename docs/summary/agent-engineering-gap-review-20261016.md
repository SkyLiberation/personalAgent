# Agent 工程差距审视：面经、招聘要求与本地证据

> 审视日期：2026-10-16。本文是当日分析快照，依据公开资料、当前工作树和既有归档，不代表新的产品验收。当前实现由[工程架构](../architecture/README.md)拥有，运行结果由[评测盘点](../evals/02-current-case-inventory.md)拥有，问题状态由[优化队列](../future/design-optimization-backlog.md)拥有；本文不建立第二份活动队列。

## 1. 判断与适用岗位

**当前工程已有较完整的 Agent Runtime 和治理机制，主要不足在于交付证据、成本闭合及真实使用约束还没有同样完整地收敛。** 面试时可以解释模型、工具、上下文、恢复、核验和完成的责任，但仍需回答：哪些用户任务在当前版本可交付、一次交付花多少资源、失败怎样恢复、为什么当前复杂度必要。

项目与 Agent 应用后端、Runtime、评测工程岗位的关联较强。算法后训练、推理引擎和大规模平台岗位还需要各自的训练实验、推理优化或部署测量；本次查阅的仓库材料不能证明这些经历。岗位匹配是根据以下样本作出的判断，不是招聘市场统计，也不评价开发者在仓库之外的能力。

值得保留的工程成果包括：模型建议与权限分离、业务事实的唯一写入口、版本与引用绑定、按需个人知识读取，以及以真实用户结果和反事实解释局部机制。具体实现从[架构主链](../architecture/core-architecture-current-state.md)进入，机制证据从[面试证据材料](../interview/06-evidence-and-release.md)反查。后续优化应在这些边界内缩短交付路径。

## 3. 当前不足与优化方向

### 3.1 用户结果已取得局部闭环，当前版本发布证据仍不齐

**正式研究目标已经有通过证据，不能继续笼统写成“研究无法交付”。** 10 月 16 日同一正式任务续验交付了确切正文，并通过独立评分；此前供应商中断和 HTTP 422 的失败仍保留。该结果关闭自己的既定用例，不要求重新采样来证明稳定。

剩余缺口是目标代码版本的完整发布矩阵，以及其他已声明但未完成的产品边界。最新审计隔离 target 中，用户请求“请帮我计算 17 加 25，直接告诉我结果”，模型转入检索与研究，约 315 秒、已提交 90,370 tokens 后仍未交付；总账外实际用量未完整取得。真实读取阶段的审计隔离反事实另行通过。该单例暴露对话交付的独立失败，不能归因成审计绑定修复失效，也不能用另一研究任务的成功覆盖它。

优化时先在既有失败轨迹中核对意图、能力投影和实际动作输入，定位最早偏离用户目标的决策；只对仍成立的问题形成最小修正。版本发布则在目标代码确定后执行原定矩阵，不因本报告增加全类别或无限稳定性门槛。

依据：[统一研究正式结果](../evals/02-current-case-inventory.md#2026-10-16-统一研究与最终回答的正式验证)、[审计隔离原始结果](../evals/02-current-case-inventory.md#2026-10-16-runtime-策略审计隔离)、[发布入口](../evals/04-running-and-release.md#release-gate)。

### 3.2 成本计量尚未完全闭合，输入量与实际费用也未分清

**预算治理需要覆盖工具内部和失败前已完成的模型调用。** 10 月 11 日正式轨迹中，Provider 已知用量与 Conversation 总账相差 62,866 tokens，精确对应两次最终核验工具内部响应。当前普通核验工具仍消费模型响应的 `.value`；统一研究改为直接记录模型响应，不能据此推定普通工具路径也已修复。选证完成后写作失败的用量提交又是另一责任边界。

最小优化方向是沿现有 typed 执行结果传递实际用量，由 Conversation 对同一执行事实聚合一次；成功、语义拒绝、契约失败和恢复重复均核对 Provider 与 Journal 等式。生产修改前须恢复相应真实阶段输入并确认当前责任，不能另建账本镜像。未知用量继续保持未知，评测评分开销与生产开销分别统计。

输入预算已有大量事实，但尚未建立费用收益结论。旧轨迹的重复输入同时存在缓存命中；统一链通过时也使用了较宽额度。因此先区分输入、输出、缓存命中、真实费率和端到端耗时，再决定是否改物化或额度。候选必须保留冻结目标、必要原文、反证和引用身份，比较同一用户结果；不以删掉核验所需材料取得 token 降幅。

依据：[工具内部用量交接](../optimization/tool-model-usage-handoff.md)、[选证用量候选](../optimization/to_verify/research-selection-usage-commit.md)、[输入预算复审](../optimization/to_verify/research-input-budget.md)、[普通核验工具](../../src/personal_agent/tools/interaction_verifier.py)、[研究调用计量消费者](../../src/personal_agent/application/conversation/service.py)。

### 3.3 研究改进仍需区分初稿、有效修订与最终交付

统一核验与最终回答已经合并，减少了研究通过后独立成文造成的交接。剩余真实反馈中，曾把“提交前自行核对”扩大为正文必须展示清单；其他来源归属、范围修订和委托交付仍按各自用例处理。新增核验阶段或反思调用不能自动解决这些问题。

优化应分别观察首次研究能否取得必要前提、一次真实反馈是否解除所指缺口，以及原任务能否交付。原文未取得就修取证，已取得却未选中就修选证，反馈误读就先校准判据，版本或引用丢失才改 Runtime。使用同轨迹实际输入和下游消费验证，避免只增加拒稿次数而没有更好的产物。

依据：[核验活动边界](../future/conversation-verification-false-positive.md)、[研究与反馈复盘](../interview/10-development-pitfalls.md#14-核验优化不能代替研究能力优化)。

### 3.4 当前 RAG 与 Memory 的效果，不能由旧榜单或存储组件数量证明

**已有精确事实召回和生命周期证据，但尚不足以推出广泛语义召回能力或图存储的独立收益。** 当前个人知识读取使用 `KnowledgeService.select_evidence()`，PostgreSQL 候选查询按词项包含关系计分。图谱是另一证据资源，不能因为部署了 Neo4j，就把个人知识回答描述成向量与图的统一语义检索。

7 月 Open/Galileo 指标属于旧 Ask 与离线策略，报告已注明代码身份和当前消费者的限制。千条规模用例证明固定候选窗口的修复，不证明中文同义改写、跨文档关系或更大规模性能。SQL 使用包含匹配也不等于已经证明性能瓶颈，仍需实际查询计划和耗时。

下一步先由真实个人知识任务确定检索目标和误差：对已确认需要覆盖的同义表达、冲突、时效或关联问题取得正式入口样本，再回放实际候选与证据，区分未召回、排序、读取和生成错误。只有相应失败成立后，才比较关键词、语义召回或重排；已有纠正、删除和身份隔离成果保留，不把未测场景写成已失败。

PostgreSQL 加 Neo4j 的部署成本还需要与同结果契约下的简单方案比较。先解释保存、删除、恢复和查询的真实约束，再决定存储范围；本次没有迁移或删除图谱的依据。

依据：[当前检索路径](../topics/retrieval-reasoning.md)、[候选查询实现](../../src/personal_agent/infra/storage/postgres_knowledge_store.py)、[历史检索报告](../evals/retrieval-benchmark-20260709.md)、[Memory 选型论证缺口](../interview/04-memory-architecture.md#41-数据库必要性仍缺同契约下的选型论证)。

### 3.5 可观测机制已有实现，恢复与运行体验的测量仍有空缺

现有归档能提取 Conversation 用量和耗时，但 `recovery_duration_seconds` 与 `replay_new_side_effects` 尚未由当前用例写入。恢复对象存在或重启成功，不能代替恢复时间和外部重复副作用的实际观测。P95 报告已有同配置至少 20 个可用样本的限制，小样本保持不可用，不为填写数字追加昂贵调用。

Web SSE 先输出处理状态，等待 `service.converse()` 完成后再分块发送最终答案。首个状态事件不等于用户已看到答案，协议分块也不等于模型实时输出。长任务等待体验应先测首个有效进展、首段答案与完整交付时间，以及用户取消后实际停止的边界；当前材料没有建立这些体验目标的失败 baseline。

在已有恢复或真实使用用例中采集实际时间和副作用事实，复用同一执行身份和现有 measurement，先验证指标是否可信。需要新的流式、取消或后台协议时，再按真实需求准入，不能恢复已经删除的无消费者流链路。

依据：[观测指标](../evals/05-observability-metrics.md)、[measurement 字段](../../evals/e2e_quality/measurements.py)、[SSE 实现](../../src/personal_agent/adapters/web/routes/entry_stream.py)、[流链路退役记录](../optimization/completed/model-streaming-retirement.md)。

### 3.6 真实使用、负反馈与运维能力尚缺可核对的交付证据

本次查阅材料主要是定向 E2E、Offline Eval 和本地部署说明，未见可据以报告活跃用户、任务节省时间、人工接管或用户负反馈回流效果的试点记录。这是证据缺口，不能据此断言没有人使用。公开面经对线上与离线差异的追问，恰好会触及这一边界。

应用方向优先围绕已经支持的知识整理、保存与召回做小范围真实使用记录：记录原任务、是否采用结果、人工修改和失败原因，脱敏后将确认的错例回流既有评测。样本与时间窗口在开始前约定，用户价值用实际任务说明，不预先承诺虚构的提效百分比。

平台方向再按确认的部署规模补并发、资源、限流、故障恢复和备份恢复测量，并说明依赖部署与维护成本。现有本地容器和调度幂等不能推出高可用或集群能力；个人使用范围也不自动需要 Kubernetes。外部 JD 中的集群要求属于岗位差距，不直接成为本项目改造需求。

依据：[部署说明](../deploy.md)、[入口的个人与轻量多用户边界](../topics/entry.md)、[指标覆盖](../evals/05-observability-metrics.md)。

### 3.7 安全已有正反例，证据范围仍须随实际部署扩展

按需个人知识、隐藏工具拒绝和用户隔离已有定向证据；多 Runtime 审计串库也已在自身责任边界修复。这些成果应保留。可选审计写入失败隔离、第三方 Trace 的数据保留及上传边界，则不能表述成完整安全保证。

扩展到共享资料或更多外部执行资源前，先核对新增的身份、授权撤销、外发和确认边界，再用真实入口验证拒绝、零错误副作用和必要审计。攻击与错误材料来自目标数据通路，不先加一个通用安全模型或分类器。只有实际生产范围需要的新安全判据才进入设计；当前定向通过不因范围外攻击可能性被重开。

依据：[可观测与治理](../topics/observability-governance.md)、[安全主讲与限定证据](../interview/03-capability-axes.md#71-安全由权限数据边界和脱敏共同承担)、[审计隔离规格](../optimization/to_verify/runtime-policy-audit-isolation.md)。

### 3.8 文档的当前状态与历史过程仍有漂移

本轮发现面试材料仍把完整研究交付写成未验收，核验专题末尾又保留旧逐项 Source 与 Coverage 消费说明；它们分别与最新正式结果和统一研究契约冲突。输入预算记录的历史段落及队列也残留等待扩预算交付的措辞，容易引导下一轮重复运行已通过目标。

本轮已修正这些当前描述，合并核验专题中的重复历史说明，并把本审视接入文档和面试索引。旧成绩、失败及原始归档保持。大型评测盘点仍混有较多诊断过程，后续按具体问题固化时应把解释留在 optimization，评测正文只保留结果身份、关键结论和证据坐标；本次没有完整审读全部历史段落，未批量删除它们。

没有独立正文、导航或有效历史职责的文件才应删除。本次涉及的文件仍有明确职责，采用段落清理；不为减少文件数量移除决定性证据。

## 4. 推进顺序与交付判据

下表是本次审视的建议顺序，不改变 Future 准入，也不新增生产实施授权。具体方案仍在原问题的唯一 Spec 中确定；已通过用例保持关闭。

| 顺序 | 优先工作 | 交付应能回答的问题 |
| --- | --- | --- |
| 第一批 | 对齐当前契约和已通过范围；定位简单对话未交付的最早决策；处理现有工具与选证用量交接 | 当前哪些目标成立；哪条真实失败仍需修；每笔已完成生产调用是否入账且恢复不重复 |
| 第二批 | 按真实任务审查首次研究、有效修订和当前知识检索；有成本或等待约束后再优化物化 | 改动是否改善原用户结果，是否引入事实遗漏，实际费用和耗时改变多少 |
| 第三批 | 根据目标岗位补真实试点或运行测量，形成目标版本发布证据 | 用户是否采用；失败如何回流；在声明部署范围内如何恢复和运维 |

每批优先完成一个有真实失败、责任明确且可验收的问题，再推进依赖它的下一项。没有失败或约束依据的点留作调查建议，不预建表、状态、Agent 或框架层；完整矩阵只用于原定发布判断。

准备面试时，围绕一条已验证用户旅程、一条真实失败修复和一项有对照的机制收益展开，讲清证据身份、成本与限制。按目标岗位选择深挖方向，不把训练、沙箱、后台、自进化和多智能体全部塞进同一工程。已有工具规模验证不支持增加 Tool Search；情景记忆、程序记忆和滚动摘要也仍需本地需求依据。
