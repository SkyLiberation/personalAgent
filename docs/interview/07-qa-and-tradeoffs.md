# 高频追问：一句结论，一个跳转坐标

> **本篇只提供面试短答，不复制第二套能力说明。** 回答先给判断，再指向唯一主讲章节；面试官继续追问时，沿链接展开问题、机制、证据和边界。

## 1. 定位与总体架构

### 这是检索增强生成，还是智能体？

**产品边界是智能体，检索增强生成只是证据子系统。** 模型还会决定下一步动作和子目标；运行外壳治理权限、执行、恢复和完成。见[项目故事](01-project-story.md)。

### 什么是智能体运行外壳，为什么单独介绍？

**它是包围模型的工作闭环，不是新的业务层。** 它把上下文、模型建议、确定性准入、动作执行、事实回注、验证和完成连起来，使“模型生成了内容”变成“系统受治理地交付用户结果”。见[运行外壳 §1](03-capability-axes.md#1-运行外壳把模型建议变成可靠的用户结果)。

### 运行外壳会不会变成通用任务框架？

**不会。** 它统一跨业务的权力协议，不拥有知识、订阅、后台项目或业务完成标准，也不要求每个请求创建计划、冻结动作或回执。

### 对话、固定流程和后台任务是什么关系？

**当前只有前两者是已准入产品路径。** 对话拥有当前交互，固定流程拥有稳定事务顺序；旧后台调查 Project 因缺少需求 baseline 且正式结果为 `0/20 delivered` 已删除。见[请求路径](02-request-walkthroughs.md)。

### 为什么不用通用持久任务？

**没有已执行失败证明当前产品需要一个通用持久任务。** 删除、投递和当前交互仍各自拥有业务状态与完成契约；后台持续运行现在明确返回能力限制，不用空转 Task 或 Project 掩盖缺口。

### 当前工程有没有计划？

**当前只有一份生产规划事实：按需创建的 `ConversationWorkingPlan`。** 它保存当前对话中的可验收工作项；固定流程由代码表达，子智能体只是有界执行资源。旧后台调查 Plan 已随第二循环删除。见[工作清单能力](03-capability-axes.md#2-按需工作清单提升复杂任务的跨轮完成能力)。

### 删除后台调查 Plan 是否说明原设计冗余？

**是产品机制层面的冗余，即使两套表没有双写。** 它们都为研究请求做分解、执行、修复与完成判断，而第二循环没有证明增量价值。当前以 delete-first 收敛为一个 Conversation 循环；未来只有 baseline 和消融成立才重新引入 durable Aggregate。见[工作清单能力 §2.7](03-capability-axes.md#27-为什么删除第二套调查规划)。

### 计划如何提升智能体能力？

**当前有三类局部收益和一组完整目标证据：显式审阅与纠偏、有来源的执行前规划、冻结服务提供方下避免重复读取，以及当前配置样本组中的完整最终交付。** `PLAN-REPLAN-001` v51 为 `15/15 delivered`，但不能外推其他模型、服务提供方、任务分布和普遍成本收益。见[工作清单能力 §2.2—§2.6](03-capability-axes.md#22-真正产生能力收益的是完整闭环)。

### `PLAN-FDBK-001` 修复了什么？

**它修复的是内部反馈契约，不是计划能力升级。** 旧的 `working_plan_no_change` 一边禁止修改 `steps`，一边要求模型修订剩余义务；目标路径只把合法修复路径明确为 `working_plan`、`actions` 和 `resolved_plan_step_ids`，并保持 `messages` 与 `inputs` 不可变。目标路径和独立消融各为 `5/5 delivered`，所以只能证明协议不变量和用户行为保持，不能声称完成率、成本或延迟提升。见[当前端到端用例盘点](../evals/02-current-case-inventory.md#1-conversation-与-knowledge)。

### 优秀智能体的计划能力是否都应该引入？

**不应该。** 当前工作清单已经满足审阅、执行前取证、事实恢复和最终 Completion 契约；v51 目标组达到既定门槛。前台依赖图、计划文件、通用任务跟踪器和专用模型路由仍没有本地失败基线，不能因为其他产品具备就引入。见[计划能力映射 §2.5](03-capability-axes.md#25-从通用计划逻辑到当前工程的能力映射)。

### 为什么清单有版本，模型需要理解吗？

**模型不理解也不回传版本。** 运行系统生成单调恢复序号，用于日志排序和响应展示；它不是授权、完成证据或并发控制令牌。见[工作清单能力 §2.4](03-capability-axes.md#24-用户调整与版本的责任边界)。

## 2. 业务能力、执行资源与决策

### 业务能力为什么不是固定流程的别名？

**业务能力表达用户可验收动作和结果责任，固定流程只是它内部不可重排的事务步骤。** “删除知识”是业务能力，准备、确认、执行和回执是内部流程。见[请求路径 §3](02-request-walkthroughs.md#3-受治理事务保存删除与恢复)。

### 业务动作为什么不全做成普通工具？

**统一调用结构不等于统一事实归属。** 保存、删除和创建后台项目必须进入具体业务写入口；普通工具执行不能拥有知识或项目生命周期。见[运行外壳 §4](03-capability-axes.md#4-业务能力与执行资源分开执行只在获准后发生)。

### 工具出现在模型上下文中为什么还不能直接调用？

**可见、获准和健康是三个事实。** 能力投影决定模型看见什么，策略与准入决定本次是否允许，真实调用结果才说明服务是否可用。

### 为什么不用关键词路由？

**关键词不能可靠区分“不要保存”“解释删除”和“删除它”。** 开放语义由模型判断；确定性代码只检查结构、权限和合法迁移，不能替模型猜目标。

### 准入可以帮模型补参数或换工具吗？

**不可以。** 准入只能接受或返回结构化拒绝原因；补目标、改参数或静默换能力会把确定性边界变成隐藏的语义决策者。

### 当前工具能力的亮点是什么？

**亮点是模型选择与真实执行之间存在准入、策略、预算、恢复和结果回注，而不是接入了多少个 MCP 接口。** 真实 GitHub/Notion、能力缺失、预算、进程恢复和大结果重读分别有定向证据。见[运行外壳 §4.5](03-capability-axes.md#45-当前工具证据证明到哪里)。

### 隐藏工具现在如何形成授权闭环？

**模型不可见只限制选择信息，因此运行时还必须再次拒绝。** `TOOL-AUTH-001` 的 baseline 复现了全量注册表可解析隐藏工具；target 让名称校验和执行都消费 canonical `exposure`，非 `public_agent` 工具在副作用前被拒绝。它证明的是工具曝光边界，不等于完整组织角色权限。见[运行外壳 §4.1](03-capability-axes.md#41-治理成本只放在真实风险边界)。

### MCP 声明了输出结构，为什么还需要本地检查？

**远端声明不是本地执行事实。** 当前 MCP 适配器会按 Draft 2020-12 检查已声明结构，并拒绝缺字段、错类型、`isError=true` 和结构化/文本 JSON 冲突；不合格内容不能进入可信 Observation。见[运行外壳 §4.4](03-capability-axes.md#44-工具结果必须先成为受约束的执行事实)。

### 为什么当前不直接加入工具搜索？

**因为当前证据不支持增加它。** 10、30、100 个公开工具规模组均为 `20/20`；100 工具组的每个样本也不超过 32,000 总令牌门槛，所以 Tool Search 已退出本轮优化。规模或模型变化后若重新失败，再按[未准入问题的共同约束](../future/design-optimization-backlog.md#3-未准入问题的共同约束)从 baseline 准入。

## 3. 冻结动作、子智能体与恢复

### 建议、冻结动作、执行事实和回执有什么区别？

**建议是模型想做什么；冻结动作是经准入后不可再扩权的待执行内容；执行事实说明已经发生什么；回执用于幂等、外部关联或恢复证明。** 四者按真实边界使用，不机械成套创建。

### 为什么读取不冻结，删除却需要？

**低风险且可安全重试的读取可以直接执行；需要确认、不可安全重试或跨请求恢复的副作用才冻结。** 见[运行外壳 §4.1](03-capability-axes.md#41-治理成本只放在真实风险边界)。

### 一致性指纹是否过度设计？

**一个指纹只在需要机械证明“确认、日志和执行引用同一冻结内容”时存在。** 它不是身份、授权或成功证明；授权内容与执行内容相同时不拆成两个指纹。

### 子智能体完成为什么不等于父目标完成？

**子智能体只交付有界产物，父智能体继续承担整合、验证和最终完成。** 远端状态为完成只能证明子任务结束。见[运行外壳 §4.2](03-capability-axes.md#42-子智能体只完成有界子目标)。

### 当前能证明多智能体更好吗？

**不能。** 当前实现展示了有界委托、`AgentArtifact`、恢复和父级 Completion 契约，真实 `E17` 也证明单次路径可达；历史显式委托组为 `10/20 delivered`，2026-08-27 当前同配置组只有 `2/20 delivered`。三类同输入价值 pilot 中，非委托 baseline 已满足结果契约，target 得分相同且没有调用子智能体，因此剩余 12 对样本按 A0 门禁停止。路径存在不等于增量价值，强制触发委托也不能制造有效对照。

### 崩溃后怎样避免重复执行？

**先恢复已提交事实，再查询对账结果不明的外部请求，只继续未完成语义。** 检查点不能替代幂等键、外部查询或补偿。见[运行外壳 §5](03-capability-axes.md#5-恢复复用已提交事实只继续未完成语义)。

## 4. 模型上下文与长期知识

### Memory 是否只有长期记忆？

**不是。** 当前工程的 Memory 包含工作记忆、对话内事实复用、由产物存储支撑的外部 Memory 和长期语义记忆；长期语义记忆只是产品证据最完整的一类。日志、追踪记录和静态提示词也不能仅因被持久化就冒充情景记忆或程序记忆。见[智能体 Memory](04-memory-architecture.md)。

### Memory 是否就是上下文工程？

**从模型视角看，Memory 是跨时间的上下文工程；从系统视角看，它还包含来源、作用域、写入资格、纠错、删除和恢复。** 检索和物化决定模型能否想起来，事实治理决定想起来的内容能否相信。见[智能体 Memory §1、§5](04-memory-architecture.md#1-memory-是受治理的跨时间上下文)。

### 当前哪类 Memory 的证据最完整？

**长期语义记忆和真实跨轮工作记忆分别有定向产品证据。** 前者覆盖 `15/15` 自然旅程及 1,020 条事实的尾部目标召回；后者在真实 GitHub 重启任务中为 target `5/5`、关闭既有事实消费后为 `0/5`。通用情景记忆、动态程序记忆和滚动摘要仍未交付。见[智能体 Memory §3、§6](04-memory-architecture.md#3-当前工程已经形成四条-memory-路径)。

### 模型上下文很大怎么办？

**保留完整真源，只注入有界片段和安全引用，让模型按需精确重读。** 权限过滤必须发生在召回之前。见[运行外壳 §3](03-capability-axes.md#3-有界模型上下文保留真源只注入当前需要的信息)。

### 模型何时停止重读？

**证据充分、资源读完、预算耗尽、能力失败或需要用户输入都可以停止。** 停止条件不是固定读到文件末尾。

### 个人证据和网页证据为什么不分两条答案链？

**最终回答只有一个结果契约。** 个人知识和网页读取分别提供受权限约束的证据，当前交互统一组织答案；来源不同不应产生两个回答责任主体。

### 为什么向量库和知识图不是事实源？

**它们是可从原始内容、证据位置和长期陈述重建的检索投影。** 把投影当事实源会使纠错、删除和来源追踪出现多套写入口。见[领域设计](05-knowledge-and-domain-workflows.md)。

### 当前 RAG 不就是向量召回再生成吗？

**不是。** 当前候选来自个人知识、本地内容、图事实和外部网页；它们先统一为带来源的证据项，再经过权限过滤、去重、融合、语义选择和预算压缩，最后由对话能力生成一个回答。见[领域设计 §4.1](05-knowledge-and-domain-workflows.md#41-检索只负责找到和组织证据)。

### 检索命中率提高是否等于智能体回答更好？

**不等于。** 召回率、重排分数和延迟只是中间指标；最终仍要检查用户答案、引用、陈旧事实排除和作用域反事实。离线 RAGBench 不能替代正式入口产品结果。

### 如何防止记忆污染？

**问答默认只读；保存必须来自用户明确意图和精确原文，纠错创建新陈述并保留关系，删除与恢复形成独立事实。** 见[领域设计 §4—§5](05-knowledge-and-domain-workflows.md#4-有证据的回答默认只读)。

## 5. 完成、预算与诊断

### 工具成功为什么不等于完成？

**工具成功只回答动作是否发生，不能证明目标满足或结果齐全。** 执行、语义验证和完成判断三分，见[运行外壳 §6](03-capability-axes.md#6-动作执行verification-和-completion-必须分开)。

### 语义验证能推翻真实副作用吗？

**不能。** 它可以拒绝“目标已满足”的声明，但删除、发送等已发生事实只能通过对应业务的补偿或新状态迁移处理。

### 预算参数会不会过多？

**只有约束不同成本或失败语义时才分别保留模型轮次、工具调用和上下文令牌。** 预算耗尽必须明确返回能力限制，不能生成未经证据支持的替代答案。

### 可观测性记录什么？

**记录建议、准入、执行、验证和完成各阶段事实及关联引用。** 它用于区分未选择、权限拒绝、服务失败和结果缺失，不写业务状态。见[运行外壳 §7](03-capability-axes.md#7-可观测性解释失败不制造业务事实)。

## 6. 证据与外部框架

### 怎样证明设计有效？

**产品变更必须用同一正式入口和自然用户输入先得到失败基线，再证明最小改动改变用户结果。** 单元测试、对象存在、追踪命中或外部框架采用同类机制都不能替代。见[证据与发布](06-evidence-and-release.md)。

### 为什么不能说当前可发布？

**定向用例通过只证明对应行为。** 发布还要求目标代码版本、完整矩阵、真实环境证据和工作树状态一致，由机器发布门禁统一派生。

### 与优秀智能体框架是什么关系？

**外部实现帮助选择机制，不替本工程创造需求。** 当前借鉴轻量会话待办、有界上下文、检查点和持久任务的边界，但是否采用仍由本地失败基线决定；不会为了拓扑相似复制通用规划器、待办工具、任务系统或后台项目。

### 当前最大缺口是什么？

**发布层的最大缺口仍是目标代码版本缺少工作树干净、完整矩阵一致的发布证据。** 能力证据方面，真实安全组已经由 `15/20` baseline 闭环为 `20/20` target；直接回答、Plan、Memory、100 工具和显式委托都有各自的样本画像。显式委托历史组为 `10/20 delivered`，当前组为 `2/20 delivered`；自动委托价值 pilot 的非委托 baseline 又没有失败，因此当前既不能准入稳定委托，也不能准入强制自动委托。旧后台调查的两个候选均为 `0/20 delivered`，相关生产机制已删除；当前最简单 Conversation 研究路径也为 `0/20`，是尚未解决的独立质量缺口。组织级权限和原生流式仍缺少失败 baseline。见[证据与发布](06-evidence-and-release.md)和[当前优化准入](../future/design-optimization-backlog.md)。

## 7. 模型、服务提供方与交互边界

### 开发过程中遇到的最关键坑是什么？

**最关键的坑是把统一结构化输出误当成原生工具调用，导致通用参数 Schema 与动态工具参数冲突，并把工作清单、委托和完成语义一起拖入反复修复。** 原生工具候选消除了参数错误却没有达到研究交付门槛，因此我们撤回候选、拆分失败阶段，而不是继续追加提示词。见[Tool Calling 阻塞复盘](08-tool-calling-pitfall.md)。

### 为什么不按请求动态选择模型？

**当前固定模型已经完成已声明的目标契约，没有动态路由的失败 baseline。** 运行系统会约束每次模型调用的用途、上下文、预算和数据外发，但不会为了形式完整新增模型路由。见[运行外壳 §1.1](03-capability-axes.md#11-模型调用必须服从结构数据外发与失败契约)。

### 结构化输出失败时为什么不直接换模型？

**网络、服务端错误、传输损坏和空结构化内容可以有限技术重试；结构不合法或语义不满足必须进入明确反馈或失败关闭。** 静默换模型会改变同配置样本组，也可能把权限、成本和语义问题隐藏成一次成功。

### MiMo 与 DeepSeek 对当前智能体有什么实际差异？

**历史证据支持“失败阶段和吞吐不同”，不支持“某个模型已经交付更好结果”。** 在已删除后台调查路径的同一 v3 评测器下，两者都是 `0/20 delivered`；DeepSeek 的入口和 worker 尾部模型延迟曾明显低于 MiMo，并在窗口内形成更多来源事实。MiMo 的结构化输出兼容性也没有避免语义修复、Plan ID 冲突和 Verification 不收敛。面试时应把传输兼容、语义合法性、运行吞吐和最终用户结果分开比较；这组历史诊断不能为已撤回架构背书。

### 提示词工程在当前系统中处于什么位置？

**提示词负责帮助模型理解任务和输出契约，不负责授权、状态迁移或完成判断。** 提示词版本必须进入评测配置身份；如果确定性不变量只能靠措辞维持，该不变量仍未实现。

### 当前怎样防止提示注入和个人信息泄漏？

**权限过滤、工具曝光门禁、模型数据外发策略和 MCP 结果契约都在模型之外执行，追踪内容默认脱敏。** 原 Content Guard 没有生产消费者，已删除；当前没有通用提示注入分类器或个人信息内容扫描。现有证据支持用户级作用域和指定工具边界，不能声称完整组织级权限或通用提示注入防御。见[运行外壳 §7.1](03-capability-axes.md#71-安全由权限数据边界和脱敏共同承担)。

### 当前是真正的流式智能体吗？

**不是完整的原生流式语义。** Web SSE 当前先完成一次对话，再切分最终文本；首个令牌延迟、中途取消和流式恢复没有产品 baseline。没有用户失败前，不新增第二套事件协议。

### 人工介入为什么不做成统一审批系统？

**确认只在真实副作用和恢复边界存在。** 保存、删除和敏感工具分别由业务写入口或执行网关拥有待确认内容；通用系统只处理身份、确认绑定和审计，不能成为第二业务事实源。

## 8. 收尾口径

**先讲用户错误，再讲责任边界和最小机制，最后给证据与不能外推的范围。** 如果一个回答需要连续列出大量类名、字段或历史过程，说明还没有讲清能力本身，应回到对应主讲章节重组。
