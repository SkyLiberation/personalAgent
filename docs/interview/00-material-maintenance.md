# 面试材料维护规范

通用表达、术语和证据措辞遵守[中文写作规范](../chinese-writing-spec.md)。本页规定面试材料如何组织现有工程事实，以及怎样处理追问暴露的缺口。

## 1. 确认事实和主讲位置

用生产代码、配置和运行证据核实现行行为，用架构与专题正文核对职责和契约，用设计与 ADR 核对取舍。阅读顺序和主讲位置统一维护在 [面试材料索引](INDEX.md)。

## 2. 一项能力集中讲清

主讲章节围绕可观察的用户结果，写清适用场景、模型和确定性代码的分工、关键输入与输出、机制改变的结果、正式入口证据和适用边界。项目故事给出全局主线，请求走查说明能力在何处出现，高频问答保留短答和主讲链接。

先讲用户问题与机制，类名和调用链随实现坐标或精确契约给出。

新增或改写能力时，先核对索引中的主讲位置，再更新正文。详细归档和发布结论放在[证据与发布](06-evidence-and-release.md)及其链接的评测盘点。

## 3. 从通用设计映射到当前工程

回答“为什么这样设计”时，先固定本工程已确认的用户结果和约束。选取满足同一结果契约的最简单替代方案，比较双方的责任边界、运行效果、代价与退出条件。说明观察到的失败、可核对约束或额外成本，分别给出能力成立与当前选型必要性的证据。外部实现可作对照，用户需要和结果判据来自本工程。

缺少必要性依据时，指出缺失的场景、反事实或方案对比，说明补设计、补适用验证或重新选型的条件。证据与实施准入按 [EVD](../devSpec/change-evidence.md#12-按实际影响选择证据)处理。

### 3.1 结论状态必须区分论证与行为

| 状态 | 可写条件与后续处理 |
| --- | --- |
| 已满足 | 正式消费者、用户结果及相称证据闭合，结论限于已验证范围 |
| 已实现，证据不足 | 生产链已消费，所声明的结果或反事实仍待核实，按 EVD 补证 |
| 设计论证不足 | 已确认场景或同契约比较不足以说明当前选择，补齐依据后再决定是否保留 |
| 边界内映射 | 结论只适用于已确认的生命周期或事实责任主体 |
| 候选未准入 | 本地需求或失败依据仍待证，记录待核实条件 |
| 已证明缺口 | 正式基线或可重复工程命令复现，已排除评测、环境及责任错位，进入对应设计与验证 |

## 4. 处理追问发现的问题

- 表达错误或过期时，核对事实并修正唯一主讲章节。
- 论证不足时，在主讲章节说明缺口，在唯一设计补机制依据。
- 待核实的产品缺口与条件候选按 [Future 规则](../future/README.md)归档。证实的工程约束写入对应设计，记录可重复依据、验收与退出条件。
- 研究能力追问分别回答初稿、有效修订和最终交付。长任务追问从目标保持、阶段进展、策略调整与完整交付取证。
