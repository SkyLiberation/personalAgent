# 面试文档写作规范

> **本目录通过持续回答 AI 智能体开发面试问题，检验并打磨当前工程与面试表达；目标是准确呈现事实并暴露真实缺口，不是为现有实现补答辩话术。** 每节先给判断，再说明责任主体、运行机制和证据边界；只解释当前成立的设计，不按开发时间记录探索过程，也不替未来设计文档保存候选方案。

## 1. 事实源与唯一职责

**事实核对顺序是：生产代码、机器可读的用例目录和执行证据 → 当前状态摘要 → 专题设计、流程设计和架构决策记录 → 面试材料 → 未来设计。**

本目录各项解释的责任归属固定如下：

- `01`：项目定位与总责任链；
- `02`：用户请求的生产路径；
- `03`：智能体运行外壳总闭环与跨业务运行机制；
- `04`：领域事实与生命周期；
- `05`：证据强度、测量与发布状态；
- `06`：短答，只链接前五篇，不复制第二套解释。

## 2. 一节只回答一个判断

**合格小节通常只需三类信息：**

1. **为什么重要**：阻止什么用户错误或工程失控；
2. **谁负责**：事实归谁、决策归谁，以及唯一写入口在哪里；
3. **证明到哪里**：端到端测试或契约测试的坐标，以及结论不能外推的范围。

禁止无信息过渡、同义收尾、代码目录流水账和“先有设计、后找理由”的叙事。一个表能讲清时，不再用长段重复。

### 2.1 关键能力必须在唯一主讲章节形成闭环

**面试材料按能力组织，而不是按代码层、开发阶段或一次追问补一句。** 每项关键能力必须有唯一主讲章节，并连续回答以下问题：

1. **能力定义**：它为用户提供什么可观察价值；
2. **失败问题**：没有它时会出现什么具体错误；
3. **运行机制**：信息如何流动，哪些责任主体共同工作；
4. **能力收益**：它实际改变了 Agent 的哪项决策或用户结果；
5. **产品证据**：哪条正式入口基线与目标路径支持结论；
6. **适用边界**：什么时候不用，以及不能从现有证据外推什么。

项目故事只给全局主线，请求路径只说明能力在哪类请求中出现，高频问答只保留一句结论和主讲链接。禁止把同一能力的“定义”写在一篇、“机制”写在另一篇、“证据”藏在第三篇，再要求读者自行拼接；也禁止为不同面试问法维护多套近似解释。

新增或修改关键能力时，先更新 [INDEX](INDEX.md) 的“关键能力唯一主讲位置”，再修改主讲章节，最后把其他文档收缩为摘要与链接。

### 2.2 先讲设计，类名只做代码坐标

**类名回答“当前实现放在哪里”，不能回答“为什么需要这个设计”。** 正文必须使用用户结果和设计语言完成论证；删掉所有类名后仍然讲不清的问题，说明该节只是在复述代码。

正文按以下顺序组织：

1. 用户会遇到什么错误，或工程会失去什么可证明边界；
2. 为什么需要独立的责任主体、生命周期或信任边界；
3. 模型、确定性代码、执行系统和业务事实的责任主体各负责什么；
4. 如果合并、删除或绕过该边界，具体会发生什么；
5. 哪条证据支持结论，以及不能外推什么。

类名、方法名、文件路径和测试节点只允许出现在三种位置：

- 小节末尾的“当前实现坐标”；
- 证据表或可复现命令；
- 精确解释某个协议字段、不变量或故障时。

禁止用类图、构造调用链或对象清单作为章节开场；禁止用“存在某个服务类、模型类或管理类”证明职责成立。提议、准入、执行事实、冻结动作、执行回执、语义验证、完成判断等术语，只有在表达跨实现稳定的权力或事实边界时才保留，不能因为它们恰好是类型名就堆进正文。

### 2.3 正文使用自然中文

**中文正文必须直接表达设计判断，不能靠英文名词串联句子。** 英文只保留在代码标识、文件路径、命令、协议或产品原名、外部证据坐标中；确需介绍英文术语时，首次写作“中文名称（英文原名）”，后文只用中文名称。

优先使用下列中文表达：

| 不宜直接写入正文 | 正文表达 |
| --- | --- |
| owner / scope | 责任主体或事实归属 / 权限范围或作用域 |
| Plan / Context / Tool | 计划 / 模型上下文 / 工具 |
| Workflow / Project | 固定流程 / 后台项目 |
| Runtime / Gateway / Provider | 运行系统 / 执行网关 / 服务提供方 |
| Proposal / Admission / Observation | 提议 / 准入 / 执行事实或观察结果 |
| Command / Receipt / Completion | 冻结动作 / 执行回执 / 完成判断 |
| revision / pending / completed | 版本 / 待完成 / 已完成 |
| steering / replay / checkpoint | 运行中调整 / 重放 / 检查点 |
| baseline / target / release gate | 基线 / 目标路径 / 发布门禁 |

术语替换不能损害含义。例如，前台计划优先称为“可验收工作项清单”：每项可以是分析、实现或用户可见交付，但必须写明预期结果和完成条件，不能只写“搜索”“读取”或“调用工具”。后台计划称为“调查规划”，因为它会根据新证据调整。除非在解释正式契约，否则不用“剩余义务”描述普通用户要求。

## 3. 术语必须分层

**术语分层的目的，是防止技术机制、业务动作和长期事实被误讲成同一种“能力”。**

| 术语 | 含义 |
| --- | --- |
| 框架协议（Framework Protocol） | 提议、执行事实和反馈等跨业务权力契约 |
| 运行机制（Runtime Mechanism） | 模型、执行网关、队列、运行日志和追踪记录等技术机制 |
| 业务能力（Application Capability） | 用户可理解、可验收的业务动作及其结果契约 |
| 产品聚合（Product Aggregate） | 拥有独立长期业务事实和生命周期的对象 |
| 接口或投影（Interface / Projection） | 协议转换或只读展示，不是第二写入口 |

工具、MCP 接口和智能体是执行资源；固定流程是业务能力内部的编排；后台项目是拥有长期事实的产品聚合。相同的工具调用格式，不代表业务事实属于同一责任主体。

默认使用“权威事实”“事实归属”“唯一写入口”。`canonical` 只用于代码或协议原名，以及一致性指纹的确定性规范化输入，不作为泛化形容词。

## 4. 证据决定措辞

**结论强度不能超过证据直接观察到的入口、用户结果和反事实。**

| 证据 | 可以说 | 不可以说 |
| --- | --- | --- |
| 正式入口的端到端测试归档 | 该输入下用户结果和反事实成立 | 所有场景成立 |
| 代码版本一致且工作树干净的完整发布门禁 | 当前目标版本满足发布证据门槛 | 未覆盖需求天然可靠 |
| 单元、契约或集成测试 | 指定不变量或组合协议成立 | 用户目标已满足 |
| 代码/设计/外部参考 | 存在某实现或候选机制 | 本工程结果已改善 |

精确数量、归档和发布结论只在 `05` 展开。未实际执行时使用“代码设计为”“仍需验证”，不得写“已验证”。

## 5. 发现真实问题时

**先判断问题属于工程缺口、表达缺口还是证据缺口，再选择唯一落点。**

| 判断 | 处理方式 | 禁止事项 |
| --- | --- | --- |
| 当前智能体确有产品行为不足 | 在 `docs/future/design-optimization-backlog.md` 记录待执行的产品基线、用户结果、反事实和最小候选方案 | 为说服面试官弱化问题，或把方案写成当前能力 |
| 当前智能体确有纯工程约束 | 在待办文档记录可量化工程基线、行为保持端到端测试、净复杂度预算和删除路径 | 编造产品失败场景，或仅凭文件行数、主观不优雅立项 |
| 当前实现成立但面试材料表述不清、错误或过期 | 核对生产代码、用例目录、执行证据和当前状态摘要后，整体修正对应文档 | 在多篇文档复制补丁式解释或维护兼容说法 |
| 当前证据不足，尚不能判断 | 明确标注“尚未验证”，必要时在待办文档以 `A0` 记录待执行基线 | 用设计、代码存在、追踪记录、单元测试或模型自述替代用户结果 |
| 基线不成立或目标已经落地 | 不创建或移除对应未来候选，并按当前事实重写面试材料 | 为保留预设优化而更换输入、入口或验收条件 |

面试问答产生的优化项仍受 `AGENTS.md` 的完整准入约束；一个尖锐问题本身不是需求证据，也不授权提前增加机制。

## 6. 提交前审计

- 每节第一段是否已经回答结论；
- 隐去类名和文件名后，是否仍能讲清用户错误、设计判断和反事实；
- 类名是否集中在实现坐标，而不是承担正文论证；
- 同一机制是否被多个文件完整复述；
- 每项关键能力能否在唯一主讲章节连续读到定义、问题、机制、收益、证据和边界；
- 项目故事、请求路径和高频问答是否只保留必要摘要与主讲链接；
- 是否还引用已经退出用例目录的用例、已移除入口或零消费者对象；
- 业务能力、工具、固定流程和后台项目是否被错误并列；
- “通过、恢复、隔离、完成、可发布”是否都有相称证据；
- 链接、代码路径和 Mermaid 是否仍能解析。
