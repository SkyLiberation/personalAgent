# 面试材料补充写作规范

> **本目录首先遵守[中文工程文档统一规范](../chinese-writing-spec.md)，本文件只补充面试材料的组织、去重和证据表达要求。** 面试材料用于准确呈现当前工程并暴露真实缺口，不为既有实现补答辩话术，也不替未来设计文档保存候选方案。

## 1. 事实源与文档职责

事实核对顺序固定为：生产代码和机器可读证据，当前状态摘要，专题设计、固定流程和架构决策记录，面试材料，未来设计。

本目录各文件的责任如下：

| 文件 | 唯一职责 |
| --- | --- |
| `01-project-story.md` | 项目定位与总责任链 |
| `02-request-walkthroughs.md` | 用户请求的生产路径 |
| `03-capability-axes.md` | 智能体运行外壳和跨业务运行机制 |
| `04-memory-architecture.md` | Memory 分类、当前路径、证据和未落地边界 |
| `05-knowledge-and-domain-workflows.md` | 领域事实与生命周期 |
| `06-evidence-and-release.md` | 证据强度、测量与发布状态 |
| `07-qa-and-tradeoffs.md` | 高频问题的短答和主讲链接 |
| `08-tool-calling-pitfall.md` | Tool Calling 阻塞的开发踩坑复盘；只引用当前状态与评测事实，不建立第二份状态账本 |
| `09-e2e-case-design-review.md` | canonical catalog 用例的设计目的与关键验收点；数量以 catalog 为准，不保存运行状态 |
| `10-development-pitfalls.md` | 按问题总结开发误判、优化取舍和已成立经验；首项为文档缺项误放，实验流水仍由 optimization 拥有，工具调用协议复盘仍链接第 08 篇 |

`INDEX.md` 只维护阅读顺序和关键能力的唯一主讲位置，不复制正文结论。

## 2. 一项能力必须在唯一章节形成闭环

面试材料按用户可观察能力组织，不按代码层、开发阶段或一次追问组织。每项关键能力必须在唯一主讲章节连续回答：

1. 它为用户提供什么可观察价值；
2. 不使用它或采用满足同一结果契约的最简单替代方案时，会出现什么具体错误或代价；
3. 模型、确定性代码、执行系统和业务事实分别负责什么；
4. 信息如何流动，机制实际改变了什么结果；
5. 哪条正式入口证据支持结论；
6. 什么时候不使用，以及现有证据不能外推什么。

项目故事只给全局主线，请求走查只说明能力在哪类请求中出现，高频问答只保留一句判断和主讲链接。禁止把同一能力的定义、机制和证据拆到多个文件后让读者自行拼接，也禁止为不同面试问法维护多套近似解释。

新增或修改关键能力时，先更新 `INDEX.md` 的唯一主讲位置，再修改主讲章节，最后把其他文档收缩为摘要和链接。

## 3. 从通用设计映射到当前工程

**每个“为什么这样设计”的回答，都必须说明当前场景为什么需要这项选择。解释不成立就是设计论证不足，必须形成补设计、补适用 E2E 场景或重新选型的具体动作。** 不能用“我这样设计可以，优秀智能体那样设计也可以”“各有取舍”“场景不同”结束回答；场景差异必须落实为本工程已确认的用户需求、结果契约和可核对约束。

判断顺序固定为用户结果、事实归属、最简单替代方案、机制贡献和证据。已有依据成立时保留设计；依据不足时明确缺口，不能仅因另一种方案存在就推翻现有机制。设计论证不足本身需要处理，但不冒充已复现的产品失败；同样不能因尚无产品失败，就免除说明设计必要性的责任。

### 3.1 当前选择必须完成同一结果契约下的比较

每项关键能力在说明运行机制之后、给出证据结论之前，必须连续回答：

1. 当前目标用户在什么自然请求、初始事实和使用条件下需要什么可观察结果；
2. 满足同一结果契约的最简单替代方案是什么，不能把删掉必要能力的弱方案作为对照；
3. 替代方案在哪个责任边界发生已观察失败、违反已确认约束，或承担哪些可核对的额外成本；
4. 当前机制怎样改变该结果，模型、代码、存储和核验各自的贡献是什么；
5. 哪些证据支持能力成立，哪些另外支持当前机制的必要性或独立收益，哪些仍是待证假设；
6. 为此付出的模型调用、实现、部署和维护成本是什么，何时应删去机制、简化或替换。

外部实现提供替代机制和反问依据，不替本工程创造需求，也不能因产品定位不同就免做比较。代码已接入、对象有消费者或 E2E 通过，只能支持其实际边界，不能自动证明当前选型优于更简单方案。确定性契约与工程约束可以作为设计依据；另主张运行机制独立收益时，按 [EVD](../devSpec/change-evidence.md#12-按实际影响选择证据)取得相称的因果证据。

补设计应明确问题、假设、方案比较、最小机制和撤回条件。补 E2E 场景应来自目标用户的真实工作、实际失败或已确认需求，固定正式入口、自然表达、用户结果和必要反事实；成功标准不能规定必须使用正在论证的组件。禁止为现成架构编造高并发、大规模或多租户需求，也不能反复运行直到得到支持原结论的样本。证据与实现准入沿用 EVD，不因面试追问扩大产品范围。

### 3.2 常见追问必须落到可检验问题

| 追问 | 不能作为结论的解释 | 必须补齐的论证 |
| --- | --- | --- |
| 为什么用数据库，不用 Markdown 文件 | 数据库有事务和查询能力，双方都合理 | 当前哪些用户结果需要一致性与恢复；带元数据和日志的最简单文件方案能否满足同一契约；具体数据库的部署成本是否必要 |
| 词项检索中的 LLM 是否只做路由 | LLM 负责开放语义，所以这是智能体亮点 | 当前真实输入中模型承担了什么不可由该检索算法完成的判断；精确标识召回修复与语义理解收益分别由什么证据支持 |
| 为什么持续优化 Verifier，不优化研究模型 | 职责不同或反馈循环已存在，所以当前投入充分 | 当前失败最早发生在哪里；准确反馈是否促成有效修订；是否把修订暴露的问题前移到首次研究，并验证完整交付与成本 |
| 当前长任务能力如何，是否需要后台 | 能运行很久、有多轮循环、保存日志或支持后台，所以能完成长任务 | 原目标和未完成要求如何保持；每阶段形成什么有效进展；跨轮如何消费已有成果；新证据或反馈如何改变策略；完整结果是否在适用预算内交付 |

### 3.3 结论状态必须区分论证与行为

统一使用以下状态：

| 状态 | 含义 | 后续动作 |
| --- | --- | --- |
| **已满足** | 生产消费者、用户结果和相称证据已经形成闭环 | 保持最小实现，不因外部功能继续扩张 |
| **已实现，证据不足** | 生产链已经消费，但尚未满足该变更已声明的用户结果或适用反事实 | 按 EVD 补适用证据，不追加泛化、稳定性或范围外门槛 |
| **设计论证不足** | 无法说明当前选择针对哪个已确认场景、为何优于满足同一契约的最简单替代方案，或必要性依据不支持结论 | 定位欠缺的需求、假设或方案比较，补唯一设计与适用 E2E 场景；条件不成立时简化、替换或撤回，不继续补答辩话术 |
| **边界内映射** | 能力只属于一个已证明的生命周期或事实责任主体 | 保持边界，不复制第二套事实 |
| **候选未准入** | 机制可能有价值，但没有本地失败基线或业务扩展 | 不实现，等待基线成立 |
| **已证明缺口** | 正式入口基线或工程命令复现问题，并已排除评测、环境错误及责任错位 | 进入现有或新增的唯一未来设计，按 EVD 定义适用反事实、验收路径和最小改动 |

“未实现”不等于“缺失”，“存在类型或单元测试”也不等于“已满足”。特定生命周期中的历史收益只支持原范围，不能直接当作当前对话能力或缺陷。

## 4. 先讲设计，类名只作坐标

正文必须先用中文讲清用户错误、责任边界、运行机制和反事实。类名、方法名、文件路径和测试节点只允许出现在：

- 小节末尾的当前实现坐标；
- 证据表或可复现命令；
- 精确解释协议字段、不变量或故障的位置。

不能用类图、构造调用链或对象清单作为章节开场，也不能以“存在某个服务类或模型类”证明职责成立。删掉所有类名后仍讲不清的内容，说明它只是在复述代码。

## 5. 证据决定措辞

详细归档坐标和发布结论只在 `06-evidence-and-release.md` 或其链接的评测盘点中展开。其他文档可以保留判断证据强度所需的最小指标，但不复制完整归档清单和排查过程。

证据措辞遵守[中文规范](../chinese-writing-spec.md#51-结论强度不能超过证据)，本目录不另设验收门禁。历史单元测试不能用于当前通过声明。

发现问题时按性质选择唯一落点：

| 问题性质 | 唯一落点 |
| --- | --- |
| 产品行为不足 | `docs/future/design-optimization-backlog.md`，记录待执行基线、用户结果、反事实和条件候选 |
| 纯工程约束 | 未来设计，记录可重复工程依据、按 EVD 选择的行为保持证据和删除路径 |
| 设计必要性论证不足 | 唯一主讲章节明确缺口，设计正文在对应权威文档补齐；待证产品需求或实施候选按 Future 规则登记，不在面试材料维护第二套方案 |
| 表达不清、错误或过期 | 核对事实后整体修正唯一主讲文档 |
| 证据不足 | 明确写“尚未验证”；必要时以 A0 登记待执行基线 |
| 基线不成立或目标已落地 | 删除候选，按当前事实重写材料 |

## 6. 提交前检查

- 解释性段落是否先给出判断，索引和操作是否直接可用；
- 每项能力是否在唯一主讲章节连续说明定义、错误、机制、收益、证据和边界；
- 项目故事、请求走查和高频问答是否只保留必要摘要；
- 正文是否使用自然中文，代码名是否只作实现坐标；
- 通用机制是否完成本地需求、生产映射和证据充分性判断；
- 当前选择是否与满足同一结果契约的最简单方案比较，避免用“双方都合理”结束必要性追问；
- 解释不成立时是否明确列为设计论证不足，并给出欠缺的设计依据、适用 E2E 场景或重新选型条件；
- “未实现”是否被误写成“缺失”，“机制存在”是否被误写成“能力充分”；
- 是否仍引用已退出用例、已移除入口或没有生产消费者的对象；
- “通过、恢复、隔离、完成、可发布”是否有相称证据；
- 研究与反馈的收益是否分别落实到首次产物、有效修订和完整交付，避免把拦截或反馈送达当作研究能力提升；
- 长任务是否围绕当前真实场景的持续进展与完整交付说明，避免把运行时长、后台运行、恢复路径或更多循环当作能力证明；
- 链接、标题锚点、代码块和 Mermaid 是否仍可解析。
