# 文档模块规范（DOC）

> 本文件适用于 `docs/**`。它继承根 [`AGENTS.md`](../AGENTS.md) 的全局门禁，只增加文档模块的局部不变量。开始修改前必须完整阅读本文件、[`docs/README.md`](README.md)、[`docs/chinese-writing-spec.md`](chinese-writing-spec.md) 和目标文档；涉及产品证据、测试或发布结论时，还必须读取根主文档命中的其他细则。

## 1. 文档是受治理的工程资源

`docs/` 是产品设计和工程交付的一部分。代码拥有可执行行为，权威文档解释行为边界、责任主体、使用方式和证据限制；两者必须指向同一当前设计。文档不能替代运行证据，代码存在也不能替代必要的设计说明。

- [`docs/README.md`](README.md) 负责目录分工和主题权威文档索引。新增文档前必须确认现有主题是否已有责任主体；能够修改原文时，禁止创建第二份说明。
- 当前架构与能力说明进入 `summary/` 或 `topics/`，固定业务链进入 `workflow/`，已接受决策进入 `adr/`，执行结果进入 `evals/`，未解决且已满足准入要求的问题进入 `future/`。面试材料只组织已有事实，并链接权威来源。
- 同一事实只能有一个权威文档。其他文档只保存面向特定读者的摘要和链接，不得复制容易漂移的状态表、流程拓扑、配置清单或证据结论。
- 业务语义、事实归属、公开契约、状态迁移、配置、部署方式或正式路径变化时，必须在同一变更更新相应权威文档。局部实现细节没有文档影响时，也必须在变更说明中明确判断。
- 当前事实、历史诊断、未来候选和评测证据必须分开保存。内容迁移后删除旧正文，不得以“补充”“最新版本”或时间流水继续叠加。
- 文档专属变更必须给出代码、配置、测试、执行归档或外部规范坐标。没有事实依据时只能标为待核实，禁止把设计意图写成当前能力。

## 2. 中文写作与结构门禁

[`docs/chinese-writing-spec.md`](chinese-writing-spec.md) 是 `docs/` 全目录中文表达的唯一规范。本节只定义工程接入，不复制其中的语法、术语和排版细则。

- 新文档和本次修改的全部段落必须立即符合中文规范。未迁移的存量文字可以保留，但不得继续新增同类问题。
- 先给判断，再说明责任主体、信息流、证据和边界。中文承担句子逻辑；有同名实现的架构角色和代码标识按中文规范保留。
- 先删除过期、重复和无来源内容，再按读者任务重组章节。禁止在末尾叠加修正段落来掩盖冲突正文。
- 修改公共术语、文件路径或标题后，必须搜索旧表述，并以可重复命令检查本地链接、标题锚点、代码块、表格与 Mermaid。

## 3. 事实强度与文档生命周期

- 没有实际执行时，必须使用“代码设计为”“文档记录为”或“仍需验证”，不得写“已验证”“已修复”或“可发布”。
- 当前状态文档只保留目标代码状态下仍成立的事实。历史失败、已否决候选和调试过程进入评测归档或 ADR；未来设计只保存尚未解决且满足准入条件的问题。
- ADR 使用“背景、决定、责任主体、证据、风险与退出条件”的结构。评测文档必须区分产品失败 baseline、指标 baseline、回归 E2E 和 supporting evidence。
- 移动或重命名文档时，必须更新 [`docs/README.md`](README.md) 及所有引用方，搜索旧路径，并删除旧正文或旧入口。

## 4. 主文档与模块规范维护

- 根 `AGENTS.md` 与 `CLAUDE.md` 必须逐字一致，各自少于 32 KiB 且不超过 200 行。
- 根主文档只保存全局门禁和任务路由；跨任务域细则进入 `docs/devSpec/`；只在特定目录成立的规则进入最接近该目录的 `AGENTS.md`。
- 一条规则只能有一个正文 owner。其他入口使用摘要和链接，不得复制完整规则。
- 模块 `AGENTS.md` 只能收紧或细化根规则，不能放宽根门禁。模块规则与根规则冲突时，以根规则为准并修复冲突。

## 5. 提交前检查

文档变更至少检查：

- 小节首段是否先给出判断，英文是否只保留代码标识、正式名称或 canonical 架构角色；
- 结论强度是否有代码、配置、测试、归档或 A 级外部规范支持；
- 当前事实、历史记录、未来候选和评测证据是否落在正确目录；
- 是否存在重复 owner、冲突正文、补丁式追加、失效路径或孤立文档；
- 本地链接、标题锚点、代码块、表格和 Mermaid 是否仍可解析；
- 主文档、模块入口、任务路由和规范识别样本是否需要同步更新。
