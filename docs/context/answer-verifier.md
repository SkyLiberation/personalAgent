# 回答核验器上下文模式

日期：2026-11-03。本文拥有回答核验器（answer verifier，也称结果核验器）的任务上下文模式。依据为本次用户明确要求及现有回答核验输入构造链；目标的产生与核验见[目标核验器模式](goal-verifier.md)，结果的生成与修复见 [Agent loop 模式](agent-loop.md)。

**状态（2026-11-04）：逐次回答的已验证 goal 快照、逐条消息与通过短记录已实现，并通过固定真实阶段及两轮正式入口验收。** 目标与回答的对应由真实已接受目标操作恢复，实际退回后的修订也进入后继请求；该限定结果不等于本页全模式或所有核验语义已经通过。机制与证据见[固化方案](../optimization/completed/verification-context-goal-binding.md)。

## 1. 目标与责任

实验组 1 接入后，`features.answer_verification` 统一控制 direct、claims 和 Python 回答核验，默认开启；关闭时跳过本职责与核验反馈链，不生成通过判决。目标核验独立关闭而回答核验开启时，输入采用当时已接纳目标的正文与提交身份，明确标为“未核验”，用户原话仍是权威；不构造虚假已通过快照。默认目标核验开启时仍严格要求实际通过回执。配置在运行和对话边界冻结，接入规格及实际验证状态见[实验组 1](../ablation/experiment.md#接入规格2026-11-05)。

回答核验器依据用户原话、仍有效的历史要求、通过目标核验的 goal 及 agent loop 实际生成的候选结果，判断本轮交付是否满足要求。核验器只返回判决和具体问题反馈；agent loop 负责补证、修订并生成新的完整结果，随后由回答核验器复验。

输入 goal 必须来自本轮实际通过目标核验并已生效的目标，保留正文及可定位的版本、提交和通过依据。目标沿用也须有本轮有效核验，不能把未通过的修订候选或其他分支的旧目标当成已接受目标。通过的 goal 仍是可纠正的工作解释，不能取代用户原话或豁免回答与原要求的冲突。

第20轮的实发请求已有完整有效目标，回答核验仍漏掉其中适用的候选名单上限。待验证的修正要求是以绑定目标为验收起点，逐项核对本轮交付及约束在回答中的实际应用。发现目标条款与用户原话冲突时，应明确指出需修订的目标条款。失败证据、检查方法与准入见[目标约束核验](../optimization/to_verify/analysis-goal-maintenance.md#第20轮的目标约束核验)。

## 2. 上下文顺序与修复循环

稳定 system prompt 说明回答核验职责、判据及输出契约；具体用户输入、通过的 goal 和候选结果来自当前真实轨迹。按用户轮次及轮内实际提交顺序保留以下内容。

| 要求 | 回答核验上下文保留的内容 | 后续条件 |
| --- | --- | --- |
| ANSWER-CTX-1 系统与用户要求 | system prompt、第 1 轮完整用户输入及仍适用的历史原话 | 明确本轮应交付的结果 |
| ANSWER-CTX-2 已通过的目标 | 本轮通过目标核验的完整 goal 及其对应身份 | 将该目标与本轮用户输入和候选结果绑定，不混用旧版或未通过目标 |
| ANSWER-CTX-3 候选结果 | agent loop 实际生成的完整结果及提交身份 | 对该确切结果进行核验，不把生成或提交记作已经交付 |
| ANSWER-CTX-4 发现问题 | 保留被拒结果、对应判决、具体问题与修订反馈 | 反馈必须交回原 agent loop，强制继续结果修复；未通过保持本轮交付阻塞 |
| ANSWER-CTX-5 修订与复验 | 在原反馈之后追加 agent loop 实际生成的新结果，再追加新的核验判决 | 仍有问题则继续反馈、修订和复验，直到无问题 |
| ANSWER-CTX-6 无问题与下一轮 | 保留绑定确切结果的“结果核验无问题”记录和原判决定位，再接续第 2 轮用户输入、通过核验的 goal、候选结果及判决 | 经原 Completion 检查接受本轮结果后，按相同模式处理下一用户轮，如此往复 |

```text
system prompt
第 1 轮用户输入
本轮通过目标核验的 goal-1
agent loop 生成的候选结果 result-1
结果核验判决
  有问题：保留问题反馈
           → 反馈交给原 agent loop
           → agent loop 修订并生成新结果 result-2
           → 新结果进入回答核验上下文，再核验
           → 仍有问题则继续上述修复循环
  无问题：保留“结果核验无问题”，绑定实际通过的结果
本轮结果通过核验并被接受、交付
第 2 轮用户输入
本轮通过目标核验的 goal-2
agent loop 生成的候选结果 → 核验 → 修订／通过
…
```

### 2.1 强制修复至无问题

结果核验失败后，Runtime 保留真实反馈并阻止该失败结果正常交付，原 agent loop 继续修复。修复可以包含补证、必要工具执行或改稿，最终必须提交新的完整候选结果并重新核验；核验器不代写结果，也不替主模型规定具体业务解法。不能用模型自述“已修复”、工具成功或旧稿的通过判决解除阻塞。

如果问题来自目标解释，agent loop 先修订 goal 并重新取得目标核验通过，再生成并核验对应结果；正确目标不因回答失败而被强制重写。新的目标正文及其通过依据必须进入后续回答核验，原目标与旧稿保持历史身份，不用新 goal 静默解释旧判决。

只有真实通过才能正常退出修复循环。既有预算、依赖或终止条件导致无法继续时，明确停止并保留未决问题，不把未修复结果记作通过或正常进入下一用户轮，也不无界重试。

### 2.2 判决与结果绑定

失败反馈、被拒结果、实际修订和复验判决按原时间顺序保留，不能只给最新结果或最新判决。“结果核验无问题”来自绑定确切稿件的真实通过回执；没有核验、回执缺失或尚未确定不能写成通过。以后修复通过时追加新判决，不改写旧失败记录，也不让已解决的旧问题继续充当当前阻塞。

用户轮次、goal 版本、结果提交和判决之间的对应关系必须可追溯。每次实际请求只包含当时已经发生的历史与当前待验结果，不预填未来修复或判决。具体角色与包装由正式请求构造器物化，待验结果是数据，不是对核验器的新增指令。

## 3. 历史范围与压缩

回答核验历史按同一可见分支的用户轮次及轮内结果提交顺序接续，保留各轮用户原话、对应已通过的 goal、候选结果、结果判决、问题反馈及实际修订。goal 作为必要输入交接，不因此重放目标核验的全部失败过程；业务材料按实际核验契约提供，不拼接主循环全部工具轨迹。

回答核验使用自己的既有历史压缩检查点，不混用目标核验或主循环摘要。压缩保留用户原话、当前完整 goal、待验结果、未决反馈及必要修订关系；旧过程摘要区分被拒稿、修复后稿、通过与未解决状态，并保留当时 goal 的对应及原件定位。历史和摘要从原 Journal 事实派生，不另建可写核验历史，也不把当前 goal 覆盖成所有历史轮次当时使用的目标。

## 5. 实现差异与验证边界

现有实现按 `answer` 职责保留用户原话、候选结果及对应判决；失败结果回到原循环，后续新稿重新核验，通过回执绑定确切正文。这些已有路径不等于本页全模式已验收，也不证明通过后的业务结果必然正确。

原实现只提供一个全局 `active_goal`，历史回答没有当时通过的 goal。现由 `VerificationEvent.verified_goal` 复用该次回答产生前真实已接受目标操作所引用的通过回执；各轮及同轮 goal 修订前后的回答保持各自快照。回答核验不再显示全局当前目标，每轮首次采用或更换目标时提供正文及通过引用，每次回答显式携带目标判决编号。正常当前回答没有已验证 goal 时拒绝构造核验请求；历史未准入尝试及澄清／限制如实标明无已通过目标，不用其他轮次目标补齐。原话、逐次结果及其判决分别物化为消息；通过判决显示“结果核验无问题”、原判决编号及结果正文摘要，失败判据及修复反馈保持完整，原始报告继续由 Journal 保存。

本次固定验收已覆盖首稿通过、一次退回后的实际修订及复验、跨用户轮的目标对应、同用户轮目标修订前后的回答绑定，以及正常当前回答缺少快照时的拒绝。后续涉及连续多次修复、停止或压缩时，仍按 ANSWER-CTX-1 至 ANSWER-CTX-6 消费真实轨迹；本次未触发的分支不记通过。实际样本、费用与边界由[固化方案](../optimization/completed/verification-context-goal-binding.md#决定性证据与边界)维护，原 task2 成绩保持。
