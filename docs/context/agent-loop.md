# Agent loop 上下文模式

日期：2026-11-03。本文拥有本次用户指定的主循环上下文模式及其检索维护对照。范围是执行用户任务的 agent loop 主模型；目标定义和目标遵循核验的输入分别由[目标核验器模式](goal-verifier.md)和[目标遵循核验器模式](goal-compliance-verifier.md)拥有。

实验组 1 的 feature flags 默认开启两类核验。关闭目标核验时仍须先维护目标，主循环根据真实操作说明“已保存、未核验”；关闭结果核验时不注入相应拒绝或修复历史，也不能声明通过。两个开关在对话内固定，引用、执行和交付检查继续生效。具体接入和验证状态由[实验组 1](../ablation/experiment.md#接入规格2026-11-05)拥有。

**状态：容量治理切片已接入，完整交互的确定性阶段回放36/36通过，已取得连续链局部证据、完整产品验证未完成；下表全部目标维护与修复模式尚未整体验收。** 下述事件表示实际发生后应如何进入上下文，不把未发生的调用、核验通过或修复写成历史事实。现有独立 Python direct 分析提供定位实例，不据此声称所有入口均已装配本页全模式。

## 1. 目标与输入责任

主模型在同一任务中持续消费用户原话、真实工具结果、核验判决与修复过程。目标维护后的工作解释可被纠正，用户原始要求仍是权威；工具执行、核验通过和最终接受分别消费各自真实事实。

稳定 system prompt 表达主模型职责与通用规则；工具定义说明本次实际可用动作。当前目标、维护状态及有效修复要求由原权威状态派生，不把动态状态永久写进稳定模板。一次上下文就是一次实际模型调用的输入，不能将完整任务时间线一次性灌入早于这些事件的请求。

已注册工具和子 Agent 的候选定义在每次能力投影时消费当前入口主体和渠道的部署拒绝规则。模型输入只物化剩余候选。派发仍独立校验实际调用的策略与参数。[能力可见性契约](../mcpDesign/README.md#522-身份入口与能力可见性)

工作区的原模型调用由实际执行回执配对。每条回执证据同时包含状态和完整路径，供模型引用给核验。审批事实与执行回执在后续快照保留。[工作区确认契约](../mcpDesign/README.md#523-工作区变更确认与接续)

## 2. 每轮接续顺序

模型缺少只能由用户提供的信息时，通过独立的 `control_request_clarification` 提问。Runtime 记录工具调用、处置和实际发给用户的问题，同一会话的后续用户回复继续进入主循环。模型能用现有材料或工具解决的缺口，继续执行相应动作。`control_submit_final` 接收答案、限制或失败。

测试模式由部署配置 `PERSONAL_AGENT_ANSWER_RESULT` 的 `test_mode` 显式开启，默认为 `false`。Runtime 完成各阶段的工具组装后，统一按测试模式的禁用名单过滤模型工具。当前名单包含 `control_request_clarification`。调用校验使用同一份过滤后的声明，拒绝反馈随原调用进入主循环。[运行方式与验证](../topics/runtime.md#回答测试模式)

“第一轮”指用户轮次，“第一次工具调用”指目标维护通过后的业务动作序号，不预定模型必须选择的业务工具。

| 要求 | 上下文中保留的内容 | 下一步条件 |
| --- | --- | --- |
| LOOP-CTX-1 系统与用户输入 | system prompt、本次工具定义；第 1 轮用户完整原话及必要材料 | 从该轮用户要求开始维护目标 |
| LOOP-CTX-2 目标维护 | 真实目标维护工具调用、候选目标及配对结果，区分候选与已生效目标 | 对本次候选或沿用提议进行目标核验 |
| LOOP-CTX-3 目标核验通过 | 保留与确切目标对应的“目标核验无问题”记录及原判决定位 | 目标维护正式生效后开放业务动作；无问题时不强制额外修改目标 |
| LOOP-CTX-4 目标核验失败 | 保留具体问题反馈、所针对目标及修改要求 | 后续主模型决策必须调用目标修改工具；修改结果继续核验，直至通过或触发现有停止条件 |
| LOOP-CTX-5 业务执行 | 第一次业务工具调用、第一次真实工具结果，随后第二次调用与结果，依此接续；失败和拒绝也按原位置保留 | 模型根据实际结果继续行动或提交候选结果 |
| LOOP-CTX-6 结果生成 | 当前用户轮次的候选结果及其实际提交身份 | 对确切候选结果进行结果核验，生成不等于已交付 |
| LOOP-CTX-7 结果核验通过 | 保留与确切候选结果对应的“结果核验无问题”记录及原判决定位 | 经原 Completion 检查接受该结果，完成本轮交付 |
| LOOP-CTX-8 结果核验失败 | 保留具体反馈、被拒稿件及后续实际修复 | 同一主循环持续修复结果，再提交、再核验；未通过不进入正常交付 |
| LOOP-CTX-9 下一用户轮 | 第 1 轮已发生的维护、核验、调用、结果及修复历史，随后是第 2 轮用户原话 | 本轮核验通过并被接受后，按相同规则处理第 2 轮；后续轮次如此往复 |

正常时间线如下，分支只在实际发生时出现：

```text
system prompt + 本次工具定义
第 1 轮用户输入
目标维护调用 → 维护结果／候选目标
目标核验
  有问题：反馈 → 强制目标修改调用 → 修改结果 → 再核验
  无问题：保留“目标核验无问题”
业务工具调用 1 → 工具结果 1 → 调用 2 → 结果 2 → …
第 1 轮候选结果 → 结果核验
  有问题：反馈 → 实际修复 → 新候选结果 → 再核验
  无问题：保留“结果核验无问题” → 接受并交付
第 2 轮用户输入 → 本轮目标维护 → 核验与执行 → 结果修复／通过
…
```

### 2.1 目标失败后强制修改

候选修订按[目标文稿契约](../optimization/to_verify/analysis-goal-maintenance.md#924-通过通用文稿编辑修订目标)实施。首次仍由 `maintain_goal` 提交完整正文；已有目标按需通过 `read_current_goal` 准备文稿，复用通用读取、搜索和补丁，再提交文稿引用。文稿准备与编辑不改变正式目标，也不能解除维护前提。未维护时只额外开放本轮目标文稿操作；`retain_goal` 仍仅用于正文确实无需改变的情况。

目标核验失败的反馈必须进入下一次主请求，并指出被拒稿件及具体问题。后续读取、搜索和补丁可继续消费未生效文稿；在目标维护成功前，正常业务工具或最终答复仍受原前提限制。工具调用、结果、提交与反馈按实际顺序配对保留，不添加历史反馈汇总区。实施核对同时检查可用动作、实际工具选择和 Runtime 拒绝边界。

文稿工具的字段用途随当次工具声明进入主请求。普通阶段分别声明创建和补丁。目标草稿阶段只保留 `tool_patch_artifact`，并把 `base_resource_id` 限于本轮合法稿件。补丁坐标和替换正文处于同一编辑项。历史中的原工具调用和返回按原身份配对保存。字段含义见[工具契约](../topics/tools.md#输入结果与错误)。

维护调用、候选、核验和生效结果在本表中按逻辑区分。现有目标核验在写入前执行，结果可以内嵌同一真实维护回执；不得为呈现时间线伪造另一条工具调用或提前记录目标生效。失败候选保持未生效，修复后的真实判决才决定是否提交。

### 2.2 结果失败后持续修复

结果核验失败后，按原时间顺序追加“被拒结果 → 反馈 → 补证／工具调用／改稿 → 新结果 → 再核验”，保留历次反馈与实际修复，不能只发送最新判决。修复仍由原主模型完成，不另起一个丢失原历史的空会话。

若实际问题是目标解释错误，主模型可回到目标修改与目标核验；结果失败本身不强制无意义地重写正确目标。核验通过只适用于被核验的目标或稿件，不能将旧通过嫁接到新版本。超时、预算耗尽、依赖失败等按既有停止契约处理，保留未解决反馈，不记录为“无问题”或正常完成。

### 2.3 动作拒绝的重试上下文

原生调用在执行前被拒时，主模型依次收到原调用和配对的 Runtime 反馈。反馈说明哪个动作被拒、原因和当前可以采取的下一步。原调用已在同一交换提供时，反馈不再附一份相同参数。未形成可配对交换时，继续从原反馈恢复可用的提议。Journal 保留完整原调用与拒绝事实，投影不改变原始记录。

若当次请求等待目标维护且整批动作因未声明名称在执行前被拒，在原交互位置用一条 Runtime 消息表达拒绝。它指出实际被拒的名称、整批未执行、本轮目标尚未维护、所有业务工具暂不可用，并列出当次已声明的目标维护动作。文稿读、搜、补丁仅适用于本轮合法目标文稿，已有澄清或限制性退出沿当次声明。该事件不发送被拒调用的参数或孤立工具回执。归档保留原调用，历史摘要使用相同的简短拒绝事实。

普通参数校验失败继续原生配对。Runtime 从当次 Schema 校验结果读取字段、实际结构和期望类型。字段要求数组且实际对象只有一个数组属性时，反馈指出该数组的位置，并说明如何直接提交数组。属性位置沿用原有字段名披露规则。反馈由当次参数生成，原调用仍提供完整参数供检查。依据与验收见[动作拒绝反馈设计](../optimization/to_verify/conversation-loop-boundaries.md#312-动作协议拒绝的事实反馈)。

全部被拒调用已在原生交换中、且修复说明已覆盖每个类型错误位置时，工具消息正文直接发送该说明。模型可以沿源路径把整个内层数组原样交给目标字段，再重新提交。诊断和原调用仍由 Journal 保留。未配对调用或修复说明不足的历史记录继续提供原诊断，避免因投影省略恢复所需信息。

未读外置原件或重复抓取的修复指引由主请求按本次工具声明生成。拒绝记录关联确切原件。主循环只列出允许该原件的读取或搜索工具，使用声明中的名称和参数，保留原拒绝的交互位置。没有可用动作时说明当前无法读取，不引导模型调用未声明的工具。范围、基线及验证见[外置原件反馈设计](../optimization/completed/runtime-feedback-repair.md#原件和调用身份)。

历史快照仅用于恢复上下文。准入拒绝将具体快照交给同一读搜投影。目标维护反馈按本次工具声明区分准备文稿和已有文稿，文稿准备失败保留原读取动作和原因。知识操作反馈按实际确认与来源约束给出修复。原生调用身份由协议绑定，重复身份时回看原执行事实。实施与验证见[拦截事实与合法修复](../optimization/completed/runtime-feedback-repair.md#目标修复和知识确认)。

### 2.4 通过状态与原始记录

“目标核验无问题”“结果核验无问题”是实际通过判决的简洁展示，仍须能定位原判决、对应对象和版本。没有执行、缺少回执或尚未确定不能写成通过。失败保留可执行反馈；以后通过时追加新判决，不改写旧反馈为成功，也不把当前已解决的问题继续作为未决要求。

2026-11-04 [通过记录精简](../optimization/completed/verification-context-goal-binding.md)已通过固定真实阶段及两轮正式入口验收：主循环仍接收原观察身份、能力和状态，发送投影只保留核验类型、通过状态、原判决编号、稿件摘要及“核验无问题”说明。完整正文和逐项报告保留在原 Journal，失败反馈不精简；投影不参与准入或完成判定。该限定结果不代表本页全部目标门禁已经完成。

## 3. 角色、历史与压缩边界

- 保留原生消息角色、工具调用身份与配对结果，并在产生它的交互之后追加相应 Runtime／核验反馈，再接后续实际修复。不能按类型把全部工具结果或全部核验集中到前面，也不能把动态 system 反馈全部搬到稳定前缀。
- 已完成至少一轮主决策后，若累计 token 预算尚有余量且低于 10%，下一轮主请求在当前 system 消息的预算快照旁提醒模型优先交付。该提醒随请求重算。触发条件与验收见[主决策后的低预算提醒](../optimization/to_verify/conversation-loop-boundaries.md#319-主决策后的低预算提醒)。
- 主循环继承同一可见分支中的历轮实际过程；核对主体、会话、run、用户轮次和调用身份，不能仅凭重复的局部动作编号消耗或去重反馈。只读取当时已发生且当前可见的材料，不恢复越权内容或未来判决。
- 主循环收到目标／结果核验反馈，不因此共享核验器的全部内部消息或推理记录。核验器的职责历史继续遵守[职责分离契约](../optimization/to_verify/analysis-goal-maintenance.md#914-分离目标核验与回答核验的职责及历史)；原生协议要求的推理块按服务方规则保留，不伪造隐藏推理。
- 容量处理采用结果外置、旧正文卸载和完整交互摘要。Journal 与 Artifact 保存原件，发送视图停止重复携带已经覆盖的正文；后续历史重建不得重新加载被覆盖的交换。保留用户原话、当前有效目标、待验结果、当前未决反馈及近期完整工具交互；摘要保留目标变化、实际执行、失败、修复、通过／未解决状态和原件定位。摘要模型读取按原顺序排列的用户请求、目标操作、调用、结果、判决、修复和已交付结果，不能从工具 stdout 推测交付状态。
- 摘要覆盖以 run 和模型决策范围绑定，跨轮同号反馈不互相消费。历史已交付回答可由有来源的摘要替代，用户原话保持原文；当前轮尾部交换及其反馈保留配对原件。卸载只改变模型投影，不改变执行、核验、授权或完成事实；原件通过现有读搜工具按需恢复。
- 在主请求实际组装完毕后，由模型 Port 对最终 Provider 请求进行无网络容量测量，达到 80% 压力阈值先摘要安全前缀，最多两次；保留约 16% 近期原生交互且至少最近两次决定。始终预留单次输出和协议空间；无可压缩前缀时，硬容量内可继续，硬容量外明确停止。摘要必须缩小实际投影，原件保存失败或未缩减不得激活。具体采用、基线、验收与实施状态见目标维护 Spec §9.20。

## 5. 实现对照与验收状态
