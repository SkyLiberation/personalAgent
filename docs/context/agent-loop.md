# Agent loop 上下文模式

日期：2026-11-03。本文拥有本次用户指定的主循环上下文模式及其检索维护对照。范围是执行用户任务的 agent loop 主模型；目标定义和目标遵循核验的输入分别由[目标核验器模式](goal-verifier.md)和[目标遵循核验器模式](goal-compliance-verifier.md)拥有。

实验组 1 的 feature flags 默认开启两类核验。关闭目标核验时仍须先维护目标，主循环根据真实操作说明“已保存、未核验”；关闭结果核验时不注入相应拒绝或修复历史，也不能声明通过。两个开关在对话内固定，引用、执行和交付检查继续生效。具体接入和验证状态由[实验组 1](../ablation/experiment.md#接入规格2026-11-05)拥有。

**状态：容量治理切片已接入，完整交互的确定性阶段回放36/36通过，已取得连续链局部证据、完整产品验证未完成；下表全部目标维护与修复模式尚未整体验收。** 下述事件表示实际发生后应如何进入上下文，不把未发生的调用、核验通过或修复写成历史事实。正式 Conversation 统一使用目标维护路径。历史验收仍按对应运行的配置及证据解释。

## 1. 目标与输入责任

主模型在同一任务中持续消费用户原话、真实工具结果、核验判决与修复过程。目标维护后的工作解释可被纠正，用户原始要求仍是权威；工具执行、核验通过和最终接受分别消费各自真实事实。

稳定 system prompt 表达主模型职责与通用规则；工具定义说明本次实际可用动作。当前目标、维护状态及有效修复要求由原权威状态派生，不把动态状态永久写进稳定模板。一次上下文就是一次实际模型调用的输入，不能将完整任务时间线一次性灌入早于这些事件的请求。

MCP 工具将 Server 的 `inputSchema` 交给模型工具定义和动作解码。可选字段可直接省略，校验错误仍通过现有动作反馈交给下一轮。[上游参数契约](../mcpDesign/README.md#524-沿用上游输入-schema)

MCP 工具结果在请求内展示一份正文。保留行继续使用实际回执的引用坐标，工具调用与结果按原顺序配对。[普通 MCP 回执投影](tool.md#普通-mcp-回执正文去重)

工作清单的调用条件与读写规则随 `control_working_plan` 的工具描述进入请求。Runtime 从 Journal 渲染当前清单。压缩后的主请求只投影待办和进行中项，模型可通过空参数读回完整清单。每次成功读取或更新的原生工具回执绑定该次看到的清单和版本。[工作清单参数](local-tools.md#5-conversation-直接声明的本地动作)

预算余额由 Conversation 预算组件从已提交用量派生。低 token 提示由[独立实验开关](../ablation/experiment.md#实验组-2低-token-余额提示)控制，仓库配置为新运行开启。完成至少一轮主决策后，若下一轮可以发起且累计 token 余量大于零、严格低于有效额度的 10%，主请求的 system 消息附加通用交付提醒，并记录提示版本。历史消息、工具声明、核验输入和已封存请求沿原路径。具体判断与接入验证见[预算治理设计](../optimization/to_verify/conversation-loop-boundaries.md#319-对话预算治理的装配边界)。

已注册工具和子 Agent 的候选定义在每次能力投影时消费当前入口主体和渠道的部署拒绝规则。模型输入只物化剩余候选。派发仍独立校验实际调用的策略与参数。[能力可见性契约](../mcpDesign/README.md#522-身份入口与能力可见性)

工作区的原模型调用由实际执行回执配对。每条回执证据同时包含状态和完整路径，供模型引用给核验。审批事实与执行回执在后续快照保留。[工作区确认契约](../mcpDesign/README.md#523-工作区变更确认与接续)

## 2. 每轮接续顺序

模型缺少只能由用户提供的信息时，通过独立的 `control_request_clarification` 提问。Runtime 记录工具调用、处置和实际发给用户的问题，同一会话的后续用户回复继续进入主循环。模型能用现有材料或工具解决的缺口，继续执行相应动作。`control_submit_final` 接收答案、限制或失败。

测试模式由部署配置 `PERSONAL_AGENT_ANSWER_RESULT` 的 `test_mode` 显式开启，默认为 `false`。Runtime 完成各阶段的工具组装后，统一按测试模式的禁用名单过滤模型工具。当前名单包含 `control_request_clarification`。调用校验使用同一份过滤后的声明，拒绝反馈随原调用进入主循环。[运行方式与验证](../topics/runtime.md#回答测试模式)

“第一轮”指用户轮次，“第一次工具调用”指目标维护通过后的业务动作序号，不预定模型必须选择的业务工具。

| 要求 | 上下文中保留的内容 | 下一步条件 |
| --- | --- | --- |
| LOOP-CTX-1 系统与用户输入 | system prompt、本次工具定义；第 1 轮用户完整原话及必要材料 | 从该轮用户要求开始维护目标 |
| LOOP-CTX-2 目标维护 | 真实目标维护工具调用、候选目标及配对结果，区分候选与已生效目标 | 对本次候选或沿用提议进行目标核验 |
| LOOP-CTX-3 目标核验通过 | 保留与确切目标对应的“目标核验无问题”记录及原判决定位 | 目标维护正式生效后开放业务动作；无问题时不强制额外修改目标 |
| LOOP-CTX-4 目标核验失败 | 保留具体问题反馈、所针对目标及修改要求 | 后续主模型决策必须调用目标修改工具；修改结果继续核验，直至通过或触发现有停止条件 |
| LOOP-CTX-5 业务执行 | 第一次业务工具调用、第一次真实工具结果，随后第二次调用与结果，依此接续；失败和拒绝也按原位置保留 | 模型根据实际结果继续行动或提交候选结果 |
| LOOP-CTX-6 结果生成 | 当前用户轮次的候选结果及其实际提交身份 | 对确切候选结果进行结果核验，生成不等于已交付 |
| LOOP-CTX-7 结果核验通过 | 保留与确切候选结果对应的“结果核验无问题”记录及原判决定位 | 经原 Completion 检查接受该结果，完成本轮交付 |
| LOOP-CTX-8 结果核验失败 | 保留具体反馈、被拒稿件及后续实际修复 | 同一主循环持续修复结果，再提交、再核验；未通过不进入正常交付 |
| LOOP-CTX-9 下一用户轮 | 第 1 轮已发生的维护、核验、调用、结果及修复历史，随后是第 2 轮用户原话 | 本轮核验通过并被接受后，按相同规则处理第 2 轮；后续轮次如此往复 |

正常时间线如下，分支只在实际发生时出现：

```text
system prompt + 本次工具定义
第 1 轮用户输入
目标维护调用 → 维护结果／候选目标
目标核验
  有问题：反馈 → 强制目标修改调用 → 修改结果 → 再核验
  无问题：保留“目标核验无问题”
业务工具调用 1 → 工具结果 1 → 调用 2 → 结果 2 → …
第 1 轮候选结果 → 结果核验
  有问题：反馈 → 实际修复 → 新候选结果 → 再核验
  无问题：保留“结果核验无问题” → 接受并交付
第 2 轮用户输入 → 本轮目标维护 → 核验与执行 → 结果修复／通过
…
```

### 2.1 目标失败后强制修改

Conversation 按[增量目标契约](../optimization/to_verify/analysis-goal-maintenance.md#当前改造版本化目标条目和增量提交)维护目标。模型先看到当前有效条目、版本、执行控制及原用户请求。此时仅声明目标维护、可用的只读目标查询和澄清或限制出口。提交 `submit_goal_patch` 后，Runtime 保留未操作条目，并按配置核验候选。空操作保留版本。澄清保存问题并结束本轮。

目标核验失败的反馈进入下一次主请求，指向具体被拒操作。维护成功后，执行请求使用已提交目标、执行控制、计划、进度和真实工具结果。目标区块是 Runtime 注入的应用数据，稳定规则由 system 提供。调用、结果、提交及反馈按实际顺序配对保留。

#### Goal 快照与待澄清事项

设计：两个阶段从同一授权分支的 Journal 恢复快照。主循环和两个核验时点用同一份双语字段说明解释 Goal 数据。版本用于提交补丁，`goal_id` 用于定位任务，`objective` 是工作摘要。条目键是服务端分配的可操作 ID。每项说明类型、适用范围、文本、状态、来源消息和可核对的验收条件。执行控制另有模式及来源。空条目表示没有本轮适用条目，`execution_control: null` 表示没有持久执行限制，现有权限仍适用。[目标核验的快照说明](goal-verifier.md#快照字段与来源)

用户已收到的澄清问题从选中任务实际交付的 `clarification_required` 恢复。归属尚未确定时提出的澄清进入当前任务的维护视图，供下轮判断。下轮在新开、插问或恢复时可一并关闭这项已显示的未绑定问题。接纳后旧任务退出该未决问题，选中任务保留问答来源。每次交付以运行 ID 为一项，按原顺序显示 ID 和问题正文。新消息、读取、目标沿用或压缩均不关闭问题。关闭须由后继维护提议引用显示的 ID 和当前用户的原话，并经 Runtime 接纳。开启核验时，核验器核对该原话是否回答问题或明确撤回；未通过的提议保留待澄清事项。提交新问题结束本轮，不应用该次补丁。与问题无关的工作可以继续，依赖答案的动作等待澄清。未决状态是现有交付及接纳事件的只读投影。

摘要只替换覆盖范围内的历史。当前快照、原用户消息和待澄清事项由 Journal 重新投影，和摘要分开发送。原交付正文及旧工具回执仍可通过覆盖快照恢复。验证比较同一实际轮次压缩前、激活检查点后及新进程恢复后的输入，核对版本、未改条目、来源、执行控制、未决问题和原件读取。LongDS 第二轮真实续接与压缩恢复的执行规格见[目标维护 Spec](../optimization/to_verify/analysis-goal-maintenance.md#第二轮接续与压缩恢复)。

实现与验证：LongDS Task 2 第二轮从实发请求续接首轮 v1，提交 v2 后执行并交付。在第二轮真实阶段的隔离副本上激活检查点，新进程恢复出相同的 Goal 区块、近期工具交换和快照原件。待澄清的保留与关闭另以真实问题和确定性反事实回放。[实发审计](../../.tmp/goal-context-20261112/product-audit.json) · [恢复检查](../../.tmp/goal-context-20261112/compression/recovery-report.json) · [澄清回放](../../.tmp/goal-context-20261112/context-replay-report.json)

LongDS、Toolathlon 与其他 Conversation 请求共用目标维护、工具反馈及恢复。目标补丁按本轮原话绑定交付方式。独立意图分类已移除。Python 与 MCP 工具可见性继续按各自授权及运行配置决定。

维护调用、候选、核验和生效结果在本表中按逻辑区分。现有目标核验在写入前执行，结果可以内嵌同一真实维护回执；不得为呈现时间线伪造另一条工具调用或提前记录目标生效。失败候选保持未生效，修复后的真实判决才决定是否提交。

### 2.2 结果失败后持续修复

结果核验失败后，按原时间顺序追加“被拒结果 → 反馈 → 补证／工具调用／改稿 → 新结果 → 再核验”，保留历次反馈与实际修复，不能只发送最新判决。修复仍由原主模型完成，不另起一个丢失原历史的空会话。

若实际问题是目标解释错误，主模型可回到目标修改与目标核验；结果失败本身不强制无意义地重写正确目标。核验通过只适用于被核验的目标或稿件，不能将旧通过嫁接到新版本。超时、预算耗尽、依赖失败等按既有停止契约处理，保留未解决反馈，不记录为“无问题”或正常完成。

### 2.3 动作拒绝的重试上下文

原生调用在执行前被拒时，主模型依次收到原调用和配对的 Runtime 反馈。反馈说明哪个动作被拒、原因和当前可以采取的下一步。原调用已在同一交换提供时，反馈不再附一份相同参数。未形成可配对交换时，继续从原反馈恢复可用的提议。Journal 保留完整原调用与拒绝事实，投影不改变原始记录。

若当次请求等待目标维护且整批动作因未声明名称在执行前被拒，在原交互位置说明实际被拒的名称、整批未执行、业务工具暂不可用及已声明的目标维护动作。归档保留原调用，历史摘要使用同一拒绝事实。

普通参数校验失败继续原生配对。Runtime 从当次 Schema 校验结果读取字段、实际结构和期望类型。字段要求数组且实际对象只有一个数组属性时，反馈指出该数组的位置，并说明如何直接提交数组。属性位置沿用原有字段名披露规则。反馈由当次参数生成，原调用仍提供完整参数供检查。依据与验收见[动作拒绝反馈设计](../optimization/to_verify/conversation-loop-boundaries.md#312-动作协议拒绝的事实反馈)。

全部被拒调用已在原生交换中、且修复说明已覆盖每个类型错误位置时，工具消息正文直接发送该说明。模型可以沿源路径把整个内层数组原样交给目标字段，再重新提交。诊断和原调用仍由 Journal 保留。未配对调用或修复说明不足的历史记录继续提供原诊断，避免因投影省略恢复所需信息。

未读外置原件的修复指引由主请求按本次工具声明生成，只列出允许该原件的读取或搜索工具。相同抓取已有外置结果时，反馈只报告重复工具调用未执行。两类拒绝按原调用位置配对。范围、基线及验证见[Runtime 拦截反馈](runtime-feedback.md#91-已修改)。

历史快照仅用于恢复上下文。准入拒绝将具体快照交给同一读搜投影。目标反馈提供当前版本和适用的条目诊断。知识操作反馈按实际确认与来源约束给出修复。原生调用身份由协议绑定，重复身份时回看原执行事实。

### 2.4 通过状态与原始记录

“目标核验无问题”“结果核验无问题”是实际通过判决的简洁展示，仍须能定位原判决、对应对象和版本。没有执行、缺少回执或尚未确定不能写成通过。失败保留可执行反馈；以后通过时追加新判决，不改写旧反馈为成功，也不把当前已解决的问题继续作为未决要求。

2026-11-04 [通过记录精简](../optimization/completed/verification-context-goal-binding.md)已通过固定真实阶段及两轮正式入口验收：主循环仍接收原观察身份、能力和状态，发送投影只保留核验类型、通过状态、原判决编号、稿件摘要及“核验无问题”说明。完整正文和逐项报告保留在原 Journal，失败反馈不精简；投影不参与准入或完成判定。该限定结果不代表本页全部目标门禁已经完成。

## 3. 角色、历史与压缩边界

- 保留原生消息角色、工具调用身份与配对结果，并在产生它的交互之后追加相应 Runtime／核验反馈，再接后续实际修复。不能按类型把全部工具结果或全部核验集中到前面，也不能把动态 system 反馈全部搬到稳定前缀。
- 主循环继承同一可见分支中的历轮实际过程；核对主体、会话、run、用户轮次和调用身份，不能仅凭重复的局部动作编号消耗或去重反馈。只读取当时已发生且当前可见的材料，不恢复越权内容或未来判决。
- 主循环收到目标／结果核验反馈，不因此共享核验器的全部内部消息或推理记录。核验器的职责历史继续遵守[职责分离契约](../optimization/to_verify/analysis-goal-maintenance.md#914-分离目标核验与回答核验的职责及历史)；原生协议要求的推理块按服务方规则保留，不伪造隐藏推理。
- 容量处理采用结果外置、旧正文卸载和完整交互摘要。Journal 与 Artifact 保存原件，发送视图停止重复携带已经覆盖的正文；后续历史重建不得重新加载被覆盖的交换。保留用户原话、当前有效目标、待验结果、当前未决反馈及近期完整工具交互；摘要保留目标变化、实际执行、失败、修复、通过／未解决状态和原件定位。摘要模型读取按原顺序排列的用户请求、目标操作、调用、结果、判决、修复和已交付结果，不能从工具 stdout 推测交付状态。
- 单次超限回执的预览和窗口续读见[工具输出超限的处理](tool.md)。原生回执被历史压缩覆盖后，按下节投影原件定位。
- 摘要覆盖以 run 和模型决策范围绑定，跨轮同号反馈不互相消费。历史已交付回答可由有来源的摘要替代，用户原话保持原文；当前轮尾部交换及其反馈保留配对原件。卸载只改变模型投影，不改变执行、核验、授权或完成事实；原件通过现有读搜工具按需恢复。
- 在主请求实际组装完毕后，由模型 Port 对最终 Provider 请求进行无网络容量测量，达到 80% 压力阈值先摘要安全前缀，最多两次；保留约 16% 近期原生交互且至少最近两次决定。始终预留单次输出和协议空间；无可压缩前缀时，硬容量内可继续，硬容量外明确停止。摘要必须缩小实际投影，原件保存失败或未缩减不得激活。具体采用、基线、验收与实施状态见目标维护 Spec §9.20。

### 3.1 压缩后如何定位工具原件

旧工具回执被工作摘要覆盖后，主模型仍需要知道从哪里找回某轮的完整结果。Runtime 在每次组装主请求时，从压缩检查点覆盖范围内被移出请求的可见回执和原调用重建定位。首次压缩与后续压缩沿用同一构造路径。Journal 保存调用和回执，Artifact 保存结果原文及历史快照。工具可用性以当次请求的工具声明为准。

每条定位用一行说明运行、决策轮次、来源工具、调用 ID、原件 ID 和本次可用的读取工具。简短的原调用参数另起一行保留原样，供辨认来源。参数超长时按调用身份到历史快照查找。

已外置的回执直接指向原件资源。成功且包含可引用内容的业务工具回执若未单独外置，逐条指向当前有效历史快照中该条回执的起始行和列。只开放搜索时，提供能唯一匹配该回执开头的关键词，搜索只返回命中片段。定位以经校验的快照与 Journal 为来源，在主请求内派生，不增加持久化索引或复制回执。定位区也保留按运行 ID 和决策轮次查阅整份快照的入口。快照回执的 `payload` 保存当时的工具结果。读取快照可恢复历史上下文，业务证据资格仍由原有引用契约决定。

已有适用检查点且至少存在一条可用读取路径时，Runtime 在主请求动态 `system` 消息中先放“已压缩工具结果的原件定位”，再放本次执行输入。服务提供方适配器随后接入当前运行保留的原生交换。当前运行仅覆盖部分历史且仍有保留交换时，工作摘要紧接在首个保留交换之前。近期原生调用和回执保持配对。定位区块只列工具 Schema 允许读取或搜索的资源，旧回执正文随被覆盖交换退出。

### 3.2 模型可见说明与原始数据

主请求用自然语言说明本轮预算、调用限制和当前目标状态。计划按步骤列出工作描述与状态，保留可用于修订的步骤 ID。工具参数 Schema、执行权限和预算门禁继续消费原 typed 契约。普通执行输入使用与工具历史一致的展示；领域数据有实际结构时，先说明用途，再保留必要的原值。已授权来源的原文和可操作引用按原值交给模型。

原件定位按运行和决策逐项列出原调用、可用工具和原件 ID。读取建议只由当轮工具声明生成。工作摘要只说明覆盖范围，恢复指引由原件定位区提供。两个消费者读取同一压缩检查点，Journal、快照内容与执行许可仍由原责任主体维护。

摘要模型按历史运行和决策读取新增交互，区分用户原话、调用与原参数、工具回执、修复、目标维护和交付。上一摘要和当前目标分区展示。持久快照继续保存原结构。用真实 Toolathlon 第 4、13、17、18、27 轮以及两次压缩输入验收预算与能力展示、无合法读工具、拒绝反馈、来源定位及原生配对。用已封存目标维护和核验轨迹核对待验对象、失败理由和原文保真。模型选择与完整任务结果单独验证。

## 5. 实现对照与验收状态
