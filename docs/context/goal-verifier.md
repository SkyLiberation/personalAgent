# 目标核验器上下文模式

日期：2026-11-03。本文拥有目标核验器（goal verifier）的任务上下文模式。依据为本次用户明确要求及现有目标核验输入构造链；主循环如何执行修订由 [Agent loop 模式](agent-loop.md)拥有，通过后的 goal 如何交给回答核验见[回答核验器模式](goal-compliance-verifier.md)。

**状态（2026-11-04）：逐条消息与通过短记录已实现，并通过固定真实阶段及两轮正式入口验收。** 当前已有按职责筛选的目标核验历史；真实运行中一次退回后修订通过，不代表目标失败后独占修改工具的门禁已完整落实。该门禁仍是实现差异，不能将本页全部要求写成已验证能力。表达修正见[固化方案](../optimization/completed/verification-context-goal-binding.md)。

## 1. 目标与责任

实验组 1 接入后，`features.goal_verification` 决定本职责是否执行，默认开启。关闭时模型仍须维护目标，Runtime 执行原确定性准入，Journal 将操作保存为无核验引用的接纳事实；不生成目标判决或核验修复反馈。主循环如实说明目标已保存但未核验。开关在运行和对话边界绑定，不能中途关闭来消除既有失败。接入规格与实际验证状态见[实验组 1](../ablation/experiment.md#接入规格2026-11-05)。

目标核验器判断目标维护结果是否忠实、完整地表达当前及仍有效的用户要求。按[增量目标契约](../optimization/to_verify/analysis-goal-maintenance.md#当前改造版本化目标条目和增量提交)，Runtime 将原补丁施加到有效快照，提供本轮适用的候选条目、验收条件、执行控制、有效原目标及差异。核验器根据本轮用户原话核对变更，尤其是约束放宽、撤销和恢复执行。核验器只产生判决及问题反馈。

这里的“目标维护结果”是由实际补丁确定的候选快照。它在 Runtime 提交后才生效。用户原话是权威依据。判决绑定候选内容、用户轮次及提交身份。

同一对话出现任务切换时，本次请求以提议选中的任务为基础恢复核验历史。已有 Goal 核验同时检查任务关系，使用本轮原话、选中任务入口及当前任务的必要对照信息。新开或插问以空目标为基础，旧任务材料只供判断归属。通过后由 Journal 同次提交归属和补丁。[主循环任务切换](agent-loop.md#同一对话中的任务切换)

### 快照字段与来源

设计：主循环、目标定义核验和动作及回答核验共享双语字段说明。模型请求保留由 Runtime 构造的 JSON 快照，供对照版本、条目 ID 和绑定内容。候选快照、已生效快照和历史回执使用各自的区块标识。历史正文与当前说明分开发送。

| 快照内容 | 含义 |
| --- | --- |
| `goal_id`、`objective` | 服务端任务身份及工作摘要。判断以本轮适用条目、用户原话和真实证据为准。 |
| `items` 的键 | 服务端分配的条目 ID，用于增量修改和定位核验意见。空对象表示本轮没有适用条目。 |
| `kind`、`scope`、`text`、`status` | `requirement` 是结果要求，`constraint` 是限制。`task` 跨轮适用，`turn` 仅用于所属轮次。`text` 保存含义和条件。`active` 为有效条目，撤销条目由历史保留。 |
| `source_message_ids`、`acceptance_criteria` | 来源 ID 定位服务器绑定的用户消息，可与原话核对。验收条件说明检查什么，空数组表示没有单列标准。 |
| `execution_control` | `null` 表示没有持久执行限制，权限仍按现行策略判定。`running`、`read_only`、`paused` 分别表示按权限运行、只读和暂停业务动作。`source_message_id` 定位设置该模式的用户原话。 |

待验提议若关闭一个已交付的澄清事项，核验请求另提供问题原文和当前用户的答复或撤回引文。核验按该材料判断问题是否已解决；Runtime 只在同一次补丁接纳时关闭。题目无待澄清事项或提议未请求关闭时，省略这一核验区块。[主循环待澄清投影](agent-loop.md#goal-快照与待澄清事项)

实现与验证：LongDS 前两轮的 3 次目标核验实发均携带字段说明，第二轮判决消费首轮生效状态及新候选。关闭澄清的请求组装在中英文中已回放，该轨迹没有产生待关闭的问题。[实发审计](../../.tmp/goal-context-20261112/product-audit.json) · [澄清回放](../../.tmp/goal-context-20261112/context-replay-report.json)

## 2. 上下文顺序与修复循环

稳定 system prompt 说明目标核验职责、判据和输出契约；用户要求与具体目标从当次轨迹进入。保留以下逻辑顺序，不将目标、判决与修订分别集中分组。

| 要求 | 目标核验上下文保留的内容 | 后续条件 |
| --- | --- | --- |
| GOAL-CTX-1 系统与用户要求 | system prompt、第 1 轮完整用户输入，以及仍适用的历史原话 | 核验当前轮实际提交的目标 |
| GOAL-CTX-2 目标维护结果 | agent loop 实际生成的完整候选 goal 及提交身份 | 对该确切目标产生判决，不预填其核验结果 |
| GOAL-CTX-3 发现问题 | 保留原目标、对应核验结果、具体问题及修订反馈 | 反馈必须进入 agent loop，强制其修订 goal；目标未通过时保持本轮核验阻塞 |
| GOAL-CTX-4 修订与复验 | 在原反馈之后追加 agent loop 实际生成的新 goal，再追加新的核验结果 | 仍有问题则继续反馈、修订和复验，直到无问题；承诺修订、读取或沿用不等于修复 |
| GOAL-CTX-5 无问题 | 保留与确切目标对应的“目标核验无问题”记录及原判决定位 | 解除该目标的核验阻塞，交回主循环继续执行 |
| GOAL-CTX-6 下一用户轮 | 保留第 1 轮目标、判决及修订过程，随后接入第 2 轮用户输入、目标维护结果及判决 | 本轮目标核验通过后，按相同模式续接下一用户轮；后续轮次如此往复 |

```text
system prompt
第 1 轮用户输入
目标维护结果 goal-1
目标核验结果
  有问题：保留问题反馈
           → 反馈交给 agent loop
           → agent loop 提交修订后的增量，Runtime 构造 goal-2
           → 新 goal 进入目标核验上下文，再核验
           → 仍有问题则继续上述修复循环
  无问题：保留“目标核验无问题”，绑定实际通过的 goal
本轮目标通过，交回 agent loop 执行与交付
第 2 轮用户输入 → 本轮目标维护结果 → 核验 → 修订／通过
…
```

本时间线只表示目标核验职责的接续，不要求核验器接收中间所有业务工具调用。第 2 轮用户输入由正常会话链交接；主循环仍须满足本轮执行、结果核验与交付条件，目标核验通过不代表用户任务已经完成。

### 2.1 强制修复至无问题

目标核验发现问题后，Runtime 将真实反馈交回原 agent loop。主循环基于当前版本重新提交受影响的条目。核验器对新候选重新判断。影响执行且无法从原话确定时，主循环提交澄清问题。

持续修复以真实通过为正常退出条件；不能忽略反馈、降低判据或把未决目标视为无问题后推进。既有预算、依赖或终止条件导致无法继续时，明确停止并保留未决问题，不宣称核验通过或正常进入下一用户轮，也不通过无界重试伪造收敛。

### 2.2 保留判决与实际修订

失败判决、被拒目标及后续实际修订都按原时间顺序保留，不能只发送最新 goal 或最新判决。“目标核验无问题”来自真实通过回执，仍可定位目标、版本与原判决；没有核验、回执缺失或尚未确定都不写成通过。以后修复通过时追加新判决，不改写旧失败记录，也不让已解决的旧反馈继续充当当前阻塞。

目标修订结果在生成之后才能进入下一次实际核验请求；当前请求不包含未来判决。具体角色与包装由正式请求构造器按服务方协议物化，不能把待验目标当成用户指令，或伪造 agent loop 的工具消息作为核验器自身的交互。

## 3. 历史范围与压缩

核验历史按同一可见分支的用户轮次和轮内目标提交顺序接续。仅滚动加入本职责所需的用户原话、目标维护结果、目标判决、问题反馈与实际 goal 修订；不拼接结果核验历史或主循环全部工具轨迹。历史指代确需其他材料时，按实际判断需要提供来源，不因此继承另一职责的全量历史。

目标核验历史使用自己的既有压缩检查点，不混用主循环或结果核验摘要。压缩保留用户原话、当前完整待验 goal、当前未决反馈及必要修订关系；旧过程的合法摘要须能区分原目标、失败、实际修订、通过与仍未解决，并可恢复原件。历史筛选和摘要继续消费原 Journal 事实，不新增独立可写的核验历史。


核验标准按条列出，退回时逐条显示判据、结论和原反馈。待验目标与原始用户要求逐字保留。判决、稿件和引用身份继续由 typed 回执绑定，模型按原输出 Schema 提交判决。

## 5. 实现差异与验证边界

当前核验 Context 按 `goal` 职责恢复目标提交及判决，保留各轮用户原话。每轮原话独立为 user 消息，候选快照作为待验数据。已发生判决按原顺序恢复。通过投影显示“目标核验无问题”、原判决编号及快照摘要。失败保留具体反馈。空补丁是本轮沿用提议，同样服从核验与写入规则。

本次固定验收已覆盖直接通过、一次退回后的实际修订与复验、通过判决绑定和多用户轮接续。独占修改工具的门禁、连续多次修复及自然压缩未在本次验收；后续改动仍按 GOAL-CTX-1 至 GOAL-CTX-6 核对真实轨迹，不把未触发路径记通过。实际样本、费用与边界见[固化方案](../optimization/completed/verification-context-goal-binding.md#决定性证据与边界)，原 task2 成绩保持。
