# 上下文管理

当前工程用历史压缩缩短旧过程，用裁剪减少无关与重复内容，用卸载移出可恢复的正文，再按需加载当前任务需要的细节。会话 Journal 保存完整交互，文件资源保存外置正文。每次模型调用使用面向当前任务的输入视图。

各模型任务的输入顺序、契约和验证状态见对应正文。

## 1. 历史压缩

**主循环。** 完整请求先计量输入，从同一任务、同一模型和请求参数最近一次成功回包锚定服务方输入 tokens，按新旧请求的估算差值调整。无匹配回包时使用完整请求估算。达到窗口 80% 或扣除输出、协议和压缩预留后的输入上限两者中的较小值，先尝试裁剪旧工具回执。重测仍达压且存在可安全压缩的旧交互前缀时，调用模型生成工作摘要。每次主决策前最多尝试两次摘要。用户原话、当前有效目标、待验结果、未决反馈和近期交互继续保留，工具调用与结果保持配对。[主循环的历史与压缩边界](agent-loop.md#3-角色历史与压缩边界)

**达压裁剪旧回执。** 每次主决策最多尝试一次新的裁剪，扫描当前任务可见的已结算工具回执，包括 Bash、历史目标快照和文件结果。保护最近两次已结算主决策、拒绝与修复反馈、未结算结果及承载当前工作计划的回执。正文超过 8,192 个 Unicode 码点时保留头部 4,096 和尾部 1,024，并标出省略量。调用 ID、消息顺序和已发布的文件定位仍随原回执发送。完整请求估算严格变小后，Journal 记录生效边界，后续请求按当前可见性重建短版。原始事实继续留在 Journal，读取路径沿既有文件契约。[实现与验收规格](../optimization/to_verify/analysis-goal-maintenance.md#达压后先裁剪历史工具回执)

主循环和工作摘要的出站硬检查都按序列化 UTF-8 JSON 字节数除以四估算输入，继续检查输出和协议预留。自动压缩取完整请求估算与「前次实际输入加估算增量」中的较大值。默认压缩预留为 65,536 tokens，小窗口下至多占扣除输出和协议预留后空间的五分之一。已冻结待消费的请求继续沿原调用恢复，避免为恢复旧动作另做摘要。计量不进入模型消息、System Prompt 或工具 Schema。目标及动作核验沿用各自的估算和输出契约。

工作摘要概括旧目标变化、执行结果、修复和未决事项。Runtime 先保存原件，再用候选摘要重建完整请求。来源一致、摘要通过校验且重建后的估算输入 token 严格下降，才激活检查点。候选校验失败时保留原检查点并报告失败。没有安全前缀时，硬容量内可以继续，超限则停止。摘要调用计入任务预算。

Skill 成功回执进入工作摘要时复用模型原先收到的回执格式和调用 ID。已生效的裁剪继续用于摘要输入。原始快照保存完整正文及资源引用。被覆盖的回执退出主请求，当前可用的 Skill 目录仍由 Step Context 提供，需要原文时可按名重读。[Skill 的压缩与重读](skill.md#4-历史裁剪摘要与重读)

**目标定义核验。** 核验输入超过专用预算时，调用模型概括已交付答案且最后一次目标判决通过的旧轮次，使用独立的摘要检查点。用户原话、当前待验目标和未决反馈仍按原文提供。没有可压缩的旧轮次时报告容量问题。[目标定义核验的历史与压缩](goal-verifier.md#3-历史范围与压缩)

**目标遵循核验。** 执行前和回答交付前共享历史覆盖边界。请求预计达到模型窗口时，Runtime 按固定规则缩短早期目标正文，省去旧代码和执行输出预览，保留最近两个已结束轮次、当前轮次和本批直接依赖的历史结果。[目标遵循核验的历史与压缩](goal-compliance-verifier.md#3-历史范围与压缩)

## 2. 裁剪

**使用场景：** 不同模型职责需要的信息不同，或同一内容以多种形式重复出现。即使请求尚未接近容量上限，也有必要减少这些输入。

**介入时机：** 每次按职责构造请求、投影历史和准备工具结果时执行，无需等到整体窗口不足。

**处理行为。** 主循环保留实际行动过程。目标定义核验接续目标提交、判决和修订。目标遵循核验按时间接续生效目标、动作、执行结果、回答、判决和修订。工具结果随配对的原生调用历史提供，重复的搜索来源描述只展示一份。

已通过的任务核验在主循环中保留简洁结论、判决身份和对象对应关系，完整报告留存，失败反馈保持完整。裁剪只改变本次展示，原始事实和保留交互的时间顺序仍以会话记录为准。

## 3. 卸载

上下文卸载指正文退出模型请求，原始记录继续保留。单次工具结果过大时按[工具输出超限的处理](tool.md)外置原件。历史摘要激活后，卸载其覆盖的旧交互。

被摘要覆盖的旧调用、配对结果和旧回答正文退出后续请求。Runtime 重建输入时沿用检查点覆盖范围，继续保留近期交互、必要反馈和当前修复过程。主循环根据当前可用的读搜工具给出原件定位。外置结果指向文件路径，符合条件的内联回执指向历史快照中的位置。[压缩后如何定位工具原件](agent-loop.md#31-压缩后如何定位工具原件)

## 4. 按需加载

**使用场景：** 模型需要查证某个细节、取得可引用原文，或者摘要与现有预览不足以支持下一步判断。

**介入时机：** 当前决策确实需要具体材料时，由模型使用已有读搜能力取得；不因原件存在就提前加载全文。

**处理行为：** 把本次实际取得的片段及来源追加到新交互。工具原件的定位与分段读取见[续读与跨轮保留](tool.md#3-续读与跨轮保留)。

搜索零命中、预览或读取了局部窗口，都不代表全文已经读完。后续需要更多材料时继续加载相应片段；判断是否执行成功、核验通过或任务完成，仍消费原始事实，摘要及历史快照本身不取得业务证据资格。

请求缩减、用户结果和任务总成本分别以对应验证证据为准。完整交互摘要与核验记录精简的验证范围见[结果卸载与完整交互压缩](../optimization/to_verify/analysis-goal-maintenance.md#920-结果卸载与完整交互压缩)和[核验上下文固化记录](../optimization/completed/verification-context-goal-binding.md#决定性证据与边界)。
