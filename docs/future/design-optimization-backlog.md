# 设计优化队列

> **本文件只保存尚未解决且有明确退出条件的设计问题。** A0 只允许执行基线并补充证据；A1 才允许定位局部根因和执行单变量消融；A2 评审通过后才允许修改生产设计。已经解决、基线未失败或根因不符的问题必须退出队列，详细历史由评测文档保存。

## 1. 当前判断

**当前没有进入 A1 或 A2 的计划能力优化。** 2026-08-20 已按预声明契约完成 `deepseek-v4-flash + json_object` 的 O0 证据刷新；三组基线均未同时达到“至少 `3/15` 个可归因计划语义失败且覆盖至少两类场景”的准入门槛，因此本轮在 A0 退出，不修改生产 Plan 机制。现有证据已经证明三项局部收益：用户可以审阅和纠正工作清单，智能体可以先执行规划安全读取再形成有依据的计划，运行系统可以在冻结服务提供方场景中恢复成功事实并避免重复读取。它们不共同证明计划提高了普遍答案正确率，也不证明成本或延迟已经下降。

最近三组重复基线暴露了值得继续观察的风险，但尚未达到生产改动门槛：

| 风险 | 当前结果 | 当前结论 |
| --- | --- | --- |
| 证据齐全后无法从工作清单迁移到最终答案 | `PLAN-STAB-001` 为 `14/15 delivered`，另有一次官方证据不足，没有计划语义失败 | 基线未复现计划缺口；退出本轮优化 |
| 用户撤回旧结果并新增结果后残留陈旧工作项 | `PLAN-REPLAN-001` 总体为 `10/15 delivered`；撤回并新增结果为 `1/5 delivered`，出现四次可归因计划修订失败 | 失败只覆盖一个场景；未达到跨场景门槛，不修改计划修订机制 |
| 缺少证据时仍错误宣布成功 | `PLAN-COMP-001` 为 `14/15 honest_boundary`、`1/15 erroneous_success` | 错误成功只有一次且只覆盖一种场景；不修改验证或完成判断 |

完整样本、配置身份和归档坐标由[当前端到端用例盘点](../evals/02-current-case-inventory.md)保存。本文件只定义后续优化顺序和准入条件，不复制排查流水。

## 2. 计划能力优化方案

状态：A0 已退出。2026-08-20 的 O0 证据刷新未达到 A1 门槛；只有出现新的用户契约、独立线上问题或模型、服务提供方及交互契约变化时，才能预声明新的 O0 样本组。

### 2.1 优化目标

计划能力只负责当前对话中的短期结果协调。优化目标按优先级排列如下：

1. 用户改变目标后，当前待完成工作项准确反映最新要求，已经完成且已经发生的事实不被改写；
2. 证据足够时，智能体能够从继续执行稳定迁移到最终交付，不重复提交相同计划；
3. 证据不足时，智能体返回明确限制或继续取得证据，不把工具成功、工作项状态或验证器调用冒充用户结果；
4. 在前三项成立后，再测量计划是否减少重复调用、模型轮次、令牌和延迟。

不在目标范围内：前台依赖图、通用任务调度器、第二套待办事实、计划文件、后台队列、专用规划模型和并发版本控制。需要跨请求和跨进程长期运行的依赖规划继续由后台调查项目拥有。

### 2.2 分阶段执行

| 阶段 | 允许动作 | 进入条件 | 退出条件 |
| --- | --- | --- | --- |
| O0：证据刷新 | 执行新的预声明基线，保存用户结果、关键反事实和成本分布 | 出现新的用户契约、模型或服务提供方配置版本，或者独立线上问题 | 基线未失败则退出；达到 A1 门槛则进入 O1 |
| O1：局部归因 | 按失败阶段区分计划修订、上下文读取、服务提供方、验证和完成判断 | 同一配置样本组至少 `3/15` 个可归因语义失败，且覆盖至少两类场景 | 根因不属于计划则转交对应责任主体；根因成立则定义单变量消融 |
| O2：机制消融 | 在独立可还原代码状态中只关闭一个生产消费点 | 已定位唯一责任主体和可机械复核的消融变量 | 消融不能解释用户结果差异则撤回候选；能够解释则进入 O3 |
| O3：最小目标路径 | 实现最小纵向切片，同步删除被替代路径 | 消融成立，目标端到端测试、指标门槛和净复杂度预算已预先定义 | 未达到目标门槛则破坏式撤回；达到门槛后进入发布回归 |

### 2.3 达到 A1 后的根因分流

以下内容只是根因分流，不是已准入的生产方案：

| 失败现象 | 决策或事实责任主体 | 可评估的最小候选 | 明确禁止 |
| --- | --- | --- | --- |
| 连续提交相同工作清单，证据齐全仍不交付 | 模型负责语义迁移；交互协议负责返回可修复反馈 | 只评估当前计划生命周期下的结构化反馈或输出投影是否阻碍最终答案 | 自动把工具成功改成工作项完成；增加预算掩盖循环 |
| 用户撤回并新增结果后仍保留陈旧待完成项 | 模型负责开放语义修订；运行系统只保护已完成项和已发生事实 | 评估“最新用户目标—当前待完成项—修订后待完成项”的语义验证 | 字符串包含判断、同义词表、确定性代码重写用户目标 |
| 缺少关键证据却宣布成功 | 领域验证器判断语义满足；完成门禁检查结果契约是否齐全 | 只在对应业务结果契约中补充真实缺失的验证或完成证据 | 把计划状态、工具成功或追踪记录当成完成证明 |
| 结果已取得但恢复后无法读取 | 资源存储、上下文物化或服务提供方拥有执行事实 | 转交大型结果重读、资源引用或服务健康责任主体 | 包装成计划字段或新增第二份结果副本 |

### 2.4 指标与门槛

每个新配置样本组继续使用来源比较、产品约束分析和事故分析三类自然请求，每类独立五次。除最终用户结果外，至少记录：

- 陈旧待完成工作项数量；
- 相同计划被拒绝的次数；
- 错误成功、诚实限制和结果不完整的数量；
- 恢复阶段的重复原始读取和重复副作用；
- 模型轮次、工具调用、总令牌、端到端延迟和服务提供方失败；
- 计划是否可见、可修订以及最终答案是否覆盖最新用户要求。

通用 A1 门槛仍为同一预声明样本组中至少 `3/15` 个可归因语义失败，并覆盖至少两类场景。进入 O3 后，目标门槛必须按具体缺口另行预声明，不能默认使用“状态为已完成”或“验证器通过”代替用户结果。

### 2.5 复杂度预算

A0 的生产复杂度预算固定为零：不得新增模型、字段、表、端口契约、适配器、规划器、固定流程、配置或生产开关。只有进入 A1 并定位责任主体后才能提出单变量候选；只有进入 A2 后才能确定净复杂度预算和同步删除项。

优先顺序固定为：先删除无效门禁或修复现有反馈契约，再评估现有模型投影和上下文消费点，最后才考虑新增结构。任何候选若使交付率下降、引入新的服务提供方失败，或不能解释同输入消融差异，立即撤回，不保留兼容路径。

### 2.6 本轮 O0 证据刷新声明

声明日期：2026-08-20。触发原因是当前正式结构化模型配置已经从历史样本组的 `mimo-v2.5` 变为 `deepseek-v4-flash`，服务提供方地址、模型版本和代码树身份也已经变化；新结果必须形成独立配置样本组，不得与历史 Mimo 样本合并。

本轮固定执行以下三组基线，每组使用三个既有自然场景，每个场景独立重复五次：

| 用例 | 本轮结果契约 | 计划语义失败分类 |
| --- | --- | --- |
| `PLAN-STAB-001` | 证据齐全后完成当前工作清单并交付覆盖最新要求的最终答案 | 证据齐全且工具无异常，但重复提交相同计划、仍保留待完成项或不能迁移到最终答案 |
| `PLAN-REPLAN-001` | 用户改变要求后修订同一计划，保留已发生事实，删除陈旧待完成义务 | 首轮存在可审阅的待完成计划，但修订后残留已撤回结果、缺少新增义务或陷入重复修订 |
| `PLAN-COMP-001` | 缺少端到端证据时明确边界，不把协议返回、结构合法或运行时成功声明为用户结果完成 | 工具无异常且官方证据已取得，但最终答案给出无保留的错误成功声明 |

配置身份固定为当前 `.env` 解析得到的 `deepseek-v4-flash`、`json_object`、Tavily、当前交互策略与各用例既定预算。每次归档继续保存提交、工作树差异摘要、输入摘要、配置样本组、评测器版本、追踪记录和校验和。服务提供方失败、请求超时、官方证据不足、测试脚手架失败和结果不完整分别分类，不计入计划语义失败。

本轮 A1 准入门槛仍为同一用例的 `15` 个样本中至少 `3` 个可归因计划语义失败，并且覆盖至少两类场景。任一用例未达到门槛即停在 A0；达到门槛也只能进入 O1 局部归因，不能直接修改生产设计。不得在样本组完成后追加运行以凑足门槛。

### 2.7 本轮 O0 执行结果与退出决定

三组有效样本均通过归档校验和检查，并分别保持单一配置样本组和单一代码树差异摘要。`PLAN-STAB-001` 在主工作树的稳定代码身份上执行；`PLAN-REPLAN-001` 与 `PLAN-COMP-001` 在独立、可还原的工作树快照 `personalAgent-e2e-snapshot-20260820` 上执行。执行期间代码身份发生变化的早期归档只保留为无效诊断，不参与结果合并或门槛判断。

| 用例 | 有效结果 | 场景分布与归因 | 模型调用 / 模型轮次 / 工具调用 | 总令牌 | 调用延迟 P95 |
| --- | --- | --- | ---: | ---: | ---: |
| `PLAN-STAB-001` | `14/15 delivered`、`1/15 insufficient_official_evidence` | 来源比较 `4/5`，产品变更 `5/5`，事故分析 `5/5`；计划语义失败为零 | `105 / 75 / 39` | `999,389` | `99.95` 秒 |
| `PLAN-REPLAN-001` | `10/15 delivered`、`4/15 stale_obligation_failure`、`1/15 semantic_pending_plan_missing` | 四次陈旧义务失败均在“撤回并新增结果”；另一次缺失计划伴随大型结果重读与预算耗尽，归入结果物化和预算责任主体 | `124 / 95 / 75` | `1,205,254` | `100.29` 秒 |

退出决定：`PLAN-STAB-001` 没有复现计划语义失败；`PLAN-REPLAN-001` 虽有四次可归因计划修订失败，但只覆盖一个场景；`PLAN-COMP-001` 只有一次错误成功且只覆盖一个场景。三组均未达到 A1 门槛，本轮不进入 O1、O2 或 O3，不新增 Prompt、Schema、Admission、预算、模型路由、验证门禁或生产开关。若未来出现新的触发条件，必须重新预声明独立样本组，不能向本轮追加样本。

## 3. 共同评测契约

1. 基线从 `POST /api/conversation/turn` 进入，经过生产组合根、真实结构化模型、Postgres、真实网页搜索，以及需要验证恢复时的真实 Web 进程重启。用户输入不得指定计划、工具、智能体、内部标识、步骤顺序或完成状态。
2. 服务提供方、基础地址、模型、结构化输出传输、额外请求体、预算、提示词与策略版本、评测器和用户输入摘要全部进入对照身份。服务提供方失败单独分类，不计入计划语义失败。
3. 基线、消融和目标路径使用相同输入、身份、初始事实、配置样本组和评测器。消融只能存在于独立可还原的提交、代码树或补丁中，并且只关闭一个已经确认的生产消费点。
4. 每份归档保存用户输入、身份、初始事实、模型与服务提供方版本、追踪记录、报告、用户结果、关键反事实、模型轮次、工具调用、令牌、延迟、重复读取或副作用计数、代码状态和校验和。
5. 不得在样本组结束后继续追加运行直到碰到门槛；环境或配置变化必须创建新的对照身份。

## 4. 新条目模板

```markdown
## <编号>：<用户错误或可量化工程约束>
状态：A0 | A1 | A2

### 同输入基线与关键反事实
### 根因与决策或事实责任主体
### 参考实现及可复核坐标
### 单变量消融和最小生产改动
### 目标端到端测试、复杂度预算与退出条件
```

新增条目必须先说明用户结果、关键反事实和最简单正式入口。外部实现只回答机制如何工作，不构成需求；产品变更没有同输入失败基线，纯重构没有工程约束基线和行为保持端到端测试时，条目只能停在 A0。
