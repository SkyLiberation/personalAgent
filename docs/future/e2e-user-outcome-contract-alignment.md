# E2E 用户结果契约对齐方案

> **本设计只处理评测资产与证据表达，不改变生产行为。** 准入状态由[设计优化队列](design-optimization-backlog.md)中的 `E2E-USER-OUTCOME-CONTRACT-001` 唯一拥有；本文不维护第二份状态。当前用例与实际断言以[当前 E2E 用例盘点](../evals/02-current-case-inventory.md)和 [`evidence_catalog.py`](../../evals/e2e_quality/evidence_catalog.py)为准。

## 1. 当前问题是结果契约与断言没有完全对齐

**两条 Product E2E 尚未自动验收其自然目标中的全部用户结果，两条 Application E2E 则只能证明流水线事实。** 如果文档或发布判断忽略这个差异，系统可能在内容不满足用户目标时得到假通过，也可能把内部执行事实误述为完整产品能力。

| 用例 | 当前声明的目标 | 当前可执行断言 | 需要对齐的事实 |
| --- | --- | --- | --- |
| `ASK-001A` | 只根据保存资料回答、逐项给出原文并呈现冲突 | 两个随机日期、冲突词、来源片段存在、Web 零调用、作用域隔离和零写入 | 用户最终看到的回答是否真正给出两项原文依据 |
| `ASK-001B` | 结合个人资料与官方文档解释智能体如何使用工具 | 随机项目代号、至少一个 OpenAI 官方 URL、作用域隔离和零写入 | 技术解释是否回答工具使用机制，而不是只附带一个官方 URL |
| `E05` | 单次固定研究入口生成结果 | 运行终态、非空 `digest` 和条目来源 URL | 当前只拥有研究流水线证据，不拥有摘要覆盖与正确性结论 |
| `E13` | 周期研究完成订阅、运行、投递和反馈 | 订阅绑定、非空 `digest`、`sent` 记录与反馈绑定 | 当前只拥有投递执行事实，不拥有用户实际收到正确内容的结论 |

## 2. 优化目标分成补验收与守边界

**Product E2E 需要补齐用户结果验收，Application E2E 只需要保持准确证据分类。** 本设计不把四条用例统一升级为语义评测，也不为支持性用例复制新的 live 旅程。

### 2.1 `ASK-001A/B` 补齐用户结果

结果契约必须继续使用现有自然请求、随机事实、正式入口和关键反事实。评测器只增加当前未被判断的用户可观察结果：

- `ASK-001A` 判断回答是否把两条相互冲突的原文依据分别呈现给用户；
- `ASK-001B` 判断回答是否基于官方来源解释工具定义或选择、调用和结果使用中的必要语义，而不是只检查 URL 域名。

评测器不得要求固定标题、固定句式、固定工具次数、固定 `Plan`、固定查询或逐字复述整段模板。内部 `EvidenceSpan`、工具结果和 URL 只提供来源证据，不能替代最终回答验收。

### 2.2 `E05/E13` 保持支持性证据定位

`E05` 继续验收单次研究运行、`digest` 与来源结构；`E13` 继续验收订阅、工作进程、投递记录和反馈链。两条用例不增加内容语义评测，也不进入 Product E2E 分母。

如果未来需要声明“研究摘要正确回答主题”或“用户实际收到正确内容”，必须先提供独立产品目标、失败 baseline 和真实渠道结果契约。现有 `E05/E13` 不能因字段存在而直接升级。

## 3. 设计决策链先证明评测器能够解决缺口

**本项先验证评测器能区分正确结果与关键错误，再修改 live E2E。** 候选只在现有密封结果或独立冻结输出上离线执行，不调用真实模型、Web Search 或外部连接器。

| 决策步骤 | 已证明依据与必要性 | 为什么能够解决当前问题 | 证伪与撤回条件 |
| --- | --- | --- | --- |
| 为 `ASK-001A` 增加最终回答结果检查 | 当前断言能看到日期、冲突词和来源片段，却没有证明用户看到两项原文依据 | 检查最终回答中的两项依据直接覆盖缺失的用户结果，不要求内部检索路径 | 无法接受表达变化正控制，或只能靠固定措辞时撤回 |
| 为 `ASK-001B` 增加工具机制语义检查 | 当前断言只要求项目代号和一个官方 URL，不能证明回答解释了工具使用 | 检查来源支持的工具定义、调用与结果使用语义，直接补齐自然请求中的结果 | 无法拒绝只有 URL 的负控制，或来源与解释断裂仍通过时撤回 |
| 保持 `E05/E13` 为支持性证据 | 两条用例只执行并断言流水线、投递和反馈事实 | 收缩声明边界可以消除证据外推，不需要改动生产行为或增加语义评测 | 若要声明内容正确，必须另建产品 baseline；不得在本项升级分类 |

三个步骤分别处理两个缺失的产品断言和一个证据边界错误，不能合并成通用评测工作流。任一步需要修改生产 Prompt 或新增 live 旅程才能通过时，说明评测候选没有直接解决当前缺口，必须停止。

每条 Product E2E 至少准备以下控制：

| 控制样本 | `ASK-001A` | `ASK-001B` |
| --- | --- | --- |
| 正控制 | 两条原文分别出现并明确冲突 | 项目代号正确，官方来源支撑工具定义、调用与结果使用说明 |
| 缺结果负控制 | 只给日期结论，不呈现原文 | 只有项目代号和官方 URL，没有工具机制解释 |
| 断裂证据负控制 | 引用另一段无关原文 | 解释存在，但官方 URL 与解释主题无关 |
| 表达变化正控制 | 列表、表格或自然段表达相同事实 | 使用同义中文表达相同工具机制 |

候选评测器必须接受全部正控制并拒绝全部负控制。字符串共现若不能满足表达变化正控制，就不得进入 live E2E；模型评测器若不能固定输入、版本、输出 Schema 和失败语义，也不得进入门禁。

## 4. 最小实现只修改评测资产

**准入候选只能修改现有结果契约、case-specific grader 或断言，以及对应评测文档。** 不新增生产模型、提示词、工具、状态、数据库表、运行分支或测试旁路。

允许的最小变化包括：

- 为 `ASK-001A/B` 增加可离线回放的 typed 结果检查；
- 把正负控制固定为评测数据，并保留版本与校验和；
- 让 `UserOutcomeContract`、可执行断言和文档使用同一结果描述；
- 保持 `E05/E13` 的 Application E2E 分类和现有执行节点不变。

禁止创建通用评测工作流、第二份用例目录、生产开关或新的完整发布命令。只有两个独立在用的语义检查形成稳定共同契约时，才评审是否抽取共享评测器；否则保留 case-specific 实现。

## 5. 验收与退出条件

**本项通过离线控制、collection、评测单元测试和文档一致性验收，不执行昂贵完整矩阵。** evaluator-only 变更不能制造新的产品证据。

验收必须同时满足：

1. `ASK-001A/B` 的正控制全部通过，缺结果与断裂证据负控制全部失败；
2. 两条 Product E2E 的 `UserOutcomeContract`、可执行断言和面试说明使用同一结果语义；
3. `E05/E13` 保持 Application E2E 分类，文档只陈述流水线与执行事实；
4. release 与 diagnostic collection 数量、节点唯一性和横切套件引用仍由 canonical catalog 派生；
5. 没有新增 live E2E、生产消费者、第二套目录或重复发布命令；
6. Ruff、评测单元测试、文档链接和规范检查通过。

如果正负控制无法稳定区分、只能依赖固定措辞，或候选需要修改生产 Prompt 才能通过，则撤回评测器候选并保持当前结论边界。验收完成后，把当前评测契约写回评测权威文档，并从设计优化队列删除本项及本文。
