# 变更证据与设计准入细则（EVD）

> 本细则适用于产品行为变更、机制收益、缺陷修复、内部重构、复杂度准入和外部机制选择。变更分类与最低证据由根 [AGENTS.md 第 4 节](../../AGENTS.md#4-变更准入速查)定义；本文规定证据如何取得、如何归因，以及设计如何准入。

## 1. 用户结果与工程约束的可执行基线

先证明问题，再提出候选。产品变更必须从目标用户、真实可见信息、自然表达、缺失结果和关键反事实出发，选择当前最简单正式入口；禁止先设计机制，再编造恰好需要它的场景。

- 新设计按根规范取得失败 baseline、单变量消融、真实 target E2E 和预设指标。当前路径已满足目标、缺口未复现或失败只来自环境与测试时，停止该产品变更。
- 缺陷修复必须定位变更前的权威契约或确定性不变量。可还原历史失败可以作为 baseline；责任边界之前有模型或服务方方差时，用真实失败数据的 Offline Eval 回放或 E2E 检查点固定前置状态、检验同一确定性责任主体，再由真实 target 验收用户结果。两个独立随机轨迹不能替代这一反事实。
- 纯内部重构必须由可重复命令证明工程约束，例如生产不可达、职责混装、依赖环、变更耦合或复杂度热点。文件行数和主观“不优雅”不能单独准入；重构前后以同一正式入口 E2E 证明行为保持。
- 纯文档修正核对代码、配置、测试、执行归档或外部规范坐标，按[文档模块规范](../AGENTS.md)验收，不制造产品失败。

真实 target 的原始用户结果与局部机制检查点按[根规范第 2.1 节](../../AGENTS.md#21-证据先于设计)分开判断。局部机制只有真实到达生产消费点、预声明检查点成立，且追踪记录排除候选引入的回归时，才可单独验收。候选未进入正式路径、自身检查点失败、引入用户结果或安全回归，或无法排除候选的因果责任时，必须撤回相应候选部分。

失败归因必须记录“原始结果、发生位置、因果责任、被否定的主张、仍成立的问题与机制”。检查点之后且因果独立的失败登记为新的产品阻塞；不得追溯否定已成立的局部机制，也不得覆盖原始 E2E 失败。局部验收后的文档迁移遵循[Future 状态收敛](../future/README.md#状态变化必须在同一变更收敛)及[按问题固化规则](../optimization/README.md#已解决问题的固化规则)。已成立的边界能力单独固化，不能把尚未通过的整体产品验收扩张成该能力的反例；固化也不能提升原证据等级或跳过生产接入门禁。

候选失败后，必须审视能否改变责任主体、输入事实、确定性边界或恢复协议，并记录正交方向及重新准入证据；没有独立方向时才停止该设计分支。这不授权保留失败代码、降低门槛、丢弃失败样本、反复重跑挑选成功结果，或叠加同义状态与 Prompt 补丁。

## 2. 产品 E2E 的最低资格

E2E 的入口、真实模型、决策链和用户结果资格统一遵守[根规范第 2.1 节](../../AGENTS.md#21-证据先于设计)。绕过目标智能体、直调 Application Use Case 或冻结模型决策的测试必须按实际边界重新分类。

证据设计还必须满足：

1. baseline、消融与 target 使用同一正式入口、用户输入、身份、初始事实和评测契约；消融只移除目标机制的生产消费点。
2. 使用生产领域模型、状态迁移、编排与持久化协议。真实 target 经过生产 Composition Root、真实持久化，以及用户结果依赖的真实模型、服务提供方与隔离沙箱。
3. 用明确命令在本地或 CI 重复执行；通过追踪记录、事件、回执或报告定位失败阶段。
4. 内部路径只作为执行后观察证据或独立机制检查。除非属于公开产品契约，不得将预期对象、工具或步骤写入用户输入或 E2E 通过条件。
5. 原始输入、运行与比较身份、代码状态、报告和校验和按[比较身份与归档](../../evals/AGENTS.md#5-比较身份与归档)分别封存。可还原代码身份必须包含 commit、tree 或 patch，不能只有不可复核的版本标签。

Test Double 的适用边界由[测试职责与覆盖](quality-security.md#1-测试职责与覆盖)统一规定。可重复消融或故障注入不能因此自动取得 E2E 资格；代码可达性、竞品资料和未执行的测试也不能替代运行证据。

## 3. 删除优先与兼容边界

生产代码只保留获准的目标路径；迁移和兼容例外必须遵守[迁移与兼容边界](migration-release.md#1-迁移与兼容边界)。

baseline 只保留不可变证据；消融只存在于独立 commit、tree、patch 或 worktree。禁止为复现实验保留生产 flag、alias、双轨测试入口、双写或永久 deprecated 字段，也不得以回滚或未来上线为由保留没有消费者的旧链路。

## 4. 禁止无证据优化、过度设计与能力空转

新增复杂度必须直接解决已证明的产品缺口或工程约束。除根规范的最小纵向切片门禁外，出现以下情况也不得准入：

- 拆分出的 Model、状态、digest、表或层没有独立责任主体、信任边界、生命周期、事务边界或保留策略。
- 把固定流程包装成通用 Planner、Task 或 Event 系统，或仅为对齐外部框架而复制其结构。
- 只证明对象、字段、Trace 或失败关闭分支存在，没有按预设门槛、样本量或重复次数证明用户结果、错误副作用、恢复、成本或延迟的收益。
- 产品变更超出已证明用户结果所需的最小复杂度，或纯重构没有降低已测工程约束。

架构结构的可达性与消费者检查见[生产可达性](architecture-ownership.md#7-生产可达性)，不可合并职责须在下一节逐项说明。

## 5. 复杂度说明（Complexity Justification）

新增架构机制前必须提交 `Complexity Justification`，至少说明：

1. 变更类别、对应基线、目标用户结果或工程约束，以及适用的消融、责任边界反事实和指标门槛。
2. 所需能力盘点：已有、需扩展、缺失及真实环境交付状态；标明正式入口到用户结果的路径与生产消费者。
3. 每个新增 Model、状态、digest、表或流程不可合并的责任主体、生命周期或边界。
4. 替代方案、净复杂度预算、同步删除项、实验代码隔离方式、文档迁移与退出条件。

一个事实、状态、digest、表或流程足够时不得拆分。只有一个实现，且没有外部边界、测试替换需求或近期第二变化来源时，不得创建 Interface、Factory 或 Registry。Command、Event、Receipt 与投影按[各自消费者](agentic-execution.md#3-toolcommanddigest-与-receipt)选择，禁止成套创建。

已存在但不能补齐上述证据的机制，必须删除、合并，或降为非权威可选投影。

## 6. 外部参考的证据分级

机制选型与遇阻后的外部复核必须按机制域比较已发布实现。每项产品设计、能力优化或架构机制在提出候选前，至少核对两个相互独立的 A 级实现；不足时记录检索范围、缺口与不确定性，停止进入实现。

| 等级 | 可采信程度 | 来源与使用边界 |
| --- | --- | --- |
| A | 可直接核对机制 | 已发布实现的可读源码、协议规范、官方产品文档；必须能定位到文件、常量或接口契约 |
| B | 需交叉验证 | 官方博客、release note、官方演讲；须与 A 级或第二个独立来源核对 |
| C | 仅辅助提出候选 | 论文、教程、示例、宣传、个人博客、未合并 PR 或 issue 描述；不能冒充已发布实践 |

引用必须标注等级、目标提交或版本、规范日期及可复核文件、常量和契约坐标；不得只读转述、PR 描述或文章摘要就断言业界做法。

每次比较形成 `External Mechanism Comparison`，记录：

- 生产构造点、消费者、事实归属与信任边界；
- 写入、合并、删除、取消、生命周期及失效语义；
- 权限、恢复、失败处理和已付出的复杂度；
- 本工程的对应失败阶段、采纳与拒绝项，以及拒绝理由。

不得因名称相同推定语义等价，也不得照搬外部对象数量、层次或拓扑。先把机制映射到本工程基线，再优先复用现有契约与写入口；无法映射的部分不得采用。新设计选择可单变量消融的最小机制，缺陷修复选择可在最早责任边界确定性证伪的最小修正。

检索起点由[优秀智能体能力组件参考](../agentRef/README.md)维护。协议与基础设施还应核对以下来源：

| 机制域 | 检索起点 |
| --- | --- |
| 工具协议与权限 | Model Context Protocol 规范；本工程边界为 `src/personal_agent/capabilities/contracts/execution.py` |
| 编排、checkpoint 与持久执行 | 本工程锁定版本的 LangGraph/checkpointer 源码；Temporal 或 Restate 的 determinism、replay、重试与补偿规范 |
| 知识生命周期与时间性失效 | graphiti-core 已发布源码中的 `valid_at`、`invalid_at` 与 provenance；本工程适配为 `src/personal_agent/memory/graphiti/llm_strategies.py` |
| 检索与证据组织 | 官方检索或 rerank 实现与评测协议；论文只按 C 级使用 |

这些坐标是检索起点，引用时必须重新核对目标版本。外部机制在别处成立，不能替代本工程准入与验收证据。

## 7. 强制开发与设计流程

每个设计步骤必须是一条可证伪的因果决定。只有“增加状态、调整 Prompt、扩大预算、增加重试”等动作而没有以下内容时，不得进入实现：

| 必填项 | 必须回答的问题 |
| --- | --- |
| 依据与必要性 | 消费哪条已执行失败事实？最早失败阶段是什么？不修改时哪个结果或约束无法满足？ |
| 责任主体 | 语义决策、确定性事实和唯一写入口分别属于谁？修改是否位于真正责任边界？ |
| 模型输入依据 | 涉及模型语义行为时，[CTX 输入审计](context-memory-retrieval.md#12-system-prompt-与-context-的设计及问题分析)发现了什么？候选改变哪些指令或 Context，保留哪些事实，怎样验证归因？不涉及模型行为时说明不适用。 |
| 最小因果路径 | 改动怎样消除失败，并到达下一个用户可观察边界？ |
| 排除项 | 哪些错误是后续连锁、环境问题或其他事项，为什么不在本步骤处理？ |
| 证伪方法 | 哪个 target、反事实或适用消融能够区分机制生效与偶然通过？ |
| 停止与演进条件 | 未达门槛时撤回哪些代码和文档？否定什么假设？哪些问题仍成立？下一方向怎样重新准入？ |

步骤必须按因果顺序推进。上一步未取得预声明证据时，后一步只能作为条件假设；同时涉及多个责任主体时应拆分验证，或证明它们属于不可分割的同一事务不变量。

执行流程如下：

1. 提取目标、范围外事项和变更类别，从[文档索引](../README.md)确认权威文档；执行相应基线或文档事实核对。
2. 依据成立后，完成事实与决策归属、架构分类、能力盘点和适用的外部机制比较；涉及模型语义行为时，完成上表的模型输入审计，再决定修改 Prompt、Context 或其他责任主体。
3. 定义 target、反事实、指标门槛、样本量、影响边界与复杂度预算。新设计另定义单变量消融；缺陷修复定义最早确定性责任边界的反事实。
4. 实现最小纵向切片，同步迁移调用方和权威文档、删除旧链路与冲突正文。
5. 新设计在独立代码状态执行消融；缺陷修复执行适用的责任边界反事实；产品变更均须在最终代码上执行真实 target。
6. 按[测试细则](quality-security.md)完成受影响验证，并按[完成检查表](migration-release.md#3-完成检查表)验收。
7. 分别封存证据，报告命令、结果、样本量与方差、净复杂度、文档变更和剩余风险。

E2E 阻塞时，上述正常验证流程转入[阻塞处理](quality-security.md#2-e2e-阻塞按目标阶段和单变量处理)，先审查用例，再定位并只修正一个责任主体。相同阻塞复现、补丁或 Plan 分支持续增长、责任主体跨层漂移或指标未改善时，停止局部修补，保留代码身份与未验证假设，重新执行第 6 节外部复核。权威设计文档只保留一个活动方案；候选取舍按第 1 节归因，不能全盘否定仍成立的证据。

## 8. 变更分析最小模板

变更说明必须覆盖以下字段；不适用项说明原因，不填造证据。

```markdown
## 目标、变更类型与范围外事项
## 基线、实际结果与最早责任边界
## System Prompt 与 Context 审计（涉及模型语义行为时）
## 设计决策链（逐项填写第 7 节必填项）
## target、反事实、适用消融、指标与样本量
## 架构分类、事实与决策归属、唯一写入口
## 外部机制比较与采纳理由
## 能力盘点、生产可达性与真实环境交付
## 复杂度增减、旧链路删除与退出条件
## 文档影响、验证命令、实际结果与未验证风险
```

遇阻时补充用例合理性、唯一修正变量与原阻塞用例回跑结果，不能只记录最后一条错误。

## 9. E2E 最小模板

E2E 描述必须让用户结果与内部路径证据分开；Test Double 需逐项说明适用边界。

```markdown
## E2E：<名称>
目标用户与公开契约：<真实可见信息和需求来源>
前置事实：<身份、初始事实和模型不可预知的数据>
用户操作：<正式入口与自然表达>
用户结果与禁止结果：<可观察交付及关键反事实>
比较证据：<baseline、适用消融或责任边界反事实、target>
生产路径与检查点：<装配、真实边界、消费者及执行后观察>
Test Double：<替代边界、Port 契约与证据限制；无则写无>
指标与命令：<预设门槛、样本量、重复次数和执行命令>
归档：<比较身份、代码身份、报告与校验和>
```
