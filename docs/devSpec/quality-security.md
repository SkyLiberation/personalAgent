# 测试、评估、观测与安全细则（QLT）

> 本细则适用于测试、评测、真实环境、追踪记录、安全与审计。准入证据设计见[变更证据与设计准入](change-evidence.md)；评测代码、比较身份和归档见[评测模块规范](../../evals/AGENTS.md)。

## 1. 测试职责与覆盖

**后续验证以真实 E2E 与 Offline Eval 为主，`tests/` 和单元测试按[根规范第 2.6 节](../../AGENTS.md#26-e2e-与-offline-eval-优先停用单元测试)停用。** 不新增、修改、修复、收集或运行这些测试，不因测试失效而补兼容代码，也不将其设为设计、开发或合并门禁。已有测试与历史结果只读保留，证据等级不追溯改写。

| 验证方式 | 责任与边界 |
| --- | --- |
| Real E2E | 目标用户经正式入口、生产链和真实模型取得可自动断言的结果；验收成功及必要的失败、拒绝、恢复和错误副作用 |
| Offline Eval | 回放真实 E2E 的完整阶段输入及真实中间产物，检验模型、检索、输入物化和局部机制；按已确定用例验收对应优化，依赖模型前置决策的目标按 EVD 连续执行；整例交付另按整例判据记录 |
| E2E 机制检查点 | 在同一真实执行证据中检查身份、权限、引用、状态迁移和恢复不变量；与整例用户结果分别计分 |
| 工程静态检查 | lint、类型、依赖、配置和文档等确定性检查；不启动单元测试，不作为产品效果证明 |

确定性逻辑无需为形式调用模型。类型与生产断言继续守住不变量，相关反例应来自实际问题，进入离线回放或 E2E 检查点；不建立逐函数、逐分支的单元测试替代套件。禁止把 `tests/` 搬到 `evals/` 后改名为 Offline Eval。直调组件、冻结模型或注入结果不因此成为 E2E，历史 Contract、Integration、Runtime Conformance 仍按实际边界解释；既有 `evals/` 诊断用例不自动重命名或纳入产品通过率。

Fake 或 Stub 仅用于声明清楚的离线诊断、第三方对照或危险副作用模拟，不证明真实接入；费用高或第三方不可控不是 Product E2E 替换真实决策、执行边界的理由。外部原始数据可作为初始场景事实固定，但替代真实服务执行须降低证据类别。已有 E2E 对 `tests/conftest.py` 基础设施 fixture 的只读引用不等于运行单元用例；不新增这类依赖，需改动时只迁出所需基础设施，不连带迁移单元用例。

语义变更的用例来源、预声明、验收与重新打开由 [EVD 第 1.4 节](change-evidence.md#14-真实用例驱动优化与验收闭环)拥有，模型依赖目标按[连续验证](change-evidence.md#11-模型依赖链必须连续验证)覆盖实际前置输出与消费者。失败归因后按第 2 节恢复已确定的验收范围。

框架和模块改动按 [EVD 实际影响与升级条件](change-evidence.md#12-按实际影响选择证据)选择相关 E2E 检查点、历史数据离线回放及静态检查，不再要求独立 Unit/Contract 套件。严格保持行为的内部重构可按该判据和 EVM 复用已有证据；模型语义、权限、副作用、恢复或无法证明行为保持的边界须执行对应验证。纯文档和无产品影响的配置变更只做相关工程检查，不触发真实模型或付费 E2E。执行规模仍受[评测效率规则](../../evals/AGENTS.md#7-e2e-执行效率是评测设计门禁)约束，禁止以停用单测为由扩大 live 测试量。

### 1.1 断言必须保护结果或关键契约

本工程停用单元测试，将验证投入用于用户结果、关键契约和真实失败边界。以下规则适用于仍在维护的 E2E 与 Offline Eval；已停用单元测试及历史结果继续只读保留。

- 新增或实质修改的断言须说明保护哪个用户结果或关键不变量，以及该约束失守会导致什么错误。说明放入既有用例契约或检查点声明，不为每条断言新增文档。用户结果与局部检查点仍分别计分。
- 内部字段名、私有方法、对象布局、调用次数或顺序、完整答案快照，只有存在明确契约或关键不变量依据时才可设为判据。仅随实现变化而失败的断言，应在本次受影响的有效评测中删除或改为结果与契约判据；不得修改生产代码迎合它们。
- 核心能力按任务要求判断答案正确性、来源支持、动作结果及适用的拒绝、隔离、幂等和恢复行为。模型可有不同的合法表达或执行路径；精确字面量、原文保真和顺序要求仅在对应契约成立时断言，不用当前实现的输出代替成功标准。
- 使用真实失败或代表性反例检查评测能否拒绝错误结果，并允许满足同一契约的合法结果通过。对象存在、工具已调用或状态已推进只能证明对应局部事实；不能因此判定用户目标完成。发现评测附加要求时按第 2 节修正用例契约与判据，生产变更仍按 EVD 取得适用证据。

### 1.2 通用核验点与真实轨迹用例

**每项核验能力须有明确、通用的核验点，并由正式输入及同一正式轨迹的真实中间结果覆盖。** 核验点说明一种可独立判断的语义关系；反馈字段共同解释该发现，不因字段数量增加任务。具体用户、资料、来源、角色、章节、行号及预期答案由用例持有，不能硬编码到生产或评测 Prompt、请求构造默认值及固定输出字段。

1. 按责任主体整理核验点、适用输入、判据、反馈及对应用例，区分来源支持、用户事实覆盖和最终交付。证据充分性判断当前输入是否包含决策所需前提；语义一致性判断前提充分时稿件与原文是否一致，两者分别计点。发现缺证不计为性质、强度或其他语义关系判断成功；前提不足时对应一致性用例标为无法判定，不计通过或漏判。规范性质与义务强度分别判断，任务覆盖不能混作事实支持；反馈对实际断言的忠实解释另行验收。核验点是分类和验收维度，同一责任主体可在一次模型决策中完成判断、分类及反馈；按每个独立发现归类，类别与理由须一致，各类用例仍独立计分。已有职责内的核验点优先复用，不为点名新增生产阶段、状态或接口。
2. 核验器用例保留目标用户经正式 E2E 入口提交的自然请求，以及该运行实际产生的草稿、证据、引用、反馈和修订；保存入口、Trace、阶段、版本、实际 SDK 与 checksum 的对应关系。回放保持完整阶段输入，不改写稿件、不裁出理想片段、不人工补证、不注入期望反馈。人为相邻样本和历史裁剪诊断只按原身份解释，不计优化验收。真实样本不足以承载本次目标时，实施前经正式 E2E 补齐；其他覆盖缺口只作覆盖信息，不据此否定已通过用例或阻止问题关闭。
3. 每个用例声明对应核验点及真实输入足以支持的判断。缺证、歧义、明确冲突、合法表达和其他职责分别标注，标签与被评模型输入分开。原句含混时先复核判据，不能为制造负例将“应”解释成“必须”或把未拒绝直接算漏放。识别、定位、相关引用、反馈忠实性及真实修订消费分别验收；仅拒稿或结构合法不计能力通过。
4. 后续每次未识别、误拒或反馈失真，先审计实际输入及标签依据，归类到已有核验点并加入该点的真实轨迹用例。找不到对应点时，在既有责任主体内补充通用核验点、边界和真实用例，再校准判据；不得登记为未归类后继续忽略，也不按专有任务名称或期望答案新增例外规则。输入缺失和服务、协议故障按其实际责任归因，不伪装成语义能力失败。
5. 核验点与用例采用唯一映射，当前研究核验的导航见[反馈能力映射](../optimization/conversation-source-support.md#核验点反馈与能力用例映射)。变化同步对应设计、评测记录和影响边界，历史评分及证据身份保持；验收与重新打开由 EVD 第 1.4 节拥有。

### 1.3 局部语义判断类修复的重复验证

**后续局部语义判断类修复，对每个关键真实阶段输入，基线与候选每组各至少验证 10 次，不能凭一次命中宣布修复。**本条适用于结果取决于真实模型开放语义判断的修复，包括来源支持、分类、范围、目标覆盖、语义抽取、路由选择及反馈解释。纯确定性校验、行为保持重构和文档修正按各自证据验收，不为凑次数调用模型。

本工程[同输入重复诊断](../ablation/claim-verifier.md#217-固定输入的二十次重复)已出现相同请求有时命中、有时漏报，错误定位也会使已指出问题的报告不可用。十次是工程最低验证次数，不是已证明稳定或具有总体统计代表性的保证。按以下规则准备和验收：

1. **真实输入与对照**：在候选实验或实施前，固定关键失败输入及必要的相邻合法对照，按第 1.2 节使用真实 E2E 的完整阶段输入。裁剪、改稿、手工补证及注入理想反馈只作诊断，不能凑正式修复次数。同一输入包含多个判断关系时，一次运行可同时审读，不按关系数重复增加调用；局部次数不机械扩大为十轮完整 Product E2E，模型依赖链仍按 EVD 连续验证。
2. **次数与可比性**：每个输入的基线、候选分别至少十次独立判定运行，不是两组合计十次。固定候选变量以外的 Prompt、材料、对象、Schema、模型、供应商参数和恢复策略，核对实际 SDK；各次不消费其他次的答复、审读或期望答案。记录温度、seed、版本及缓存等已知或未知条件。历史基线仅按 EVM 的比较身份和失效边界复用，重复解析、评分、服务重试或结构恢复均不能增加独立次数。
3. **先固定判据和预算**：唯一设计写明每个输入的组别、次数、执行顺序、准确可用反馈的标准、合法关系误拒门槛、其他反馈审读、组级通过条件、成本上限及停止规则。通过条件须满足被修契约，不把“比基线多命中一次”自动写成缺陷已恢复；仅主张概率改善时按该目标预先设定比较判据。费用不足不得临时减次数、裁必要材料或放宽门槛，未完成部分如实报告。
4. **保留每次完整结果**：每次判定保存原始输入、首响应、适用正式恢复后的结果、实际反馈及逐物理调用用量。首响应与恢复后结果分别记分，不能用恢复成功覆盖首次错误；各次彼此独立，不重跑直到命中，不挑成功样本。模型生成的错误类别、无效定位、错误引用或不可用报告均是失败结果，不按服务故障剔除或补跑替换；无完整响应、服务异常及未知用量另行归因并按预声明恢复或停止。
5. **逐关系审读和汇总**：分别记录准确命中、漏报、已发现但反馈失准、输出契约失败、合法关系误拒和未决；同一运行的这些观察按各自分母报告，不能相加冒充更多独立样本。解释、类别、位置及证据须对应同一实际差异，文字提及问题却目标错误不能计为准确可用反馈。报告各组实际次数、分子／分母、未执行项和成本，不把同一输入十次当作十个独立任务；需要概率或置信区间时，预声明方法及其假设。
6. **结束与生效边界**：成功声明须完成最低次数及预声明整组通过条件，达到后即按 EVD 关闭，不再追加稳定性采样。预声明的失败早停可以提前否定候选，但不能声称完成整组次数；测量固定次数下的波动或命中频率时，不因语义结果提前结束。预算、服务及安全停止条件继续适用。本条自 2026-10-20 起用于后续新增或重新准入的修复验证计划，不追溯改写历史成绩或为已关闭用例补加门槛。

## 2. E2E 阻塞按目标、阶段和单变量处理

E2E 失败只是一条待归因事实，不能直接授权修改生产行为。不得从终态、预算耗尽或最后一条错误反向猜根因。遇阻时按以下顺序处理：

1. 按[归档规则](../../evals/AGENTS.md#5-比较身份与归档)封存原始运行，固定输入、运行与评测身份，保留完整追踪记录和结果。
2. 核对用例唯一验收目的。每条断言必须对应用户结果、必要反事实或全局权限、隔离、幂等和副作用不变量；内部工具、步骤、调用次数、预算和状态只有属于公开契约时才能成为 Product E2E 通过条件。
3. 发现附加要求时，先修正 canonical case contract、评测器或用例分类。该失败只证明评测设计错误，不能作为产品修复 baseline，也不得通过增加 Prompt、预算、状态或降级路径迎合。
4. 用例合理后，从正式入口沿 Trace、Proposal、Admission、执行事实、Verification 和 Completion 定位最早关键失败。涉及模型决策时，按 [CTX 输入审计](context-memory-retrieval.md#12-system-prompt-与-context-的设计及问题分析)核对该次实际请求，不能只凭终态或可见理由归因。区分服务不可用、输出契约违规、环境和脚手架错误；后续连锁错误不得冒充根因。
5. 只选择一个用户结果必经链上最早且责任明确的阻塞，核对它与原方案差异的因果关系。确认非原方案引入时按[EVD 第 7.1 节](change-evidence.md#71-独立阻塞优先解决并保持方案一致性)优先解决，并保留原方案。必须说明最小改动如何切断因果链、到达下一可观察边界，哪个反事实可以证明归因，以及失败时撤回什么；否则继续定位，不进入对应生产编码。
6. 完成一次有界修正后，先按预声明用例检查原失败边界，已有有效且身份一致的局部证据不重复运行。完整用户结果或生产接入属于本次目标时，再回跑已确定的原子 E2E；仅以真实完整阶段输入验收的局部优化，按 [EVD 闭环规则](change-evidence.md#14-真实用例驱动优化与验收闭环)通过即关闭，不临时追加整例重跑。相邻 E2E 按实际影响选择，完整矩阵用于发布判断。
7. 按 [EVD 方案复审门禁](change-evidence.md#72-重复阻塞先复审方案再继续)的修正计数与预声明判据确认同一阻塞仍未解除时，先停止受影响路径的候选实验、生产补丁和整轮重跑，审计各次真实输入、差异与失败，再更新唯一设计并取得重新准入依据。门禁同时适用于 Offline Eval 和独立阻塞；协议通过不能覆盖目标语义失败，更换 Prompt 或模块不能重置尝试。隔离诊断按 EVD 继续；局部证据成立后才恢复原 E2E，原方案和独立工作按因果边界保留。

每次分析保存“用例目的与必要断言、合理性结论、最早失败阶段、唯一阻塞及责任主体、与原方案的因果关系、原方案保留条件、下一条最小验证与恢复入口”。评测代码另按[模块规则](../../evals/AGENTS.md#3-每条用例必须有唯一验收目的)登记用例和审查记录。

原始 E2E 与局部检查点的判断必须分开。合法 typed 终态不自动表示通过或候选失败；归因和候选取舍统一按[EVD 第 1 节](change-evidence.md#1-用户结果与工程约束的可执行基线)，不得以局部通过覆盖产品失败。

### 2.1 核验漏放先验证最小充分上下文

**核验器放行已确认的错误时，必须先排除无关信息干扰，在最小充分且准确的 Context 下检查能否识别，再决定当前核验任务设计是否合理。** 最小充分输入诊断按预声明判据解释；仍不满足核验契约时，停止对应生产准入并复审设计，重新准入执行 [EVD 第 7.2 节](change-evidence.md#72-重复阻塞先复审方案再继续)。

1. 封存真实漏放请求与输出，核对错误标签的权威依据，固定现行 Prompt、输出契约、模型、配置、预算及恢复策略。按 [CTX 输入与推理记录审计](context-memory-retrieval.md#12-system-prompt-与-context-的设计及问题分析)审计实际发送内容和构造链，已有推理记录用于区分未注意、判断后放弃报告及输出遗漏，先排除服务、协议与评测错误；记录提及问题不能替代实际识别通过。
2. 先审计正式阶段的完整真实输入，逐项说明哪些声明、历史、自评或重复投影与目标判断无关，哪些主体、条件、范围、性质限定及来源身份是必要前提。缺前提的短输入不能称为最小充分输入；必要前提缺失时先定位取得或物化边界。
3. 为区分输入干扰等假设，可按 [EVD 隔离诊断](change-evidence.md#13-探索与生产准入边界)在真实请求副本上进行有界裁剪模型诊断。保留必要前提，不补造事实或注入期望反馈；固定 Prompt、模型、输出契约、预算及恢复策略，以原始请求为对照，预声明输入差异、判据、样本与成本上限。封存原始与裁剪后的实发 SDK 请求、输出及身份。诊断可在生产修正前进行，无需先修改正式物化链；结论限于对应输入下的观察，不计能力通过率、优化验收或问题关闭。
4. 优化验收用例按第 1.2 节逐字复用完整真实阶段输入，不人为裁剪或补证。输入物化修正及必要读取经正式链取得新的真实中间结果后，再登记对应样本；目标所需样本在实施前补齐。预声明来自真实 E2E 的正反样本、判据、成本和停止条件，保存实发 SDK 输入与实际 typed 输出。明确错误检查目标问题是否识别，合法样本允许正确结果通过，歧义及缺证分别计分；拒稿、字段合法或出现关键词不算识别。完整历史真实阶段输入回放按 Offline Eval 验收对应局部优化，其他覆盖信息不成为通过后的追加门槛。
5. 按预声明判据确认最小充分输入仍不满足核验契约时，停止受影响任务的候选扩展、生产补丁和整轮重跑，在唯一设计中重审核验目标、职责、判据、输入输出契约、模型可执行性及上下游分工。诊断反例限定到实际输入与声明，不以一次失败宣称该类任务普遍不可行；有证据支持的最小修正按 EVD 第 7.2 节重新准入，原因待证时继续有界隔离诊断。
6. 裁剪诊断中识别成功只证明该输入下能够识别。沿实际生产链区分必要信息未取得、未物化和已见但被干扰等原因，再依据实际请求修正责任边界。按已确定的完整真实用例验收，目标涉及连续链时消费同轨迹实际前置输出。用例通过即认可对应优化成功；唯一根因或稳定识别率仅在本次已明确主张并设定判据时验证，不成为事后追加条件。

## 3. Observability、安全与审计

追踪记录只记录任务所需的运行事实，不得包含不必要的密钥、完整敏感内容或跨作用域数据。按适用性记录 `trace_id`、tenant/user、thread/task、goal、proposal/version、policy/version、command/authorization digest、tool/provider、attempt、latency、token/cost、receipt、verification、completion 和错误分类。

- 入口解析身份与作用域，并贯穿调用链。
- Policy 决定是否允许及是否需要审批；执行网关统一执行授权、风险、预算与审计。
- Prompt 不能替代权限控制；高风险操作必须绑定明确的 target、payload、授权与确认。
- 批量、删除、外发、不可逆和高成本操作默认提高风险等级。
- 审批、授权、Command、Journal、Receipt、补偿和 Completion 必须关联同一任务及 canonical digest 链路；审计记录不可被普通业务更新覆盖。
