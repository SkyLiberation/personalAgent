# 上下文、记忆与检索细则（CTX）

> 本细则在任务涉及 Context、System Prompt、模型输入、反馈执行异常、Memory、RAG、Artifact、检索、权限过滤、预算物化或 Capability Projection 时生效。通用事实归属见[架构边界与事实归属](architecture-ownership.md)，测试要求见[测试、评估、观测与安全](quality-security.md)。

## 1. Context 的处理顺序

必须遵守[根规范第 2.4 节](../../AGENTS.md#24-决策执行与完成不得混装)的处理顺序：先按权限与作用域筛选可见内容，再按需求召回、由模型选择语义相关内容，最后按预算压缩并注入模型 Context。

### 1.1 模型输入优先表达语义，机器消费保持结构化

**面向模型的任务说明、运行状态、工具反馈和修订要求，应优先用简洁自然语言说明其意义；面向运行系统的模型动作与判别结果，必须遵守对应 typed contract。** 这种区分取决于消费者，不取决于传输外壳是否为 JSON。自然语言正文可以装在结构化工具消息中，模型输入也可以保留更适合精确比较的表格、列表和结构化数据。

- 运行系统产生的关键反馈必须说明涉及哪个对象、发生了什么、适用范围及对下一步的约束。模型需要据此修订时，说明允许的处理方向；禁止代替模型补写业务答案或把未知事实写成否定结论。不得只返回错误码、布尔值或未解释的内部字段名，让模型猜测其业务含义。
- 模型可见的计数和状态必须交代单位、范围及影响决策的未知或缺失语义。说明必须进入实际模型请求；Python 注释、未发送的 Schema 描述、日志和仅向用户展示的文本不能算作模型已获得说明。
- 引用 ID、资源引用、URL、行号、可直接调用的参数和协议字面量按原值保留，并按需解释用途。证据原文、代码、原始 JSON 和多模态内容保持所需保真度，禁止为追求自然语言而改写证据、丢失对应关系或掩盖截断；来源数据须与运行系统指令清楚分隔。
- 模型可见说明由既有 Context 物化边界依据 canonical typed facts 生成，只是可重建的只读投影。运行系统继续依据 typed facts 准入、执行和判定覆盖，禁止从这段说明反向解析控制流、建立第二事实源，或要求模型复述系统已经拥有的执行事实。
- 同一信息只保留当前决策所需的表达，避免把完整内部对象和同义长文重复注入。模型供程序消费的输出使用最小必要结构，字段语义与校验遵守 [COD](code-structure.md#6-生产-prompt-是版本化代码契约)；用户可见正文无需为了形式统一拆成无消费者字段。

例如，累计读取反馈可以表达为：“此来源共 120 行，累计完整返回 30 行，尚有 90 行未完整返回。读取覆盖不足不能支持全文缺项结论；可继续取证，或将陈述限定于已返回片段。”这里的计数由运行系统计算；完整返回不代表模型已理解全部内容，也不自动证明文档确实缺项。总数未知时应明确说未知，不能计算或编造剩余量。

依据与适用边界见[外部源码比较](../agentRef/context-engineering.md#4-模型可见反馈与机器协议的表达分工)。该规范不证明自然语言总比 JSON 有效，也不证明现有修订失败由字段表达导致。修改生产物化或 Prompt 时仍须按 [EVD](change-evidence.md) 验证实际发送内容、事实保真及用户结果；没有失败证据时不得据此批量改写工具协议或新增通用转换框架。

### 1.2 System Prompt 与 Context 的设计及问题分析

**模型输入审计是语义行为设计与问题定位的必要环节。** 对回答无据、反馈未执行、检索或计划空转、工具误选、错误终止等问题，必须先检查失败决策实际收到的输入，再提出模型能力、Prompt 或运行机制的归因。已有可复用审计只需核对输入差异与失效部分，不从头重做；纯确定性问题与不涉及模型行为的文档变更无需制造模型测试。

审计以实际发送的请求及其构造链为准。须核对模板渲染、运行系统附加文字、工具说明、数据物化、裁剪与服务提供方适配；只搜 Prompt 注册目录不够。归档保存可还原的请求身份、版本与必要证据，遵守安全规则，不复制密钥或无关私人内容。尚无运行请求的新设计先声明预期输入契约与审计方案，接入后用实际请求核对，不能把草案冒充已发送内容。

| 检查面 | 必须回答的问题 |
| --- | --- |
| 输入来源与权威 | 本轮有哪些消息、角色、顺序、工具定义及动态区块？每项由谁产生、为何注入？用户目标、稳定规则、执行事实、外部正文和模型自评是否明确分开？ |
| 指令的关系 | 哪些是硬约束、当前修订要求、默认策略或仅说明操作方法？是否存在冲突、重复、失效规则，或不可用能力的操作指引？不能只检查是否出现“禁止”“优先”等关键词。 |
| 反馈与历史 | 最新适用拒绝是否完整进入输入、指向具体对象和支持缺口？它与旧 Plan、自评、旧动作拒绝如何区分？旧约束不得扩大到其他请求，历史拒绝也不能无依据标为已解决。 |
| 目标与修复出口 | 输入是否将用户结果误写成固定工具路径、持续检索或读取完成？反馈能否表达补证、修订、合理限制及停止边界，而不代写答案、强制无依据策略或放宽确定性门禁？ |
| 信息保真与成本 | 原文、引用身份、资源范围、已读／未读事实和必要上下文是否完整保留？长度、重复量、截断位置及缺失信息是什么？字符数与 tokens 分开记录，不能仅凭长度认定干扰。 |
| 实际决策与结果 | 分别有什么证据证明输入已发送、模型表达理解、动作执行、修订生效和用户结果满足？服务提供方返回的可见理由只辅助定位；未提及不能证明未看到，提及也不能证明正确执行。 |

设计须明确稳定 System Prompt、当前目标与成功标准、当前运行反馈、历史记录、证据正文和工具契约各自的职责、可信边界、适用范围及更新条件。区块按当前需要选择并清楚分隔；最新适用反馈对当前修订的约束应明确，不因旧自评而失效，也不得越过用户目标、权限或预算。工具用法和续读参数只表示能力，不能自动成为工作义务。具体分区、消息角色与顺序须适配实际服务提供方协议，不统一规定“全部移到 system／user”或“放在末尾就有效”。

发现疑点后，先区分输入缺失、表达冲突、范围误解、数据干扰和已理解但未执行等假设。记录原输入、候选差异、保留事实、责任主体、预声明判据与停止条件，再按 [EVD](change-evidence.md) 和 [QLT](quality-security.md)验证。整体重组同时改变多项输入时，只能声称整体候选的观察收益；不能把结果归因于其中一句话、某个角色或 Context 变短。冻结输入诊断不能冒充真实 E2E。

禁止从一次可见理由或少量成功动作推断唯一根因、稳定正确率或产品修复。已经证明有效的读取、引用、拒绝及修订机制必须作为保留条件，除非相应反例证明应撤回；不能为简化输入静默删除必要事实或历史失败。正式接入继续由既有 Context 物化边界消费 canonical facts，不从实验日志读取事实，不新增持久镜像，也不从模型可见文案反向解析控制。

本条规范的工程依据与经验边界见[第 109 节输入审计及重组对照](../optimization/document-absence.md#补充持续续读指引与-system-prompt-组织审计)。该记录支持将审计纳入流程，不证明某种排版、消息角色或提示表述对所有模型有效；生产 Prompt 的注册、版本及通用输出契约仍由 [COD](code-structure.md#6-生产-prompt-是版本化代码契约)拥有。

## 2. 存储边界

- Agent State：保存当前运行所需的结构化状态；
- LLM Context：保存当前模型调用实际可见的内容；
- Checkpoint：保存恢复执行所需的快照；
- Artifact Store：保存大文本、文件和中间产物；
- Long-term Memory：保存跨会话可召回的事实或经验；
- Retrieval Index：保存检索投影，不作为事实权威源。

State 优先保存 `ArtifactRef`，不得复制大型 Artifact。RAG 只负责检索和证据组织，不得成为隐藏的 Router 或 Planner。检索策略必须由数据与评测驱动，禁止为单一 benchmark 硬编码；中间检索指标不能替代最终答案与证据正确性。

## 3. Capability Projection 与服务提供方绑定

Capability definition 由对应 Application owner 管理。模型可见 capability、工具 schema、服务提供方可用性和检索结果都是临时只读投影，必须先经过 visibility 或 policy，再进行 materialize。投影可以帮助模型选择 Application Capability，不能替智能体完成开放语义选择，也不能反向成为定义或可用性事实源。

只有完整满足同一 `CapabilityEquivalenceClass` 的服务提供方才能确定性绑定。存在语义差异时，必须由模型或外部权威选择。
