# 代码组织与实现约束细则（COD）

> 本细则适用于可读性、功能模块化、Code Agent 开发上下文、内部类型、payload、依赖注入、生产 Prompt、编排、错误分类、命名和编码智能体行为。事实与分层由[ARC](architecture-ownership.md)拥有；证据和复杂度准入由[EVD](change-evidence.md)拥有。

## 1. 不变量必须有唯一归属

每条结构性不变量须有命名责任主体和确定性失败判据。提交前说明承载类型或模块、拒绝或失败条件及已执行的适用检查；仅依赖模型方差偶发触发不算覆盖。验证按 [EVD 实际影响](change-evidence.md#12-按实际影响选择证据)选择，不为每个字段或辅助结构机械新增破坏样本；权限、副作用和恢复等关键反事实仍按对应门禁执行。

靠字符串键、散落条件或注释维持的内部不变量视为未实现；重命名字段或更换服务方后不得静默失效。概念映射到代码不等于为每个名词创建对象。

设计模式只隔离已证明的变化、真实依赖或信任边界，并受[EVD 复杂度准入](change-evidence.md#5-复杂度说明complexity-justification)约束。禁止为每个类创建 Interface、Factory 或 Manager，使用模式掩盖职责不清，或让 Strategy/Router 承担开放语义、Adapter/Converter 同步可独立修改的镜像事实。

## 2. 类型边界与 payload 所有权

判定类型边界要看谁写入、谁读取，不能只看字段是否规整。内部自写自读字段及跨层 identity、scope、digest、资源引用遵守根规范的 typed 门禁。

无 schema 的 `dict[str, Any]` 或 raw JSON 只允许承载外部拥有的内容，在读取处做 typed 校验。普通文本内容可以是字符串，身份、资源引用和状态不能借字符串规避类型边界。校验失败显式报告边界错误或契约规定的事实缺失，不将内部协议损坏隐藏为空值；禁止默认成功，或用字符串包含与相似度代替校验。

内部集合可使用键值类型明确的 `Mapping`、`TypedDict` 或现行 Model；序列化可使用由该 typed contract 生成并在读取边界校验的 JSON。类型门禁约束消费契约，不要求每个字典或序列化层另建一个 Model。

内部 typed contract 不要求将整个对象原样注入模型。面向模型的语义说明与面向程序的结构化消费，按 [CTX 表达分工](context-memory-retrieval.md#11-模型输入优先表达语义机器消费保持结构化)处理；可读文本只投影已有事实，不承担内部状态或控制协议。

### 2.1 已有文字通过引用传递

**模型对已有具体文字的复述、引用或转交，必须通过引用绑定原文，由 Runtime 恢复原文。** 验收项、证据摘录、待编辑片段及已验证产物均按其唯一责任主体的现行契约处理；模型负责选择引用及生成新的语义判断、解释或修订内容。

1. 输入从当前可见权威事实派生 typed 引用及阅读正文。引用绑定所需身份、版本与作用域；小型身份集合进入本次合法取值约束，大型原文沿既有坐标或连续范围契约物化。
2. 模型输出只提交所选引用及本轮新增语义字段。已有文字的身份、定位、复制和搬运不得要求模型重抄全文、旧字符串或引句来证明；生成的新内容与所引用的原文分别表达。
3. Runtime 从本次权威输入恢复原文，校验引用属于当前可见集合及适用版本，再交给实际消费者。需要完整覆盖时逐项检查未知、遗漏和重复引用；引用错误显式归为输出或准入契约失败，零写入、零有效回执。
4. 原文展示、反馈与最终交付消费 Runtime 恢复的同一文本；模型语义判断仍接受对应 Verifier，Completion 绑定实际通过产物。恢复引用不能改写判断状态、补齐业务内容或把语义拒绝变成通过。
5. 设计审查检查模型输出字段、实际请求、解析绑定、反馈、恢复和用户返回的完整消费链。依据真实转录失败回放原文保真与身份拒绝，再连续验证真实模型返回及正式入口；被替代的全文复制字段、字符串定位和指令在同一变更删除。

## 3. 模块职责、规模与生产可达性

一个模块须有清楚的主要职责。检查它是否混装多个 Application Capability 的准入、结果契约或展示投影，以及这些职责是否有独立变化原因；不能用一句话是否包含“以及”或文件行数直接判定 God Service。

- Service 按稳定的业务责任和变化原因组织；同一 Aggregate 的相关操作可共享 Service，每项 Application Capability 的准入、结果契约与投影仍有明确归属。多个独立能力共用入口时，入口负责路由与协调，由各能力承担业务职责；不能按类名或能力数量机械拆分，也不能混装独立生命周期与写入责任。
- 抽出的准入模块须按 EVD 以适用契约检查、实际输入对照、Offline Eval 或 E2E 检查点验证其边界，且不得反向依赖编排。
- 类、字段、Repository 方法、投影、Adapter 及注入式协作者均须通过[生产可达性检查](architecture-ownership.md#7-生产可达性)。仅测试、迁移脚本或文档引用的结构不算能力落地；明确保留期的测试或迁移设施按其真实用途声明。

### 3.1 可读性优先

可读性是设计和实现的首要组织标准。读者应能从入口、命名和 typed 输入输出看懂主要路径、事实归属与失败语义；在满足行为、权限和事实门禁的前提下，优先选择理解成本更低的实现。

- 函数围绕一个可说明的任务组织，输入校验、事实派生、外部调用和结果物化按责任呈现。先处理明确的拒绝与退出条件，再展开主路径；复杂条件用业务名称表达，避免多层嵌套、隐式状态和远距离变量修改掩盖因果关系。
- 同一职责的相关实现相邻，按调用或信息流组织；只在有明确输入输出的责任边界抽取函数。保持局部直观的顺序逻辑，禁止为了缩短函数把连续逻辑拆成需要往返追踪的碎片。
- 名称说明角色、动作或事实，注释解释必要依据、约束和取舍；删除重复代码表意或已过期的注释。使用项目格式工具保持一致排版，避免一行混装多项职责。
- 评审沿真实入口走读成功及关键失败路径，确认所需事实、协作者和变化位置可定位。格式或位置调整按实际影响证明行为保持；字符串、Prompt、Schema 和错误变化仍按对应契约验收。

### 3.2 功能模块化与开发上下文

模块化用于控制 Code Agent 的开发上下文：一个局部任务应能以该功能的内聚实现、typed 契约及直接协作者为主要阅读范围。这里的开发上下文是理解和修改源码所需的信息；运行时模型 Context 仍由 CTX 拥有。

- 按稳定功能职责和真实变化原因划分模块，明确入口、输入输出、内部协作及依赖方向。调用方通过清楚的契约使用模块；该职责的内部规则在唯一实现处集中，避免通用 `utils` 聚集无关规则、跨模块私有状态或循环依赖扩大查阅范围。
- 拆分前说明实际任务需要查阅哪些职责、当前混装或耦合如何扩大范围；拆分后列出真实消费者、直接依赖、被删除的旧实现及新的查阅路径。新增跳转、传参和协作成本须计入净理解成本；可读性下降时保留内聚顺序逻辑或重新选择边界。
- 文件行数、函数长度、圈复杂度和类数量只触发评审，不能成为拆分配额或上下文收益的充分证据。新增或显著增长的模块、类须说明拆分或保留理由；类数量增长须对应删除量与真实边界，不为减小文件创建无职责的 Manager、Helper、转发层或接口。
- 功能内部的确定性协作可以直接调用；Port 与依赖注入用于第 5 节的真实依赖或信任边界。迁移调用方并删除被替代定义，按 EVD 核对行为与依赖保持；单纯阅读范围下降不能声称模型效果或产品能力改善。

## 4. LangGraph、Router、Planner 与 Workflow

编排只组织工作，不接管业务事实或开放语义决策。具体边界如下：

- Graph 表达编排与迁移，不拥有领域事实；Node 只提取输入、调用 Use Case、写回结果，不复制业务规则。
- GraphState 只保存 typed 运行必需状态，大对象使用 `ArtifactRef`；恢复复用已完成步骤的事实，副作用遵守幂等与恢复协议。未完成模型请求可以按明确重试契约重新调用，不能把恢复解释为重新生成已冻结 Command。
- Router 或智能体输出 Goal、Intent 或 Application Capability Proposal，不选择 Repository、Provider、内部 Workflow 或 Project 模式，也不输出执行完成事实。
- Workflow 只编排具体能力内的固定业务不变量，不是框架层、用户入口或能力类型。新增 Workflow 须有真实多阶段协作、固定不变量，以及实际需要的事务、审批、恢复、审计、重试或补偿边界；简单顺序调用保留在 Service 或 Application Pipeline。纯职责抽取按 [EVD](change-evidence.md#12-按实际影响选择证据)证明工程约束与行为保持，产品行为改变才适用对应失败 baseline 与 target，不为命名或目录补造产品失败。
- 固定依赖由契约或具体 Workflow 定义；只有 Observation 会改变未知依赖时才使用 Planner，Planner 不负责授权、执行或完成判定。
- Plan 只有其依据、依赖、进度、预算或完成义务被生产代码消费时，才能成为强制契约。审阅前只可执行 Policy 投影为 planning-safe 的低风险读取；planning-safe 不等于严格 read-only，其他执行会关闭新 Plan 的审阅迁移。
- Project 是拥有动态、需持久保存的业务事实的 Product Aggregate，不得作为通用 Workflow、路由分支标签或所有长任务的容器。
- Workflow 内固定低风险步骤优先由 Service 执行；模型动态选择或需要统一执行网关治理的执行资源才封装为工具。

## 5. 错误、注入与命名

错误按实际边界区分校验失败、语义拒绝、授权拒绝、能力缺失、执行或暂时失败、Verification/Completion 失败及不变量破坏；不要求每个模块机械创建全部错误类。禁止用空结果、默认成功或模糊 fallback 掩盖异常。契约允许的无命中、空集合或可选值缺失可正常返回，必须与执行失败、未知或内部协议损坏区分。

模型、Repository、工具、Policy 和外部服务提供方在真实依赖或信任边界通过既有 typed Port 注入。影响预算、过期、身份、幂等或恢复的时钟与 ID 来源须可注入；单一调用可使用语义明确的 typed callable，不为每个来源新增 Interface。纯内部确定性函数无需机械建立 Port；评测不得 monkey patch 生产规则来构造通过结果。

命名须表达业务角色和生命周期。除非边界明确，禁止使用 `data`、`info`、`manager`、`processor`、`handler` 等泛化名称。

## 6. 生产 Prompt 是版本化代码契约

本文拥有生产 Prompt 的通用语义契约。生产模板按[Prompt 模块规范](../../src/personal_agent/kernel/prompt_templates/AGENTS.md)注册、版本化和消费；声明行为保持且只迁移位置时，以实际发送字节对照为依据，不能同时声称修复语义缺陷。评测 Prompt 遵守本节语义要求，但不因此进入生产注册表。

所有生产、核验与评测 Prompt 都必须在其职责范围内通用，不能硬编码某条用户问题、研究对象、固定主题清单、理想分点、参考答案或该样本的判断结论。具体任务与用户验收要求由实际输入提供，场景资料由其数据责任主体经 typed 边界显式传入；不得在模板、请求构造器的默认值或固定输出字段中换一种方式藏回具体问题。输出 schema 表达通用判断，随任务变化的检查项来自当前输入。工具协议、引用语法及安全边界属于可固定的职责契约；示例只解释通用规则，不为某条评测定制答案。

新增或实质修改前，必须完成 [System Prompt 与 Context 设计审计](context-memory-retrieval.md#12-system-prompt-与-context-的设计及问题分析)，将动态物化和实际请求纳入分析；不能仅修改模板而遗漏运行系统、工具说明或历史反馈中仍生效的同类指引。

新增或实质修改的 Prompt 采用结果优先、最小充分表达，覆盖以下语义。按职责合并内容，不机械要求每个简单判别模板都有五个标题：

| 分区 | 必须表达的内容 |
| --- | --- |
| 任务目标 | 本轮语义决定或最终产物；先说明用户或下游消费者需要什么 |
| 必要 Context | 每类输入的权威来源、作用域、可信边界与清楚分隔；外部内容是数据而非指令 |
| 成功标准 | 动态投影当前用户要求、领域 `required result contract` 或工作清单中的用户可见结果，逐项可判断 |
| 硬约束 | 禁止编造、越权、扩大范围或覆盖确定性事实 |
| 输出形式 | typed schema、字段语义、字段间一致性及只允许返回的内容 |

Structured Outputs、`json_schema`、字段和枚举只约束形状。结果 Prompt 必须指出下游实际消费的完整产物字段；标题、提纲、占位符、写作意图、状态自述或主题复述不能替代该产物，除非用户请求的就是这些形式。判别 Prompt 同样须说明被评对象、逐项判据与相邻边界，不能把词面提及当成语义满足。

模型输出契约按 [EVD 奥卡姆剃刀与复杂度准入](change-evidence.md#5-复杂度说明complexity-justification)保留完成当前决定及下游消费所需的最小语义。已有分类、说明和引用足够时，不要求模型再输出重复的分类轴、属性值或确认结论；不得仅为展示判断过程要求无必要的逐维度记录。评审同时核对新增输出带来的模型理解、一致性判断和代码解析、校验、映射成本；诊断字段按其实际用途隔离，不因可观察性就成为生产必填项。

中文必须承担任务逻辑、Context 边界、成功标准、决策规则、约束、示例、失败处理和停止条件。英文仅保留翻译会失真的技术术语、Provider 或协议字面量、代码标识、typed 字段或枚举及 URL；不得用整段英文规避中文语义问题。明确的英文或多语言产品契约须独立版本化、独立评测，保留中文主 Prompt 的独立 target。

复杂智能体 Prompt 还须明确可见工具与权限、失败处理、重试上限和停止条件。只暴露当前可用的最小工具面，不能假装代码中不存在的能力。权限、执行事实、唯一推导、状态迁移和预算强制终止由确定性责任主体拥有；Prompt 不能替代。工具、查询、推理顺序或实现路径只有本身属于产品契约、安全协议或事务不变量时才能固定。

分类、路由和准入 Prompt 明确输出契约、适用判据与冲突优先级，单选类别须互斥，多选契约明确组合规则。出现实测歧义时，先校准规则与输入边界，用该失败类别的相邻正反例验证，并检查分类、理由和下一阶段一致；正反例进入评测，不自动追加到生产 Prompt。确需在 Prompt 中使用示例时，示例须贴近输入分布、覆盖相邻边界、保持输入输出结构一致，并证明必要性；只能泛化失败类别，不能复制某条 E2E 的专有名词、答案、URL、标题或措辞，也不能每个反例追加一条例外。

每条指令只陈述一次。出现歧义先重组既有规则，不在扁平长段落末尾追加补丁。没有证据表明示例优于清楚规则时，优先使用短目标、动态成功标准与返回前自检；Prompt 增长须报告输入成本，并以代表性评测证明必要。

Prompt 优化的用例来源、验收与重新打开由 [EVD](change-evidence.md#14-真实用例驱动优化与验收闭环)拥有；比较固定 Prompt、Provider、模型、输入、schema、预算和重复次数，声明的候选变量除外。

静态检查及离线输入回放验证注册、输入分隔、typed 输出和代码侧不变量；真实模型评测验证语义边界；Product E2E 只验收用户结果，不固定措辞、工具路径或中间分类。模块内版本字段与具体检查遵守 Prompt 模块规范。

## 7. 编码智能体行为

### 工具参数范围与可修复拒绝

工具设计必须区分静态格式、当前可用取值与执行时不变量。程序已知的参数由代码绑定；需要模型选择的已有身份应在参数定义中给出当前合法集合。引用等大型范围应从同一可见权威状态派生文档及连续区间，不维护第二份可写目录，不为每个可能组合创建枚举；跨字段及区间完整性仍由唯一执行校验负责。

模型可见 Schema、参数说明与实际执行范围必须一致并随状态更新。JSON 模式中的提示不能冒充服务端严格 Schema 约束，合法格式不能冒充语义正确。可修复参数拒绝必须保留原提议、错误位置、原因及当前合法范围，经真实反馈路径交给模型，并保持业务状态未修改；不能因确定性校验已拦截就直接终止整个任务。恢复受明确预算约束，服务失败、权限拒绝和内部不变量不得混作可修复参数错误。实验如为首次调用准确率而预声明遇错停止，必须说明不覆盖恢复能力，不得据此否定后置方案。

实现前的变更说明、用户改动保护和完成声明遵守根规范；设计步骤与遇阻复核执行[EVD 流程](change-evidence.md#7-强制开发与设计流程)，E2E 失败执行[QLT 阻塞处理](quality-security.md#2-e2e-阻塞按目标阶段和单变量处理)。

无法确认事实责任主体、授权边界或外部契约时，明确阻塞原因并停止相关实现，不得猜测或用新增降级路径掩盖缺口。
