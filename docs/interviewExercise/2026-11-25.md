## 第 1 题 · 单步最多运行 800 秒，怎样交付近一小时的 Agent 任务

Recoup 的定时 Agent 要完成研究、核验和报表投递。原来由一个 `runAgentStep` 执行整个 Agent 循环。平台最多让一次步骤执行 800 秒，部分运行被反复终止。复盘中的两个失败运行分别耗时 72.4 和 73.4 分钟，均在第 5 次尝试失败。同一付费客户还曾连续两天各收到三封报表。团队拆分后，在预览环境重放另一项真实定时任务，55.7 分钟内完成 44 个迭代，最长单步 203.5 秒，交付一封满足要求的邮件。**在单步上限为 800 秒的前提下，你会在哪里切分执行步骤，下一步需要怎样接上前一步的结果？如果一轮里的单个操作本身也可能超过 800 秒，这种切法还能用吗？**[Recoup 生产复盘与预览重放 #1918](https://github.com/recoupable/app/issues/1918)

选题来自字节抖音电商 Agent 开发一面第 5、10 问，分别追问长任务的单步超时设计和重启时要保存的状态。百度地图 Harness 岗位要求任务规划执行、持久化和故障恢复。[牛客面经，2026-10-13 发布](https://www.nowcoder.com/discuss/939623386806751232?sourceSSR=dynamic) · [百度 J106366，2026-10-10](https://talent.baidu.com/jobs/detail/INTERN/64cd87b2-4690-4192-948e-2aadb01cd87d)

### 理论分析

**把平台的 800 秒上限用在单次执行上，把整体任务留给工作流协调。每个步骤完成时，要交出下一步真正需要的结果。**

- **在哪里切。** Agent 循环可以按「一次模型调用及其对应的有界工具处理」切分。外层按模型停止原因决定继续，收齐工具结果后才把原生消息追加到下一轮。已完成步骤的输入输出保存在工作流记录里。连续执行 44 个这样的步骤可以累计超过 800 秒，只要每个步骤都能在上限内完成。提高重试次数只会让原来的超长步骤反复遇到同一上限。[Vercel Workflow 的步骤与恢复](https://github.com/vercel/workflow/blob/main/docs/content/docs/v4/foundations/workflows-and-steps.mdx)
- **什么时候要再切。** 203.5 秒是一次重放里观察到的最大值。部署时还要检查单轮耗时是否受模型和工具时限约束，并预留结果收集和持久化时间。若某项外部工作本身可持续超过 800 秒，且服务支持异步提交，短步骤只负责提交并返回作业 ID。工作流随后挂起等待完成信号，再从已知作业取得结果。纯计算任务可优先按输入分块。仅把循环挪到外层，仍会让一个超长同步操作撞到平台上限。
- **如何验业务可行。** 同时看单步最大耗时、整次耗时、已完成步骤的重做次数和最终报表内容。这次 55.7 分钟的交付说明总时长可以跨过单步上限。那封邮件还包含预期 5 条机会，格式和费用条件通过团队核对。只看流程结束、或者只看最长一步低于 800 秒，仍无法确认客户收到了合格报表。[Recoup #1918 的 Done 段](https://github.com/recoupable/app/issues/1918)

### 理论分析

**先检查金标摘要是否进入候选集，再决定调召回还是重排，最后独立判断证据对断言的支持方向。**

- **候选没有 45638119。** 检查分块和索引，必要时调整召回。已有候选传给任何重排器都无法产生遗漏摘要。
- **候选有它，最终证据没它。** 固定候选，用问题和候选全文重排后再裁剪。分别记录候选命中、重排后证据命中和模型实际读到的句子。若排名已靠前但裁剪删掉第 5 句，应修证据装配。公开答法同样把低成本的广召回与小规模的成对判断分开。[Sentence Transformers 检索与重排](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/)
- **同一摘要能回答两题。** 对 51 和 53，这份摘要都高度相关，结论却相反。把相关性得分当支持概率，会把 51 判错。单独评分检索命中和最终标签。

## 第 3 题 · MCP 能列出只读工具，为什么还是 403

一个代码审查助手要汇总私有仓库某个 PR 的 CI 检查。GitHub MCP Server #2381 记录同一个 classic PAT 已有 `repo`、`read:org` 和组织 SSO 授权，Hosted MCP 的 PR 详情、文件和评论可读，`pull_request_read(method=get_check_runs)` 却返回 403。同一 PAT 直接走 GitHub REST 的同一检查端点返回 200。怎样向用户报告结果，并定位是工具入口权限、上游动作权限还是其他策略？[原始报告，2026-04-24](https://github.com/github/github-mcp-server/issues/2381)

选题来自字节剪映 AI 应用开发一面的安全执行与读取范围追问，对应归档第 24–26 问。百度 Agent 应用全栈的职责涵盖 Tool/API 调用与可执行任务系统。[牛客原帖，2026-09-24 发布](https://www.nowcoder.com/feed/main/detail/7211e82c75284d23a89b569cd9dc289d) · [原问归档](https://mianstack.com/interview/mj-nc-2026-0556/?view=questions) · [百度 J99974，2026-07-21](https://talent.baidu.com/jobs/detail/GRADUATE/6f9c3a86-6557-409d-8fa7-e6f4c68d6765)

### 理论分析

**把能调用什么工具和工具能读取哪些资源分成两次授权判定，403 应呈现为 CI 检查结果不可得。**

- **从故障阶段归因。** 同一 PR 的详情读取成功，至少说明路径可达且部分读取获准。检查失败发生在 head SHA 的 check-runs 请求，另有 REST 200 对照。记录资源、方法、授权路径与失败阶段。托管安装权限是报告者的解释，部署构建和实际授权链还需运营方核实。
- **从工具名下钻到具体动作。** `pull_request_read` 同时承载多种方法。工具曝光名单、只读标记和 PR 的读取权限均不足以证明 `get_check_runs` 获准。MCP 授权规范进一步要求 HTTP 访问令牌绑定到目标资源，并区分认证失败和权限不足。[MCP 授权规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)
- **从观察得出用户结论。** 200 加空列表可报告当前没有可列出的检查。403 对应未知。只有事先部署并为同一用户和资源授权了另一条等价读取路径，才考虑切换，避免使用服务全局凭据掩盖权限差异。

### 本工程改进设计

先在隔离 HTTP MCP 服务回放同一 PR 的详情 200、检查 403 和检查 200 空集。三类结果消费方应分别见详情、权限不可得、合法空集，模型不接触凭据。如果多主体授权成为正式需求，在 MCP 装配处按会话认证主体与 endpoint 解析授权，按授权上下文隔离连接，绑定请求资源与原主体后再派发。一名用户撤权或无授权时零下游调用，另一名用户的连接与回执不受影响。保持这一候选限定于确有分用户授权的服务。

## 第 4 题 · 怎样验收表格 Agent 交付的舍入和显示

选题来自字节 aime 一面第 30、33 问，分别追问整体效果评估和失败归因。百度岗位要求把业务任务沉淀为可复现评测资产。[牛客 9 月 10 日一面，9 月 15 日帖](https://www.nowcoder.com/feed/main/detail/ed5e9d17f26e489da94afbf1241b885e?sourceSSR=post) · [百度 J106616，2026-10-16](https://talent.baidu.com/jobs/detail/INTERN/4bd782af-7dc6-44c1-b02a-e31bb6bc7cb2)

### 理论分析

**验收器应读回提交文件的可见单元格，并用原始输入与金标检查显示值和格式。**

- **先确认读的是最终版本。** 完成消息、截图、执行返回成功只辅助诊断，结果层应从提交路径重新打开可交付工作簿。此基准有评分器主动保存的安排，生产验收则应事先明确谁负责交付文件。Anthropic 的公开答法同样主张用环境里的结果评分，轨迹用于诊断。[Agent 评测答法](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)
- **用边界值判结果。** 150,000,000 除以十亿为 0.15，按十进制半位向上得 `0.2 B`。用向下截断会得到 `0.1 B`，漏空格也会失败。再检查数值行全量和 A 列保真。

## 第 6 题 · TypeScript 手撕 LRU Cache，并讲清它在 Agent 中缓存什么

用 TypeScript 实现容量为正整数的 `LRUCache`。命中 `get(key)` 返回值并刷新访问顺序，未命中返回 `-1`。`put(key, value)` 插入或覆盖，超容量逐出最久未使用的键。两项操作平均 `O(1)`。原题容量为 1–3000，键为 0–10,000，值为 0–100,000，总调用最多 200,000 次。力扣 146 样例容量 2，写入 1、2 后读 1，再写入 3。请指出下一次读 2 的结果，写出实现并说明动态 MCP 工具为什么需要类似淘汰策略。[力扣原题与样例](https://leetcode.cn/problems/lru-cache/)

### 理论分析

**用哈希表定位节点，双向链表维护使用顺序，读命中和覆盖都把节点移到最近使用端。**

- **谁被淘汰。** `put(1,1)`、`put(2,2)`、`get(1)` 后，从最旧到最新为 `2,1`。写 3 时删 2，因此 `get(2) == -1`。只在写入时更新顺序会误删 1。
- **覆盖怎样计容量。** 找到同一个节点就更新值并摘挂，容量不变。未命中读取也不占容量。哈希查找平均 `O(1)`，移动节点和淘汰固定次数，空间 `O(capacity)`。公开题解给出相同不变量。[公开解法](https://leetcode.cn/problems/lru-cache/solutions/12711/lru-ce-lue-xiang-jie-he-shi-xian-by-labuladong/)

### 代码实践

用 `Map<number, CacheNode>` 定位节点，带哨兵的双向链表维护访问顺序。`root.next` 指向最久未使用的节点，`root.prev` 指向最近使用的节点。命中或覆盖时摘下原节点并挂到最近使用端。超容量时摘下最旧节点，再删掉 Map 中的同一键。以下代码包含力扣原题完整样例。

```typescript
class CacheNode {
  prev: CacheNode = this;
  next: CacheNode = this;

  constructor(
    readonly key: number,
    public value: number,
  ) {}
}

class LRUCache {
  private readonly nodes = new Map<number, CacheNode>();
  private readonly root = new CacheNode(-1, 0);

  constructor(private readonly capacity: number) {
    if (!Number.isInteger(capacity) || capacity <= 0) {
      throw new RangeError("capacity must be a positive integer");
    }
  }

  get(key: number): number {
    const node = this.nodes.get(key);
    if (node === undefined) return -1;

    this.unlink(node);
    this.appendNewest(node);
    return node.value;
  }

  put(key: number, value: number): void {
    const existing = this.nodes.get(key);
    if (existing !== undefined) {
      existing.value = value;
      this.unlink(existing);
      this.appendNewest(existing);
      return;
    }

    const node = new CacheNode(key, value);
    this.nodes.set(key, node);
    this.appendNewest(node);

    if (this.nodes.size > this.capacity) {
      const oldest = this.root.next;
      this.unlink(oldest);
      this.nodes.delete(oldest.key);
    }
  }

  private unlink(node: CacheNode): void {
    node.prev.next = node.next;
    node.next.prev = node.prev;
  }

  private appendNewest(node: CacheNode): void {
    const previousNewest = this.root.prev;
    node.prev = previousNewest;
    node.next = this.root;
    previousNewest.next = node;
    this.root.prev = node;
  }
}

const cache = new LRUCache(2);
cache.put(1, 1);
cache.put(2, 2);
const actual = [cache.get(1)];
cache.put(3, 3);
actual.push(cache.get(2));
cache.put(4, 4);
actual.push(cache.get(1), cache.get(3), cache.get(4));

const expected = [1, -1, -1, 3, 4];
if (JSON.stringify(actual) !== JSON.stringify(expected)) {
  throw new Error(`expected ${expected}, got ${actual}`);
}
console.log(actual);
```

本次用 TypeScript 编译器的 `--strict` 模式编译后，在 Node.js 中运行。原题的五次读取依次返回 `[1, -1, -1, 3, 4]`。覆盖会刷新顺序、容量为 1 时正确保留值 0 并淘汰旧键、非法容量被拒绝，这三项边界检查通过。

### 本工程改进设计

一个取消入口时，给单个受治理命令加暂停即可。存在多个同类受治理写入口时，可复用统一的暂停／恢复机制，避免每条动作各自实现确认状态。航空用例拥有政策和订单事实，网关消费确认，航空服务原子校验版本并按命令 ID 去重。命令状态未知时先按 ID 查权威回执，再按结果决定恢复或反馈。

```text
quote = airline.decide_cancel(user, reservation, reason)
if quote.denied: return refusal(quote.reason)
command = admission.freeze(user, quote.order_version, quote.refund, quote.digest)
confirmation = confirmation_store.await_matching(command)
if confirmation.rejected: return declined
receipt = airline.cancel_once(command.id, command.order_version, confirmation)
return complete_only_after(airline.read_back(receipt))
```

验收先按原始任务 19 和 1 各回放一次。19 在确认前零写入，确认后读回同一订单的取消状态与对原 169 付款的退款冲销。1 只读 `Q69X3R` 并解释拒绝，零取消或退款写入。再在通过的 19 上使用待确认期间订单版本变化和重复提交两个反例，断言过期选择零写入，已成功的命令重复投递只返回同一回执。这是基于上游代码与真实基准数据的设计推演。
