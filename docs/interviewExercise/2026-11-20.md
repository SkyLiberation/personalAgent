### 理论分析

**模型按逐工具 Schema 提议调用，运行时按本轮定义检验参数，能力服务再核对业务约束和权限。** 传输层先检验调用 ID、工具名和参数对象。形状校验检查类型、必填项和范围。领域校验再检查资源归属及跨字段约束。默认值由声明它的执行边界应用。失败回执带调用 ID、出错字段和可修正原因，模型可以重提该调用。

### 理论分析

**批准应绑定用户看到的那个动作，并由执行前的确定性检查消费。** 预览支持异步确认时，把主体、资源和规范化参数封入已准备的命令。确认请求带该命令的标识或摘要，执行端比对当前待处理对象和权限。条件不符就维持待确认或拒绝，命中已完成的同一命令则读取原回执。

例如两个确认卡片分别显示“保存来源 A”和“保存来源 B”。A 卡提交 B 的 `turn_id`和 A 的预览摘要，服务端比对不符就返回冲突。一起核对身份、目标和摘要的成本集中在需要人工决定的写操作。内存中的一次性确认可借用挂起调用本身绑定范围。 [一次性批准分支](https://github.com/deepseek-ai/deepseek-harness/blob/2e39e70496aa02986ca6a820c5d497e816b69d7e/packages/sandbox/sandbox/src/escalation.ts#L233-L260)

## 第 3 题　哪个工具可以并发，遇到写操作怎样安排顺序？

### 理论分析

**只有彼此独立且执行效果可重叠的调用才并发，独占动作形成顺序屏障。** 检查参数是否依赖前一步结果、能力是否声明允许并发、以及同资源写入和下游限流是否允许重叠。用有界执行池控制并发量，用调用 ID 和提议顺序收集结果。

手写例子。`读 A、读 B、写 C、读 C` 中，A、B 可同时开始，写 C 等两读完成，最后读取 C 的新版本。若写 C 的参数必须根据 A 的实际内容生成，模型应在看到 A 的结果后再提议写 C。直接并发可能把尚未读取的内容当作确定输入。 [并发分类](https://github.com/deepseek-ai/deepseek-harness/blob/2e39e70496aa02986ca6a820c5d497e816b69d7e/packages/core/tools/src/pipeline.ts#L99-L115) · [批内屏障和补位](https://github.com/deepseek-ai/deepseek-harness/blob/2e39e70496aa02986ca6a820c5d497e816b69d7e/packages/core/tools/src/batch.ts#L186-L219)

## 第 4 题　工具超时以后，什么时候可以自动重试？

**面经追问。** 牛客 Coding Agent 一面自述（7 月 6 日面试）问到命令超时、文件不存在和权限不足时，怎么选择重试或恢复。 [牛客 Coding Agent 一面](https://www.nowcoder.com/feed/main/detail/5733bf8605d44262a596ad7ba738e737?toCommentId=22770379)

### 理论分析

**超时只证明调用方等不到结果，自动重试要另查操作是否可安全重复。** 先区分尚未启动、已确认停止和外部结果未知。纯读可以在剩余预算内按策略重试。写操作若具备下游幂等约束，可用同一个操作键查询或重提。既无法核对结果、也无幂等契约时，停在待核对，等外部回读或人工处理。
