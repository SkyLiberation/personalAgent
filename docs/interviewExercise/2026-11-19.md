## 第 1 题 服务重启后，Agent 如何接续会话并避免重做副作用？

面经追问服务重启后如何加载未完成任务、保持一致性。Anthropic 的 Claude Managed Agents 岗位明确要求建设长期会话的持久化与断线恢复。 [牛客拼多多面经 02、03，2026-09-09、09-08](https://www.nowcoder.com/discuss/929182554303787008?sourceSSR=post&weFlow=true) · [Anthropic 官方岗位](https://job-boards.greenhouse.io/anthropic/jobs/5395767008)

### 理论分析

**恢复时按原命令核对外部结果。会话记录能恢复用户目标，原命令及其回执决定这一笔副作用还需要做什么。** 以「在项目群发送一次归档通知」为例。服务端先保存命令 C17，冻结发送账户、目标群、消息正文和幂等键 `notice-17`。派发状态持久化后才发网络请求。外部服务返回消息 ID 后，服务端把它写成 C17 的回执。重启后按 `session_id` 恢复对话，按命令 C17 核查执行。一个会话可以合法发送多条不同通知，所以幂等键要绑定具体操作，并跨重启复用。

| 重启后读到的记录 | 恢复动作 |
| --- | --- |
| C17 已保存，尚未登记派发 | 在原授权仍有效时，可按原命令首次派发。前提是正式执行路径都要求先持久化派发状态。 |
| C17 有已提交的成功回执，载明消息 ID | 读回消息 ID，继续生成答复。 |
| C17 已登记派发，尚无回执 | 标为结果未知。若权威查询能按原操作查到消息，补写回执。若查询结果明确证明原操作未执行且不会晚到，重新校验原授权后可执行。服务方也可以通过有效的幂等契约允许原样重试。 |
| C17 结果未知，外部既无法核对也无法幂等重试 | 保留未知状态，暂停这项写入，把命令和现有证据交给人核对。 |

最危险的时点是群里已经显示通知，Agent 却在保存回执前宕机。此时本地只知道 C17 可能执行过。恢复如果把这条通知交给模型重新规划，重新生成的命令和幂等键会被外部服务视为一次新发送。正确做法是取回 C17 原本的身份和正文，再根据外部证据处理。

## 第 3 题 BM25 和向量检索怎样融合，什么时候值得调整现有排序？

面经追问双路结果如何融合、收益发生在哪一环。Binance 的 AI Agent Engineer 岗位明确要求 RAG 与向量检索的应用经验。 [牛客淘天面经 03，2026-07-23](https://www.nowcoder.com/discuss/928330146736537600) · [Binance 官方岗位](https://job-boards.greenhouse.io/binance/jobs/5002667101)

### 理论分析

**先在同一可见语料上做双路召回，再按名次融合，最后用同一批标注查询检验取舍。** BM25 擅长错误码和专名，向量有助于找到同义改写。标准 RRF 对候选在每路的名次 `r` 加 `1/(k+r)`，缺席加零。这样不依赖两个分数的量纲。

手写例中，查“E42 导出中断”，A 只在关键词路排第一，C 只在向量路排第一，B 两边均排第二。用 `k=60` 时，A、C 各约 0.0164，B 约 0.0323，B 排前。若真正需要的是只有 A 才有的错误码操作说明，这种排序也可能有损。检查精确项与同义项的分层指标，命中损失时回看分路深度、融合和重排各自的贡献。

## 第 4 题 Agent 的 Web 流式接口怎样推送进展，断开后怎样避免重复执行？

### 理论分析

**提交输入和订阅进度是两个操作。** Runtime 把公开进度、工具结果和最终交付写成可排序的事件，客户端按会话或运行身份订阅。用 SSE 时，可用 `event` 区分事件类型，给已提交事件写入 `id`，重连时携带最后收到的事件 ID。服务端校验归属后补齐事件，历史缺口超出保留范围时用快照恢复视图。

例如，浏览器看完会话 S 的第 12 条事件就断开。它重开 S 的事件流，把第 13 条及后续事件补到视图上。提交的响应丢失时，用原请求 ID 确认输入是否已受理。用户在执行中追加「改查今年的目录」，是一次 steering 操作，可以在原轮次的下一步生效。将请求排到下一轮时，才会在当前轮结束后开始新的执行边界。
