# Agent 开发每日面试训练要求

## 交付

每天出七道中文面试题，各附完整答案。第 1 至第 4 题考查 Agent 开发理论与工程设计，第 5 题是 AI 辅助编程实践题，第 6 题是 TypeScript 手撕代码题，第 7 题是面向 Agent 业务场景的代码设计题。按上海时区取日期，将完整题组保存为 UTF-8 Markdown 文件 `docs/interviewExercise/YYYY-MM-DD.md`。缺少目录时创建，同日重试复用同名文件。Codex 运行结果同时给出完整题组和本地文件路径。

## 选题与来源

- **出题前先读考点总结。** 阅读[考点总结](考点总结.md)，确认历次已设计的考点。发现定稿题组尚未收录时，先按原题补齐，再选题。
- **新题不能重复已有考点。** 将每道题要求候选人作出的主要技术判断和关键边界，与历次题目及同批其他题目逐项比较。如果仍用同一判据和处理方式，换场景、数据、工具、开源实现、编程语言或问法也算重复，须换题。同一大主题可继续考查，题干须交代会改变答案的条件，并要求新的判断或解法。手撕代码题按题意、约束和核心解法判断是否重复。
- **先从面经和 JD 确定要考的能力。** 每道题先核对公开 Agent 开发面经里的具体问题或追问，再用岗位描述（JD）中的对应职责判断岗位相关性。题稿写明哪条面试问法和哪项岗位职责导出了本题，分别附原页链接及可查日期。面经优先选近期、问法可核对的复盘。JD 以中国国内职位为主，优先用招聘方在 BOSS 直聘等平台发布的岗位原页或企业官方招聘页。任一选题依据缺失时换题。
- **以技术问题定义考点。** 模块设计题明确要考的职责、接口或协作边界。能力设计题明确要考的工作机制、适用条件、取舍或验证方式。第 5、6 题分别明确要考的工程实践和核心算法。用「首次成交设备」作场景时，可考查 Text-to-SQL 能力怎样获取指标定义、按事件粒度生成查询并核验结果。
- **先定考点，再选例子。** 根据面经和 JD 写清主问题、候选人要作出的技术判断，以及哪些条件会改变答案。再选业务场景给出用户目标、正常流程、已有输入、技术约束和可验证的结果。一个案例只覆盖部分考点时，用第二个案例、官方示例或标明假设的推演补齐。找不到完全匹配的业务案例时，可以用教学场景，保留原定的技术考点和关键边界。禁止从本工程已有设计或测试倒推题目后再补面经与 JD。
- **主案例优先选完整工作流。** 优先找业务团队实践、可核对的产品流程、公开数据集中的具体任务、官方示例或开源仓库的实际用例。选择能说明用户想得到什么、系统正常怎样交付、条件变化后怎样判断的材料。Issue、报错单和缺陷讨论默认用于解释故障分支。考点本身是诊断或缺陷修复时，可以用 Issue 作主材料，同时交代正常流程及用户后果。题组避免反复用同类报错承载原理和设计题。
- **按材料类型注明证据。** 引用真实场景时附来源及样本编号、记录位置或提交号，核对输入、约束与适用的结果或评分规则。删减和匿名化须保留会改变判断的原始条件。改编和教学推演要标明新增条件，可构造最小输入、正例和反例，并用公开契约或已核对的实现支持预期判断。无法证明的现网行为、量化效果和运行结果列为待核实。
- **公开答法。** 每道题拟定后、定稿前，用原问法或同义问法检索公开回答、讨论或工程复盘，阅读原文，提取其中的判断和取舍。附来源链接。只有近似答法时，交代它能支持哪个考点及与本题的差异。找不到时，记录检索范围。
- **第 5 题的实战依据。** 定稿前交叉核对至少两份相互独立的公开一手材料，如开发者复盘、工程团队实践报告、仓库提交或配置。引用能直接支撑场景的材料，说明实践者遇到的问题、做法和生效条件。标明哪些是可复现检查、有对照的结果或作者自述。有量化数据时写清指标和比较口径。缺少量化指标时引用可核验的输入、代码差异、日志或实际观察。
- **第 5 题的实践主题。** 每天换一个具体场景，轮换全局与目录 `AGENTS.md`、Skill 的触发和步骤、帮助模型理解代码库的模块职责与入口、Codex 与 Claude Code 的分工和交叉审查、子代理的使用时机与交接、并行或上下文隔离。结合实战材料解释对正确率、耗时、返工或协调成本的影响。
- **第 6 题的面试来源。** 选用 Agent 开发面试中实际出现过、题意可核对的手撕代码题。附面经或公开面试材料原页，注明可查的岗位、时间及原题位置。依据原题还原输入、输出和关键约束。原题附有代码时，标明所用片段的来源。再查这类算法在 Agent 工程中的实际用法。面试来源或算法用途缺少可核验依据时换题。
- **第 7 题的设计主题与开源依据。** 先定要考的模块职责、能力机制或设计取舍，再用业务实践、公开任务或标明假设的教学场景给足条件。按「讲解依据」查找能支撑关键机制的成熟开源实践，固定 Git 提交，沿实际入口核对装配、触发和消费链。开源实现可以来自同类问题，说明适用前提及迁移差异。轮换生命周期 Hook、中间件、分层、面向切面、业务逻辑与技术机制分离、Saga 等主题。

## 讲解依据

- **标准做法以固定版本的开源源码为准。** 用 [`reference-open-source-solutions`](../../.agents/skills/reference-open-source-solutions/SKILL.md) 核对实际实现，优先查 DeepSeek Harness，找不到同一机制再查其他成熟的开源项目或组件。代码实践应有足以核对关键链路的固定实现，理论分析保留该实现没有覆盖的考点，注明其依据或推演条件。遇到证据缺口时，说明已查范围和能确认的结论。
- **personalAgent 用于题目确定后的工程对照。** 将本工程的设计、代码和评测用于「当前工程的不足」与「本工程改进设计」，说明在同一业务条件下怎么做、有何差距或证据缺口。从[面试索引](../interview/INDEX.md)定位材料，按[维护规范](../interview/00-material-maintenance.md)核对生产代码、运行轨迹和评测。注明 Git 提交及相关未提交改动。第 5 题也可用本地提交差异或可复现检查定位问题。

## 每题的答案结构

题稿和运行结果都用二级标题标记第 1 至第 7 题。每题依次使用以下四个三级标题，题组正文到第 7 题结束。

1. **理论分析。** 开头用一句可直接口述的话回答问题，后续**按面试考点逐条讲**。
   - 按事先确定的技术考点逐条作答。每条用一个具体的技术判断命名，例如「工具发现模块怎样判定目录已完整」，说明判断依据及选错后的影响。主例没有覆盖的边界，用题干中明确标记的追问或答案中的推演补充。用公开答法补充取舍，来源附在对应内容末尾。
   - 每条先给结论，再说明机制、成立条件或取舍。涉及识别、比较、选择、阻断或停止时，交代检查什么输入或状态、用什么判据、命中后做什么。用真实材料中的数据或已标明假设的前后状态走一遍，至少说明一个典型错法及其后果。
2. **代码实践。** 用固定 Git 提交的实际源码，从正式入口、装配、核心处理讲到结果怎样被消费，附可复核坐标。选一个具体场景，展示必要的字段、请求或前后状态，标明示例与实际运行证据。使用 DeepSeek Harness 时，先归纳与考点相关的机制，再逐点说明输入、触发条件、判定、动作和下游消费，覆盖默认行为、可选装配和影响结果的失败或回退分支。第 5 题还要用开源指令、Skill、配置或源码说明如何拆任务、约束修改范围、审查差异和验证结果。
3. **当前工程的不足。** 用本地依据说明 personalAgent 在同一场景下的做法、已确认的不足或证据缺口，以及对结果的影响。用一句话给出改进方向，链接到本题的「本工程改进设计」。
4. **本工程改进设计。** 针对上节的一个问题，说明借鉴的开源机制、最小改动、源码落点和责任边界。写清触发条件、输入、输出和消费方，交代如何隔离变化并保护受影响的准入、执行、状态与恢复。给出可执行的验证方法、通过条件和至少一个反例，标明已证结果、待验证内容和引入前提。证据只够确认缺口时，先设计验证。超出工程业务范围时，说明适用边界。

第 6、7 题在上述结构中补充各自的交付要求。

- **第 6 题给出可运行的 TypeScript 算法实现。** 讲清解题思路、时间和空间复杂度及边界条件，运行 TypeScript 解答并用来源可查的样例验证结果。结合一个实际 Agent 实现，指出算法用在什么环节、处理什么输入、结果由谁消费，以及它解决了什么工程问题。附固定版本的源码坐标。
- **第 7 题基于开源实践给出服务于业务的代码设计。** 先用固定版本的源码说明开源项目怎样处理同类问题，附入口、装配点和消费方的源码坐标。再对照题干的业务目标与约束，说明哪些机制可复用、哪些需要调整以及理由，并比较更简单的做法。给出关键接口或伪代码，讲清模块职责、调用顺序和适用的失败处理。用题干中的业务用例说明如何验收用户结果，注明示例是原始用例还是教学推演。禁止编造开源实现或实测数据。

## 表达与排版

- 每节开头先给核心判断，适度加粗结论和判据。一段讲一个观点。并列考点用项目符号，流程用编号。具体例子、已有证据和待验证方法分别成段，源码坐标放在对应段落末尾。重复标题可设独立锚点。

## 交付检查

- **确认考点查重并及时登记。** 定稿前按最终题干和答案逐题确认技术考点没有与旧题或同批其他题重复。保存定稿题组后，必须在同一次生成任务中立即更新[考点总结](考点总结.md)，逐题登记日期、题号、技术考点和判断依据。同日改题时按日期和题号更新对应条目。核对总结与定稿题组一致后再交付。
- **回查考点覆盖。** 每题能否从面经原问和 JD 的相关职责说明选题理由？逐条对照事先确定的主判断和关键边界，确认没有因为材料覆盖不全而省略。查主案例是否讲清正常流程，Issue 是否出现在诊断或故障分支，本工程材料是否用于题目确定后的对照。
- **只读题干。** 能否理解用户预期结果、正常流程和变化，并看出候选人要解决的技术问题及约束？原始事实是否可回查，改编或教学推演的条件是否已标明？
- **只读理论分析。** 换一个业务场景后，能否独立说清每个考点对应的技术判断？能否用题中材料或明确的推演解释判据和后果？核对代码实践是否展开影响结果的机制与分支，示例能否走到实际消费者。
- **对照证据。** 逐题回查场景来源、样本或记录位置，以及输入、关键数据和结果。核对面经、岗位原页、七题公开答法或检索记录、第 5 题两份独立一手材料及固定源码坐标。检查结论是否在证据范围内，本地不足、候选改进和验证结果是否一一对应。
- **核对第 6、7 题。** 第 6 题的原题能否在 Agent 开发面试材料中查到，TypeScript 实现能否按原题约束运行并通过可查样例，算法用途能否在实际 Agent 链路中定位？第 7 题的关键机制能否用固定开源源码核对，怎样从开源案例迁移到本题，选型和失败处理是否符合业务条件，验收能否证明用户结果？
- **保存后回读。** 核对 UTF-8、题数、题型、四个答案部分的顺序、各题不足到本题设计的链接、来源链接和排版。确认运行结果同时给出完整题组和文件路径。
