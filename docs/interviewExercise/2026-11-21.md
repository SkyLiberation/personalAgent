### 理论分析

**把变化放到旧历史之后，尽量保住从请求开头连续相同的部分。** 比较同一路由的相邻实发请求，查看 System Prompt、工具声明和有序历史的第一处差异。即使差异后面的历史逐字相同，模型计算它时也会用到改过的前文。遇到工具撤权时，应及时更新可用工具和准入。最后结合服务方返回的缓存读量、首 Token 延迟和用户结果验收。

下面用剩余任务预算从 9,000 降到 8,000 个 Token 举例。这个数字是给模型调整下一步策略的提示，运行时按实际用量和配置决定调用是否放行。

```text
覆盖早期值
上次   [系统规则] [预算 9000] [已有历史]
本次   [系统规则] [预算 8000] [已有历史] [工具结果]
相同   [系统规则]

保留旧消息并追加新值
上次   [系统规则] [已有历史] [预算 9000]
本次   [系统规则] [已有历史] [预算 9000] [工具结果] [预算 8000，以此为准]
相同   [系统规则] [已有历史] [预算 9000]
```

第二种组织里，旧值仍在历史中。末尾消息指明当前使用 8,000，服务方则可继续复用实际请求里相同的前缀。

### 理论分析

**执行方提交完整结果，模型先看预算内的预览和可重读引用。** 判断时先量化可发送的内容，保留调用 ID、执行状态和边界提示。超限且原件保存成功时，用引用加预览替换模型可见内容。结果有明确结构时优先保留关键字段，普通日志可以保留首尾，让模型按需读中段。

例如 300 KB 的日志前面是启动参数，最后才有业务诊断。只留前 50 KB 会让模型先补一次读取。首尾预览能显示诊断，模型再按原引用搜索中间记录。保存失败时，必须让调用方知道有效的读取范围，并沿既有容量检查处理大输出。 [预算与卸载分支](https://github.com/deepseek-ai/deepseek-harness/blob/2e39e70496aa02986ca6a820c5d497e816b69d7e/packages/spill/spill-policy/src/index.ts#L91-L131)
