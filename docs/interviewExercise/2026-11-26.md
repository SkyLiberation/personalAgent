## 第 1 题｜怎样为并行测试多个客户应用的 Agent 设计沙箱？

**题干。** AI 测试平台 Lark 接收开发者的自然语言需求，生成并运行端到端测试，把截图和日志随测试报告交付。早期在本机或常规 CI 执行。后来要同时跑大量客户用例，有时需要访问客户的真实应用和数据，也有用例要在执行环境内启动 Docker 来拉起客户开发环境。团队改为按测试创建临时 E2B 沙箱，从包含浏览器和测试工具的模板启动，结束后销毁。请设计从分配环境到交付报告的链路。**设计追问。** 同一团队如果只做离线仓库检查，能否选择更轻的方案？若分配环境失败，或测试进程超时但沙箱还活着，分别怎样处理？这些是面试追问，案例没有公开对应故障日志。[Lark 公开实践与团队采访](https://e2b.dev/customers/lark-case-study)

### 理论分析

**按测试的信任边界分配环境，以任务身份明确文件、凭据和出网权限，并用外部控制面限制资源、收取产物和确认回收。**

- **隔离单位怎样选。** 任务使用 `tenant_id`、`run_id` 和授权的环境模板，由控制面分配独立实例。Lark 的客户间互不信任，还有在环境内运行 Docker 的要求，因此将客户代码和 Docker 放入独立内核的 microVM，不把宿主 Docker socket 授权给它。单用户、可信仓库里的离线检查，可以在满足文件和进程边界时用本地 OS 沙箱。容器可提供独立文件和进程视图，通常仍共享宿主内核。选型取决于信任和运行需求。
- **文件、网络和凭据怎么约束。** 挂载或复制本次测试所需的代码和数据快照，写入留在任务临时空间，只将批准的截图和日志发布给本租户。宿主只读仍可能泄漏可读文件。运行需访问客户应用时，出网由沙箱外的策略限定到批准目标。对敏感凭据优先由代理按目的地注入，或发限资源、限时间的测试令牌。离线检查关闭出网，模型所在服务的网络连接由自己的策略管理。把长期密钥放进共享模板，会使随后启动的其他租户实例继承它。
- **并发和资源怎样约束。** 在调度时检查租户并发配额，启动时给环境 CPU、内存、磁盘和时间上限。若允许启动容器或大量子进程，再单独限制进程数量及输出体积。PID 命名空间隔离进程视图，配额由相应执行层强制。达到单任务上限时，只停止该任务并报告原因。
- **失败和回收怎样判断。** 分配失败或环境未就绪时，返回环境失败并保持零测试派发。环境就绪后的测试失败、超时或策略拒绝，要依据实际调用事实回传。先将授权产物交付，再结束执行环境、撤销凭据，并由控制面确认实例不可达且资源已回收。客户端停止等待或收到删除请求的成功响应时，回收仍可能在进行。[公开答法与不同部署条件](https://claude.com/resources/articles/enterprise-guide-to-securing-coding-agents#containing-agent-actions-with-sandboxing)

### 理论分析

**先独立求首次访问和首次交易，再从实际首次交易的会话取设备。**

- **总体和日期。** 对 `20170201–20170228` 分区内全部会话求每个访客最早访问日。另展开 `hits`，只保留有交易 ID 的命中，再求最早交易日。两者在访客上取交集计算日差，`0` 是合法的当天成交。若先过滤交易再取最早访问，首次访问与成交都从交易数据中算，四天会被误报成零天。
- **设备归属。** 交易设备必须来自匹配成交事件的会话。官方 SQL 以访客和首次交易日连接设备，同日跨设备时日期无法提供唯一键。若新增唯一第一笔的需求，使用 `visitStartTime` 与毫秒级 `hits.time` 比较实际事件时间，再依据业务认可的稳定键处理同刻并列。参考论文用真实方言、数据和执行结果评价 SQL，SQL 可执行只能说明数据库接受了请求。[公开答法与基准论文](https://arxiv.org/abs/2411.07763) · [日期联接和日差](https://github.com/xlang-ai/Spider2/blob/cafb867313aab4e674652054198f383cf4018943/spider2-lite/evaluation_suite/gold/sql/bq001.sql#L14-L52) · [hit 毫秒偏移](https://github.com/xlang-ai/Spider2/blob/cafb867313aab4e674652054198f383cf4018943/spider2-lite/resource/documents/google_analytics_sample.ga_sessions.md#L181-L190)

## 第 6 题｜TypeScript 手撕：给出依赖顺序并检测环

**选题依据。** 字节 AI Agent 开发岗 2026-09-10 面经 01 第 9 问要求依赖拓扑排序或环检测。百度 Agent 引擎 J103885（2026-07-29）要求 TypeScript／Node.js、异步编程和 Agent 引擎开发。[面经](https://www.nowcoder.com/discuss/930603820395036672?sourceSSR=post&weFlow=true) · [国内 JD](https://talent.baidu.com/jobs/detail/SOCIAL/d56ce9b0-296b-4615-9497-115968d4fc14)

**题干。** 面经没有公布输入签名，采用对应的力扣 210 输入契约。给 `n` 个编号 `0..n-1` 的任务，`[a,b]` 表示先做 `b` 才能做 `a`，输出任意完整合法顺序，无法完成时返回 `[]`。`1≤n≤2000`，端点合法，无自环或重复边。原样例 `n=4`，边为 `[[1,0],[2,0],[3,1],[3,2]]`。考虑某些任务完全无依赖，或图中只有一部分陷入环。[原题与样例](https://leetcode.com/problems/course-schedule-ii/)

### 理论分析

**用 Kahn 算法逐个取出入度为零的任务，最后按出队数判断能否完成全图。**

- 建边 `b → a`，先把所有零入度节点入队。处理 `0` 才能释放 `1`、`2`。两者都处理完才释放 `3`。漏扫孤立节点会把合法输入错报为环。
- 如果队列处理完仍有节点，剩余子图中每个节点都还有前置依赖，沿依赖一直找就会遇到环。只处理完无环部分时也要返回空。时间和空间都是 `O(n+m)`，其中 `m` 为边数。使用下标推进队列，避免逐次搬移数组。[公开答法](https://neetcode.io/solutions/course-schedule-ii)

### 代码实践

```typescript
function findOrder(numCourses: number, prerequisites: number[][]): number[] {
  const downstream: number[][] = Array.from({ length: numCourses }, () => []);
  const indegree = Array<number>(numCourses).fill(0);

  for (const [course, prerequisite] of prerequisites) {
    downstream[prerequisite].push(course);
    indegree[course]++;
  }

  const order: number[] = [];
  for (let course = 0; course < numCourses; course++) {
    if (indegree[course] === 0) order.push(course);
  }

  for (let head = 0; head < order.length; head++) {
    for (const course of downstream[order[head]]) {
      indegree[course]--;
      if (indegree[course] === 0) order.push(course);
    }
  }
  return order.length === numCourses ? order : [];
}
```

将这段实现取出用 `tsc --strict` 编译并交给 Node.js 验证。三个力扣原样例分别输出 `[0,1]`、`[0,1,2,3]`、`[0]`。另查有环加孤点时返回 `[]`，孤立任务与合法子图并存时仍输出全部节点。

**Agent 工程使用。** Google Lightflow 的 CLI 从清单装配 Runner，编译器验证阶段并把 `run_after` 传给 Python `graphlib.TopologicalSorter`，循环依赖报 `EngineError`。实验预览按编译顺序消费各阶段，执行路径再根据依赖状态执行或跳过。季度营收样例里先查 SQL，再分析差异，审核批准评论后才允许渲染。这是依赖排序的实际应用，题中 TypeScript 是独立算法实现。[CLI 入口](https://github.com/google/lightflow/blob/2940cc4b4ad702d20b16c1a76a5716b223a9bf98/lightflow/__main__.py#L19-L24) · [编译和判环](https://github.com/google/lightflow/blob/2940cc4b4ad702d20b16c1a76a5716b223a9bf98/lightflow/compiler.py#L512-L534) · [预览消费](https://github.com/google/lightflow/blob/2940cc4b4ad702d20b16c1a76a5716b223a9bf98/lightflow/dry_run.py#L318-L387) · [执行消费](https://github.com/google/lightflow/blob/2940cc4b4ad702d20b16c1a76a5716b223a9bf98/lightflow/lib.py#L1300-L1346) · [营收流程样例](https://github.com/google/lightflow/blob/2940cc4b4ad702d20b16c1a76a5716b223a9bf98/examples/quarterly_revenue_brief/lightflow.yaml#L19-L57)

## 第 7 题｜代码设计：旅行 Agent 如何撤销只成功了一半的组合预订？

**选题依据。** 字节剪映 Agent 开发岗一面复盘于 2026-08-03 发布，首问考查工作流原子性并追问失败后的回滚实现。百度 Agent 引擎 J103885（2026-07-29）负责异步状态持久化及策略强制执行。设计题聚焦跨服务补偿由谁拥有。[面经](https://www.nowcoder.com/discuss/913899716599873536) · [国内 JD](https://talent.baidu.com/jobs/detail/SOCIAL/d56ce9b0-296b-4615-9497-115968d4fc14)

**题干。** DTM 公开的实际用户案例是去三亚机票、三亚酒店和返程机票的组合预订。原流程按各供应商分别预订，要求三项全部成功，否则取消已成功项。供应商都提供对应撤销接口，独立项需要并行避免错过库存，结果确认可能从 1 分钟到 1 天。现设计一个旅行 Agent 入口接收这个用户目标。如果某项确定失败、另一项已成功、还有一项处于进行中，怎样编排补偿并对用户报告？再考虑供应商改成不可撤销时，原选型是否成立？[案例原文](https://github.com/dtm-labs/dtm.pub/blob/79c1cc851ff633b0e38486f47e59e0b59752d6d0/docs/practice/saga.md#L96-L142) · [不可撤销边界](https://github.com/dtm-labs/dtm.pub/blob/79c1cc851ff633b0e38486f47e59e0b59752d6d0/docs/practice/saga.md#L145-L174)

### 理论分析

**Agent 生成组合请求，业务协调器负责履约与补偿，三个权威订单共同决定对用户的状态。**

- **什么时候允许补偿。** 三项都成功才能报告组合已确认。一项确定失败时，已确认的订单进入补偿。进行中分支按供应商的订单状态和取消契约收尾，仍可能留下有效订单时不能报告已全部撤销。补偿失败要保留进行中或需人工处理状态。退款和取消只操作本组合的订单。
- **什么时候换更简单的做法。** 若上游已有原子组合预订接口，直接调用它。各项独立且有可用撤销接口时才由 Saga 对接。不可撤销项需要留到可安全承诺的阶段，或者改用供应商预留／确认协议。两个都可能失败且不可撤销的写入无法由 Saga 保证全成全撤。[公开答法与补偿注意事项](https://temporal.io/blog/saga-pattern-made-easy)

### 代码实践

**已核实的开源链路。** DTM 调用者用 `NewSaga` 和 `Add(action, compensate, payload)` 绑定同一分支的正反动作，经 `Submit` 进入服务。服务生成分支并按持久状态推进。默认串行，有相应配置和独立项才并发。分支确定失败切入 `aborting`，处理该分支和先前可能已产生效果的分支，所有所需补偿成功后标记为失败终态。收到 `ONGOING` 会更新调度，案例配置为 60 秒，并由分支先读取已建订单再查供应商。DTM 的补偿接口仍需自己守住空补偿与并发边界。[SDK 入口](https://github.com/dtm-labs/dtm/blob/18146ee53bafbf094b1a5f12ca7e8a29bdb57edd/client/dtmcli/trans_saga.go#L15-L63) · [接纳提交](https://github.com/dtm-labs/dtm/blob/18146ee53bafbf094b1a5f12ca7e8a29bdb57edd/dtmsvr/api.go#L22-L42) · [持久分支装配](https://github.com/dtm-labs/dtm/blob/18146ee53bafbf094b1a5f12ca7e8a29bdb57edd/dtmsvr/trans_process.go#L68-L101) · [依赖与补偿选择](https://github.com/dtm-labs/dtm/blob/18146ee53bafbf094b1a5f12ca7e8a29bdb57edd/dtmsvr/trans_type_saga.go#L92-L122) · [失败和终态](https://github.com/dtm-labs/dtm/blob/18146ee53bafbf094b1a5f12ca7e8a29bdb57edd/dtmsvr/trans_type_saga.go#L209-L267) · [进行中调度](https://github.com/dtm-labs/dtm/blob/18146ee53bafbf094b1a5f12ca7e8a29bdb57edd/dtmsvr/trans_status.go#L216-L260)

**本题设计。** 供应商适配器返回业务订单引用和权威状态，协调器负责组合状态，Agent 入口消费投影。三项具有可撤销性后才接受全成全撤的契约。调用顺序示意如下。

```text
TripCapability.submit(approvedTrip) -> tripId
BookingPort.reserve(part, operationId) -> pending | confirmed(ref) | rejected
BookingPort.status(ref) -> pending | confirmed | rejected | cancelled
BookingPort.cancel(ref, cancellationId) -> pending | cancelled | needs_attention
TripCoordinator.advance(tripId) -> confirming | booked | compensating
                                  | rolled_back | needs_attention
```

验收用三亚原案例的三个受管订单。全成时各供应商均有且只有一个有效订单。返程确定失败时，模拟已成功的酒店和仍进行中的去程，最终只有确认三方皆无有效订单才允许 `rolled_back`。若去程后来确认且取消被拒，结果保持待处理并明确列出订单。这个故障排列是设计验证，案例未公布供应商的逐次运行日志。

### 当前工程的不足

personalAgent 现有研究流程把产物综合、验证和运行状态放入固定业务流程，通用工具执行边界保存动作事实。没有查到旅行组合预订的正式能力，也没有识别到必须使用跨供应商补偿的现有用户结果。只在存在该业务前提时考虑[独立组合能力](#q7-design)。[业务执行分段](../../src/personal_agent/application/research/service.py#L362-L410) · [执行分责](../devSpec/agentic-execution.md)

### 本工程改进设计

若实际引入组合预订，将组合责任放在独立应用能力。复用现有受治理命令承接用户确认，组合协调器持久化配置版本、分支事实和补偿进度，对话只读状态。供应商 Port 自行约束取消资格、费用和订单身份。先跑上面的三项全成、晚确认后补偿与不可撤销反例，验证供应商终态及用户显示一致。若缺少安全的补偿契约或有单一原子接口，停止这一候选。
