## 第 1 题｜多轮 RAG 遇到“它对试用期员工适用吗”，怎么决定是否改写？

人事同事用内网知识库查制度。上一轮 Agent 引用了 A 合同的差旅条款，没拿到适用人群。现在同事问“它对试用期员工也适用吗？”知识库还有一份 B 合同，对试用期员工的规定不同。检索结果必须给出对应合同的条款和出处。

请给出这一轮的查询和回答条件。如果上一轮同时讨论了 A 和 B，或者手上已经有 A 合同的适用条款，分别怎样处理？如果误把“试用期”改成“实习期”，会在哪一步查出问题？

**场景依据。** QReCC 测试集会话 `2057` 第 `3` 轮，历史把范围限定为美国版《MasterChef》第 10 季，用户追问谁赢了，参考改写补回节目和季数，参考答案为 Dorian Hunter。本题沿用“历史给实体，当前轮问新属性”的结构，把节目换成合同，补入歧义和已有证据两个分支。 [QReCC 官方发布，`qrecc-test.json`](https://zenodo.org/records/4769775)

**选题依据。** 牛客字节面经第 4 场追问查询改写和用户意图重写。百度岗位要求有大模型 RAG 平台建设经验并了解完整检索链路。 [字节面经，2026-08-18](https://www.nowcoder.com/discuss/922659050167226368?sourceSSR=home) · [百度 J104290，2026-08-20](https://talent.baidu.com/jobs/detail/SOCIAL/97e52a20-c09c-43d1-b2e6-ad4a62eea1bf)

### 理论分析

**能唯一确定合同且缺少条款时才改写查询，已有适用条款就直接引用，指代不清就问清楚。**

- **指代消解。** 检查最近的用户问题和已引用的合同。如果只能指向 A，就把 A 补进查询，同时保留“差旅”和“试用期”。两份合同都可能是指代对象时，直接问“你指 A 还是 B？”ConQRR 的公开答法是把会话中的指代补成独立检索问题，并用证据命中衡量改写。 [ConQRR 原论文](https://aclanthology.org/2022.emnlp-main.679/) · [LangChain 的独立问题提示](https://github.com/langchain-ai/langchain/blob/bdf1cd383ce36dc18381a3bf3fb0a579337a32b5/libs/langchain/langchain/chains/conversational_retrieval/base.py#L282-L328)
- **复用证据还是重新检索。** 已有 A 的差旅条款但缺适用人群时，检索“A 合同差旅条款对试用期员工的适用范围”。已有同一合同的适用条款且当前仍有效时，直接引用。SELF-multi-RAG 用上一轮资料已经足以作答的场景说明如何省掉一次检索。 [SELF-multi-RAG 论文图 1](https://assets.amazon.science/8c/e8/8384303b4f28a424d47fd9d4dc95/learning-when-to-retrieve-what-to-rewrite-and-how-to-respond-in-conversational-qa.pdf)
- **改写保真和错误定位。** 改写供检索器使用，回答消费原话与命中的条款。先查实际 `query` 有没有把“试用期”换成“实习期”，再查返回的出处和条款。如果查询正确却召回 B，问题在召回或排序。若只拿到 B 的条款，A 的适用结论仍无依据。 [LangChain 分支及输入](https://github.com/langchain-ai/langchain/blob/bdf1cd383ce36dc18381a3bf3fb0a579337a32b5/libs/langchain/langchain/chains/history_aware_retriever.py#L51-L68) · [回答消费](https://github.com/langchain-ai/langchain/blob/bdf1cd383ce36dc18381a3bf3fb0a579337a32b5/libs/langchain/langchain/chains/retrieval.py#L58-L67)

## 第 2 题｜MCP 工具在第二页，客户端怎样发现它并处理半途失败？

平台接入一个原来只返回单页的政策查询 MCP 服务。客户端连接后会读取目录，再按配置注册工具。服务升级后，运维发现配置中的 `lookup` 报不存在。连接日志显示，首个 `tools/list` 只返回 `read_policy` 和 `nextCursor: "p2"`，拿 `p2` 再请求能得到 `lookup`，响应没有下一页游标。

客户端在哪一步可以认定 `lookup` 存在或缺失？如果第二页超时，分别说明首次启动和已有可用目录时的处理。第一个工具成功注册后，如果第二个名字发生冲突，如何收尾？

### 理论分析

**取得完整且通过校验的目录后再注册，分页失败报告发现错误，已有可用目录时保留旧注册。**

- **翻页终点。** 每次 `tools/list` 返回一页，Runtime 根据 `nextCursor` 决定是否继续。即使当前页没有工具，只要拿到 `p2` 就把它作为下一次 `params.cursor` 原样传回。直到没有续页游标，才可判定目录里是否缺 `lookup`。只看首页会给出假的“工具不存在”。C# SDK 的公开答法把自动聚合与单页读取分成两个接口。 [C# SDK 工具分页](https://csharp.sdk.modelcontextprotocol.io/v2/concepts/pagination/pagination.html) · [TypeScript SDK 游标循环](https://github.com/modelcontextprotocol/typescript-sdk/blob/dd22ba25ddbe7cd8822e1fe9c738a974996a28f6/packages/client/src/client/client.ts#L1727-L1753)
- **发布条件。** 两页成功、工具名通过校验、发起此次发现的连接仍具备发布资格时，才能登记新目录。正常场景应能按配置找到并调用 `lookup`。发起同步后如果连接已换代，迟到的旧结果不能覆盖当前目录。 [DeepSeek 聚合和资格检查](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/mcp/mcp-client/src/tools.ts#L144-L229)
- **失败发生在哪一步。** 第二页超时或聚合失败发生在发布前。冷启动报同步失败。旧连接仍有效时，刷新失败只记错误并保留旧目录。发布时注册冲突则撤销这次部分发布，并交连接监督处理。分阶段处理避免既暴露半份目录，又把超时报成工具不存在。 [连接重同步](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/mcp/mcp-client/src/connection.ts#L320-L352) · [发布回滚](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/mcp/mcp-client/src/tools.ts#L216-L238)

## 第 3 题｜学习小组换了两次主题，旧记录补录后，Agent 怎样回答当时和现在？

一个跨学科学习小组定期更换研读主题。负责人会在会议纪要里记录新主题从何时开始，有明确截止时间的也会注明。小组同一时点只安排一个主要主题。Agent 从第 20 天开始接收纪要，启动时没导入此前的资料。第 85 天，负责人整理归档时找到了第一阶段的纪要，补交给 Agent。

第 90 天，负责人准备给新成员发学习小结，也要确认接下来的会议有没有定主题。他请 Agent 根据纪要梳理小组的主题变化。以下是 Agent 按接收顺序看到的全部相关记录。

| Agent 收到记录的时间 | 记录内容 |
| --- | --- |
| 第 20 天 | 从今天起，主要主题改为文艺复兴艺术。 |
| 第 45 天 | 从今天起，主要主题改为现代物理，持续到第 80 天开始。结束后等待小组另定主题。 |

## 第 4 题｜换货 Agent 说办好了，却多换了一件，应该修哪一层？

### 理论分析

**业务方定义成功条件，客户确认本单目标。Runtime 写入前检查模型提议，写入后核对订单结果。离线评测由独立评分器判分。**

- **谁生成验收标准。** 换货业务负责人规定，确认的替换项必须全部完成，其余商品保持原样，告知客户的结果须与订单一致。订单业务流程将客户确认的 `T → T′` 和初始订单代入这套规则，得到本单标准「T 换成 T′，K 保留」。模型可以提出换货方案，客户的确认决定哪份方案生效。评测工程师在运行前把同一业务规则写成断言，并在用例中保存预期终态，供独立评分器读取。 [美团关于业务专家与可执行判据的实践](https://tech.meituan.com/2026/08/07/Agent-Evaluation.html)
- **谁判断模型提议可以执行。** Runtime 的准入代码在写入前核对订单号和每对旧、新商品 ID 是否与当前确认清单一致。A 的提议多带 K，应拒绝整笔请求并返回差异，供模型重新提议。归因时先确认模型实收上下文是否包含「只换 T」。B 的请求通过了这个检查，应追查订单服务的实际更新范围，确保事务提交只改变指定商品。客户确认两件且均符合政策时，两对都匹配就应放行。用「每次最多换一件」会误拦合法批量换货。 [美团工程实践中的链路观测和归因](https://tech.meituan.com/2026/08/07/Agent-Evaluation.html)
- **谁判断执行结果通过。** 订单服务提供实际订单状态。Runtime 的结果校验器在交付前按本单标准对比读回结果，完成门禁收到通过证据后才允许宣告成功。离线评分器独立读回实际状态，与用例的预设断言对比。两种校验都能发现 A、B 额外改了 K。回归时固定初始订单和判据，回放 A 检查服务零实收且订单不变，回放 B 的正确请求检查只改 T。再走自然语言入口，分别验证合法单件和双件换货及答复，防止靠禁用写入拿到零错换。用正确终态及额外改 K 的终态验证评分器能正确区分两个结果。 [Anthropic 对最终状态和回归评测的说明](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

## 第 5 题｜AI 编程实践：怎样让“排障”和“方案验收”两个 Skill 在对的时候触发？

团队用开发助手处理 Agent 核验问题。仓库里，排障 Skill 先读取实际模型请求和判定轨迹。方案验收 Skill 从已确定的修复出发，写对照、判据和停止条件。团队在同一历史故障档案上准备三条请求，想判断两份描述是否足以分流。

| 请求 | 助手当前拿到的材料 |
| --- | --- |
| “它怎么把错金额判对了？帮我定位失效在哪。” | 一次误判的请求和轨迹，尚无已定修复。 |
| “修复方案定了，怎么用这个失败样本验收并决定是否保留？” | 同一失败轨迹和已确认的修复方案。 |
| “那个失败用例还在跑吗？” | 当前运行 ID，只查状态。 |

三条分别应该怎么处理？如果第一条已经加载正确的 Skill，最终却没读实际请求就归因，应该改触发描述还是步骤？给出修改范围、差异审查和验收方法。

**场景依据。** Scott Spence 的公开对照含匹配任务、难例和无需 Skill 的反例。Vercel 的 Next.js 16 评测还记录了读到指导却漏改配置的案例。本题沿用「近邻触发例」和「加载后仍可交付失败」两种设计。表中三条请求和工作资料为面试改编，适用于 personalAgent 两种维护任务。 [Scott Spence 沙箱评测，2026-02-08](https://scottspence.com/posts/measuring-claude-code-skill-activation-with-sandboxed-evals) · [Vercel 工程复盘，2026-01-27](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)

### 本工程改进设计

**先按三个检查点收基线，再只改最早失效的位置。**

1. 在临时检出中固定模型、客户端版本和仓库指令。用同一真实故障归档，把表中三条各跑两次新会话。采集选中名称、成功读取 `SKILL.md` 或等价事件、首份证据、最终交付和耗时。
2. 验收分别是定位到可追溯的最早失效点、交出带对照和通过条件的验收计划、只读状态。反例是加载正确却没读原请求就归因，或查状态时误改方案文档。
3. 若复现选择错误，只允许改一个目标 `SKILL.md` 的 `description`。若正文已加载但跳步，只查正文第一步的要求是否足够明确，再决定是否改这一步。借鉴 `dsh-doc` 的证据顺序和权限边界。用 `git diff --name-only`、`git diff --check` 审查，再用留出问法复跑，分别报告调用、加载和交付的分子、分母及耗时。此候选只改变开发助手的说明，不改变产品 Runtime 的准入、执行或恢复。本次仅完成静态差异核对，效果待测。
