# 中文文档与回答写作规范

> 本文拥有中文表达、术语与排版，事实治理及生命周期由 [DOC](AGENTS.md)拥有。新文档和修改段落立即适用；存量按受影响主题迁移，不因一次修改要求重写全库。

## 1. 目标与适用范围

本规范适用于工程文档和对用户的回答，包括进度说明、问题解释和交付报告。写清结论、理由和影响判断的限制。

## 2. 中文句子的强制结构

### 2.1 先给判断，再解释原因

先回答读者的问题，再给出理解结论或作出决定所需的原因、机制和证据。索引、命令说明和检查清单直接给出入口或操作。

读者再次表示不理解时，定位原解释的歧义，用一个具体例子重新说明；不重复堆叠术语或原有措辞。

说明完整工程方案时，依次写清问题及影响、做法及取舍、依据与验证范围。只问某一环节时，展开该环节及必要前提。涉及模型上下文时，按[实际请求展示方法](../.agents/skills/manage-model-context/SKILL.md#21-用具体用例展示-context-原文)给出证据。

### 2.2 一个句子只表达一层主要关系

用常用词和具体动作写清谁在什么条件下做什么、产生什么结果。多个因果关系分句或用表格表达，修饰语紧邻对象。

### 2.3 并列关系必须同类

并列项应处于相同层次。业务能力、运行机制和业务项目不能混称一种能力；提议、执行事实与业务状态不能混作同一种结果。无法用同一上位概念概括时分别说明。

### 2.4 指代必须明确

代词应有唯一候选；跨段引用使用具体名称。“当前”须由文档状态、代码坐标或日期限定，历史计划不能长期充当现行事实。

## 3. 中文术语与英文保留规则

### 3.1 中文承担句子逻辑，架构角色名保留原文

用中文解释职责、流程和条件。引用具体实现或契约时保留精确标识。产品、标准和协议保留正式名称。

例如：“服务提供方通过执行网关返回 `Observation`，运行系统随后检查交付条件。”同一段同时讨论产品概念与机制时，先解释产品含义，再给实现坐标。

### 3.2 首次出现的外部协议术语说明中文含义

陌生行业术语首次可写“中文含义（英文原名）”，后续保持一致。常见产品名、正式协议名和代码标识不为满足格式重复翻译。

首次使用本工程专用概念时，先说明其含义和在当前问题中的作用，再给出缩写、变量或代码标识。变量涉及数量、范围或状态时，说明影响判断的单位和取值含义。

### 3.3 代码标识必须使用反引号

正文中的类型、函数、字段、状态、环境变量和命令参数用反引号。先说明事实或职责，再提供标识，不用对象清单替代设计论证。

## 4. 标点、数字与排版

- 中文句子使用中文标点。代码、路径、URL、命令、协议片段和原始日志保留原格式。
- 中文与英文、数字之间保留半角空格，中文标点两侧不额外加空格。
- 范围和章节引用在同一文档使用一致写法，标题清楚表达主题。
- 同一表格列或列表层级使用平行句法；用表格或列表帮助比较，不为排版制造层级。
- 代码围栏和 Mermaid 保持语法有效，图中解释性文字优先使用中文，标识不因中文化改写。

## 5. 事实、证据与时态

### 5.1 结论强度不能超过证据

| 依据 | 可支持范围 |
| --- | --- |
| 正式 E2E 归档 | 该输入、代码与配置下的用户结果和反事实 |
| 目标 clean revision 的完整发布证据 | 已声明发布契约及覆盖范围 |
| Offline Eval 或局部历史证据 | 指定样本和前置条件下的局部结论 |
| 代码、设计或外部参考 | 实现或候选机制存在，不能证明本工程用户结果改善 |

明确标出未执行、未到达、未知用量和缺失证据。旧评测及停用单元测试按原身份描述。

直接陈述已核实的事实和决定。结论有不确定性时，说明缺少什么依据及其影响。

### 5.2 当前事实与历史事实分开

历史结果按原身份和日期描述，现行说明只保留仍成立内容。正文落点和状态迁移执行 [DOC](AGENTS.md#3-事实强度与文档生命周期)，不在写作规范重复生命周期流程。

## 6. 各类文档的附加要求

| 文档类型 | 内容要求 |
| --- | --- |
| 接口与运维 | 原样保留字段和命令，说明前置条件、含义及失败语义 |
| ADR | 背景、决定、责任主体、证据、防护设计与退出条件；准入要求由 REL 拥有 |
| 当前状态摘要 | 先说明状态与证据限制，再给正式路径和权威链接 |
| 专题与固定流程 | 解释责任、信息流和协作，代码坐标用于反查 |
| 评测说明 | 保留机器编号与分类，中文说明结果、阶段和证据边界 |
| 未来设计 | 按第 6.1、6.2 节编写 Spec，说明需求、契约、方案与验收；实施状态和实际证据按第 5 节记录 |
| 面试材料 | 用真实用户结果、实现与证据解释取舍，见[面试材料维护规范](interview/00-material-maintenance.md) |

### 6.1 设计文档写法

**设计正文说明怎样解决已确认的问题，并把防止设计出错的措施直接写进方案。** 本节适用于方案、候选、Future 详细设计和 ADR 的设计部分。

1. 从问题、目标及依据写到最小机制。独立方向分别写目标、依赖及验收，协作通过契约连接，互斥候选并列比较。必要性与复杂度按 [EVD](devSpec/change-evidence.md#5-复杂度说明complexity-justification)说明。
2. 把防护写成责任、契约、不变量及可验证条件。说明何时拒绝、怎样处理失败、什么证据会推翻假设、何时撤回。已确认风险与例外按 [REL](devSpec/migration-release.md#2-adr-准入)记录。
3. 实施次序和验收按 [EVD](devSpec/change-evidence.md#7-强制开发与设计流程)执行，正文更新按 [DOC](AGENTS.md)处理。

例如，版本防护写为“准入精确比对 `base_ref` 与当前版本。版本过期时拒绝动作，写入数为零”。

### 6.2 Spec 结构与需求追溯

新增或实质修改的方案、候选、Future 详细设计与 ADR 的设计部分采用 Spec。Spec 先说明触发条件和预期结果，再说明怎样实现及验收。

| 内容 | 必须写清的问题 |
| --- | --- |
| 目标、范围与依据 | 解决什么已定位问题，服务谁，哪些行为保持，事实与待证假设分别是什么 |
| 需求与行为规格 | 用稳定编号标识可独立验收的需求；写清触发条件、必须产生的结果及适用的失败行为，不用“更准确、合理优化”等意图替代结果 |
| 架构分析 | 确定模块、目录、调用关系及代码落点前，按 [ARC](devSpec/architecture-ownership.md#81-设计阶段的架构分析)对照现行架构说明职责与事实归属、依赖、复用、装配及迁移依据 |
| 方案与契约 | 谁拥有事实和判断，输入输出、合法范围、不变量、状态变化及反馈由谁消费；基于架构分析说明最小机制如何满足需求 |
| 验收规格 | 将需求关联到适用的现有用例、真实阶段回放或工程检查，写清前置输入、触发动作、可观察结果和通过／失败判据。新增 E2E 按 [EVD 验证范围](devSpec/change-evidence.md#12-按实际影响选择证据)决定 |
| 实施与删除计划 | 按依赖顺序列出改动、消费者迁移和旧路径删除，各项引用所实现的需求及验收用例 |
| 状态与决策依据 | 区分已确定需求、候选方案、待定项、已实现和已验证；记录必要取舍、已有证据及尚未取得的证据 |

小改动可合并相邻小节。需求编号只用于追溯，直接在原表或正文关联需求、实施项和验收用例。待定项写明缺失依据、影响和解决动作。改变需求、契约或方案时，同轮同步受影响的关联项与状态。

## 7. 存量文档迁移顺序

先核实事实和正文归属，再移除冲突与过期表述，最后调整中文表达并同步引用。改动限于本次涉及的主题，原始日志保留原值。

## 8. 提交前门禁

审读结论、术语、指代及证据措辞，确认范围与读者的问题一致。文档结构和引用按 [DOC 提交前检查](AGENTS.md#5-提交前检查)核对。
