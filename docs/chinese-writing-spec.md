# 中文工程文档统一规范

> **本规范是 `docs/` 目录全部文档的中文写作门禁。** 新增文档和任何被修改的段落必须立即符合本规范；存量文档先删除冗余、过期和无权威来源的内容，再分批迁移。当前第一批迁移范围是 `docs/future/` 与 `docs/interview/`，其他目录尚未完成迁移不表示可以继续新增不符合规范的文字。

## 1. 目标与适用范围

工程文档必须让读者用自然中文直接理解结论、责任主体、运行机制和证据边界。约束的是句子的表达逻辑——中文承担主谓宾、条件和因果，不用英文名词拼接句子；不是把架构术语全部替换成中文。有对应代码实现的角色名保留原文，规则见 §3.1。规范适用于：

- 根目录说明、专题设计、固定流程、接口、部署和环境文档；
- 架构决策记录、当前状态摘要、未来设计和评测文档；
- Mermaid 图中的说明文字、表格标题、注释和示例解释；
- 面试材料及其索引。

以下内容可以保留原文，但必须与中文正文清楚区分：

- 代码标识、字段名、类型名、文件路径、命令和环境变量；
- 在代码、`CLAUDE.md` 或评测归档中有同名实现的架构角色名，例如 `Proposal`、`Admission`、`Observation`、`Command`、`Receipt`、`steering`；
- 协议、标准、产品、模型和服务提供方的正式名称；
- 用例编号、机器状态值、错误码、归档路径和校验和；
- 为精确复现而保留的短日志、请求或响应片段。

## 2. 中文句子的强制结构

### 2.1 先给判断，再解释原因

每个小节第一段必须回答本节的核心问题。后续内容按需要说明：

1. 为什么这个问题重要，会阻止什么用户错误或工程失控；
2. 谁拥有决策或事实，唯一写入口在哪里；
3. 信息如何流动，失败时如何处理；
4. 哪条证据支持结论，结论不能外推到哪里。

禁止使用“下面介绍”“显而易见”“综上所述”等无信息过渡，也禁止在结尾重复首段已经表达的判断。

### 2.2 一个句子只表达一层主要关系

中文句子优先采用“责任主体 + 动作 + 对象 + 条件或结果”的结构。一个句子包含三个以上并列分句时，应拆成多句或表格。修饰语必须紧邻被修饰对象，避免英文式长前置定语。

不合格：

> 运行系统通过恢复计划绑定的执行事实并在模型上下文中继续消费从而在跨轮场景下避免重复读取并提升完成能力。

合格：

> 运行系统恢复与当前工作项绑定的成功执行事实，并把它们重新放入模型上下文。模型可以直接消费已有结果，因此不必在下一轮重复读取原始资源。

### 2.3 并列关系必须同类

同一并列项必须处于相同层次。业务能力、工具、固定流程、运行机制和后台项目不能并列称为同一种“能力”；提议、执行事实和业务状态也不能混成同一种“结果”。并列项无法使用同一个上位概念概括时，应拆分说明。

### 2.4 指代必须明确

“它”“该对象”“这个状态”“当前方案”等指代只能在前一句存在唯一候选时使用。跨段落引用必须写出具体名称。正文中的“当前”必须能由文档状态、代码版本或日期确定，不能长期指向已经变化的实现。

## 3. 中文术语与英文保留规则

### 3.1 中文承担句子逻辑，架构角色名保留原文

**本规范约束的是句子的表达逻辑，不是把术语全部译成中文。** 判据是这个词在本工程有没有对应的代码实现或契约：

- **有同名实现的架构角色名保留英文原文。** `Proposal`、`Admission`、`Observation`、`Command`、`Receipt`、`Verification`、`Completion`、`digest`、`steering`、`checkpoint`、`replay`、`baseline`、`target` 在代码和 `CLAUDE.md` 中是 canonical 名称，译成中文会切断文档与代码、评测归档之间的反查链，也会让同一个类型在不同语境下得到两个不同中文词。
- **描述性的通用词使用中文。** 下表这类词在本工程没有对应类型，中文表达更自然：

| 英文术语 | 中文正文统一表达 |
| --- | --- |
| Agent | 智能体 |
| Tool | 工具 |
| Workflow | 固定流程 |
| Runtime | 运行系统 |
| Gateway | 执行网关 |
| Provider | 服务提供方 |
| owner | 责任主体或事实归属 |
| scope | 权限范围或作用域 |
| revision | 版本 |
| pending / completed | 待完成 / 已完成 |
| fallback | 降级路径 |
| cohort | 同配置样本组 |
| trace / archive / grader | 追踪记录 / 归档 / 评测器 |
| release gate | 发布门禁 |

- **产品语义与机制名称不是同一层。** `Plan` 作为前台产品概念写“可验收工作项清单”，作为后台 `PlanProposal` 的机制引用保留原名；`Project` 作为产品概念写“调查项目”，作为 aggregate 引用保留原名。同一段落中两种用法并存时，先写中文产品语义，再用反引号给出机制坐标。

保留原文的角色名必须放进符合中文语法的句子，由中文承担主谓宾和条件关系。

不合格，英文名承担了句子结构：

> Provider 通过 Gateway 返回 Observation 后 Runtime 执行 Completion。

合格，中文表达逻辑，角色名保留：

> 服务提供方通过执行网关返回 `Observation`，运行系统随后进行 Completion 判断。

### 3.2 首次出现的外部协议术语说明中文含义

介绍外部协议或行业术语时，首次写作“中文名称（英文原名）”，后文只使用中文名称。本工程自有的架构角色名不属于此类，按 §3.1 直接使用原文。产品名和代码标识不翻译。

### 3.3 代码标识必须使用反引号

类型名、函数名、字段名、状态值、环境变量和命令参数在正文中使用反引号，例如 `ConversationWorkingPlan`、`plan_ready` 和 `STRUCTURED_MODEL`。代码标识不能承担设计论证；正文必须先用中文说明它代表的事实或职责。

## 4. 标点、数字与排版

- 中文句子使用中文逗号、句号、冒号、分号、问号和引号；代码、网址和原始协议片段保留英文标点。
- 中文与英文、数字之间保留一个半角空格；中文标点前后不额外加空格。
- 范围使用“至”或短横线时保持全文一致；章节引用使用“第 2 节”或“§2”，同一文档不混用多套格式。
- 标题直接表达判断或主题，不使用全英文标题；产品或协议原名可以放在中文标题后的括号中。
- 表格同一列使用相同句法，不能把名词、完整句和状态码混排为同一级内容。
- 列表项必须能接在引导句之后自然朗读；同一列表统一使用名词结构或完整句。
- 代码块、Mermaid 图和机器输出不得为了中文化而修改标识或语法；图中的解释性节点应优先使用中文。

## 5. 事实、证据与时态

### 5.1 结论强度不能超过证据

| 证据 | 可以写 | 不可以写 |
| --- | --- | --- |
| 正式入口的端到端测试归档 | 该输入下的用户结果和关键反事实成立 | 所有场景天然成立 |
| 干净代码版本的完整发布门禁 | 目标版本达到已声明的发布证据门槛 | 未覆盖需求也可靠 |
| 单元、契约或集成测试 | 指定不变量或组合协议成立 | 用户目标已经满足 |
| 代码、设计或外部参考 | 存在某个实现或候选机制 | 本工程用户结果已经改善 |

没有实际执行时使用“代码设计为”“文档记录为”或“仍需验证”，不得写“已验证”“已修复”或“可发布”。机器状态值可以原样保留，但必须用中文解释其产品含义。

### 5.2 当前事实与历史事实分开

当前状态文档只保留目标代码状态下仍成立的事实。历史失败、已否决候选和调试过程进入评测归档或架构决策记录，不得继续作为当前能力描述。未来设计只保存尚未解决且满足准入要求的问题，不能追加完成流水。

## 6. 各类文档的附加要求

| 文档类型 | 附加要求 |
| --- | --- |
| 接口与环境文档 | 字段、请求和命令保持原样；解释字段含义、前置条件和失败语义时使用中文 |
| 架构决策记录 | 使用“背景、决定、责任主体、证据、风险与退出条件”的中文结构；不得用对象清单代替决定理由 |
| 当前状态摘要 | 先写当前判断，再给生产路径和证据；删除已经迁移或失效的历史叙事 |
| 专题与固定流程 | 只主讲一个责任边界；其他能力使用链接，不复制第二套解释 |
| 评测文档 | 用例编号和机器分类保持原值；用户结果、失败阶段和证据限制使用中文 |
| 未来设计 | 先给失败基线和准入状态，再写条件候选；未进入准入阶段的内容不得写成实施计划 |
| 面试材料 | 按“错误、机制、收益、证据、边界”组织；类名只作为实现坐标 |

## 7. 存量文档迁移顺序

存量文档不得直接进行全局术语替换。每个目录按以下顺序处理：

1. 删除过期入口、旧状态、重复解释和没有消费者的候选方案；
2. 确认每项事实的唯一主讲文档，并把其他文档收缩为摘要与链接；
3. 核对生产代码、机器用例目录、执行证据和当前摘要；
4. 按本规范重写保留内容；
5. 检查链接、标题锚点、代码块、表格和 Mermaid 语法；
6. 记录尚未迁移的目录，不得把“尚未迁移”写成“已经符合规范”。

## 8. 提交前门禁

每次文档变更必须回答以下问题：

- 小节首段是否已经给出明确判断；
- 中文句子能否脱离英文承担完整的主谓宾和条件关系；
- 英文是否仅用于代码标识、有同名实现的架构角色名、协议、产品原名或机器状态；
- 是否把有代码实现的角色名译成了中文，或让同一个类型在不同语境得到两个中文词；
- 类型名和字段名是否使用反引号；
- 同一列表或表格是否保持相同语法层次；
- “通过、恢复、完成、已修复、可发布”是否有相称证据；
- 当前事实、历史记录和未来候选是否落在正确目录；
- 是否先删除冗余和过期内容，再进行中文迁移；
- 本地链接、标题锚点、代码块和 Mermaid 是否仍可解析。

发现不符合项时，修改范围内的文档不得以“后续统一处理”为由继续新增同类问题。尚未进入迁移批次的存量目录可以保留原状，但其中任何新写或实质修改的段落必须符合本规范。
