# 中文工程文档统一规范

> 本文拥有中文表达、术语与排版，事实治理及生命周期由 [DOC](AGENTS.md)拥有。新文档和修改段落立即适用；存量按受影响主题迁移，不因一次修改要求重写全库。

## 1. 目标与适用范围

文档应让读者用自然中文理解结论、责任、机制和证据限制。规范适用于说明、专题、接口、运维、ADR、摘要、Future、评测、面试及图表文字；代码、路径、命令、协议、产品原名和机器日志保持原值。

## 2. 中文句子的强制结构

### 2.1 先给判断，再解释原因

解释性段落先表达判断，再按需要说明原因、责任、信息流和证据。索引、命令说明和检查清单可直接给出入口或操作，不机械补一段重复结论。删除无信息过渡和重复总结。

### 2.2 一个句子只表达一层主要关系

优先使用“责任主体 + 动作 + 对象 + 条件或结果”。多个不同因果关系拆成句子或表格，修饰语紧邻对象；不要以固定字数或并列数量代替可读性判断。

### 2.3 并列关系必须同类

并列项应处于相同层次。业务能力、运行机制和业务项目不能混称一种能力；提议、执行事实与业务状态不能混作同一种结果。无法用同一上位概念概括时分别说明。

### 2.4 指代必须明确

代词应有唯一候选；跨段引用使用具体名称。“当前”须由文档状态、代码坐标或日期限定，历史计划不能长期充当现行事实。

## 3. 中文术语与英文保留规则

### 3.1 中文承担句子逻辑，架构角色名保留原文

引用代码实现或契约保留精确标识，描述一般含义使用中文。同一个词出现在代码中，不意味着所有正文都必须写英文；也不强制把所有架构术语翻译成中文。

| 语境 | 写法 |
| --- | --- |
| 代码类型、字段、枚举、命令或配置 | 使用原值和反引号，如 `Proposal`、`scope`、`in_progress` |
| 事实、权限与作用域的一般描述 | 使用中文，首次需要反查时补代码标识 |
| 产品、标准与协议名称 | 保留正式名称，必要时首次说明含义 |
| 指令、流程和机制论证 | 中文承担主谓宾和条件逻辑，不堆叠英文名代替解释 |

通用表达优先使用“智能体、工具、固定流程、运行系统、执行网关、服务提供方、责任主体、作用域、降级路径、同配置样本组、追踪记录、归档、评测器、发布门禁”。描述具体类或契约时保留其标识。

例如：“服务提供方通过执行网关返回 `Observation`，运行系统随后检查交付条件。”同一段同时讨论产品概念与机制时，先解释产品含义，再给实现坐标。

### 3.2 首次出现的外部协议术语说明中文含义

陌生行业术语首次可写“中文含义（英文原名）”，后续保持一致。常见产品名、正式协议名和代码标识不为满足格式重复翻译。

### 3.3 代码标识必须使用反引号

正文中的类型、函数、字段、状态、环境变量和命令参数用反引号。先说明事实或职责，再提供标识，不用对象清单替代设计论证。

## 4. 标点、数字与排版

- 中文句子使用中文标点，代码、URL 和协议片段保留原格式。
- 中文与英文、数字之间保留半角空格，中文标点两侧不额外加空格。
- 范围和章节引用在同一文档使用一致写法，标题清楚表达主题。
- 同一表格列或列表层级使用平行句法；用表格或列表帮助比较，不为排版制造层级。
- 代码围栏和 Mermaid 保持语法有效，图中解释性文字优先使用中文，标识不因中文化改写。

## 5. 事实、证据与时态

### 5.1 结论强度不能超过证据

| 依据 | 可支持范围 |
| --- | --- |
| 正式 E2E 归档 | 该输入、代码与配置下的用户结果和反事实 |
| 目标 clean revision 的完整发布证据 | 已声明发布契约及覆盖范围 |
| Offline Eval 或局部历史证据 | 指定样本和前置条件下的局部结论 |
| 代码、设计或外部参考 | 实现或候选机制存在，不能证明本工程用户结果改善 |

不将未执行写成通过，不将局部通过扩大为产品完成。单元测试及旧分类按根规范只读解释，不作为后续门禁。未知用量、未到达阶段和不可用证据明确标注。

### 5.2 当前事实与历史事实分开

历史结果按原身份和日期描述，现行说明只保留仍成立内容。正文落点和状态迁移执行 [DOC](AGENTS.md#3-事实强度与文档生命周期)，不在写作规范重复生命周期流程。

## 6. 各类文档的附加要求

| 文档类型 | 内容要求 |
| --- | --- |
| 接口与运维 | 原样保留字段和命令，说明前置条件、含义及失败语义 |
| ADR | 背景、决定、责任主体、证据、防护设计与退出条件；准入要求由 REL 拥有 |
| 当前状态摘要 | 先说明状态与证据限制，再给正式路径和权威链接 |
| 专题与固定流程 | 解释责任、信息流和协作，代码坐标用于反查 |
| 评测说明 | 保留机器编号与分类，中文说明结果、阶段和证据边界 |
| 未来设计 | 按下节说明要解决的问题、解决机制与防护设计；实施状态和实际证据按第 5 节记录 |
| 面试材料 | 组织已有错误、机制、收益、证据与边界，不复制运行流水 |

### 6.1 设计文档写法

**设计正文说明怎样解决已确认的问题，并把防止设计出错的措施直接写进方案。** 本节适用于方案、候选、Future 详细设计和 ADR 的设计部分。

1. 以可读性为首要组织标准，写清具体问题、目标结果，以及责任主体如何通过最小机制取得该结果；按需给出字段、信息流、写入规则和验收条件。涉及代码组织时，按 [COD](devSpec/code-structure.md#32-功能模块化与开发上下文)写清功能入口、契约和协作，使 Code Agent 能定位局部任务需要的上下文。
2. 设计时考虑方案会引入的问题，落实为明确的责任、契约、不变量、执行约束和验证条件。涉及模型复述或转交已有文字时，按 [COD 文本引用规则](devSpec/code-structure.md#21-已有文字通过引用传递)设计引用和原文恢复的责任。正文写这些防护措施，不另列潜在问题或风险清单。
3. 不用“方案不能做什么”“不保证什么”“不解决什么”等能力排除说明充实正文。相关机制需要协作时，直接说明各自承担的动作与交接条件。
4. 失败语义、拒绝条件、证伪与退出条件按可执行规则表述；实施状态和已执行结果按事实记录。例外或兼容决策继续按 REL 记录依据与控制措施。
5. 落地遇到独立阻塞时，按[EVD 第 7.1 节](devSpec/change-evidence.md#71-独立阻塞优先解决并保持方案一致性)写清归因、优先解决的责任、原方案保留条件和恢复入口。修复或设计变化同步同一正文，保持目标、职责、机制和验收的一致性；独立阻塞设计归属其自身问题，原方案只保留一份现行正文。
6. 同一阻塞修正后仍复现时，按[EVD 方案复审](devSpec/change-evidence.md#72-重复阻塞先复审方案再继续)在同一设计中重审失败链与具体机制，记录被反例否定的假设、仍成立的证据和下一方案的新因果依据。写清重新准入和原入口恢复条件，并改写失效方案正文，不能只追加下一轮尝试。
7. 核验漏放的设计先按 [QLT 最小充分上下文诊断](devSpec/quality-security.md#21-核验漏放先验证最小充分上下文)排除干扰，说明必要事实与裁剪保真。最小充分输入仍漏放时重审任务合理性、职责与判据；识别成功时依据实际链定位输入责任，条件局部结果与正式验收分别记录。

例如，版本防护写为“准入先精确比对 `base_ref` 与当前版本，过期动作拒绝且零写入”；正文保护写为“Runtime 按选中范围合并，其余正文和引用逐字保留”；内容验收写为“合并后的完整新版交给 Verifier 核验，通过后进入交付”。

## 7. 存量文档迁移顺序

先核实事实与正文归属，再清理冲突，最后调整中文表达。不要全局替换术语或改写原始日志。按主题迁移并同步引用；范围外旧文字不阻塞局部交付，本次不继续新增同类问题。

## 8. 提交前门禁

检查修改段落的判断、语法、指代、并列层次、术语和证据措辞；结构、生命周期与引用统一执行 [DOC 提交前检查](AGENTS.md#5-提交前检查)。机械检查通过不能替代内容审读。
