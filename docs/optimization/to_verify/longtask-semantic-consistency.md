## 2. 参考、替代方案与选择

[smolagents 与 OpenHands SDK 的固定源码比较](../../agentRef/runtime-recovery.md#9-原始目标工作记录与最终复核的分工)支持原目标与可变理解分开、当前稿与真实历史共同检查、反馈回到原 Agent。它们没有要求本工程逐条输出用户原话的坐标，也不证明核验一定能纠正 LongDS 错误。首版复用本工程现有核验阶段和完成边界。

**先验证更小的 Context 位置候选。** [实际要求区位置](verify_results/longds-analysis.md#10-要求区在实际请求中的位置)确认 criterion 已在首条 system 前部，每次重建；第 2 轮标准之后仍有 88,040 字符。当前没有“未注入”证据，也没有位置导致失败的因果结论。参考[通用框架的公共 Context 构造](../../agentRef/context-engineering.md#8-通用框架的要求表达与采用依据)，先单独比较把同一现有要求区移至动态执行输入末段的较小改动；不与独立核验、标准改写、assistant 历史裁剪、规则展开或新增模型阶段合并。该候选只是减少长执行投影隔开当前要求的程度，不能修正错误或遗漏的 criterion。

Conversation 继续从冻结 `ReviewCriteria` 物化一次要求区，稳定的通用规则留在原 system，原会话保持，要求区单独置于本次 Typed execution inputs system 末段；没有执行输入时用同一角色的独立动态要求消息。不新增模型输出字段、用户原话选择协议、Goal 状态或调用。Adapter 原生历史仍在其后追加；本轮布局模拟只将距离降为 17,583 字符，不声称到达整个 wire 尾部。若一定要放在原生工具历史之后，需要另行审计 typed Model Port、Provider 配对和实际消息构造，不将其包装成一次模板移动。

实施前先固定零模型请求对照：原用户正文、criterion 字符串、工具声明、调用／回执配对、身份及预算不变，仅要求区位置变化，空标准仍为空。语义效果先以 task2 第 2 轮真实失败决策和连续实际后继为对象，按 QLT 单列两版本各十次及具体额度，先封存可执行回放与原名单判据；第 3／24 轮作为错误标准的独立边界，不把位置变动当成它们已修复。位置及表达已按 §9 独立预算实施三组阶段回放，不扩用 Q0／V1 额度。通过后也只关闭已证明的位置机制边界；独立核验仍为后续需要能力与净收益验证的候选。

**目标展示采用自然语言标题和编号清单。** 采用依据是 OpenCode 默认公共 system／Instructions 渲染链和 LangChain 通用 middleware 的文字提示，见[固定源码比较](../../agentRef/context-engineering.md#8-通用框架的要求表达与采用依据)。只借鉴可读正文与内部结构分离，不采用 Gemini CLI 等客户端的模型相关表达作为本项准入依据；也不复制这些框架的 Todo、规则状态或额外能力。条目编号是本工程的展示选择，并非外部统一 criterion 协议。

位置对照保留原 JSON 外壳仅为隔离变量，不是目标展示决定。表达形式对照在同一位置、同一权威说明和同一 criterion 原句下，比较 JSON 字符串数组与自然语言清单；不同时改变提取、要求作用域或独立核验装配。具体展示和不变边界由 §4 拥有，次数及额度在相应真实阶段实验前另行封存，不借用位置组或 Q0／V1 的额度。自然语言展示已接入，未将其登记为注意力或正确性改善，实际结果由验证记录拥有。

**独立核验尚非已证明的必要机制。** 历史 LongDS 失败证明需要改善约束遵循，不证明增加一次独立 LLM 调用比原循环自检更有效。[外部标准来源与核验比较](../../agentRef/verification-and-observability.md#8-独立核验的价值与标准来源)也没有统一要求默认增加 grader。结果检查的职责保持，确定性不变量仍由代码处理；本设计的 `direct+required` 仅是待验证的分析实验装配，不是所有任务或生产默认的新增前提。独立核验是否值得采用，要同时看实际纠错、误拒／错误修订及完整调用成本。

| 候选 | 机制、成本及与失败的关系 | 决定 |
| --- | --- | --- |
| 只增加遵守要求的提示 | 原文已经可见仍发生误解；核验仍缺实际上下文和计算依据 | 不作为完整修复 |
| 原主 Agent 按原文及实际成果自检 | 复用现有循环和模型理解，成本较低；同一误解可能在生成与自检中重复 | 保留为更简单的比较方向，不能因本设计研究独立核验就宣告其无效 |
| 模型选择用户片段、输出 `sources` 并以原文替换改写标准 | 增加消息／行号选择、嵌套字段、漏选、准入修复及消费者迁移成本；当前用户文本规模下没有足够收益依据 | 撤下该要求引用候选，不进入本切片实施 |
| Runtime 提供完整用户原文＋模型改写的辅助标准＋真实执行与当前稿 | 代码直接传递已保存原话；核验可以发现辅助标准的误解或遗漏，不依赖前置模型先选对片段 | 采用为当前待验证候选；没有新增要求片段选择字段或选择阶段 |
| 独立业务状态库、常驻 Planner 或规则引擎 | 当前原件与工作产物已可读；把开放业务语义转给 Runtime，增加事实 owner | 首版不采用 |

修正依据是完整原话已有可信存储、当前真实输入规模及额外选择协议的成本，不是新模型实验结果。未声称简化方案已经改善正确性、费用或延迟；收益继续按本设计的真实用例验证。

| 对比边界 | task2 原装配 | 当前候选的净变化 |
| --- | --- | --- |
| 主 Agent 的原始目标和历史 | 原用户消息、旧回答及本轮请求已持续进入模型 | 保持；没有新增主 Agent 目标信息，不据此主张更关注或更懂目标 |
| 标准识别与输出 | 每轮一次 Intent；输出带 `source` 的要求对象，准入后冻结改写字符串 | 复用该调用，简化为辅助标准列表，去掉要求片段选择；不新增识别模型 |
| 标准的作用 | system 已说明用户消息决定交付范围，改写列表以“验收条件”注入并冻结；本次 none 装配未实际用于独立核验 | 明确列表只是可错的理解；新增核验消费者不能按错误列表拒绝符合原文的回答，不把这种说明计作主 Agent 新增信息 |
| 实际程序和成果 | 执行、原件保存、读搜及反馈已存在 | 保持原执行事实，另为候选核验只读物化本轮实际程序／结果，不假装主 Agent 已读额外材料 |
| 独立核验及修订 | 全部 34 轮 `direct+none`，没有独立语义检查及其反馈 | 显式实验装配完整原文＋辅助理解＋实际成果＋当前稿，验证识别和反馈是否能促成修正；价值未证，不默认生产接入 |

**直接纠错机制是语义核验、反馈与修订。** 针对 criterion 误解或遗漏仍适用要求，本候选在原 `direct+none` 分析装配中启用既有语义核验，并补齐其输入。核验模型独立依据用户原要求检查辅助标准及实际成果，发现冲突后反馈给原 Agent；Agent 修正当前理解，按需重算或改稿，再提交核验。要证明的是错误被识别、反馈被实际消费且交付改正，不是要求字段或引用校验通过。

**原文与引用承担支撑职责。** 用户原文给核验提供判断依据，引用可辅助定位相关原话；两者都不执行语义判断或修订，增加引用本身不能解决 criterion 识别错误。本切片直接提供完整用户原文，已撤下要求片段选择协议；删除该协议属于简化，不能登记成 criterion 识别准确率改善。

**核验时机与收益范围。** 当前复用交付前的核验入口，在检查本稿时识别辅助标准偏差，再由原 Agent 修订工作理解；没有新增“Intent 输出后立即核验并重提取 criterion”的阶段。因此，本候选考察的是识别错误对交付的影响能否被纠正，不能宣称执行前的 criterion 已被校正或提取器准确率已提升。独立核验的纠错收益、误拒和成本尚未验证。

## 4. 架构分析、契约与消费者

依赖仍为正式入口 → Conversation Application → 既有 Model／Tool／Artifact Port，外层 Adapter 及组合根提供原实现。没有新增 Application Capability、业务 Aggregate、模型阶段或可写业务状态。

**原话由原消息拥有。** `InteractionTrace.messages` 保存本次冻结的用户输入；Runtime 从中按原顺序投影全部 user 正文，作为核验请求内的只读 `user_context`。本次 run 身份和输入摘要绑定来源，模型不再输出要求的消息索引、行号或摘录。若用户指代旧回答或产物，提供本轮实际使用的对应材料并标为非用户要求；缺少必要被指代内容时报告缺证，不能只靠辅助标准猜出原意。

**改写标准保留为辅助理解。** 意图输出将原 `ReviewRequirement(criterion, source)` 简化为 `criteria: tuple[str, ...]`，复用 `ReviewCriteria.criteria` 的字符串列表，不新增 `requirements/sources`。它表示 Intent 模型理解到的检查方向，不是用户原话或可独立生效的验收基准。删除要求专用的 `ReviewRequirement` 及单 `source` 输出；`UserTextReference` 继续只用于原有交互相位、后台授权来源等现行控制契约，不移动类型或扩大该用途。辅助标准是新生成的解释，原话由 Runtime 搬运，符合 COD 对原文转交与新语义的区分。

**辅助标准生成的输入范围。** 现有 Intent 会把全部 user／assistant 消息物化进请求。读取 task2 第 34 轮[原 Trace](../../../.tmp/lr2/t01/capture/turn-34.trace.json)得到 user 21,957 字符、assistant 225,296 字符；这是会话正文规模，不是实际 tokens 或错误原因证明。生成 `criteria` 不默认需要全部 assistant 历史：独立完整的请求可只依据当前 user，“其余不变”等继承需保留历史 user 条件，用户采纳或指代某个助手方案时，对应内容才作为解释上下文，不能自动成为用户新增要求。这里不引入独立模型进行选段，也不将“只给最新 user”设成通用规则。

当前同一次 Intent 调用还承担交互相位和后台要求识别，不能仅按 `criteria` 的需要裁剪整个调用。后续输入优化先核对正式真实阶段中的独立请求、条件继承、方案采纳及阶段转换，比较现行完整输入与按职责收窄的输入，确认没有删除必要指代前提；需要的当前计划或待审材料复用既有正式状态。第 3 轮数量例外和第 24 轮当前 credit 口径作为已知提取错误，后续须检查标准本身是否忠于有效用户要求，并与主 Agent 是否正确执行分别报告；引用恢复或原文到达不作为语义通过判据。实际请求体、模型和输出合同固定后再定义语义对照及额度，不把字数下降计作理解改善，不扩用原核验 Q0 的次数或预算。本轮仅记录该输入优化候选，不改生产或启动模型验证。

**模型可见要求区的表达契约。** 内部继续保存 typed `criteria` 字符串列表，`_requirements_instruction()` 在既有 Context 物化边界确定性渲染 Markdown 标题、简短权威说明和编号清单。按原列表顺序保留每条 criterion 原句、语言和限定，不调用模型转写、概括或翻译；不补充模型未提取的规则。多行文字保持在同一条目内，空列表不编造条目，原用户请求及适用核验触发继续有效。原始用户消息保持原渠道，不另建目标字段或复制为第二份可写要求。

目标结构如下，占位符只说明渲染位置：

```text
## 用户要求的辅助理解
以下条目由模型提取，可能有遗漏或误解；以用户原始消息和仍适用的要求为准。

1. {第 1 条 criterion 原句}
2. {第 2 条 criterion 原句}
```

该决定只改变辅助要求区供模型阅读的正文形式；内部模型、工具参数、回执、核验标识和结构化输出保持各自 typed／JSON 契约，展示编号不充当 `criterion_id`。direct 核验增加只读 `user_context` 和 `interpreted_criteria`，后者仍由现有 `ReviewCriteria.criteria` 派生；其辅助要求正文复用同一表达规则，不增加模型输出字段。`execution_basis` 继续从实际执行派生。模型若需要指出理解偏差，在原反馈中说明，不要求重新输出用户原话作为证明。

**核验基准不由辅助标准定义。** 专用分析 required 合同保留 Runtime 拥有的“当前用户目标与仍适用约束”和“来源／实际执行支持”两个通用检查项。`success_criteria`、`VerificationCriterion`、`ResearchGoalRequirement` 及 `rN` 从适用的 Runtime 核验合同派生；模型的辅助标准不再生成独立的必达项。核验必须发现辅助标准误解、遗漏或越过用户原文，但不能因稿件没有遵守一条错误的辅助标准而拒绝符合用户要求的回答。语义通过、失败或缺证仍由现有报告表达；辅助理解偏差可写入原反馈，不增设业务状态或第二份标准。

| 责任 | 正式生产者与消费者 | 改动与保持 |
| --- | --- | --- |
| 原话及身份 | 原 `InteractionTrace/Journal`、正式请求 | 原文只读投影，绑定同一冻结输入及权限；无独立原话存储 |
| 意图与主模型要求区 | `interaction_intent.py`、`models.py`、`interaction_prompt.py` | 只输出辅助 `criteria`，删除要求片段选择；相位／后台来源校验保持 |
| 工作理解及成果 | 既有 JSON Artifact、Journal 观察、读搜工具 | 模型按需记录本轮新理解及成果关联，后继读取；不新增最新记录 owner |
| 程序及执行 | Python `Command/Receipt`、Artifact | 原程序、输入清单、双流及终态继续拥有执行事实 |
| direct 核验 | `_verify_before_send` → `interaction_verifier.py` | 完整 user 原文、辅助理解、当前稿及真实执行进入两个现行消费者 |
| claims 消费者 | `research_goal_requirements()`、`research_support_input()` | 与 direct 使用同一原文权威及辅助理解语义；保留统一 goal 检查，不另建核验阶段 |
| 完成及恢复 | `answer_results.py`、SubmittedFinal／Completion、组合根 | 专用分析 required 不受辅助标准为空控制；原预算、实际请求及同稿返回保持 |

模型 Schema、准入、Journal、主 Prompt、direct／claims 核验及当前有效评测消费者同一变更迁移，删除旧要求 `criterion/source` 和撤下的 `sources` 契约；不能并行保存两套可写标准。普通对话的既有触发、交互相位及 `none` 诊断身份保持；共享消费者迁移须核对真实输入与职责，不从 LongDS 外推其效果。旧封存仍按原源码解释。

## 5. 当前口径、工作记录与成果复用

工作记录是模型可变的理解，原用户要求及执行原件各有原 owner。模型在口径、分支、被否定结论或可复用成果有实质变化时，按需用现有 JSON Artifact 记录新解释及其实际成果依据；不要求每次调用填表，也不要求逐条截取用户原文。记录存在、文件名或 JSON 形状不作为用户结果通过条件。

同 run 使用现有精确 patch；跨 run 读取旧记录并 `create` 新的增量记录，引用旧产物、写本轮新理解，保持跨 run patch 禁止。Runtime 不解析业务公式或分支来决定当前规则；多个记录冲突时，主 Agent 据原请求与真实成果修正理解，核验独立判断。最新文件和旧自评不自动胜出。

**目标更新与理解修订。** 每个新用户请求形成新 run，完整实际历史由当前请求冻结，意图阶段生成本次辅助标准。用户可以修改、补充或恢复旧条件；模型依据全部 user 原话判断哪些仍适用。Runtime 不按消息新旧自动解决业务冲突。同 run 恢复沿用原消息和已提交的辅助解释；反馈可纠正当前工作理解，不把原始辅助解释升级为不可质疑的用户标准。

反馈不重写冻结的用户消息或原 Intent 输出。发现 `exactly three`、lead 等错误时，主 Agent 可修正当前解释及程序、成果和回答；再次核验仍以用户原文为准。下一轮消费实际已交付修订稿和合法历史原件，不能仅因旧程序较新、执行成功或旧标准仍存在就复用错误口径。工作记录按需生成，是否建立文件不计通过；跨轮计算和回答实际使用修正后的口径才计通过。

模型可根据真实成果修正理解、方法和计划；发现误解时修订程序、成果选择和回答。改变用户目标须有新用户要求或已有明确授权，不能由工具失败、模型笔记或核验反馈代替。不新增 Goal 修订状态机，也不为纠正模型理解重新改写用户原文。

| 用户变化 | 模型必须处理的关系 | 执行／恢复边界 |
| --- | --- | --- |
| 只改一项，其余保持 | 结合完整历史保留仍适用条件，只改指定项 | 新程序及输入产生新执行事实，不修改旧结果 |
| 临时敏感性检查 | 区分主口径与本次假设，比较各自成果 | 临时结果不因最近算过就替代主口径 |
| 回到历史状态或组合历史读法 | 据原请求和匹配程序／结果选择定义 | 不按轮次自动挑产物，不拼接不兼容公式 |
| 条件变了仍用旧结果 | 检查数据、程序、参数及总体是否适用 | 不适用时重算或说明缺口，旧 Receipt 仍保留 |

**每次主模型请求。** 沿现有 `build_interaction_system_prompt()` 重建要求区，将辅助标准标明为可纠正的理解；完整当前请求及正式入口的实际历史仍通过原会话消息传入。目标输入与工作记录、摘要、执行事实和最新反馈分区表达。压缩不能用摘要替代原用户要求；必要原件缺失或容量不足时沿原准入／反馈处理，不静默裁掉。

这保证实际输入的来源和角色可核对，不保证模型内部注意或理解正确。实际请求审计分别检查原文到达、辅助理解性质及最新反馈，真实动作、修订和连续用户结果验证语义遵循；不以模型复述目标证明理解成功。

## 6. 核验材料、反馈与交付

**触发与判断。** 本候选的独立 Python 授权分析实验组显式配置 `verification=required`；在该已配置的合同内，每个最终 `answer` 必须核验，辅助标准为空也不能绕过。是否将这一装配采用为生产方案须通过本设计的能力与收益判断，不因原文传递方案而自动决定。普通非分析触发和 `none` 诊断身份保持，不增加动态任务分类器或默认核验开关。

**标准如何确定。** 用户原文拥有业务目标、范围及变更；已有产品合同拥有授权、执行终态、来源身份等固定不变量；模型改写只辅助解释。明确且可计算的检查由确定性代码负责，开放业务语义由模型结合原文判断。用户或正式任务已有 rubric 时直接提供；没有时，核验可直接理解完整原文，不必另建标准识别模型。含混到影响结果且无法从现有事实确定的要求沿原澄清机制处理，不让 grader 或模型摘要静默补成硬条件。

核验先按完整用户原文理解当前目标及仍生效的条件，再审视辅助标准、程序、成果和当前回答。辅助标准只是阅读提纲：遗漏时仍检查原要求，冲突时以原要求为准。不得按一条错误辅助标准反向判合法回答失败；也不得因为回答满足全部辅助标准，就忽略用户原文中未被提取的义务。

| 输入 | 来源、物化和限界 |
| --- | --- |
| `user_context` | 当前 run 冻结消息中的全部 user 正文及原顺序，由 Runtime 直接提供，包含完整当前请求；不经模型选段、摘要或重抄 |
| `interpreted_criteria` | Intent 模型的辅助标准只读投影，清楚标明可有误解和遗漏，不作为独立验收基准 |
| 当前稿 | 当前 SubmittedFinal 的确切正文及引用，不以提纲、旧稿、工具结果或准备写的内容替代 |
| 明示引用 | 原 `cited_units/CitedEvidence` 的来源及坐标保持，不伪装作者已经引用 Runtime 另行取得的材料 |
| `execution_basis` | Journal 派生的本 run 已终态 Python 程序／回执，以及本轮实际读取的历史程序／结果；按 ActionObservation 或 Artifact 身份恢复唯一执行关联、完整程序、输入清单及实际返回主模型的输出范围。失败／未知明确保留，不自动选最后一次执行当正确结果 |
| 材料不足 | 必要历史、被指代成果、输出或输入前提缺失时，返回 `insufficient_evidence` 与具体缺口；不以辅助标准、笔记或文件名猜补 |

`execution_basis` 只是执行事实的本次只读投影，未带用户可见代码引用的正文也可使用真实计算依据；不能将无明示引用等同没有执行依据。历史结果仅在本轮实际读取或合法明示绑定后纳入，Runtime 不替模型挑有利结果。需要数据正文时按实际缺口补读，不无界注入全部历史执行。

现有 direct 工具先逐 `CitedDraftUnit` 调用 `interaction_cited_support`，通过后再调用 `interaction_semantic_verification`；前置拒绝可提前返回。两处均获得本次完整 user 原文、辅助理解和真实计算依据。单位的明示来源归属仍按其引用检查，计算支持可用明确标记由 Runtime 恢复的执行材料；整稿调用判断用户目标，前置支持不替代它。原拒绝与三态输出保持，不声称一次 workflow 只有一次模型调用。

核验恢复的程序与主 Agent 实际已读内容分别记录。本候选不新增核验工具循环，缺材料沿原反馈交主 Agent 补读再提交。完整请求按原 Model Port 容量准入；用户文本有限不代表所有任务都短，超限时反馈实际缺口，不自动转为模型片段选择或静默裁剪原要求。代码存在或打印“通过”均不证明符合用户规则。

核验区分原要求、辅助理解、实际程序、结果与本稿，只评估当前稿采用的口径，不把合法临时假设或已废弃试算当当前结论。沿原 criterion ID／反馈说明冲突及可修订对象，不提供官方答案、解题代码或 Runtime 编造的正确值。主 Agent 决定修订程序、重算、换用匹配成果、补证或返回限制，再提交完整稿。

全部 user 原文、辅助标准、程序及证据版本、读取范围与当前稿均进入实际工具参数和 `expected_digest`。回执仅在同一运行及相同输入下复用；新用户请求不继承旧通过或旧拒绝。交付仍返回通过核验的确切正文，语义失败不因轮次耗尽降级成功；原预算、服务及未决执行停止边界保持。

对应机制是同一个交付前语义核验及反馈回环，不是给每轮新增专用检查器。原始要求、程序和成果提供上述对照所需对象；核验反馈指出与原要求的冲突，主 Agent 承担修订和真实执行。表格写明的是候选如何作用于具体失败，不代表模型已具备该识别及修订能力；各行都须由真实结果验证。

七项只覆盖已定位的代表机制，不声称解释全部 31 个零分。[整体审计](verify_results/analysis-correctness.md#8-task2-整体方案审计)保留尚未逐字段归因的轮次；E2 对全部 34 轮评分并定位残留失败。评测端的隐藏参考字段不能写成核验器的新业务要求；有争议的缺字段判分与已证实的错误数值／集合分开记录，不改写旧分数，也不以推测承诺核验器必然达到官方全分。

Q0 仍为原四项输入、八次 workflow 的资格诊断，不扩用其预算，也不冒称历史已有这次核验。V1 在独立回放身份下消费封存的完整真实会话、实际 Intent、程序／结果和稿件，经正式构造器形成两版本请求；原 `none` run 不改装配。实际反馈继续交给原主循环，以真实模型、Python 和实际再提交验证修订，不注入理想标准、正确程序或模拟反馈；这属于 Offline Eval，完整 Product E2E 另从空对话进入。不能还原必要真实阶段时先补齐材料或从正式入口取证，不裁剪材料凑次数。

V1 每项每版本固定十个独立旅程，共 140 次初始 workflow 提交，修订与再次核验另按实际消费累计。错误输入须 10/10 产生准确可用反馈、10/10 修订后达到该项原用户结果；合法第 4 轮误拒 0/10。首判、协议恢复、首次修订及最终结果分开报告，错误已识别但未改正不能计修复。七项完整身份、可执行回放／断言及 token／时间上限未封存前，不启动 V1。

**识别能力与引入价值分别验收。** Q0／V1 回答核验能否识别真实错误并产生可消费反馈；E1／E2 回答该装配下连续用户结果是否成立。它们不自动证明独立核验优于把相同预算用于主 Agent 自检。采用前先利用真实错误稿的责任边界反事实，比较直接交付与核验后实际修订，分别报告准确纠错、合法误拒、被误导改坏、未决，以及全部前置支持、整稿判断和修订消耗的 tokens／延迟。主张优于同预算自检时，须另封存相同模型、任务和总预算的对照、判据及停止条件；没有该对照就不作必要性或最优性结论。本轮不增加付费组数或自动启动比较；不在成本上限内取得净改善时，不准入新增独立核验装配，已成立的输入保真或局部能力仍按原判据保留。
