# 个人知识 Agent 的场景拓展 Spec

原问题编号：`NON-RESEARCH-TASK-DIRECTION-001`，保留选型取舍与来源追溯。2026-10-17 起草，2026-10-18 澄清研究扩展可以参与长任务验证后，独立新业务不再单独排队。本文保留场景比较及未采纳会议规格；当前主线由[研究扩展 Spec](knowledge-decision-delivery.md)拥有，准入由 [Future 队列](../../future/design-optimization-backlog.md)拥有。外部任务事实由[数据参考](../../agentRef/task-benchmarks.md)拥有。

## 1. 目标、范围与依据

**选择能减少用户协调负担、需要持续积累有效进展、结果可以验收的场景。** 当前优先补齐研究能力及长任务的交付证据，研究扩展可作为主线；独立新业务不是前置条件。仅有个人知识问答、冲突清理和改稿，尚不足以支撑这一展示；为展示而建设采购、客服或通用办公平台，也超出当前目标。执行边界由完整目标及实际缺口决定，不先选外部工具，再靠追加恢复和核验机制包装成长任务。

长任务沿[现有定义](../../interview/03-capability-axes.md#51-长任务以持续进展和结果收敛为核心)：同一目标下有依赖的多轮决策，实际成果被后续消费，新事实影响策略，最终交付完整结果。日历跨度、应用数、运行时间或强制三轮对话不能单独证明它。

### 1.1 部署痛点与选型依据

以下来源于 2026-10-18 复核。它们支持痛点及任务类型存在，不证明本工程已改善相应问题；场景推荐是基于这些证据与本工程边界作出的判断。

| 与本工程相关的痛点 | 外部依据及适用限制 | 选场景时需要观察的行为 |
| --- | --- | --- |
| 能运行但不能持续正确交付，用户仍需逐步监督 | [MAP 正式论文](https://proceedings.mlr.press/v306/pan26a.html)访谈 20 个团队并调查 86 名生产／试点系统从业者，可靠性为主要挑战；68% 在不超过 10 步后需要人介入。它描述样本实践，不是所有 Agent 的能力上限 | 自动完成有依据的必要工作，只把关键缺失信息和用户决定交回；交付看结果，不看工具次数 |
| 质量与评测不足，运行轨迹好看不等于有用 | [LangChain 调研](https://www.langchain.com/state-of-agent-engineering)中质量为首要阻碍，观测采用率高于离线评测。问卷在 2025-11 至 12 月收集，页面 2026-06 发布，不能当成 2026-10 新采样或全行业统计 | 预先固定可读产物、实际业务结果和禁止副作用；不以 Trace、计划完成或回答流畅代替 |
| 请求省略重要约束，知道历史却未用于下一动作 | [π-Bench](https://simplified-reasoning.github.io/Pi-Bench/)用持久会话、工作区及隐藏约束检查主动消歧与完整交付；已读 researcher 的 20 题及 profile、episode | 从合法历史与资料恢复相关偏好；缺关键事实时针对性询问，后续动作实际使用回答 |
| 私人资料分散，跨来源理解与实际行动不能脱节 | [MyPCBench](https://github.com/ljang0/MyPCBench)把匿名请求改写到一致的合成人物与应用；已核对筹备及改期题。它是模拟环境，不能替代真实提供方接入 | 资料支持议题和范围，日历提供当前排期事实；变更后更新正确对象并核对结果 |
| 环境在等待中变化，Agent 忙等、早停或重复执行 | [SentinelBench](https://www.microsoft.com/en-us/research/articles/sentinelbench-a-benchmark-for-long-running-monitoring-agents/)研究有独立事件时间轴的监测任务；时间轴和应用均为合成 | 若真实目标需要等待，区分未满足、满足、取消和到期；减少无变化时模型调用。当前先作为后续候选，不直接恢复任意后台循环 |

上述来源的任务与评分核查见[新增材料](../../agentRef/task-benchmarks.md#7-个人上下文事项执行与时间变化任务)。网页来源快照及 SHA-256 见[报告清单](../../../.tmp/agent-pain-scenarios-20261018/reports/source-manifest.json)。公开材料的存在与目标用户是否愿意采用是两项判断，实际需求仍待固定。

### 1.2 当前可复用基础与缺口

- [Conversation](../../../src/personal_agent/application/conversation/service.py)及其工作清单、已提交执行事实，提供跨轮消费与继续推进的基础；已有收益仅限[原用例证据](../../interview/06-evidence-and-release.md#5-成对证据只支持对应设计)，不转计新场景成绩。
- [KnowledgeService](../../../src/personal_agent/application/knowledge/service.py)及资料读取提供个人项目事实；原始材料、Claim、稿件和执行记录分别沿现行 owner 管理。读取许可不等于可以向参会人公开全部内容。
- [ArtifactService](../../../src/personal_agent/application/artifacts/service.py)已有作用域读取和生成内容提交，但用户侧读取、版本接续及对外分享要分别核实。会议业务候选将完整准备稿交给用户，日历只放其批准的议题摘要。
- [当前架构](../../architecture/core-architecture-current-state.md#6-工具mcp-与智能体)允许受治理的 MCP 能力映射。生产源码未发现日历业务接入；通用 MCP 存在不等于已能查询、改期或邀请。会议业务候选选了飞书测试日历，实际租户、身份、权限及接入仍待准备，不因此进入长任务主线。
- [后台边界](../../architecture/core-architecture-current-state.md#4-后台持续运行边界)只支持已定义周期业务，不提供任意目标的响应后接续。会议业务规格仅按前台交互及用户后续输入推进；主场景重选不自动获得后台生命周期，也不以周期研究代替动态事项看护。

## 2. 当前推荐与定位

**当前先验证“公开检索方案的复现实验与比较”，长任务主展示资格由实际轨迹判断。** 候选已取得源码和数据，具体请求、成果依赖及验收由[研究扩展 Spec](research-experiment-acceptance.md#11-首个用例公开检索方案复现实验)拥有，尚无运行成绩。英文 SciFact 比较不能直接决定中文私人知识库选型，固定扫描也不能自动证明持续推进。独立新业务不再作为本轮额外待办。会议筹备与改期继续退出主选：三案主要是准备稿、确认建会及用户明确指定的修改，追加未知写入恢复仍不能补齐持续进展证据。保留其业务规格，不据此推进日历接入。

| 场景 | 用户结果 | 当前取舍 |
| --- | --- | --- |
| 项目评审筹备与改期 | 有依据的准备稿、用户批准的议题摘要、正确的日程及变更结果 | 退出长任务主选；保留业务候选及来源，不继续扩成事务平台 |
| 个人机会的条件跟进 | 机会满足个人条件后提示或推进已授权下一步，未满足时等待 | 对应持续运行痛点，但需新的后台生命周期与真实需求，暂不先做 |
| 目标型项目答辩训练 | 基于真实作答诊断、追问和复盘 | 与个人知识接近，但题目判据与反馈校准成本较高，仍为备选 |
| 方案共创、审校及关联知识维护 | 实际新版或有效知识被维护，未选内容保留 | 辅助候选，主要复用已有研究、写作及知识能力，不作为新增主方向 |
| 公开检索方案复现实验 | 实际比较基线及候选，交付配置、原始结果及可复现依据 | 首个研究执行与交付切片，正文归[研究扩展](research-experiment-acceptance.md#11-首个用例公开检索方案复现实验)；长任务能力待实际成果消费及接续验证，尚无 baseline 或 target 成绩 |

### 2.1 产品定位与最简单替代

当前[产品名称](../../../README.md)保持。“个人知识支撑的事项执行”仍是候选定位，尚未因会议方案变成产品决定。真实日历读写会向个人助理扩展，受限实验执行会向个人研究工作台扩展；两种代价分别论证，不以增加业务种类或扩大平台范围替代长任务证据。

最简单替代方案是同一模型结合普通对话历史、资料读写及日历工具；已知时间和参会人的单次建会也可由表单或确定性脚本完成。资料理解和下一动作选择是任务需要的语义决策；本工程要另外回答：在真实资料规模、跨轮、等待、部分执行及失败边界下，Harness 怎样保持目标、有效成果和执行约束，并以什么证据证明贡献。若简单路径已经满足同一用户结果及约束，不新增专门会议 Agent、规划器或任务平台。

[工程架构](../../architecture/README.md)继续拥有现行责任链；本轮不改公共 loop、hook、middleware、插件协议或业务事实 owner。详细主循环候选仍由[原 Spec](conversation-loop-boundaries.md)拥有。

### 2.2 展示目标：Harness 对持续交付的贡献

**本项目要展示运行系统怎样让同一模型在实际执行约束下保持进展并可靠交付。** “资料理解、影响判断、动作选择”主要描述模型职责；仅以自主规划难度评判场景，也没有回答 Harness 的工程贡献。用户给出明确步骤仍可能需要可靠的上下文、授权和恢复机制；机制必要性要看真实边界和对照结果。

这里的 Harness 包括围绕模型循环的上下文物化、运行事实、动作准入、能力调用、预算和交付协议。具体业务继续拥有材料、日程与合法迁移；公共主干由[主循环 Spec](conversation-loop-boundaries.md#3-主干与职责)拥有，不在本场景另建运行系统。第 3.4 节三案尚未运行，下表分别说明代码基础与场景缺口。

| Harness 边界 | 在这个场景应承担什么 | 已核实基础与仍缺证据 |
| --- | --- | --- |
| 有界上下文与可恢复原文 | 大结果保留完整原文及作用域引用，本轮只物化所需索引／窗口；后续能补读遗漏依据，而不是反复注入全部历史或只留无源摘要 | [Context 物化](../../../src/personal_agent/application/conversation/context_materialization.py)及 [Conversation 的卸载和补读](../../../src/personal_agent/application/conversation/service.py)已有实现；当前材料是否实际触发该边界、同预算下是否改善交付尚未验收，也不能据此宣称已有任意会话自动压缩 |
| 进展与跨边界接续 | 保留有效稿件、已提交动作与结果、尚欠工作；接续时从权威事实构造输入。待执行任务的恢复与已交付后的新请求分别处理 | [Journal](../../../src/personal_agent/application/conversation/journal.py)已有工作清单绑定事实投影和文件持久化，并在 [Runtime](../../../src/personal_agent/orchestration/runtime.py)装配；当前三案只有连续会话，不检验重启或上下文轮换，也不证明日历副作用可恢复 |
| 授权与部分执行 | 将批准绑定到确切对象、参会人和摘要，执行时不让模型重新生成批准正文；区分未执行、已成功和结果未知，对未知外部写入按提供方能力对账或明确停止 | [工具网关](../../../src/personal_agent/governance/gateway.py)已有 grant、策略和幂等原语；业务确认仍限现有知识动作，日历绑定未接入。通用超时重试或本地幂等记录不能证明外部写入恰好一次，提供方对账及部分完成协议仍待核实 |
| 子能力的统一治理 | 任务需要研究或委派时，给出有界输入和权限，消费结果引用及明确停止原因；内部调用继续计量，子级成功不能直接完成父级目标 | [AgentGateway](../../../src/personal_agent/agents/gateway.py)已有作用域、提交及返回结果治理；研究内部与主循环仍存在已记录的职责混合，完整模块化边界是候选。当前会议用例不要求子 Agent，不能为展示强制委派 |
| 交付与有界停止 | 按本任务结果契约消费业务事实和必要语义判断，分别解释成功交付、等待与限制；确定性 Gate 不自行判断准备稿语义 | 沿用 [Verification／Completion](../../topics/verification-and-completion.md)及原预算协议；具体依据与判据见[本场景完成验收](#35-完成判据材料与日历分别验收)。日历结果链路未接入；不为所有步骤添加模型 Judge |

这些机制接在每轮模型输入和动态动作执行的共同边界。业务路径可以变化，各能力仍消费同一身份、授权、事实引用及预算契约；稳定的日历事务由业务代码封装。hook、middleware 和模块装配只是组织这些职责的方式，存在这些名称不构成收益。

固定源码可支持这种职责划分：[Deep Agents 的装配](https://github.com/langchain-ai/deepagents/blob/fd3e64ab6b605450bed5a2c22ef2ec84cd40542e/libs/deepagents/deepagents/graph.py#L894)把文件工具、子能力、摘要、审批等 middleware 及 checkpointer 交给 `create_agent`；[OpenHands 的 Conversation 运行循环](https://github.com/OpenHands/software-agent-sdk/blob/6530325e9dd0ea1b6b4f1994d7dab52764cfc3f1/openhands-sdk/openhands/sdk/conversation/impl/local_conversation.py#L1933)管理运行、暂停及停止条件，再驱动 Agent 步骤。2026-10-18 复核既有快照并校验摘要，未运行外部项目；它们分别提供装配与生命周期参考，不证明本工程日历恢复有效，也不要求照搬其 hook 控制权。完整比较仍由[源码参考](../../agentRef/multi-agent-and-delegation.md#11-子能力调用与内部循环的源码核对)拥有。

### 2.3 如何让用例检验 Harness

现有三案只作为材料、批准范围、实际日程及变更结果的业务验收候选。排期可按规则计算，S3 已列出主要修改项；实际覆盖不足以说明 Agent 如何在一个未交付目标下自主推进多个相互依赖的成果。连续会话、恢复与同模型机制对照分别有价值，也不能相互替代为完整长任务成绩。

一个更能区分执行 Harness 的独立候选边界是：用户批准实际提议后，提供方可能已创建事件，本地却未收到成功回执，随后进程中断。接续时应恢复确切批准和已有准备稿，依据提供方支持的幂等或查询机制核实动作结果；确认已执行时复用实际事件，只继续仍未完成且仍获授权的动作。无法确证时报告不确定并停止相应写入，不凭相似标题认领事件，也不直接重发创建。调用记录、回执与外部业务状态各有 owner，本地日志不能填补未知外部事实。

该候选尚未登记为可执行用例，也不是当前已实现的能力。它只能说明一种执行恢复边界，不能补齐长任务持续进展的证据。仅在另有真实会议需求时，先核实提供方的查询／幂等、参与人部分完成和授权契约，再固定独立验收；必要故障发生在真实请求和服务之间，不注入理想模型结果，也不追加到第 3.4 节三案的关闭条件。

机制收益按以下顺序准备：先固定真实用户结果、实际材料规模及执行边界；再选一个必要机制，保留同模型、工具能力、业务输入、服务事实及预算的可比简单路径；最后分别检查完整用户结果与该机制的因果边界。安全与权限底线保持，不能用生产越权路径当对照；隔离消融按原证据规则执行。上下文看有据交付及实际输入成本，接续看成果可用及必要重复工作，副作用看实际事件、参与人和不确定状态是否正确处理。没有测到差异就不主张独立贡献，也不预写简单循环必然失败。

当前选型结论是：会议保留业务候选，但停止把它作为长任务主展示继续设计；主场景按下节重新选择。[既有机制证据](../../interview/06-evidence-and-release.md#5-成对证据只支持对应设计)按原任务解释，不转计本场景成绩；新增生产结构仍需原准入证据。

### 2.4 长任务主展示应观察持续进展

**核心问题是一个完整目标怎样经过多次有依赖的推进形成可交付成果。** 工作清单、上下文、恢复、预算和完成门禁支持这一过程，各自存在或局部通过不构成长任务成绩。已有跨轮／重启复用证据继续成立，尚缺的是代表性复杂目标的完整交付与机制贡献。

| 选型时检查什么 | 需要看到的实际行为 | 常见替代品为何不够 |
| --- | --- | --- |
| 目标由谁持续承担 | 用户提出完整目标后，Agent 据真实结果继续选择必要工作，只把关键用户决定交回 | 用户逐条布置下一动作，主要说明指令跟随；不排斥真实的用户中途调整 |
| 中间工作是否累积 | 形成能被后续消费的事实、配置、分析或产物；有效成果被保留，未完成部分有据可查 | 只有工具调用、口头进度或重复改写，无法说明向完整结果推进了多少 |
| 新结果是否改变推进 | 实际实验、资料缺口或执行反馈改变后续工作，旧成果按适用范围复用，失效结论停止沿用 | 预写固定动作链或只换最终措辞，没有证明结果影响了后续行动 |
| 工作上下文能否接续 | 在任务真实需要跨上下文时，恢复原目标、当前成果及缺口，继续完成剩余工作 | 只恢复一个待执行请求，或始终保留完整聊天记录，不足以证明跨上下文持续工作 |
| 整体结果是否验收 | 初始用户结果及必要约束得到检查，阶段进展与完整交付分别报告；机制收益另作适用比较 | 一次 Judge 通过、工具成功或中断恢复，不独自证明全部目标完成 |

这些是新主场景的选型与取证问题，不是追加到旧三案的关闭条件。实际任务能够简单完成时就简单完成；不设最低调用数、强制三轮、虚构事故或故意缩小上下文来制造长任务。主展示确需某种跨上下文能力时，该主张必须由实际边界覆盖。

2026-10-18 复核 [Anthropic 的长任务 Harness 实验](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)：其重点是跨上下文保留功能目标、形成增量成果并按实际用户路径验证，压缩和循环本身仍会出现半成品及提前结束。它是全栈开发实验，不能直接证明个人知识场景有效，也不要求照搬初始化 Agent、Git 记录或全部机制。

当前沿[公开检索方案复现实验](research-experiment-acceptance.md#11-首个用例公开检索方案复现实验)准备研究扩展，用户角色、中文请求、公开数据及交付验收已具体化；环境、权限、预算和正式 baseline 仍待取得。旧 CSV 候选已收敛到该唯一主线。只有实际形成依赖成果消费及必要接续证据，才主张覆盖到的持续推进能力；若固定脚本已满足同一契约，优先简化，不预授长任务主展示资格。

## 3. 业务候选：个人项目评审筹备与改期

### 3.1 用户目标与最小交付

改编自然请求：

> 帮我准备并安排下周的项目评审。结合我的项目记录，整理这次值得讨论的进展、依据和未决问题，给我一份准备稿，并找合适的时间。时间、参会人和要放进日程的议题摘要先让我确认；确认后创建日程。资料不够时只问影响安排或评审内容的关键问题。

价值假设是减少用户在项目资料、待确认问题和排期之间逐项协调，降低遗漏、无据表述和错误邀约。它不是已测得的省时收益。首版限定一个项目、一次评审、一个日历提供方；完整准备稿面向用户，批准的摘要面向批准的参会人。邀请已创建不代表对方已接受，评审已安排不代表评审已举行。

有依赖的候选信息流：

```text
用户目标＋可见项目资料＋相关历史
→ 判断已有进展、依据与关键缺口，必要时询问或研究
→ 读取当前日历，提出议题、参会范围和可行时段
→ 消费用户对真实提议的确认或变更
→ 提交获准日程，核对实际结果，交付准备稿
→ 用户后续提出改期／缩小范围时，消费当前事实继续处理
```

这表示可能的信息依赖，不是固定工具顺序。只缺时间时可以先询问；现有材料足够时不额外研究。后续改期、故障或中断仅在真实任务需要或预声明反事实中出现，不人为加入主线凑长任务。

### 3.2 需求与责任

| 编号 | 必须产生的结果 | owner 与防护 |
| --- | --- | --- |
| M-01 有据准备 | 准备稿区分实际进展、已验证结果、待证判断和未决事项，能定位项目依据 | 模型判断内容，Knowledge／资料 owner 提供事实；不编造实验、完成状态或评审结论 |
| M-02 关键消歧 | 从合法资料恢复相关约束；未知且影响安排的事实被确认，后续动作实际消费回答 | Conversation 统筹目标；不将旧偏好覆盖当前明确要求，不把所有资料问题推回用户 |
| M-03 当前排期 | 提议与最终日程满足已确定的日期、时区、时长、不可移动事项及适用缓冲要求 | 日历提供方拥有日程事实；只知道用户空闲时，不声称所有参会人均可参加 |
| M-04 批准范围 | 按本次请求，确认前不建会或外发；确认后仅使用批准的对象、参会人和摘要 | Admission 与执行沿现行授权边界；范围变化重新绑定当前动作，不静默外发完整知识库或准备稿 |
| M-05 实际交付 | 用户能读取完整准备稿；日历中存在正确事件，最终答复对应实际事件和当前材料 | Artifact 拥有内容，提供方拥有事件与邀请状态；工具回执、材料生成或模型口头声称不能独自完成目标 |
| M-06 变更接续 | 后续变更更新正确事件，保留未受影响成果；执行结果不明时先核实，避免重复建会 | Conversation 消费已提交事实，实际事件 ID 和当前状态来自执行系统；不另建可写日历镜像 |

项目材料中的开放语义按适用核验契约判断；时间区间、对象、参会范围及实际事件状态用确定性事实核对。不为每个读取、每个段落或每次工具调用添加独立 Judge。合法操作和恢复协议以选定提供方的正式契约为准，尚未确认的幂等、更新冲突和邀请语义不得靠候选代码假定。

后续反馈针对实际结果表达，不要求 S1 必须生成某个标题或必须把候选方案写进日历摘要；已经符合新范围的部分允许不修改。S3 本身已给出明确的新授权，不为形式再询问同样的确认。若真实服务状态使该时段不可用，原授权不覆盖新时间，转为提出替代并等待必要决定，不能擅自改约束。移除乙可能产生提供方的移除通知，不把它误判为再次邀请；最终答复只按实际状态描述。准备稿可以完整呈现在正式对话中，也可用有效产物链接交付；未要求独立文件时，不额外以下载编辑器为门槛。

**两个独立反事实。** 每项使用新的隔离世界和会话，沿真实 S1 结果继续；不复用前一个成功样本的理想提议。

| `MEETING-PREP-CONFLICT-001` | S1 合法预览后，由准备器使用独立身份向真实测试日历新增占用，阻断所提周四空档；用户再确认刚才的周四提议 | 执行前发现当前事实已变，保留准备稿，不建冲突会议或擅自挪原占用；提出实际可行的周五替代。用户确认实际替代后才执行，最终满足同样的材料、范围及日程结果 |

CONFLICT 的环境变化只创建实际占用，不给 Agent 注入工具返回、替代时段或修好的计划；预览错误时保留失败，后续阶段记未到达，不由准备器纠正。该例证明本次确认前状态变化的消费，不声称飞书提供原子时段预留，也不证明所有并发竞争均被阻止。

**评分、预算和准入。** M-01／M-02 检查完整实际稿件、用户要求及提供给 Agent 的来源；M-03 至 M-06 从真实提供方独立读回事件与有效参与人，并比较初始世界及批准内容。必要时用测试甲身份核实相应邀请可见，不以 SDK 成功代替用户可用结果；移动端推送送达不是本组已声明结果。摘要和原文保持采用确定性比对，语义评分允许不同合法表达、议题组织和取证路径，不把参考答案原句或工具顺序当金标。

原用户结果与机制检查点分别报告，能力归因按 [Harness 边界](#22-展示目标harness-对持续交付的贡献)及[机制对照](#23-如何让用例检验-harness)。若主张工作记忆、恢复或规划机制有独立收益，再固定同输入的简单路径及适用因果比较；本组三条能力用例不自动证明任何机制优势。进程崩溃、结果不明恢复、全员可用性和后台持续工作不在首批结果主张中，按真实需要另立边界，不在本组通过后追加为关闭条件。

若会议业务另行入选，保留三条各一次的候选验收，报告失败及未到达，不追加稳定性采样。实际测试账号、身份权限、资料导入引用、业务授权绑定、生产日历接入及语义评分校准仍待取得；模型、预算和可执行命令须在运行前冻结。当前会议未入选长任务主线，不据此启动生产接入或模型实验；本轮模型调用和产品 E2E 均为 0。

### 3.5 完成判据：材料与日历分别验收

**以 S2 为例，整体交付需要“准备稿满足本次要求”与“实际日程符合批准”同时成立。** 本场景候选将 M-01 的完整稿语义验收声明为必需判断，复用现有研究／内容核验及其有效同稿结果；日历结果由代码读取实际事实检查，Completion 不再调用一次整体 Judge。下表是 M-01 至 M-06 的候选验收映射，不新增生产 Schema、核验阶段或通用任务状态，也未改变现行核验触发；通用判定责任由[主循环完成设计](conversation-loop-boundaries.md#41-完成依据从哪里来)拥有，日历接入仍未实现。

| 必需结果 | 输入、判断与通过条件 | 哪种表面成功仍不够 |
| --- | --- | --- |
| 有据准备稿 | 将原用户要求、完整当前稿和项目材料交给既有研究／内容核验，判断来源支持、当前与候选区分及内容覆盖；本场景要求有效通过结果，已有同稿判断按原规则复用，不叠加第二次同义核验 | Artifact 非空、标题包含“验证”、引用 ID 存在，均不能证明正文满足要求 |
| 可读交付 | 完整确切稿件随正式答复交付，或由用户在合法作用域读取当前有效产物引用；代码核对其身份、版本及访问 | 文件已写盘或内部 receipt 存在，不等于用户拿到完整稿件 |
| 获准事件已成立 | 以本次实际批准及 Command 绑定定位真实事件；提供方读回的日期、时区、时长和摘要按预声明比较关系符合批准，必要缓冲依据当时相关日历事实检查 | 创建请求返回成功，不能单独证明时间、摘要正确或当前可行；摘要原文一致由确切内容绑定，不能靠模型复述 |
| 参与人符合范围 | 从提供方核对有效受邀身份与本次批准集合，按提供方语义区别组织者和参与人；所需邀请结果必须实际成立 | 事件存在、参与人数相同或模型声称“已邀请”不足；邀请已建立也不等于对方接受或推送送达 |
| 本次写入已确定 | 原业务 owner 没有与本次交付必需结果相关的未决确认或未知执行结果；缺失时先核实或明确停止，不重发假定失败的创建 | 已发出请求、Plan 全部 completed 或耗尽预算，均不能补成成功事实 |

确定性检查成立的前提是有明确目标身份、获准参数、可信事实和正确的比较关系。例如事件开始时间等于批准值是可机械判断的；“准备稿是否把候选写成已实现”需要解释正文及来源，不能由字段相等、关键词或 Gate 自行推出。业务确认批准外发范围，不自动代替内容语义验收。外部事实只按声明读取时点解释，不把单次读回说成未来日程永远有效。

若实际事件正确但完整稿仍混淆当前与候选，材料义务尚未成立，不能报整体完成；修订稿后原语义报告是否仍适用按原版本和输入绑定处理。若稿件通过但乙未成功加入，日程义务尚未成立，不能以 Judge 通过放行；副作用由日历业务处理，不能只修改最终措辞。两者成立才允许交付当前确切结果，语义判断仍可能误判，产品 E2E 应独立检查实际完整稿及提供方状态。

S1 交付预览后是等待批准，循环可以返回但建会目标未完成。S2 已交付事实保留，S3 按新要求验收原事件变更及当前材料；取消则按取消范围检查保留稿件及零新增安排。预算或故障退出报告实际限制／失败，不因循环停止而计作成功。

## 4. 辅助候选与保留价值

方案共创、审校及关联知识维护继续服务有用的材料维护需求。当前主要是研究、写作、范围控制及受控知识写入的组合，不自动作为新增业务或长任务收益。上一版的 `DOC-REVISE-001` 未登记或执行，本轮撤下其主方向实施清单，保留公开素材及需求边界；不改变任何历史产品结果。

修订素材由 [ARIES 与 Open Canvas 核查](../../agentRef/task-benchmarks.md#5-知识材料修订的具体来源)拥有。ARIES 作者新版含新增实验，不能由只有旧稿的模型补造；Open Canvas 的实际编辑链证明可定位实现存在，不证明本工程改稿正确或自主推进。

若用户另行要求改稿或维护知识，仍须以当前有效引用、实际选择和真实新版验收，未选内容保持，原始资料保留。稿件、Note 和 Claim 生命周期分别处理；只有明确保存要求才走原 Knowledge 写入口。已注册知识工具的 `scoped_agent`／`workflow_activity` 曝光不等于主模型可用，正式入口接通情况先核实。

受限实验及产物交付由[研究扩展 Spec](knowledge-decision-delivery.md)拥有，不另算新业务方向。答辩训练也不因多轮追问就获得长任务或学习收益结论，需实际作答及可靠评分。

## 5. 已比较但不推进的方向

| 方向 | 本轮取舍 | 仍保留的资料价值 |
| --- | --- | --- |
| 采购需求协调 | 需要人员协商、预算及独立事务语义，超出本轮一个日历边界，不作为优先产品方案 | [任务与评分审计](../../agentRef/task-benchmarks.md#4-非代码业务场景的具体任务)保留 |
| 商家售后、航空订单、电信客服 | 需要新的角色、服务权限与领域状态，本轮不推进 | 政策、初始世界及工具事实不外推为个人知识能力 |
| GitHub 事项跟进 | 已选三事项与本工程真实目标的联系不足，不创建远端工作台 | [DeepAgents 记录](../../agentRef/task-benchmarks.md#3-deepagents-上游事项的具体材料)保留组件和关闭原因的区分 |
| 通用编码与环境排障 | 可展示诊断交付，但工作区、进程及服务执行扩大产品边界 | 不为知识及评审场景附加 Shell 平台 |
| 持续机会看护 | 与 SentinelBench 的时间变化痛点相关，但当前缺真实等待目标和后台准入依据 | 保留独立事件、未满足时不误报及成本测量方法；不恢复已撤回调查 Runtime |

这些方向未被产品实验否定。当前取舍依据用户目标、边界及资料可达性，不能因新增 benchmark 就恢复整套跨行业实施计划。“不过度扩展”也不解释为完全不能增加执行能力；任何新增边界须从完整用户目标证明必要性，日历不再是预选的长任务执行面。

## 6. 实施、删除与退出

1. 当前只沿研究扩展准备首个实验交付切片，按第 2.4 节核实成果依赖及持续进展；不把独立新业务选型作为前置待办，也不推进原日历实施清单。
2. 检索实验只沿[研究扩展正文](research-experiment-acceptance.md#11-首个用例公开检索方案复现实验)准备环境、权限、预算与正式 baseline，不在这里另建研究或实验平台。
3. 会议若因独立业务需求重新入选，再核实资料入口、测试日历权限及真实调用语义，冻结第 3.4 节用例、预算和正式 baseline。缺口成立后才补必要映射、授权与交付；不把恢复、后台或额外 Judge 作为必加功能。
4. 用户结果与机制贡献分别验收，简单路径足够时保留简单路径。候选没有真实需求、无法取得事实或被 baseline 否定时，撤回相应生产扩展，保留来源和取舍。
5. 已验证结果进入现行权威正文；原问答、研究与已有机制的独立问题按原规格闭环，既有局部成果不因主展示重选而作废。

本轮完成的是公开痛点、具体任务及候选范围核查；本工程模型调用、产品 E2E 和生产改动均为 0。当前实现与发布资格仍由[工程架构](../../architecture/README.md)及[评测盘点](../../evals/02-current-case-inventory.md)拥有。
