这些问题共用一个“交付前核验→真实反馈→主 Agent 修订→再核验”的机制，不是七套新检查器。各行的输入对象和冲突关系不同，必须逐项证明该关系确被识别、修订程序／成果确已生效，才能声称对应问题被解决。核验材料不足时返回缺证，不能假定模型只凭最终表格就能发现历史池错。

引用、完整原文、程序原件及工作记录是这个回环的支撑，不独立执行纠错。保留已有 Python、Artifact、Context、压缩和恢复；引用协议简化只降低选择成本，收窄 assistant 历史另做原因对照；NUM 精度／原件提交及 claim 消融继续后置。共享 Schema 迁移仍须固定普通／claims 的真实回归输入及预算，不能用 task2 证明其他消费者语义保持。共同新增成本是核验、修订及重算的调用和延迟、输入容量及误拒；没有七套独立机制的成本或收益主张。

采用依据复用[固定 smolagents／OpenHands 调用链](../../../agentRef/runtime-recovery.md#9-原始目标工作记录与最终复核的分工)：原任务与派生理解分开、真实历史与当前稿共同检查、反馈继续被原 Agent 消费。它支持上述回环结构，不证明模型能识别表中任何一项具体错误，也不保证阻止首次错误。NUM 的 Quarto／smolagents 采用关系仍由[成文候选](../analysis-result-correctness.md#2-参考机制与取舍)拥有。

### 8.3 本轮修正及下一可执行边界

本轮关闭设计表述和覆盖规划缺口：明确识别错与后续执行错分别归因；引用属于支撑；交付前核验不等于执行前修正提取器；V1 固定 task2 第 2／3／4／5／6／24／34 轮，并把真实反馈、实际修订、再次核验和后轮消费分开取证。输入对应的完整结果及合法对照由[SEM §7](../longtask-semantic-consistency.md#7-验收用例比较身份与预算)唯一拥有，不在本文复制一份答案表。

尚未运行的验证不写成审计通过：原 Q0 保持四项、两版本共八次 workflow；V1 七项各版本十个独立旅程，即 140 次初始 workflow，后继修订另计；E1 是 task2 1—6 连续新对话，E2 是新对话完整 34 轮，并在 21→22、30／33／34 及各修订后接续点检查残留失败。Q0 只是资格诊断，V1 才判断相应局部修复，完整任务未达 34/34 保持未完成；局部既有关闭不被独立后续失败重开。

下一步先准备零模型的完整输入台账、正式请求构造及可执行回放／结果断言，固定实际容量、U+1 核验调用、修订旅程、绝对截止和逐阶段额度；同时补共享消费者的回归身份。上述准备未完成不启动对应模型组。只在已有合法授权及具体额度内运行，不继承旧 60M 许可或扩大原 Q0 预算。与当前直接交付原稿比较实际纠错、合法误拒、被改坏及完整成本；只有额外做同预算自检对照，才可主张独立核验优于自检。

本次审计完成的是方案边界及验证计划修订，未完成的是运行器、具体预算、模型效果和产品验收。生产修复不能用文档检查、模型复述或检查字符串代替；已验证执行基础继续保留。
