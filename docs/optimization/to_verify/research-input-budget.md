## 已证明事实

删除自动复核并解除 Coverage 引用阻塞后，同一中文正式入口仍在 2,000,000 产品 token 原预算下未交付。实际 2,034,940 tokens、50 物理请求、2,587.80 秒，完整用量与 Runtime 相等，服务未知零。c1–c8 Source 通过，c9 的具体出处及全篇否定范围反馈未完成修订；Coverage、Final、Completion 和 grader 未到达。原 0/1 保持，见[正式密封](../../../.tmp/coverage-reference-production-target-20261015/REPORT.json)。

本轮 94.03% 是输入：Source 十八次输入 895,350 tokens，每次相同的 1,198 个去重坐标，单次 48,029–53,971；选证十六次输入 737,884，写作／动作十五次输入 279,089。原会话和冻结目标在所有选证请求中相等，没有据此证明目标丢失。源材料在单次内没有重复坐标，跨调用重新提交的事实见[零调用审计](../../../.tmp/coverage-budget-review-20261015/REPORT.json)；输入量不等于实际费用，也不能单独证明延迟或语义干扰。

原始响应另证实输入缓存已生效：Source 十七次有缓存明细的请求，846,258 输入中 617,344 命中，比例 72.95%；另一次 49,092 输入的缓存明细缺失。全轮四十五次有明细请求中，1,715,789 输入有 972,608 命中，比例 56.69%；另五次明细缺失，不能按零命中计算。缓存折扣、实际账单及首字延迟未核实，不据总输入量认定费用瓶颈。当前 Runtime 按服务方 `total_tokens` 累计执行预算，缓存命中仍计入该总量；这是停止条件事实，不证明预算口径应立即修改。

实际 writer 多次在修复引用缺口时新增断言，随后继续接受有据反馈；不能把有进展的正常修订定义为核验阻塞。自动 earliest_failure 指向早期已恢复的取证缺口，不能替代最终预算停止归因。当前未证明每次反馈均有问题，也没有正式用户结果通过。

## 重复预算失败后的取舍

同一原预算再次失败后曾停止整轮重跑。2026-10-15 用户明确要求先扩预算验证交付，再分析输入优化；按下节新预算只执行一次独立正式样本。原已验 Source、引用恢复、评分器和全部失败身份保持，同义 Prompt 补丁与输入裁剪仍不准入。

本日检索两份 A 级机制：[OpenCode V2 compaction](https://dev.opencode.ai/v2/docs/compaction/)按窗口保留近期内容、持久原历史并明确摘要有损；[LangChain short-term memory](https://docs.langchain.com/oss/python/langchain/short-term-memory)在调用前按 token 管理、过滤或汇总历史。本项目的大头是每次新物化的同一原文目录，普通历史摘要不能直接解决；核验需要精确原文、来源身份、已读范围和冻结目标，不能用摘要替代引用或删掉反证材料。不同版本的 compaction/prune 参数不混用，不引入框架。

输入优化留待完整交付及重复阻滞核查之后，再按缓存命中、实际费用、延迟和预算约束判断必要性。可能的原资料保真、按需取回及完成预算预留均保持待证。统一六类单次 Source 的证据用途保持：绑定引用只能支撑当前断言，实际返回范围用于判断资料缺失描述。
