## 79. 生成禁令在动作与真实拒稿修订循环中的迁移

**禁令在一次真实拒稿后的合法修订稿中保持，完整循环被两个协议问题阻塞。** 预声明见[实验计划](../../.tmp/coverage-ban-loop-20260912/plan.md)。两条轨迹各一次：一条从第 77 节原错误交接的 72/122 继续，一条从第 78 节真实拒稿和已有 88/122 读取状态恢复。后一条校验并恢复原 Receipt，使用生产函数重建工具信封，未编写新的语义反馈。

两条均先进入现有动作阶段，随后自主读取、生成 Final、调用未修改的 Verifier；真实拒稿继续返回动作阶段。唯一候选变量是每次 Final 加入同一禁令，动作及 Verifier Prompt 不变。每条最多 16 次父级决定、32 次读取、三份新稿、1.2M tokens；模型、thinking、接口与单次 32768 输出、480 秒、零重试保持。

分别检查无据全文否定、API 范围、补证、真实反馈后的修正及完整来源支持，首次有效通过后独立复核，不能用错误通过证明闭环。冻结初始上下文且未经过完整 Admission、Journal 与 Completion，归类为 Offline Eval 和读取 Integration，不是正式入口 E2E。生产代码及配置保持，GPT Researcher 继续暂停。

### 两条轨迹的实际结果

**补证、生成约束和有效回执必须分开判断。** 两条均按预声明保留协议失败，没有将普通文本转成 Final，也没有修补标准字面量制造回执。

| 轨迹 | 已发生的局部行为 | 停止位置与判定 |
| --- | --- | --- |
| 原交接继续 | 六次读取，新增 32 段至 104/122；自主用 `Image` 定位到第 58 段，并在随后文本中使用结果格式条款 | 第五次动作模型调用未返回工具调用，虽然请求设置 `tool_choice=required`，却直接输出普通答案文本。生产提取器报 `provider_action_missing`，零合法 Final、零新 Receipt；未到禁令消费点 |
| 真实拒稿恢复 | 原回执与原稿绑定保持；模型先请求 Final，没有新增读取。新稿未作全文缺项否定，保留 API 区别，并将通用调用引用的强制概括改为原文 `should` | 随后 Verifier 返回四项报告，但改写其中两项标准，无法生成有效 Receipt。只有一份新合法 Final；封装字段仍使用“必须”，完整支持未通过 |

第一条的初次 wire 与第 77 节动作分支相同。新增读取发生在 Final 禁令出现之前，所以只能证明这条已有动作通路的自主补证，不可归因于生成禁令提高了读取量。非法阶段输出虽然引用了第 58 段，也不具备正式交付或语义验收资格。其最早阻塞是模型没有遵守动作阶段协议，不是禁令或资料不足。

第二条 Verifier 删除了 URL 标准中的空格，将“官方 URL”返回成“官方URL”；来源支持标准中的“或 URL 正确”也变成“或URL正确”。报告数量为四，Pydantic 形状可解析，但标准集合不再等于原输入，生产校验按契约拒绝生成回执。原始报告确实指出剩余“必须”表述强度不足；这只能作为诊断方向，不能伪装成有效拒稿再驱动模型。类似标准空格漂移在第 69 节已出现，本轮不将它归为新禁令引入的语义错误。

### 保留成果与下一责任边界

**保留第 78 节禁令及本轮修订中的局部遵守，不据协议失败全盘撤回。** 本轮一份合法新 Final 没有恢复无据文档否定；另一条尚未进入 Final，不能计作禁令失败或成功。原文的图像、文件数组及无返回值处理再次被自主找到，获取机制的这项局部事实也保留。

完整循环验收仍欠有效回执和用户结果。下一步须先核对阻塞该验证的现有协议责任：动作阶段缺少调用时为何变为模型不可用，以及 Verifier 为何依靠重新生成标准全文来确认标准身份。先保留当前请求、响应和责任边界，不以放宽判据、静默匹配空格、接受任意文本或新提示补丁制造成功。生产修正若取得准入证据，应复用现有协议恢复与标准责任主体，再回跑原阻塞轨迹；不另建 Verifier，也不重新验证同义禁令。

两条合计 **八次真实调用、480,390 tokens、344.009 秒模型调用时间**，未达到 token、读取或新稿上限，不属于预算不足。完整请求、响应、原回执恢复、逐行原文校验、候选哈希与阶段判断见[本轮归档](../../.tmp/coverage-ban-loop-20260912)及[复核结果](../../.tmp/coverage-ban-loop-20260912/review.json)。481 份生产及测试 Python、`.env` 和第 78 节禁令字节保持；历史第 47 至 78 节正文保持。本轮没有正式 E2E 或生产接入完成声明，活动边界同步 Future。

## 80. 恢复生产适配器后复核动作协议失败

**第 79 节的诊断脚本绕过了一次现有协议纠正，不能据此判定生产 Runtime 没有恢复。** 生产 `OpenAIModelClient._generate_chat` 已在必选动作缺失时增加协议反馈并重试一次，连续失败才向外抛出；`JsonObjectStructuredAdapter` 继承这条路径，正式装配使用该适配器。旧诊断脚本直接调用 SDK 与 `_extract_action_invocations`，没有经过 `_generate_chat`。上轮“模型动作违规”的观察保持，但将立即停止归因于生产缺少恢复的解释证据不足，本节明确更正。

本轮先修复验证脚手架：调用生产 `generate`，只在传输边界记录请求与响应，不复制解析和纠正规则。原失败归档保持。预声明见[本轮计划](../../.tmp/action-protocol-repair-20260912/plan.md)：严格重放第 79 节前五份真实响应，每次核对完整 wire；第五份违规交给生产适配器，其后的纠正和决定均使用真实 MiMo。保留来源、读取状态、Final 禁令、来源必检和修订循环，不新增生产恢复分支。

局部判据为拒绝非法文本、触发现有纠正、恢复合法动作及后续 Final；完整来源支持单独判断。相反控制为连续两次缺失动作仍被拒绝。沿用 16 次父级决定、32 次读取、三份新稿及含重放 1.2M tokens 上限。证据归类为 Runtime Conformance、Offline Eval 和读取 Integration，不是正式 E2E。生产原有边界已记载于[运行时专题](../topics/runtime.md)和 [ADR 0017](../adr/0017-separate-action-selection-from-final-delivery.md)，本轮没有新增该能力。

### 原反例的恢复结果

**同一份违规响应经生产适配器恢复，后续产生三份合法 Final 和两份有效拒稿回执。** 历史前五份请求与响应逐字段一致，原来已读的 104/122 个 OpenAI 片段保持。第五份违规响应触发一次 `provider_action_missing` 纠正，新增消息之外的全部请求字段保持，真实 MiMo 随后返回合法读取动作。该读取只返回已见片段，没有新增覆盖；后续自主请求 `prepare_final`，未将原来的普通文本转换成 Final。

第一份和第二份 Verifier 均生成有效 `failed` 回执，现有诊断循环消费原回执后重新进入动作与 Final。第二稿将角色及标识字段的“必须”改为“应”；第三稿又将关联值“必须匹配”改为“应匹配”。这证明协议恢复与真实反馈消费可用，不能据此声称每条反馈正确或完整稿得到支持。

七项既有确定性测试通过，覆盖一次缺失动作成功纠正、连续两次缺失仍拒绝、非法动作参数拒绝及 Conversation 失败边界。命令为 `.venv/Scripts/python.exe -X utf8 -m pytest tests/test_structured_model.py tests/test_conversation_interaction.py -k 'missing_required_provider_action or main_conversation_logs_missing_provider_action or main_conversation_decision_maps_provider_failure_to_unavailable or fails_closed_on_invalid_provider_actions' -q --junitxml=.tmp/action-protocol-repair-20260912/contract-results.xml`。这些测试没有把服务方连续失败伪装成可交付答案。

### 修订中的语义反例与独立协议阻塞

**恢复流程后，语义错误仍在，而且第三稿重新出现了文档级否定。** 三稿都将 Chat Completions 的 `role/tool_call_id/content` 示例概括成全部工具结果的结构，未区分已读的 Responses `function_call_output/call_id/output` 示例。关联值仍写成模型返回的 `call_id`，与 Chat Completions 示例中的 `toolCall.id` 不一致。第 58 段的结果格式条款已实际可见，获取不足不能解释全部这些错误。

| 产物 | 局部结果 | 剩余问题 |
| --- | --- | --- |
| 第一稿与有效拒稿 | 无文档级否定；回执指出义务强度扩大 | 未指出 API 范围和字段身份错误 |
| 第二稿与有效拒稿 | 两处“必须”改为“应”，再次进入修订 | 回执将稿件的“应包含”复述为“必须包含”；仍集中于强度，没有发现范围错误 |
| 第三稿与原始报告 | 关联值也改为“应匹配”；原始四项均为 `satisfied` | 新增“文档未明确将这些要求描述为强制性协议约束”；原始报告认可该概括，但因两项标准空格漂移未生成有效回执 |

第三稿仍只读到 104/122。已读第 14 段的 `should` 只描述一般调用引用，不能证明所有结构字段都没有强制性规定；它也不是直接写明全部结构非强制的否定条款。前两稿遵守 Final 禁令的事实保留，但第三稿构成该候选在修订中的反例。不能再宣称这条禁令稳定解决文档否定，也不能把本轮语义反例归为尚未消费禁令。

最后一份报告把“官方 URL”改成“官方URL”，并删除来源支持标准中 URL 周围的空格。四项形状完整、原始状态全部 `satisfied`，生产集合校验仍拒绝生成 Receipt。故本轮没有有效误放，也没有完整用户结果；原始理由认可错误只能证明语义判断方向有问题，不能冒充已经发生了正式交付。标准身份问题与第 79 节相同，不静默修改响应或人工补造回执。

### 取舍、用量与归档

**本轮修复验证入口，停止给生产补加已经存在的动作重试。** 新记录器复用生产 `generate`，仅在传输边界保存证据；第 79 节旧脚本与失败归档保持历史身份，后续不再用该旁路判断生产恢复能力。原有读取、来源必检和修订经验继续保留。Final 禁令只保留为已测条件，停止将当前版本作为足够的修复候选；下一语义诊断应区分修订为何只改义务词、反馈为何错误复述当前稿、以及逐项支持为何漏掉 API 范围，不再叠加同义禁令。

本轮严格重放五次历史调用，新增 **十次真实 MiMo 调用、698,362 tokens、511.319 秒模型调用时间**。含重放用量为 971,039 tokens，未触及 1.2M 上限；最终停在第三份 Verifier 的标准身份校验，不是预算耗尽。三份新 Final、两份有效失败回执和一份原始无效报告均保存。

完整证据见[本轮归档](../../.tmp/action-protocol-repair-20260912)、[自动审计](../../.tmp/action-protocol-repair-20260912/review.json)及[逐稿人工复核](../../.tmp/action-protocol-repair-20260912/semantic-review.json)。本轮 481 份生产及测试 Python、`.env`、Final 禁令与历史第 47 至 79 节正文保持；生产净复杂度变化为零。文档检查覆盖 15 份文件及历史迁移，不新增 E2E 或生产接入完成声明；活动取舍同步 Future。
