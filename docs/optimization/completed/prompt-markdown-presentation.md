# 工程提示的 Markdown 表达

**工程自有生产提示已按既定范围统一表达，并通过双语正式入口验证。** 长指令使用 Markdown 标题、段落和清单；短反馈可直接为普通段落。关闭的是表达一致性问题，不主张改善 task2 的数值正确性或目标遵从率。

## 问题与采用机制

原有实例 Catalog 已覆盖中英文资源，但主循环、研究、核验及协议修复混用括号标题、Markdown 和长段落，动态执行区还使用硬编码标题。维护者难以沿相同结构比较指令和实际输入。

采用[OpenCode、LangChain 公共路径](../../agentRef/context-engineering.md#8-通用框架的要求表达与采用依据)的可读正文与结构化协议分工，固定源码于2026-10-28再次核对。现有`PromptSpec / PromptCatalog`继续拥有资源与版本，各Application和Adapter拥有自身指令；无需新建转换器、业务字段、状态或模型阶段。

33条中英模板仅调整标题和空白，原句、顺序、限定、变量、owner与输出契约保持，版本同步增加`-md1`；360条原资源保持。新增`conversation.execution_inputs`把动态执行区标题接入同一Catalog，注册总数为每种语言394条。原JSON载荷及criterion末尾位置保持，criterion继续使用原编号清单。

主循环的交付策略属于目标区子节，使用三级标题；通用动作协议另起二级区块，插槽前后保留段落边界。其余分区按实际职责选择，不为每条短提示补齐固定五个标题。模板仍存放在原Python模块中，文件后缀不影响发送正文。

## 保真与接入边界

工具参数、JSON数据、Schema、来源、代码、原始输出及历史消息保留原协议和原文。模型阅读正文是既有事实的只读投影，权限、执行、恢复、预算及完成仍由原责任主体决定。第三方库独立提示由其原契约拥有，不在最终请求上递归替换文字；不能用Catalog数量宣称全部第三方内容已改写。

当前装配见[架构正文](../../architecture/cross-cutting.md#2-模型调用的实际组合)，后续维护遵守[Prompt规范](../../../src/personal_agent/kernel/prompt_templates/AGENTS.md)。task2原轨迹使用原冻结源码，新排版不混入其历史或成绩。

## 验证与经验

全资源原句及变量对照、15份真实SDK输入物化、17个实际工具至18个当前动作、14个阶段Schema及中英共6种正式拼接检查通过。独立审查没有发现正文或协议漂移，指出了已有句子粘连；新增标题会使通用规则落入交付子节，因此在同一排版范围内补齐层级及段落，正式builder对照通过。

中文和英文各一次正式HTTP旅程，均从自然请求上传原CSV，经真实Flash thinking、实际读取和Final交付前两行原文及12列名。源码冻结、实际请求、费用和范围由[验证记录](../to_verify/verify_results/prompt-markdown.md)拥有；使用direct/none，仅作为本次接入smoke，不是完整研究核验、task2验收或发布证据。

后续新的真实请求再次出现工程长指令分区混杂、动态包装遗漏或标题改变原指令作用域时，按EVD加入该真实用例并重开本问题。第三方材料原有格式、短反馈没有标题，或独立业务语义错误本身不是重开条件。
