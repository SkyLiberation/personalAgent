# 会话持久化检查点与 SQLite 批量提交

DeepSeek Harness 的 headless 入口可以凭 Session ID 和新问题跨进程接续。显式选用 SQLite 时，本次上游更新让同一存储实例中的多个会话共用一次提交，检查点仍等待各自的写入结果。personalAgent 已能凭 `turn_id` 恢复原轮次。要在新进程开始下一轮，客户端仍需提交完整消息前缀，服务端据此前缀选择历史分支。[选题与记录](README.md#选题与记录)

本文记录优化前的对照。之后 personalAgent 已切换到服务端有序历史，设计与验证见 [ADR 0054](../adr/0054-session-run-step-journal.md)。

## personalAgent 的同场景路径

Web 新轮次和恢复入口都经 Runtime 的 `converse` 进入 `ConversationService.respond`。组合根注入 `FileInteractionJournal`。Journal 按轮次版本写 JSON 快照，先同步临时文件再原子替换，模型请求与响应原件另存。同一 `turn_id` 的恢复由入口取回原消息和附件，再校验主体和运行绑定。已有终态可直接返回，未完成的轮次从已接纳动作和模型响应原件接续。[Web 入口](../../src/personal_agent/adapters/web/routes/conversation.py#L183-L253) · [Runtime 装配](../../src/personal_agent/orchestration/runtime.py#L355) · [Journal 注入](../../src/personal_agent/orchestration/runtime.py#L457) · [Runtime 入口](../../src/personal_agent/orchestration/runtime.py#L1008-L1015) · [文件 Journal](../../src/personal_agent/application/conversation/journal.py#L1111-L1231) · [原轮次校验和终态](../../src/personal_agent/application/conversation/service.py#L411-L503) · [接续已接纳动作和响应](../../src/personal_agent/application/conversation/service.py#L580-L641)

新轮次的 `ConversationTurnRequest` 要求 `session_id` 和 `messages`。`FileInteractionJournal.session_runs` 扫描各轮次最新快照，按主体和 Session 筛选。`prior_analysis_turns` 再用客户端消息前缀、已交付答复和原绑定匹配前驱。主请求从匹配到的轮次投影适用的原生调用及回执，交给模型适配器。因此换进程后，只有 `session_id` 和新问题的客户端会缺少历史匹配所需的前缀。它可以恢复持有 `turn_id` 的原轮次，但不能用新轮次入口自动重建原分支。[新轮次请求结构](../../src/personal_agent/adapters/web/routes/conversation.py#L48-L67) · [扫描和归属](../../src/personal_agent/application/conversation/journal.py#L1169-L1187) · [分支选择](../../src/personal_agent/application/conversation/model_history.py#L306-L331) · [主请求选择历史](../../src/personal_agent/application/conversation/service.py#L2103-L2115) · [主请求物化](../../src/personal_agent/application/conversation/service.py#L2201-L2205) · [适配器派发](../../src/personal_agent/application/conversation/service.py#L2429-L2445)

## 差距与最小验证

- **已证实的差距。** DeepSeek Harness 的 Session 日志拥有有序前史。personalAgent 文件 Journal 保存原轮次事实，客户端前缀决定新轮次在哪条历史上接续。这个差距影响只保留 Session ID 的客户端。两边都有持久化和接续路径，存储格式本身无法解释既有任务的答复得分。[现行架构](../architecture/core-architecture-current-state.md#8-持久化恢复与观测)
- **设计取舍。** ADR 0054 已把服务端有序历史和原子提交列为后续设计。适合复用上游的持久化边界与原记录重建思路，本地仍由 Conversation 冻结前驱并约束授权、核验和交付。服务端接管后，原客户端前缀匹配由已提交的前驱引用取代。是否进一步采用跨 Session 批量提交，取决于独立写盘耗时和并发证据。当前暂无相同负载下的测量。[ADR 0054](../adr/0054-session-run-step-journal.md#决定)
- **最小验证。** 复用上述第 14 轮原问题，在同一正式 Web 入口和当前协议下准备两份等价的第 13 轮已提交状态。启动新进程后，一份提交原完整前缀，另一份只提交同一 `session_id` 和新问题。先在模型派发前捕获逻辑请求与前驱，核对是否保留第 13 轮口径及同一组合法工具回执。现行源码预期两份输入选出的前驱不同。服务端历史方案的通过条件是两份都接回同一合法前驱并物化相同的必要历史，换主体时历史零披露。这项检查可以用既有真实输入做零模型回放。实际出站保真及答复正确性仍需要分别取证。[生命周期规格](../optimization/to_verify/conversation-loop-boundaries.md#320-sessionturn-与-step-生命周期)
