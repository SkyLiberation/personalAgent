## 差距与最小验证

**源码已确认的差距。** 有唯一匹配邮件时，PTC 程序可以读搜索返回值、取出邮件 ID，直接调用读信工具，然后向主模型输出用户要的材料要求。personalAgent 现有 MCP 接口要在搜索与读取之间再经过一次主模型决策。独立动作并发可以缩短等待，依赖关系仍由模型跨步推进。这影响需要多次按结果转接的任务。该样本已经成功交付，单个交接省下的模型请求是否降低整题成本、延迟或错误率仍待验证。

**设计取舍。** personalAgent 让每个业务动作沿现有端口经准入执行，并让模型看到动作与回执的配对。PTC 把可程序化的局部控制流和中间数据放到执行侧，同时承担子调用预算、执行记录和进程失效的处理成本。本样本适合验证现有搜索与读信之间的只读交接。发信继续由显式的邮件能力及其现有准入和回执负责。 [本地决策与完成职责](../architecture/core-architecture-current-state.md#32-会话运行与主决策的现状)

**最小验证。** 在隔离的测试邮箱回放历史任务的检索阶段，使用原题邮件正文和同一只读工具清单。固定上游目标提交，在正式会话入口对照 `standard` 与 `ptc`。以确定性模型响应驱动边界回放。将唯一命中的 ID 从历史值 `1` 改为另一个有效 ID，排除写死参数。预期原生路径在消费搜索回执后发起下一次模型请求，PTC 路径在一个 `run_code` 内依次调用搜索和读取。两条路径都应交付来自同一目标邮件的材料清单，且读信实参等于当次搜索返回 ID。再回放一次无匹配响应，读信和发信执行数均应为零。以实际请求、调用记录和用户可读清单核对。本轮只读核对了源码及历史归档，这组回放尚待执行。
