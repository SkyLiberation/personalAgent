# 会话模型推理档位

DeepSeek Harness 允许用户在同一个会话中切换模型的推理档位，从下一个尚未开始准备的步骤生效。它还允许配置者为同一个档位声明服务方实际接收的值。personalAgent 已能把部署指定的推理参数送到服务方，但聊天主循环没有会话级档位入口。用户用同一模型逐步核算复杂规则时，无法在浏览器里只为当前会话调整推理档位。

## personalAgent 的对应路径

1. **聊天入口接收任务。** `App` 将会话 ID、请求 ID 和用户文本等字段组装为请求，`streamConversationTurn` 将它们发到 `POST /api/conversation/turns`。Web 的 `ConversationTurnRequest` 禁止额外字段，路由按身份将用户文本和会话信息交给 `converse`。`ConversationService._build_decision_request` 组装原生工具决策请求，主请求没有设置 `reasoning_effort`。聊天入口与主决策构造均没有消费用户选中的档位。[浏览器组包](../../frontend/src/App.tsx#L374-L386) · [HTTP 发送](../../frontend/src/api.ts#L301-L315) · [入口结构](../../src/personal_agent/adapters/web/routes/conversation.py#L50-L64) · [业务交接](../../src/personal_agent/adapters/web/routes/conversation.py#L193-L233) · [主决策请求](../../src/personal_agent/application/conversation/service.py#L2407-L2435) · [调用与记录](../../src/personal_agent/application/conversation/service.py#L2594-L2608)
2. **部署拥有该主链的默认档位。** `Settings.from_env` 将 `STRUCTURED_EXTRA_BODY` 和结构化模型绑定读入 `StructuredConfig`。Runtime 创建一个结构化模型客户端并注入 `ConversationService`。`StructuredModelRequest` 已有可选 `reasoning_effort`，现有编码器让显式请求值优先于同模型绑定的部署默认。`MiniMaxPolicy` 会按模型校验档位，最终由 SDK 发送。以已配置 `adaptive + medium` 的 Web 部署为例，浏览器用户可以继续提交同一个任务，但在正式入口只能沿用 `medium`。具有配置权限的操作者可以修改部署参数并重建 Runtime。两者使用现有厂商策略和预算链路。[配置读取](../../src/personal_agent/kernel/config_env.py#L65-L85) · [配置绑定](../../src/personal_agent/kernel/config_env.py#L250-L265) · [模型客户端装配](../../src/personal_agent/orchestration/runtime.py#L225-L232) · [Conversation 注入](../../src/personal_agent/orchestration/runtime.py#L451-L468) · [请求字段](../../src/personal_agent/capabilities/contracts/model.py#L361-L376) · [适配器默认值](../../src/personal_agent/infra/structured_model.py#L342-L362) · [参数优先级](../../src/personal_agent/infra/model_providers/openai_compatible.py#L35-L51) · [MiniMax 校验](../../src/personal_agent/infra/model_providers/minimax.py#L8-L19) · [SDK 发送](../../src/personal_agent/infra/structured_model.py#L497-L505)

## 差距与最小验证

**取舍。** 上游面向用户可配置的多模型会话，档位选择和当前调用的配置均可从 Session 查到。本地正式聊天固定到部署绑定，调用方已有显式档位字段，权限和预算仍由原调用链负责。源码证实的差距是用户控制的会话档位缺少入口和消费。若真实需求成立，最小对照可以先在同一已部署模型下复用现有会话、主决策请求与厂商校验，观察显式档位能否作用于下一步调用。核算结果是否改善单独取证。

**最小验证。** 固定一份佣金材料、同一个用户问题、MiniMax 模型绑定以及 `adaptive + medium` 部署默认，用隔离的 HTTP 接收端记录第一个 `agent_interaction_turn` 的请求体。在正式入口做三个对照。普通聊天应发送 `medium`。基线在请求体加 `reasoning_effort: high` 应被入口拒绝且不发送模型请求，直接写进提问只会增加消息正文。若接入会话选择，先在会话 A 选 `high` 再发送，A 的主请求应变为 `high`，未选档位的会话 B 仍应为 `medium`。再验证 `minimal` 在发出请求前被 MiniMax 校验拒绝。若基线已可在相同部署下由会话操作改变实际参数，则本报告所述差距不成立。这个验证只需观察参数交接和拒绝，本轮未执行。
