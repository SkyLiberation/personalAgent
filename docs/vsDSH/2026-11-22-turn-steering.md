# 运行中补充指令与浏览器重连

**personalAgent 已能把补充指令送入原轮的后续模型请求。现有 Web 界面在刷新后只恢复原轮提交，无法从服务端恢复补充指令的显示。** DeepSeek Harness 的 Web 界面会重读会话的待处理队列与已入档消息，因此能在重连后恢复两类记录。用户可以确认「选最便宜的」是否已经交给原轮，并据此决定是否需要再发。后端是否接收、模型是否读到、最终答复是否满足要求，各有对应证据。

## 最小验证

针对浏览器恢复差距，复用邮轮用例的第一条原文和正式 Web 入口。在一条隔离的浏览器回放中，控制一个浏览步骤暂停，让同一条补充先获得 `202`。保持后端运行，刷新同一标签页。第一次在领取前检查界面是否能恢复「待接续」。继续原轮，确认下一份模型请求只出现一次该原文，再刷新检查界面是否恢复同一条补充。用原轮 ID 与补充请求 ID 对照后端事实和 UI，另以一个终态后被 409 拒绝的新 ID 验证界面不会把它显示为已接收。根据源码，当前 Web 恢复路径可能遗漏已接收的补充，已领取的原文仍能通过受限的轮次 GET 核对。这个回放只判定投递、重连及显示，不重新判断邮轮答案。

如果回放确认差距，可复用 Journal 的队列与轮次修订，向同主体浏览器提供按请求 ID 定位的只读状态，恢复时用该状态补齐显示。现存回执和已领取记录提供关联坐标。是否需要单独展示「已进入模型请求」仍待验证，领取记录与限制终态之间的区别已有源码依据。本次完成源码和历史归档核对，回放及修订均为后续验证事项。
