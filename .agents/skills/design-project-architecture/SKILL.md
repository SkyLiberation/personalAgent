# 架构设计与维护

架构是系统为完成业务目标，对系统边界、组件职责、事实与决策归属、协作契约、依赖及运行方式作出的关键安排。目录、分层图和技术选型只是表达或实现这些安排的方式；判断架构是否合理，要看它能否以可接受的复杂度完成实际业务并满足必要约束。

## 1. 从业务问题定义架构目标

- 聚焦本轮一个具体业务问题，写清目标用户、正式入口、输入与初始事实、用户结果及必要失败或拒绝条件。已有架构复审也须回到其服务的业务，不能只核对代码是否符合旧设计。
- 提取实际影响设计的质量目标和硬约束，如权限隔离、成本、延迟、恢复或局部修改成本。给出适用场景及可判断条件，标明已确认事实与待证假设；不为选定技术补造需求。
- 从[现行架构](../../../docs/architecture/README.md)、代码地图和实际调用方取得现状，区分有效约束、已实现行为与候选方案。定义与设计按 [ARC 架构分析](../../../docs/devSpec/architecture-ownership.md#81-设计阶段的架构分析)进入本问题的唯一设计；纯现状文档修正按 DOC 处理。

## 2. 将业务场景设计成具体架构

1. **确定系统边界。** 识别用户、外部系统及其权威事实，明确本系统接收什么、负责什么、交付什么。先推演关键业务场景，再确定内部结构。
2. **划分责任与权力。** 按业务能力、事实生命周期和真实变化原因划分组件，确定每个业务事实的唯一 owner、合法写入口，以及语义决策、确定性治理、执行与完成的交接。架构角色与物理包分别判断，不为凑齐层次创建空壳。
3. **定义协作契约。** 说明组件的输入输出、事实或引用来源、调用前提、失败语义及适用状态变化。调用方消费 typed 契约，外部实现经实际依赖边界注入；跨业务机制满足 [ARC 框架准入](../../../docs/devSpec/architecture-ownership.md#4-framework-capability-准入与边界)，不能靠共享底层模块吸收业务规则。
4. **设计运行过程与装配。** 从正式入口走到用户结果，说明谁构造、调用、读取和写入谁。按实际影响处理权限、事务、副作用、资源释放，以及拒绝、取消和恢复；业务主流程与技术切面按[编码质量 skill](../write-quality-code/SKILL.md#2-隔离切面保持业务主流程清楚)分开。需要图时选择有助于理解的系统边界、组件或时序视图，不要求全套图。
5. **比较并选定最小方案。** 先复用适用的[开源实践对照](references/open-source-practices.md)，明确“参考怎样设计、当前怎样设计、差异为何必要”。比较能解决同一问题的直接方案及有必要的替代方案，说明业务收益、质量取舍、额外状态和协作成本。独立方向分别设计，互斥候选并列比较；不拼成一套共同实施方案。

新设计须能定位到职责、契约、装配和真实消费者，不能止于组件名或待建文件清单。沿用既有边界时说明保持依据即可；外部实践的适用条件与本地有效性分别验证，已有有效来源不为同一决定重复调研。

## 3. 检查架构是否合理、符合业务

用本轮真实场景逐项走读设计，检查以下关系是否成立。每个结论给出设计或代码坐标；不以术语齐全、图形整齐或静态检查通过代替判断。

| 检查重点 | 必须成立的关系 |
| --- | --- |
| 业务覆盖 | 关键用户结果有完整责任链；必要拒绝与失败能明确交接，不靠未设计的人工步骤、默认成功或旁路补齐 |
| 职责与事实 | 每个组件有明确业务或技术责任；业务事实和决定不被多个组件独立拥有，协调入口不吸收所有业务规则 |
| 依赖与变化 | 同一变化的规则内聚，独立变化通过必要契约隔离；局部业务变更不无故扩散至多个无关模块 |
| 运行可行性 | 设计的权限、状态、持久化、副作用和资源生命周期在实际运行边界可落实，装配与消费者存在或有明确接入方案 |
| 成本与必要性 | 每个新增边界、状态、抽象及框架机制对应已确认需求，收益足以解释新增协作、理解和运行成本 |

发现关系不成立时，定位最早责任或缺失契约，修正具体设计后再推进依赖它的实现。需求冲突时明确优先级与取舍；方案可行但效果待证时固定验证计划，不把待验证写成已成立。完整必要性与逐点 E2E 审计另用[方案审计](../audit-project-proposals/SKILL.md)，本技能聚焦架构设计的业务适配及可落地性。

## 4. 从实际链路维护架构

先搜索入口、构造点、全部受影响调用方及恢复消费者，再核对实现。分别检查：

- **静态依赖：** 哪个包实际导入哪个包，允许边由 `scripts/check_layers.py` 拥有。
- **装配与调用：** 哪个工厂选择实现、谁在什么分支调用它、结果由谁消费；注册、注入或类存在不等于实际生效。
- **事实与生命周期：** 哪个 owner 产生、读取、更新和恢复事实，资源在什么作用域创建与关闭；调用图不等于事实归属图。

据此区分处理：

| 现状 | 推进动作 |
| --- | --- |
| 实现符合有效契约，架构正文过期 | 更新现状正文与代码地图，不制造实现改动 |
| 实现违反仍适用的职责或依赖边界 | 在授权范围内修正最小责任链；旧设计本身也有问题时先修订设计 |
| 真实业务需求使原架构不再适用 | 按 EVD 更新唯一设计，实质边界决定按 REL 记录，再迁移实现与消费者 |
| 仅物理布局不同，尚无职责或契约问题 | 准确记录实际落点；目录差异本身不构成全库搬迁理由 |

不通过扩大允许集合、动态导入、运行时查找或向 `kernel` 搬运业务代码来隐藏依赖问题。无关缺陷单独记录；维护过程中发现的新问题按[方案推进分析](../analyze-proposal-progress/SKILL.md)判断因果关系，不强行耦合。

## 5. 同步、验证与交付

同轮维护唯一设计、受影响实现、架构正文及检查规则，迁移全部生产者与消费者并删除旧路径。现行系统责任进入 `docs/architecture/`，代码地图记录真实入口与直接协作者，横切正文记录实际装配，详细契约留在原权威专题；不在多处复制同一设计或验收状态。

从仓库根按实际影响选择检查：

- 规范或架构文档变化：`.\.venv\Scripts\python.exe scripts/check_dev_spec.py`，核对本地链接、锚点和入口镜像。
- 代码包或依赖变化：`.\.venv\Scripts\python.exe scripts/check_layers.py`，另取适用的导入和类型检查；既有脚本未覆盖的动态装配、包内职责和事实归属沿实际路径核实。
- 行为保持或产品变更：按 [EVD](../../../docs/devSpec/change-evidence.md#12-按实际影响选择证据)取得分类证据，验证安排由方案推进 skill 拥有。静态 DAG 通过不能证明业务合理、权限成立或用户结果达标；纯文档不运行产品 E2E、真实模型或停用的单元测试。

交付说明具体业务问题、架构判断与依据、关键设计及取舍、实际改动和删除项、已执行检查及剩余条件。只读分析不自动实施变更；达到已确定验收条件后结束，不追加范围外改造。

本技能拥有架构定义、设计、业务适配检查与维护方法；事实归属、分层和生产准入由 [ARC](../../../docs/devSpec/architecture-ownership.md)及根规范拥有，局部代码组织由编码质量 skill 拥有。
