# 编码质量

围绕业务职责组织高内聚、低耦合的代码：相同变化原因的实现内聚，不同变化原因通过明确契约隔离。只处理本轮受影响的入口、单元和直接协作者，无关问题单独记录。

## 1. 确定业务责任与变化点

- 从真实入口和调用方确认用户结果、业务事实、状态生命周期及唯一责任主体，再按[架构分析](../../../docs/devSpec/architecture-ownership.md#81-设计阶段的架构分析)确定模块、契约和装配位置。
- 将同一业务责任的规则与状态放在一起，每项能力的准入、结果契约及投影有明确归属。同一 Aggregate 的相关操作可共享 Service；多个独立能力共用入口时，入口只负责路由与协调，不混装独立生命周期和写入责任。
- 区分稳定业务规则、可替换算法、外部协议与横切技术职责，先复用现有能力和 typed 契约。调用方通过契约协作，不穿透内部状态或反向依赖编排；真实依赖边界的注入遵守 [COD](../../../docs/devSpec/code-structure.md#5-错误注入与命名)。

## 2. 隔离切面，保持业务主流程清楚

主流程用业务语言表达判断、动作及交接。业务规则和状态迁移留在其 owner；日志、追踪、计量等技术职责在明确边界组合，避免在业务分支中重复埋点、计时、协议转换或重试。

先核对[现行横切组合](../../../docs/architecture/cross-cutting.md)的工厂与消费者，再按实际需要选择最小机制：

| 当前需要 | 优先方式 | 选择依据 |
| --- | --- | --- |
| 功能内部的确定性处理 | 内聚函数或显式顺序调用 | 输入输出清楚，无需外部替换或信任隔离 |
| 可替换的模型、存储或外部执行依赖 | 既有 typed Port + Adapter | 真实依赖或信任边界，在组合根注入 |
| 同一 Port 的追踪、计量或既定技术重试 | 实现相同 Port 的 Decorator | 明确包装顺序；记录与重试分别承担各自契约 |
| HTTP 等传输入口的通用处理 | 现有 Middleware | 只处理传输边界，不替代业务校验 |
| 资源与请求内观测范围 | Context Manager，必要时使用 `ContextVar` | 生命周期可明确关闭；跨线程或任务传播按实际调度核验 |
| 授权、预算、幂等与完成判定 | 既有 Policy、Admission、Gateway 或业务 owner | 在实际读取、执行与完成边界显式检查 |
| 业务原子写入 | Application 确定范围，存储实现原子操作 | 不把外部副作用或多存储写入伪装成单一数据库事务 |
| 已确认的重复读取成本 | owner 声明的派生缓存 | 按 [ARC 缓存规则](../../../docs/devSpec/architecture-ownership.md#61-派生缓存与投影)管理来源、失效、权限及失败 |

在 Composition Root 显式装配，写清切入点、调用顺序、失败语义和作用域。禁止通过包扫描、方法名通配、运行时替换或全局事件监听暗中改变生产调用链；不为应用 AOP 新建通用织入、容器或 Hook 框架。输入输出、重试、授权、证据与异步生命周期必须满足 [COD 横切边界](../../../docs/devSpec/code-structure.md#51-横切关注点与显式组合)。

## 3. 保持可读性并控制单元规模

读者应能从入口、命名和 typed 输入输出看懂主要路径、事实归属与失败语义。**禁止超大文件、超大类、超大函数，禁止在失控单元中继续堆入新职责。** 新增或显著增长的单元按以下表现判断：

| 单元 | 失控表现 | 处理方向 |
| --- | --- | --- |
| 文件／模块 | 独立职责、生命周期或技术实现混装，局部修改需要查阅大片无关实现 | 按稳定功能与真实变化原因划分，相关实现相邻，入口和直接依赖清楚 |
| 类 | 同时拥有不相关的状态、规则或生命周期，形成全能 Service／Manager | 将行为归还对应 owner，通过明确契约协作 |
| 函数 | 混合可独立变化的规则或阶段，跨抽象层次，靠共享可变状态串联 | 在明确输入输出的责任边界提取，主函数保留同一抽象层次的业务顺序 |

先处理明确的拒绝与退出条件，复杂条件用业务谓词表达，避免深层嵌套和远距离变量修改。名称说明业务角色、动作或生命周期；注释解释依据、约束与取舍，删除复述代码或失效的注释，排版使用项目工具。

结合实际行数、分支、嵌套、参数、依赖和修改扩散说明拆分或保留理由，不按类名、能力数量或行数配额机械拆分。拆分前指出混装职责及当前查阅范围；拆分后核对局部阅读入口、契约、直接协作者及新增跳转、传参和协作成本。净理解成本没有下降时重新选择边界，禁止缩行、机械搬运、空壳转发或按“一类一文件”交差。

## 4. 清除影响本轮的代码坏味道

新增或改动代码不得引入下列坏味道；受影响路径已有问题时，在确认职责和消费者后做必要整理。

| 坏味道 | 最小处理 |
| --- | --- |
| 重复业务规则、散落魔法值、内部协议靠字符串键维持 | 回到唯一 owner，复用命名规则及 typed 契约；外部 raw payload 在读取边界校验 |
| 循环依赖、访问私有状态、Service Locator 或全局可变服务 | 修正依赖方向，在真实依赖边界注入；通用 `utils` 中的无关规则归还各自职责 |
| 长参数列表、重复参数组、靠布尔开关混合不同职责或函数操作他人内部数据 | 核对行为归属，按内聚业务输入组织；不为每个函数新增 Model，确有替换需求再引入策略 |
| 吞错、默认成功或空结果掩盖失败 | 按 [COD 错误边界](../../../docs/devSpec/code-structure.md#5-错误注入与命名)区分合法空结果、未知和失败 |
| 无消费者抽象、重复写入口、被替代分支或无职责包装层 | 核对调用方后删除或合并，迁移全部真实消费者，不保留双轨 |

## 5. 按真实变化选用设计模式

引入模式前说明真实变化点、直接实现的不足、最小机制及真实装配与消费者；计入删除量、新增抽象和间接调用，按 [EVD 复杂度准入](../../../docs/devSpec/change-evidence.md#5-复杂度说明complexity-justification)判断。能用清楚函数或顺序调用解决时保留直接实现。

边界机制按第 2 节选择。同一职责中确需替换的确定性算法可用 Strategy 或 typed callable；构造与选择复用现有工厂及组合根。禁止为每个类成套创建 Interface、Factory、Manager 或提前引入 Registry、事件框架。模式不得掩盖职责不清，不得用 Strategy／Router 代替开放语义决策，也不得用 Adapter／Converter 同步可独立修改的镜像事实。

## 6. 走读与交付

- 沿真实入口走读成功和关键失败路径，核对业务主流程、切面契约、规模和坏味道；迁移全部受影响调用方，删除被替代定义、装配及失效说明。
- 按影响运行适用的[层级检查](../../../scripts/check_layers.py)、导入／类型等静态检查，并按 [EVD](../../../docs/devSpec/change-evidence.md#12-按实际影响选择证据)取得行为保持或产品变更证据。验证计划使用[方案推进分析](../analyze-proposal-progress/SKILL.md)，遵守根规范的单元测试停用要求。
- 报告实际职责与规模变化、查阅范围和协作成本、必要的模式取舍、已执行检查及未验证边界。只读质量评审仅报告有坐标和证据的问题，不自动实施修改。

本技能拥有编码组织、拆分、坏味道处理和机制选择方法；[COD](../../../docs/devSpec/code-structure.md)拥有实现门禁，[ARC](../../../docs/devSpec/architecture-ownership.md)拥有事实归属与依赖边界。涉及架构定义或跨模块职责、依赖与装配调整时，使用[架构设计与维护](../design-project-architecture/SKILL.md)。
