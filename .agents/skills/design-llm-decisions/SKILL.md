# LLM 决策设计

## 1. 从任务结果反推决策

1. 固定用户结果和约束，再写清本次调用必须决定什么、依据和合法选择是什么、输出由谁消费。资料不足时定义补证、澄清、修订或停止的条件。
2. 根据决策关系选择最小结构。权威事实能唯一推导的结果交给确定性代码。材料齐全且范围明确时用单次调用。业务依赖固定但阶段需要语义判断时，由既有流程编排。下一步依赖未知观察时，复用模型动作与反馈循环。
3. 主模型先在正常决策中理解目标。单独增加任务理解调用，须有明确消费者，例如路由、待确认方案或供后续复用的任务定义，并解释额外成本。模型提取的目标仍以用户原意为准。[任务理解实践](../../../docs/agentRef/llm-decision-practices.md#4-任务理解不自动形成前置调用)
4. 按 [EVD 采用规则](../../../docs/devSpec/change-evidence.md#61-先参考采用再按实际调整)核对适用机制，沿已有用例推演各次调用的输入、合法选择和消费者。参考源码用 `reference-open-source-solutions`，完整场景推演用 `design-project-architecture`。

## 2. 复杂任务怎样分步推进

- 将任务拆成产生事实或产物的子目标，明确依赖和完成条件。向模型交接整体目标、当前子目标、已知和欠缺事实及可用动作。阶段化应降低判断负担，每次调用应有独立的决定或结果。
- 用实际执行结果决定补证、修订、继续或交付。状态变化时更新现有计划并复用结果引用，工具只消费自己的业务参数。只对真实消费者提供必要计划、动作和依据。
- 子目标完成后检查整体交付。重复动作没有带来信息增量时，定位最早缺口，按既定预算和停止条件处理。

## 3. 让必要信息真正进入模型输入

1. 按本次决定组织稳定规则、当前目标、权威事实、外部材料和适用反馈。任务专属条件从真实用户输入、有效历史和工具结果注入。审查 Prompt、Schema、工具说明、示例及默认值，确保固定契约未预埋具体任务、解法或答案。[COD 通用性约束](../../../docs/devSpec/code-structure.md#6-生产-prompt-是版本化代码契约)
2. 每个职责接续本职责相关的实际交互，按 `manage-model-context` 查对应模式、历史和压缩边界。跨调用交接当前目标、约束、实际成果、证据和未知项。核验须取得实际待验结果与必要证据。用引用交接时，确认下游有权限和入口重读决定所需原文。
3. 动作来自本次真实可见且获准的能力，说明前提、参数和结果。系统已知的身份与固定值由代码绑定，模型选择已有对象时提供合法引用范围。
4. 服务方返回的 `think` 等推理块按实际续接协议处理。不同职责之间显式交接业务结论、依据与未知项。服务方协议要求保留的推理块与业务正文分别处理。[输入审计](../../../docs/devSpec/context-memory-retrieval.md#12-system-prompt-与-context-的设计及问题分析) · [上下文实践](../../../docs/agentRef/model-context-lifecycle.md)

## 4. 输出契约服务于正确决定

### 4.1 从消费者确定模型必须输出什么

- 对每个字段说明具体消费者、读取时点及该值如何改变判断或动作。仅解析、存储或转发的字段，须找到最终作用才能保留。重复语义或作用的字段合并或删除。
- 模型输出语义选择和必要新内容。权限、作用域、版本绑定、执行事实及已知确定性值由 Runtime 处理。选择已有对象或文字时提交有效引用。
- 用能表达必要决策关系的最浅 typed 结构，保留条件的组合关系、排序适用范围及数量上限。按下游所需保留开放表达。

### 4.2 明确字段意义与输出场景

- 工具说明写明触发条件、效果及如何使用结果。业务字段及枚举说明来源、选择条件、单位、有效范围，以及省略、`null` 和空值各自的含义。更新操作区分完整替换和增量更新，明确省略项如何处理。
- 对易混分支写清“场景 → 动作或类别 → 应填字段 → 下游效果”，用经过实际契约校验的完整示例说明必要的组合关系。说明落入实际模型请求可见的工具定义、字段描述或输出指令。[字段语义与场景设计](../../../docs/agentRef/output-schema-design.md)

### 4.3 核对实际协议与修复出口

- 沿模型实发请求核对字段说明、嵌套、必填、默认值、组合约束及服务方严格模式。区分原生结构化输出、工具参数和 Prompt 约定的 JSON。
- 按 [COD 参数恢复规则](../../../docs/devSpec/code-structure.md#工具参数范围与可修复拒绝)保留原提议、错误位置、原因及合法修复范围，检查下一次请求的反馈消费。分别核对首响应、协议恢复和用户结果。

## 5. Runtime 怎样支持纠错和完成

用真实执行或核验反馈驱动下一次决定。分清参数修复、语义修订和服务重试的责任、预算及停止条件。按 [EXE](../../../docs/devSpec/agentic-execution.md)处理准入、执行、反馈、恢复和完成。引用或格式修复成功后，仍按对应用户结果验收。

## 6. 验证与交付

在唯一设计记录每次调用的责任、证据交接、最小输出及消费者、运行支持与验收判据。用 `analyze-proposal-progress` 确定比较、重复及跨模型调用的连续验证方法。
