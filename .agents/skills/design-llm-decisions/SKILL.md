# LLM 决策设计

目标是让语言模型（LLM）依据真实信息作出能推进任务的决定，并交付满足用户要求的结果。结构契约（Schema）规定字段、类型与约束；运行系统（Runtime）提供当前事实、校验、执行及反馈。两者共同服务于决策正确性，不能用格式合法或调用成功代替任务完成。

## 1. 从任务结果反推决策

- 固定一个具体问题、用户结果及明确约束，再说明本轮模型必须决定什么、下游如何消费。把“语义判断正确”“动作执行成功”“整体任务完成”分别定义，避免模型替系统确认权限、执行事实或完成状态。
- 写清作出正确决定所需的事实、判断规则与合法选择；前提不足时说明可以补证、询问、修订或暂停的条件。系统可取得的信息先由现有工具取得，只有无法取得且影响判断时才向用户澄清。
- 确定具体方案前，按[参考开源方案](../reference-open-source-solutions/SKILL.md)核对方向适用的成熟实现，可复用仍有效的[已有实践](references/open-source-practices.md)，形成合理支撑方式及必要差异；不先任意设计再靠试跑寻找方向。新增机制按 EVD 准入，跨模块责任按[架构设计](../design-project-architecture/SKILL.md)分析。
- 在依赖该方案的实验或实现前，基于已有适用用例及其真实输入输出和轨迹，按[场景与预期推演](../design-project-architecture/SKILL.md#21-实施前推演场景与预期)设计完整决策链。写清各次调用的实际输入、合法选择、输出消费者及候选预期，覆盖这些用例涉及的正常、缺证、误判、反馈修复、跨轮及停止场景；不拼造理想上游输出或凭设想增加需求。验证检验这些预期，不能代替对 Context、Schema 和 Runtime 协作的基本设计。

| 决策条件 | 设计方式 |
| --- | --- |
| 结果可由权威事实唯一推导，或属于权限、不变量 | 确定性代码处理，模型只消费必要说明 |
| 所需材料齐全，判断范围明确 | 单次模型调用、清楚输入和最小输出契约，配合本地校验 |
| 业务依赖固定，但阶段语义需要模型判断 | 由现有用例服务或固定流程编排依赖，阶段消费实际前置结果 |
| 下一步依赖尚未取得的信息或执行反馈 | 由模型在反馈循环中选择动作并依据新事实调整，现有循环合理适用时复用 |

理解任务不自动需要独立调用。优先由主模型在正常决策中理解目标、澄清缺口并推进；只有前置分析产生明确的路由、待确认方案或后续确需复用的任务定义，且拆分收益足以解释额外成本时，才单独调用。按[任务理解实践对照](references/open-source-practices.md#4-任务理解不自动形成前置调用)核对消费者与替代方案。模型提取的标准仍是用户要求的解释；回答应满足其中正确的要求，冲突时纠正解释，不能靠冻结或独立提取取得更高权威。

审批、外部副作用或跨进程恢复等约束，按实际边界追加治理，不因任务复杂就成套引入规划器、多智能体、持久状态或多模型反复核验。

## 2. 复杂任务怎样分步推进

1. **拆成有结果的子目标。** 每项说明要取得的事实或产物、必要输入、依赖及完成条件，始终关联整体用户目标。拆分应降低单次判断负担；独立方向分开，不能把所有问题压进一次大输出，也不能机械按“思考步骤”拆成调用。
2. **提供当前阶段的决策依据。** 保留整体目标与约束，说明当前子目标、已确认事实、尚缺信息和可用动作。模型选择足以推进当前子目标的动作；确定性代码不预先写好本应由新观察决定的策略。
3. **执行并观察真实结果。** Runtime 校验并执行获准动作，将实际结果、拒绝、缺失和适用范围交回。模型据此判断补证、修订、继续下一子目标或交付，不能仅凭“我已完成”的自述推进。
4. **累积进展并修订计划。** 复用现有计划与结果引用，保留已成立成果、待办、未知项及依赖。仅在工作状态变化时更新计划；工具只接收业务参数，不重复维护步骤身份。新问题按[方案推进分析](../analyze-proposal-progress/SKILL.md)判断关联，后续失败不直接抹去局部收益。
5. **按整体结果结束。** 子目标全部完成仍须核对最终交付。缺少信息增量或重复受阻时定位最早缺口，按已有预算、停止与恢复规则处理，不靠无界重试推进。

外显信息以真实消费者所需的计划、动作、结果及必要依据为限，不为展示思考过程增加必填字段。调用轮数和计划文本不作为任务成功或自主决策能力的证明。

## 3. 让必要信息真正进入模型输入

具体任务上下文的检索与维护使用[模型上下文管理 skill](../manage-model-context/SKILL.md)；涉及上下文模式修改时必须调用，并先维护 `docs/context` 中对应正文。

Context 指一次调用中模型实际接收的指令、材料、消息历史、工具定义及反馈。同一任务可以经过多次职责不同的 LLM 调用；任务相同，不代表每次都应共享完整消息列表。设计此部分时核对 [Hermes 与 DeepSeek Harness 的源码实践](references/context-lifecycle.md)，区分外部实现事实与采用建议。

### 3.1 按本次职责组织表达

- 先说明这次调用要决定什么、需要哪些前置结果、输出交给谁，再从整体目标和已确认成果组装必要输入。区分稳定规则、当前目标、权威事实、外部材料及最新适用反馈；运行时对象或 Python 类型存在，不等于模型已经看到其内容。
- Markdown 适合组织长指令、任务说明、进度和摘要，短反馈可直接表达；消息角色、工具调用与结果、Schema 及多模态内容保持原生协议。不能把整段会话压成一个 Markdown 字符串而丢失来源、调用身份和角色，也不能仅凭格式认定输入清楚。
- 提供充分且相关的信息，保留关键限定、必要原文及引用关系。说明字段与状态的含义、单位、范围，以及未知、缺失和截断；外部数据与指令分隔。按 [CTX 输入审计](../../../docs/devSpec/context-memory-retrieval.md#12-system-prompt-与-context-的设计及问题分析)检查最终请求及构造链。
- 可用动作来自当前可见且获准的能力，说明用途、参数、前提与结果。程序已知的身份或固定参数由代码绑定；模型选择已有对象时提供当前合法引用范围，不能让模型猜内部 ID。
- **禁止在固定 Prompt 中预先加入针对特定任务的描述。** 固定内容只表达职责范围内的通用规则与协议，不得预埋具体题目、任务对象、专属条件、解题路径或答案线索，也不得借工具说明、Schema 描述、示例或请求构造器默认值变相加入。具体任务目标、约束及材料从当次真实用户输入、有效历史和工具反馈动态组织，不能将样本专属条件改写成看似通用的固定提示。
- 中文表达任务逻辑和判断条件，采用当前目标的相邻正反例检查歧义。

### 3.2 多次调用怎样交接

**按任务与决策职责分别组织滚动历史。** 同一职责的后续调用持续追加与其任务相关的实际交互，不能每次只给最新单轮输入而丢失前序过程；不同职责不共用一份无差别的全量历史。职责独立不等于调用无历史，也不要求新增 agent 或独立日志。

| 调用关系 | Context 组织 |
| --- | --- |
| 行动循环（agent loop）决策 | 保留多轮模型回答、实际工具调用及配对结果，继续追加本轮行动、执行反馈和修订；失败、拒绝及未解决反馈按原交互保留，不能只保留成功结果或最终回答 |
| 目标核验（goal verifier） | 按[目标核验器上下文模式](../../../docs/context/goal-verifier.md)接续“用户原话 → 目标维护结果 → 判决 → agent loop 修订 goal → 再核验”，保留历轮事实；不混入结果核验历史或主循环全部工具轨迹 |
| 回答核验（answer verifier） | 按[回答核验器上下文模式](../../../docs/context/answer-verifier.md)接续“用户原话 → 已通过核验的 goal → 候选结果 → 判决 → agent loop 修订结果 → 再核验”，按用户轮次保留对应关系；不混入目标核验全部过程 |
| 其他职责独立的阶段或独立子任务 | 按本阶段职责定义相关历史，并交接整体目标、当前子目标、相关前提、实际成果与证据、未知项和输出要求；后续同职责调用继续累积，不默认复制其他职责全部输入输出 |
| 必须理解完整交互才能继续的分支 | 显式选择继承相关历史或完整的已结束交互，核对工具配对与服务方协议；不能默认所有子任务都需要继承 |

**历史筛选后，除有明确必要理由的特殊情况外，统一按原始交互的时间顺序拼接。** 按职责筛选决定保留哪些历史，不改变所保留交互的相对先后；禁止将多轮历史按类型集中分组后输入，例如先放全部目标、再放全部回答或工具结果、最后放全部核验反馈。时间顺序须保留跨类型交互的因果关系与工具调用／结果配对，不能为排版或实现方便而重排。

确因服务方协议或其他必要条件调整组织方式时，说明理由和适用范围，保留原交互顺序及对应关系的可追溯依据，不以特殊情况为由默认按类型分组。稳定系统指令、工具定义与当前状态可单独组织，但不能借这些区块重新归类多轮历史。

滚动历史须明确目标、稿件、核验和修复的对应关系及当前有效版本，不能把历史版本同时当成现行要求。核验后的实际修复必须进入后续核验输入，不能只传最新稿而丢掉此前反馈，也不能把模型承诺修复记为已修复。必要的原始用户要求和判断依据仍作为本职责的当前输入提供，不以历史筛选替代。

历史选择遵守职责边界，并按本次决定的信息依赖判断。目标解释需要用户原话、必要的历史答复及展开指代所需的执行材料，不能只保留过去的目标解释对话；材料可以来自其他职责，但不因此重放其全部工具轨迹。无法可靠划定相关范围时，先在本职责相关材料内保留较完整的上下文，再依据实际输入及任务结果验证缩减；没有重读能力时，不以空引用代替必要材料。

上游输入中仍有效的约束和判断前提必须传递；上游输出按实际用途保留结论、产物、来源和不确定性，不能只交一句“已完成”。核验调用取得原始目标、实际待验结果及必要证据，不能把生成者的自评当作通过依据。共享任务状态与各调用的局部历史分清作用，局部发现由结果消费方确认后用于后续判断。

**think 与业务交接分开。** think 指服务方返回的推理内容或推理块，不保证可见或可跨模型使用。同一会话续接时，按具体模型、模式及工具协议保留和回传所需字段、签名或不透明内容，不统一删除、改写或拼进正文。独立阶段不默认复制上游 think；下游所需的结论、简要依据、证据和未知项应显式交接，不能只藏在上游推理中，也不强制输出完整思考过程。

### 3.3 历史怎样增长、压缩和恢复

- 区分供审计或恢复的运行记录、当前保留的会话历史、最终发给模型的请求。需要的原始记录按明确生命周期保存；保存记录不等于每轮全部重发，也不要求永久保存所有临时快照。
- 正常续接追加响应与实际观察；动态状态有变化时传递当前版本，说明旧版本已失效，避免同一快照反复堆积。稳定前缀可服务缓存，但缓存命中不能成为保留过期事实的理由。
- 根据实际请求预算决定何时裁剪、外置大结果或压缩旧交互，计入系统提示、工具定义、多模态及适用输出预留。采用参考默认值前核对其预算口径，不把某项目阈值当通用常数。保留当前目标、有效约束、相关成果、未决问题及必要的近期交互；不拆断工具调用与结果配对，不改写服务方要求原样保留的协议内容。
- 摘要用于继续任务，保留用户纠正、关键决定及依据、成果位置、待办与下一步；更新时合并仍有效事实，去掉已被替代内容。摘要标明来源与作用，不能凭摘要新增授权或把未验证判断升级为执行事实。精确值或原文仍影响决定时，保留原件或通过确实可用的入口重读，不能只提供模型无法访问的 ID。
- 检查压缩后的会话能否一致恢复、遗漏材料能否实际找回、失败时如何保留可用状态。保留日志不自动提供重读能力；减少 tokens 不单独证明压缩有效，按第 6 节验证后续任务结果。

## 4. 输出契约服务于正确决定

**Schema 是模型提交决定的操作界面。** 设计既要让程序能校验，也要让当前模型容易生成合法参数，并能根据真实反馈修正。不能把内部数据模型直接导出就视为设计完成。工具参数和独立结构化结果都适用；给用户的正文保留为正文。

### 4.1 从消费者确定模型必须输出什么

- **禁止保留没有具体消费环节的字段。** 先写清本次决定及必要分支，再逐字段定位谁在什么环节读取其值、用于什么判断或动作、影响什么结果，之后才选类型。仅被解析、校验、存储或原样传递，不能单独证明字段有用；说不清实际用途的字段删除，不以可能有用或方便观察为由保留。
- **禁止保留作用冗余的字段。** 即使字段都有消费者，也要检查是否重复表达同一信息、承担相同作用；不能说明独立语义或消费差异的字段应合并或删除，不能靠改名、换类型或增加一致性校验保留重复表达。
- 模型输出业务选择与必要内容。权限、作用域、版本绑定、执行回执及系统已知的确定性值由 Runtime 负责；已有文字通过有效引用恢复。模型确需选择对象时，输入提供现成引用及其含义，避免重抄完整身份、摘要或长引用对象。
- 结构要保留决策关系，例如条件须同时满足、排序只作用于合格项、数量是上限。不能只保留孤立标签，也不能把开放语义强塞为不适用的枚举或确定性公式。

### 4.2 明确字段意义与输出场景

- 工具说明写清何时调用、何时不调用、调用后发生什么，以及返回结果如何使用；字段说明写清它在当前决定中的作用。不能用字段名、类型名、自动生成的 `title` 或“当前状态”等同义复述代替解释。
- 对需要模型填写的业务字段，包括嵌套字段，说明内容从哪里取得、何时必填／可选／禁止、合法值与单位，以及省略、空值和更新的含义。枚举还须解释各值的选择条件；模型选择引用时，说明可选范围，不要求猜测或自行构造。
- 按实际决策分支列清“场景 → 选择的动作或类别 → 应填与不应填的字段 → 状态或下游效果”。用必要的完整合法示例解释易混分支和字段关联；只展示对象形状而不说明何时使用，不算完成场景设计。简单契约可用短段落，不机械增加表格或示例数量。
- 将上述说明落入实际导出的字段 `description`、工具说明或对应输出指令，并检查生成与适配链。可在已有检查入口发现缺少说明的业务字段；不能只检查是否存在 `description`，还须检查它能否指导选择和填写。方法及固定源码依据见[字段语义与场景设计](references/output-schema-design.md)。

### 4.3 让合法参数容易生成

- 选择完成当前决定所需的最浅结构。只有一个文本字段且没有独立语义的包装、同一信息的多处复述及无消费者的嵌套应简化；不能为减少层级丢失必要关系，或把 typed 参数改成任意字典、JSON 字符串。
- 明确字符串、对象、数组及数组元素的形状；分别定义省略、`null`、空字符串和空数组的含义，禁止相互冒充。未知不能填成否定、零值或伪造事实。需要时提供经实际契约校验的最小完整示例，覆盖已出现的易混形状。
- 将场景中的字段组合落实为契约，不能把组合规则只藏在本地 validator 中；按服务方实际能力选择分支表达、参数说明或拆分操作，不默认一个可空大对象或拆成多个工具更好。
- 更新已有状态时明确完整替换还是增量更新、未提交字段如何处理、何时保留或撤销。默认值和省略不能静默删除有效条件；不让模型反复复制与本次变更无关的大段状态而没有必要性依据。

### 4.4 核对实际协议与修复出口

- 分别检查内部类型、模型实际收到的工具说明及 Schema、服务方约束和本地校验器。核对引用定义、组合分支、必填项、默认值及严格模式是否实际受支持、生效；原生工具调用不自动等于服务方保证参数合法，原生结构化输出、工具参数和 Prompt 要求 JSON 不能混称。
- 字段描述、分支规则和必要示例必须实际进入请求。Python 注释、类型名、有效 JSON Schema 以及一次合法输出，都不能单独证明模型理解了契约；校验形状也不能证明语义正确。
- 失败反馈在原调用上指出错误字段、期望类型或条件、实际不符及可采用的合法形状；组合错误应保留有意义的分支定位。只纠正参数表达，不代写业务结论、转换原错误载荷或降低准入要求。
- 检查下一次实际调用是否修正，并区分首响应、协议恢复及业务结果。重复同类错误时，复审字段必要性、嵌套、分支、示例、服务方适配和反馈消费，不只追加禁止措辞、扩大重试或删报错字段；按方案推进 skill 的既有停止规则处理。

用实际请求和原始响应核对设计；零模型检查不能替代真实生成及反馈恢复证据。技能保留通用方法和可定位的外部源码，不嵌入具体任务、运行目录或临时故障记录；本地问题及验证结果留在各自权威记录。

具体通用 Prompt、类型与引用门禁由 [COD](../../../docs/devSpec/code-structure.md)拥有；不通过增加理由、置信度或同义分类字段来替代清楚判据与必要信息。

## 5. Runtime 怎样支持纠错和完成

- 从当前权威状态物化输入，接收模型决定，校验结构、引用与适用前提，再交给原治理与业务入口执行。参数失败按第 4.4 节保留原提议并反馈；Runtime 不暗中补业务参数或生成替代答案。
- 参数或输出协议修复、语义修订、外部暂时故障分别处理。恢复次数、输出额度、累计成本和停止责任有唯一责任主体；权限拒绝及不变量破坏不交给通用重试吞没。
- 工具结果按原调用身份交回，明确实际成功、拒绝、失败或未确定。依照既有契约记录原始响应与耗用，恢复复用已成立事实；跨持久执行边界按 [EXE](../../../docs/devSpec/agentic-execution.md)处理，不重新生成冻结命令。
- 仅在契约需要时使用既有语义核验和完成检查。清楚反馈哪项用户结果或依据仍缺失，让模型选择合法修正；有界语法修复不等于语义正确，模型提交最终答案也不自动产生完成事实。

## 6. 用真实任务验证并定位错误

先固定目标及验收，再检查成功、易混边界、缺证和适用恢复场景。区分模型决定、执行结果与整体交付，复杂任务连续消费同一轨迹实际前置输出。次数、比较条件及局部收益保留由方案推进 skill 拥有；合法表达和不同执行路径可以通过，中间非目标内容本身不算失败。

失败时沿实际消费链定位应修正的设计或实现：

| 失败边界 | 核对与修正方向 |
| --- | --- |
| 决策依据缺失或失真 | 检查真实输入及阶段交接、取得、物化、裁剪、摘要和恢复位置，补足必要前提 |
| 依据已齐但选择错误 | 校准目标、判断规则与相邻边界；确需拆分时说明它如何降低判断负担 |
| 决定正确但格式或引用错误 | 检查 Schema、适配、本地校验和反馈消费 |
| 决定正确但未执行或执行结果丢失 | 检查装配、准入、调用绑定及真实结果回传 |
| 局部通过但用户目标未完成 | 检查尚缺的业务产物与交付条件，保留已成立的局部收益 |

交付在本问题的唯一设计中写清：目标与各次调用的决策责任、实际输入与交接、适用的历史及 think 处理、最小输出及消费者、必要运行支持、错误恢复和验收。说明采用的参考机制与本工程差异，不新增重复设计账本。只读任务仅给分析；本技能创建或纯文档维护只做技能与文档检查，不调用产品模型或停用的单元测试。
