# 问题描述

方案落地遇到阻塞时，先让读者明白问题是什么、怎样发生并传导、以前是否出现过，以及关键在于哪个责任环节，再讨论解决办法。描述以当前目标和真实证据为依据，不用错误码、组件名或“验证失败”代替说明。

## 1. 先取得描述依据

- 明确当前推进的目标、设计预期及被阻断的结果，核对正式入口、触发条件和实际运行身份。只读取与本次阻塞相关的实现、输入输出、反馈和权威记录，不为描述问题启动额外模型或整轮重跑。
- 沿同一轨迹追溯最早偏差及后续消费，分清触发条件、直接阻塞、已确认原因和末端报错；时间相邻不能直接当作因果。缺少依据的环节标为未知，说明尚需核对什么。
- **LLM 决策类错误，优先分析同次调用已有的 `think`（服务提供方返回的推理记录）及输出中的决策理由。** 对照实际输入、决策输出和下游处理，核对模型采用的目标、事实、规则与取舍，区分理解偏差、决策错误、输出遗漏或消费失效，不能仅凭最终错误修改 Prompt。记录不可用时明确缺口，不补造推理；可见理由只辅助诊断，不能单独证明根因。记录绑定、证据边界及必要的中立追问按 [CTX 决策依据分析](../../../docs/devSpec/context-memory-retrieval.md#121-利用-think-与中立追问核对决策依据)执行。
- 检索此前的设计、问题记录与验证证据，按失败行为、责任边界和触发条件比对。相同报错不必然同因，换名称、模块或版本也不自动成为新问题。

## 2. 先回答三个问题

按以下顺序组织，每项用必要的一小段说明；窄问题可合并，但不能省略影响判断的前提和历史。

1. **本次究竟是什么问题？**

   先说明本来要完成什么、在哪一步出现何种预期与实际差异。按“前置条件或变化 → 最早偏差 → 下游怎样接收并处理 → 最终阻塞与用户影响”讲清链路，不能只罗列执行时间线。

   **必须说清输入输出，不能省略。** 对每个关键环节说明实际接收了什么、来自哪里，本应输出什么、实际输出什么，以及下游实际收到并使用了什么。用直白语言概括内容并保留影响判断的关键字段、值和范围，不能只给对象名、错误码或日志链接。没有输出时说明未执行、拒绝或失败的实际状态；尚未核实的输入输出明确标为未知，不省略或补造。

   区分已经发生的失败、未到达的后续步骤，以及仍然成立的局部结果，附关键事实坐标。

2. **之前是否出现过？**

   明确是首次查见、同类复现、旧问题回归，还是证据不足暂不能确定。出现过就给出原记录，说明当时怎样处理、验证到什么范围、本次有哪些相同点和变化；不能把临时绕过写成已修复，也不能忽略已完成的一次有界修正。没有找到时说明已查范围，不把“未查到”写成“从未出现”。

3. **问题关键在谁、哪个环节？**

   指出负责关键输入、决策、执行或反馈的主体：它本应做什么、实际做了什么或缺了什么，怎样影响下一环。区分最早偏差的产生方、后续未拦截或未消费的环节与末端报错方，明确当前最需要核对或修正的责任边界。这里的“谁”指有证据支持的模型、组件、调用方或外部依赖，不作无依据的个人归责；根因未定时先报告最早已确认边界及待区分假设，不猜测归责。

## 3. 说明边界与后续衔接

- 先用直白语言解释专用概念及其作用，再给代码标识、日志或文件坐标；事实、推断和未知分开，结论不超过实际证据，不复制长日志或无关历史。
- 对用户的问题描述不等于阻塞已解除。按已有授权继续定位、修复和验证；只读任务停留在分析，不自动扩大为生产修改。
- 本技能拥有阻塞的描述方法。机制和设计取舍由[方案说明](../explain-project-solutions/SKILL.md)展开；方案去留、实践核对与验证安排由[方案推进分析](../analyze-proposal-progress/SKILL.md)处理，重复阻塞的停止与复审遵守 [EVD](../../../docs/devSpec/change-evidence.md#72-重复阻塞先复审方案再继续)。不在此复制它们的流程或另建问题账本。
- 技能只保留通用方法；具体任务、故障及运行证据放在各自权威记录中。表达与证据措辞遵守[中文写作规范](../../../docs/chinese-writing-spec.md)。
