# 工程问题与方案说明

围绕用户问题，按“问题 → 做法 → 参考依据”组织因果说明。

方案落地受阻时先按[问题描述](../describe-project-problems/SKILL.md)说明因果链、历史与责任，再按需展开本技能的机制和取舍。

方案审计、优化复审和逐点覆盖核对使用[工程方案审计](../audit-project-proposals/SKILL.md)；已有方案在验证中的去留及新问题关联分析使用[方案推进分析](../analyze-proposal-progress/SKILL.md)。

## 回答结构

完整方案说明使用以下三个编号项，默认每项一小段；窄问题只保留相关项，用户指定格式时遵从其要求。

1. **问题**

   写清失败或缺口、对用户结果的影响和直接原因，附关键工程证据。原因未定位时说明假设及缺失依据。

2. **做法**

   说明机制怎样解决上述问题、复用和改变什么，再给必要的职责或代码坐标。交代关键代价、适用边界，以及候选、已实现或已验证状态。

3. **参考依据**

   引用开源方案时复用[参考开源方案](../reference-open-source-solutions/SKILL.md)核对的实现与采用对照；其他依据就近链接，说明采用部分和本工程调整。未核对来源标为待核实，没有外部参考时说明工程内依据。

## 表达边界

- 先回应用户关心的判断，再解释因果关系。字段、调用链和时序按理解需要展开，不复述执行流水或扩展为实施计划。
- **非通用概念或变量必须先说明再使用。** 首次引入工程专用概念、缩写、变量或代码标识前，用直白语言说明其含义及在当前问题中的作用；变量须说明代表什么，必要时补单位或取值含义。禁止直接摆出未说明的名称，让读者依赖后文、链接或猜测理解；也不能用另一个未说明的非通用概念充当解释。
- 必要性与已验证效果分开表述；参考实现存在不代表本工程有效，未取得的结果如实说明。
- 引用就近放置，优先使用权威正文、真实证据和原始来源，不复制大段日志。

本技能拥有回答结构，通用表达与证据措辞遵守[中文写作规范](../../../docs/chinese-writing-spec.md)；设计、实现和验收仍按仓库规范执行。
