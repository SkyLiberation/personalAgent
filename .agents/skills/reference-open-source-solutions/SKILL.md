# 参考开源方案

围绕一个具体工程问题，从开源代码还原实际做法，再说明本工程怎样采用。每项结论都要回到具体实现，不能把项目总结、功能清单或概念相似当成分析完成。

## 1. 明确问题与源码依据

- 先确定要参考的机制、当前缺口及需要回答的实现问题。智能体机制从 [REF 导航](../../../docs/agentRef/README.md)定位已有来源；其他开源项目按同一方法核对，不为扩大项目数量搜索无关能力。
- 固定仓库、提交或可解析的发布版本，读取对应代码。README、官方说明、博客和已有总结只能帮助定位或补充，**未分析实际源码，不得得出已确认的实现结论**；源码链接本身不等于已读源码。
- 可复用已核对且仍适用的源码证据，先确认版本、实际分支和依据有效，只补变化与缺口；只有总结而没有可复核的源码分析时，必须补查，不能因已有总结跳过。

## 2. 沿真实装配与消费链分析

从正式入口追踪到本次机制的实际消费者，读取足以解释该链路的代码，不机械扫描整个仓库：

1. **入口与生效条件。** 谁创建、注册和装配该能力，哪个配置或分支使它可用，默认值在哪里实际读取。区分默认启用、可选、示例和未被生产入口使用的路径。
2. **输入与决定。** 谁提供什么输入，怎样构造、转换或筛选；核心函数怎样判断分支并产生参数、调用或结果。涉及模型时追踪实际 Prompt、Schema、消息和工具定义的生成及发送，不能只读类型或模板。
3. **执行与消费。** 谁执行操作、写入或更新哪些状态，输出由谁读取，怎样改变下一步或最终结果。按本次影响核对事实归属、生命周期、权限和外部依赖；只有接口声明或对象存在不足以证明机制生效。
4. **失败与边界。** 对相关的拒绝、错误、预算、取消、恢复和结束分支，说明反馈返回哪里、谁据此继续或停止。源码中的容错、默认值及失败完成语义要如实说明，不能只摘取有利分支。

每个分析点绑定固定版本的关键文件、符号及必要行号，并说明调用方、被调用方和消费者怎样连接。看到一个函数不足以推定全项目行为；未找到实现时说明检索范围，不把未找到写成不存在。

## 3. 将每项发现落成可实施对照

**先比较方案，再确定改动范围。** 按 [EVD 方案选择与复杂度准入](../../../docs/devSpec/change-evidence.md#5-复杂度说明complexity-justification)判断已有实现与参考机制的优劣，在采用对照中说明保留、修正或替换的依据；不能把少改代码或现有布局作为优先理由。

对每个准备采用的机制，写清以下内容；简单机制可用短段落，不能只列一个点再粗略说“增加某模块”或“参考其做法”。

| 问题与机制 | 参考实现具体怎样做 | 本工程如何采用 | 依据、代价与验证 |
| --- | --- | --- | --- |
| 作用于哪个具体缺口或责任环节 | 入口、触发条件、实际输入输出、关键处理与消费者 | 对应责任主体、现有入口或协作者、契约与状态变化、装配及消费位置 | 固定源码坐标、必要差异与成本、适用用例及未验证边界 |

- 本地建议须说明复用什么、修改什么、删除或替换什么，以及从输入到结果怎样接通；按实际需要落实字段含义、配置、反馈和恢复方式。尚缺决定或无法定位必要消费者时，明确缺项，不能宣称可直接落地。
- 明确采用原机制、适配或不采用的理由。差异由当前业务、契约和约束解释，不凭同名概念照搬对象数量，也不为支持既定方案选择性解释源码。
- 比较多个项目时对齐同一机制及问题，不能以不同功能的项目清单冒充独立实现比较。已有实现对照由设计、审计与推进分析复用，不分别维护同义表格。

## 4. 证据与交付边界

- 分清源码已核实、文档声明、设计推导和实际运行已验证。源码能证明相应实现及条件，不能直接证明本工程收益、正确率或性能；未执行的分支和验证不得写成通过。
- 源码未公开、不可访问或未找到时，说明已查范围与缺口，保留待核实候选；不能用官方总结或闭源产品说明补写内部实现。证据分级、独立来源数量和采用准入遵守 [EVD 外部参考规则](../../../docs/devSpec/change-evidence.md#6-外部参考的证据分级)。
- 结论按“问题 → 源码实现 → 本地采用与差异 → 证据及验证边界”组织，来源就近引用；记录进入既有参考条目或本问题唯一设计，不另建重复方案账本。
- 只读调研给出具体分析和可实施建议，不自动授权生产修改、运行第三方代码或付费实验。技能只保留通用方法，不堆入具体任务、临时故障和运行记录。
